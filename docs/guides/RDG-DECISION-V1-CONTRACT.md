# RDG Decision v1 — технический контракт

> **СТАТУС: ДЕЙСТВУЮЩИЙ КОНТРАКТ ДЛЯ РЕАЛИЗАЦИИ.** Сверка 2026-11-06. [Смысл модели](RDG-ACTIVE-CONTRACT.md) · [функции и тесты](RDG-FUNCTIONS-AND-TESTS.md).

## Схема и ядро

[JSON Schema](../../tools/contracts/rdg-decision-v1.schema.json), [kernel](../../tools/rdg-decision-model.py), [dispatch профилей](../../tools/rdg-model-profiles.py) — проверяемые источники полей, enum и команд. `rdg-decision-v1` не является молчаливой интерпретацией старого R/A owner.

| Данные | Контракт |
| --- | --- |
| `nodes` | Requirement, Decision, Graph Action с общей identity |
| `objects` / внешние Actions | Context, Canon, Info, Finding и разрешённые отдельные действия; Evidence — только совместимое чтение; не произвольные kinds |
| `decisionGroups`, структурные отношения | Основания, обязательность, взаимоисключение, общие участники; фиксированная точка support/cascade |
| `workGraphs` | Ссылки `memberIds/rootIds` на те же сущности; опциональный `colorKey`; не отдельный Graph/Plan owner |
| `decisionContextIds` и `dependencyPurpose=decisionContext` | Совместимые и настраиваемые process-only ссылки; не структурные родители |
| `review` | `required`, `causeEventIds`, `pins`; не подменяет result/selection |
| События | Принимаются прежние форматы; дополнительные точные сведения появляются при записи нового события |

Связи: `DERIVES`, `DRIVES`, `INTRODUCES`, `REQUIRES_ACTION` и membership групп задают структуру. `CANON_FOR`, `INFO_FOR`, `CONTEXT_FOR`, `EVIDENCE_FOR` и `DEPENDS_ON` имеют отдельные роли. Полный словарь и допустимые пары предоставляет [реестр политик](../../tools/rdg-dependency-policies.py).

## Политики и проекции

Определения политик namespace-wide, типизированы и версионированы. Binding закрепляет версию и участников; динамические роли имеют явные anchor/direction/type/depth и условия. Потеря применимости сохраняет disabled binding. Автоматические применения имеют стабильный ID, без дублирующих Graph edges.

| Поле ответа / события | Назначение |
| --- | --- |
| `dependencyCatalog.localApplications` | Read-only роли, текущие наборы, пути, участники, применимость и per-actor observations общего resolver |
| `dependencyCatalog.invalidationRecords` | Read-only карточки из Graph events, review и применений; не второй stale evaluator |
| `dependencyImpacts` | Записанный эффект. Доступные policy/version/rule/operation, matched IDs и snapshots; старые записи могут быть короче |
| `dependencyTransitions` | Lifecycle применения; новые записи также сохраняют `targetId`, `participantRoles`, `relationSnapshot` |
| `reviewResolutions` | Новый факт подтверждения: целевой элемент и разрешённые `causeEventIds` |

`describe_applications` и `describe_invalidation` не записывают Graph. Исторические данные берутся из события; текущая проверка применимости использует kernel. Snapshot нельзя заменить текущими именами/отношениями без отметки. Совместимый `info` у прямой политики Decision означает прежнее Info его Canon; прямое Info элемента — отдельное наблюдение.

Команды `binding_save/disable/activate/remove`, `automatic_disable/activate/remove` проходят существующий writer/CAS/guards. `automatic_remove` оставляет tombstone; явная активация deleted ID отвергается. Изменение версии определения не меняет pinned binding. Матрица: [policy suite](../../tests/rdg-dependency-policies-v2.test.py).

## Владельцы и API

[Application](../../tools/rdg-portable-service.py), [model](../../tools/rdg-portable-model.py), [store/coordinator](../../tools/rdg-portable-store.py) отвечают за доступ, composition и durability. Копии структур не создают новых прав записи.

1. `schema` даёт разрешённую форму запроса и ожидаемые inputs.
2. `preflight` проверяет права/типы/refs/ревизии без предметной записи и возвращает `inputBinding`.
3. `apply` принимает тот же request и binding; результат подтверждается `receipt`.
4. После неопределённого ответа читается receipt той же `transactionId`; exact retry не создаёт новый эффект.

Graph, Plan, layouts и Registry координируются своими owners. Создание процесса не создаёт неявные Working Graph или Plan. Вложение подтверждения означает действительные проверенные bytes, а не произвольное имя артефакта. `review` проверяет union входных pins и доверенный snapshot-контекст атомарно; другая причина не подтверждается автоматически заметкой.

`ready/lens` — бумажное определение без фактического выбора, выполнения и процессного контекста. `copy` и insert/capture remap сохраняют локальные IDs/refs, происхождение и независимость владельцев по объявленной операции. Сохранённые исторические refs не разрешают запись в current owner.

[Application tests](../../tests/rdg-portable-service.test.py), [Plan/restart/CAS](../../tests/rdg-decision-integration.test.py), [system scenarios](../../tests/rdg-decision-system.test.py).

### Матрица операций API для ИИ

Основной маршрут — JSON Application через private gateway; Agent передаёт те же сообщения. Записи из таблицы проходят `schema → preflight → apply → receipt`, затем указанный readback. `requiredInput` отмечает поля для заполнения, `inputChoices` — типы новых сущностей и Findings. Форма не является результатом операции; семантические условия проверяет preflight/writer. Настройка ролей доступа не входит в этот этап сверки; используется подготовленный доступ ИИ.

Для нового процесса: `schema` с `op:create, coreModel:rdg-decision-v1` возвращает `role:working` и требует собственного `rootReason`. Опциональный `role:ready|lens` выбирает бумажное определение; у lens обязателен `lensKey`. Agent `schema --action create` выбирает основной профиль; legacy задаётся `--model-profile rdg-core-v1`. Прежний RPC без селектора сохраняет совместимый `rdg-core-v1/ready`; предпочтительный профиль указан в `profileSelector.preferred`. Селекторы `coreModel/role` допустимы только при создании, `entityKind` — только у `core/paper_edit add`; существующий профиль ими не меняется.

Типизированный `add` строит допустимую начальную связь R/D/Action с фокусом, Canon/Info — справочную связь; Finding получает subject из фокуса D. Неприменимая опора не подменяется выдуманным объектом: заполняется реальный ID из процесса. Дополнительные поля и изменённые связи сверяются с [JSON Schema](../../tools/contracts/rdg-decision-v1.schema.json); форма не является полным генератором всех комбинаций команды. Для ready/lens `coreCommands` содержит только paper-команды; Finding и процессный контекст туда не переносятся.

Ошибка input/refs/CAS означает исправление непринятого намерения с новым transactionId; после неопределённого apply сначала читается прежний receipt. `PREVIEW_INPUTS_CHANGED` требует нового preview. Семантические guard-ошибки (например, FINDING_SUBJECT_REQUIRED или незавершённые обязательства) не исправляются выставлением результата вручную. Прежние Evidence/resolve/proposals читаются совместимо; их новое создание не входит в API основного профиля.

Границы этапа: **T1/T2 реализованы в исходниках; выпуск определяется точным READY и установленным buildId**. `read(summary|item)` и `history(compact|item)` имеют facet/limit/cursor, прежний полный ответ доступен без новых параметров. `batch` объединяет текущие разрешённые `core`-команды и `plan_create/place/unplace`, не более 100 шагов одного owner; Graph-команды предшествуют Plan-командам (перемежение сейчас явно отклоняется). Questions/answers и estimates поддержаны в batch. `schema(batch).unsupported` перечисляет оставшиеся ограничения: Planning Meta Action реализован в исходниках T5, нет batch для Registry/owner migration, result confirmation, approval/lock и cross-owner. Этот этап ещё не доказал p50/p95 на 50/500/5000. Семантический поиск Canon и актуальность содержания линз не доказываются этой матрицей. History фильтрует режим/время; focus в view spec не ограничивает события элементом, поэтому Agent/CLI отклоняют `history --node` явно. Cross-owner Decision refs/Plan и вложенные forks остаются вне поддержанного профиля. Настройка прав доступа и сквозной проход по согласованным линзам — отдельные этапы [плана](RDG-DEVELOPMENT-PLAN.md#удобство-api-для-ии).

Самостоятельная [Question](RDG-ACTIVE-CONTRACT.md#вопросы) поддерживает canonical CRUD, ответы/оценки, Viewer-редактирование, явный перенос legacy, copy/remap и batch. Старые embedded questions читаются без записи, их изменение требует `question_migrate`. T5/Planning Meta Action и сквозная приёмка по линзам остаются отдельными задачами.

## ТЗ оставшегося внедрения

**Статус: целевое ТЗ 2026-11-06, не отчёт о реализации.** Scope — оставшиеся части согласованного API/методологического этапа: компактное чтение, пакетная запись, Questions, оценки Action, планировочные метадействия Plan, полноценные фундаментальные линзы/рекомендации, обычные источники и новый сквозной пример. Семантические нормы принадлежат [действующему контракту](RDG-ACTIVE-CONTRACT.md), содержание линз — [проекту и карте покрытия](RDG-LENSES.md#полное-целевое-содержание-model); здесь находятся технические формы и приёмка. Точные новые имена полей/операций ниже задают целевой контракт и должны появиться в schema после реализации.

### Границы и общие требования

Использовать существующие kernel, Application/coordinator, codecs, owners и общий writer UI/AI. Сохранять schema → preflight → apply → receipt/readback, CAS/pins/locks, атомарность и exact retry прежнего transactionId при неопределённом исходе. Все новые операции должны обнаруживаться через публичную schema, Agent/CLI и private gateway. Валидация одинакова для UI, прямого API, generic add/edit, copy/import и пакетной записи. Не вводить второй writer или межпроцессные структурные ссылки.

Graph и Structure используют одни IDs, данные и действия; новые вспомогательные объекты не становятся строками/узлами только ради доступности UI. Сохраняются компактные основные сведения и раскрываемые подробности. Ни чтение, ни создание на бумаге, ни применение линзы само по себе не назначает selection/completion/disposition. Предметные изменения попадают в существующую историю с before/after там, где они известны; фильтры History и семантика cosmetic сохраняются. Новые содержательные записи Questions/ответов, оценок и планировочных метадействий входят в «Без технических»; «Важное» расширять без отдельного смыслового основания не требуется.

Реализованные Findings, роли контекста/его происхождение, вложенные группы Context, политики/disabled, временные развилки/конец и четыре режима History входят в регрессионную приёмку. Настройка прав/новых ограниченных ролей, ИИ–ИИ, Gendocen, экспериментальные модули, вложенные forks и автоматический ресурсный планировщик в этот этап не входят. Существующие ограничения и права не обходятся.

### Компактные чтения и пакетная запись

**T1 — чтение.** Расширить существующие read-маршруты параметрами `detail`, `include` и постраничным чтением: обзор процесса, элемент, его контекст/Canon/Findings/Questions, конкретные применения зависимостей, Plan и History. Детальные названия допустимых facets и формы курсора предоставляет schema, общий проектор формирует данные. Ответ содержит owner/revision, реальные IDs и явные сведения о загруженных частях; незагруженное не выдаётся за пустое. Курсор привязан к версии снимка; смена версии даёт явный конфликт/повтор чтения, а не смесь состояний.

Обзор и карточка без соответствующего `include` не включают полный dependencyCatalog, весь журнал, остальные сущности или bytes вложений. Каталоги/списки имеют limit/cursor, подробности читаются по ID. Старые запросы без новых параметров сохраняют совместимость; Agent использует компактный маршрут по умолчанию и запрашивает нужные подробности адресно. Неподдержанный фильтр, включая существующий `history --node`, не должен молча игнорироваться. Новую фильтрацию истории по элементу это ТЗ не объявляет обязательной.

**T2 — пакетный авторинг.** Добавить публичную `batch`-форму для упорядоченных операций одного процесса и его Plan, до 100 шагов за запрос. Поддержать создание/изменение основных сущностей, групп/связей, Questions/ответов, оценок и планировочных метадействий; неподдержанные операции явно перечислить в capabilities. Registry/live migration не включать скрыто в пакет процесса. Шаг имеет локальный alias; последующие шаги адресуют уже созданное через alias, который общий resolver переводит в ID. Итоговый receipt возвращает соответствие alias→ID и результаты шагов.

Один пакет — одно логическое намерение с общим transactionId и начальными expected revisions: полный preflight без записи, затем атомарное применение через coordinator. Ошибка последнего шага/конфликт не оставляет первые шаги; uncertain reply восстанавливается по тому же receipt. Сохраняются реальные события и их порядок, пакет не превращает несколько выборов/исполнений в один вымышленный факт. Явные выборы проверяют обычные основания; пакетное создание не принимает Decisions автоматически. Не перечитывать Graph/каталог с диска и не пересчитывать весь dependencyCatalog после каждого шага, если это не требуется семантикой.

Снять baseline и итоговые p50/p95, bytes ответа, число RPC/транзакций и время coordinator на одинаковых изолированных графах порядка 50/500/5000 элементов. Для карточки размер ответа ограничен запрошенными facets/страницей, для batch создание N элементов не требует N отдельных сетевых циклов schema/preflight/apply. Время измерять отдельно от UI и внешнего ввода. Не задавать вымышленные миллисекундные SLO и не использовать хрупкий wall-clock assert вместо проверки объёма/числа обращений. Результат этапа включает сравнение и объяснение оставшихся затрат.

<a id="read-focus-branch-b03a"></a>
### Фокус и полная ветвь — B03A

**B03A реализован в исходниках 2026-11-08 по этому ТЗ.** Адресная [приёмка](../../tests/rdg-scoped-read.test.py), HTTP Gateway и полный учебный рецепт включены в CI; выпуск определяется точным READY, установленная версия и Windows/UX отдельно. Исходная задача: `open --node` сейчас возвращает карточку `item`, а существующий фокус доступен внутри большого `full` вместе с чужими для задачи данными. Нужны адресные пакеты чтения существующего фокуса и всей структурной ветви, без полного owner/dependencyCatalog. Смысл областей принадлежит [контракту](RDG-ACTIVE-CONTRACT.md#фокус-и-структурная-ветвь).

**1. Публичные запросы и совместимость**

Расширить существующий `read.detail` значениями `focus` и `branch`; использовать прежние `packageId`, `nodeId`, `include`, `limit`, `cursor`. Это режимы одного read, без нового endpoint, owner или writer. `nodeId` обязателен; `branch` принимает только Requirement/Decision основного профиля. Оба новых режима поддерживают rdg-decision-v1; прежние full/item legacy сохраняются. `focus` использует существующую семантику фокуса данного профиля, включая Action и уже поддержанные вспомогательные элементы; внешний Action читается как обычная карточка с предметными ссылками, без структурных потомков. Поддержанные root kinds публикуются в schema. Неподдержанный профиль/kind отклоняется явно.

```jsonl
{"method":"read","packageId":"<package-id>","detail":"focus","nodeId":"D-SQL"}
{"method":"read","packageId":"<package-id>","detail":"branch","nodeId":"R-STORE","limit":25}
{"method":"read","packageId":"<package-id>","detail":"branch","nodeId":"R-STORE","include":["entities"],"limit":25,"cursor":"<entities.nextCursor>"}
```

Без `include` запрашивается стандартный содержательный пакет, перечисленный ниже; явный `include` выбирает только названные секции. Пустой список означает стандартный пакет, а не «загружено всё пустое». Schema сообщает набор по умолчанию, допустимые секции, ограничения и формы ответа. Прежние `summary/item/full`, отсутствие `detail`, фильтры и формы ответов сохраняются. `view`, `includePlan`, `recordId` с новыми режимами не принимаются: область уже определена режимом, Plan запрашивается секцией. Старый `item` не получает скрытую семантику focus.

Agent/CLI: `open --node ID --detail focus` и `open --node ID --detail branch`. Обычный `open --node ID` остаётся `item`; help/schema объясняют разницу карточки, фокуса и ветви. Gateway принимает те же формы и выдаёт тот же пакет; Agent не добавляет к нему весь каталог линз. Опция `--all-pages` последовательно собирает запрошенные страницы одного снимка, при конфликте прекращается явно; без неё видны остаток и команды продолжения. Никакого скрытого перехода к full при ошибке.

**2. Структурная область**

- **Focus:** состав структурных участников, связей и групп совпадает с существующим `focused_view`, а не с произвольным «всем относящимся к элементу». R показывает ближайших детей и свои альтернативы; Decision — собственное ближайшее продолжение. Соседние альтернативы родительской группы в Decision-focus не добавляются. Поддеревья детей не раскрываются. Материалы пакета не становятся новыми структурными участниками.
- **Branch:** корень R/Decision и транзитивное продолжение по активным `DERIVES`, `DRIVES`, `INTRODUCES`, `REQUIRES_ACTION` и структурному членству DecisionGroup, разрешённому текущим kernel (включая поддержанное Decision→Decision). Продолжение содержит все состояния Decisions, в том числе невыбранные и исключённые; состояние возвращается явно, UI-фильтр их не вырезает. WorkGraph membership, Plan, `DEPENDS_ON`, предметные/контекстные ссылки и рекомендации не расширяют обход. Переходы через границу WorkGraph внутри того же owner сохраняются.
- Прямые структурные родители корня возвращаются как краткие `ref/kind/title` и основания связи (edge либо membership/group). Не загружать их поддеревья и полный body только из-за родительства. Если тот же объект отдельно нужен как реальный источник контекста, его body допустим в этой роли с явным основанием.
- Для потомков сохраняются также входящие структурные связи от родителей вне ветви: внешний конец — краткая граничная ссылка; вверх обход не продолжается. Сохраняются все родители, связи и memberships, а не только выбранное дерево визуализации.
- Канонический body каждого включённого объекта возвращается один раз в секции `entities`, под существующим qualified ref. Материальные секции и повторные вхождения ссылаются на него. Родительские/граничные refs сами по себе body не требуют. Description/Markdown/value/условия/оценки и обычные semantic state поля не обрезаются и не пересказываются.

**3. Циклы, общие участники и порядок чтения**

Поверх канонических связей вернуть плоскую секцию `outline`: строка корня и строки переходов с `occurrenceId`, `parentOccurrenceId`, `ref`, основанием перехода и `mode: expand|reference`. Это вычисляемые адреса строк ответа, не новые IDs сущностей. При `reference` обязательна причина `cycle|shared|boundary|unavailable`. Строка ссылки содержит kind/title и qualified ref, по которому можно запросить отдельный фокус/ветвь.

Использовать детерминированный DFS и различать текущий стек пути и уже раскрытые объекты. Переход к предку текущего пути — `cycle`: сохранить переход, дать ссылку и прекратить раскрытие. Повторное достижение уже раскрытого объекта вне стека — `shared`, а не цикл. Первое достижение раскрывается; остальные его входящие связи сохраняются ссылками. Список не перечисляет все возможные пути экспоненциально. Порядок использует существующий порядок групп/членов, где он задан моделью, затем стабильный ID как tie-break; одна версия даёт одинаковый порядок на всех страницах. В entities первым идёт body корня, затем структурные участники в порядке первого раскрытия outline, затем материалы в стабильном порядке; межсекционные refs могут ссылаться на body следующей страницы. Родители не становятся раскрываемыми строками outline: их место — parents, корень остаётся единственной начальной раскрываемой строкой.

Обход не имеет скрытого ограничения глубины. Допустимые текущим kernel циклические структуры читаются с cycle refs, что проверяется через реальный API на изолированном owner. Защита чтения не разрешает создавать связи, запрещённые kernel: валидатор остаётся прежним; обычная ошибка недопустимого Graph не маскируется успешным ответом. Прерывание по ресурсному пределу — явная ошибка без признака полной ветви.

**4. Содержательный пакет**

В focus предмет содержательных секций — сам корень; его структурные соседи получают свои полные bodies, но не рекурсивные Inspector-пакеты. В branch предмет — все уникальные R/Decision/Action структурного продолжения. Нынешние участники-источники exact focus также сохраняются. Материальные ссылки не запускают новый структурный обход.

| Секция | Содержание и граница |
| --- | --- |
| `parents` | Краткие прямые родители корня и основания связи |
| `entities` | Полные канонические bodies структурных участников и необходимых материалов; один body на qualified identity |
| `edges`, `decisionGroups`, `decisionMemberships` | Связи области, граничные связи, группы/членство с исходными IDs и состояниями. Для обрезанной группы явно `membersComplete:false` и исходное число членов; отсутствующий sibling не выглядит отсутствующим в owner |
| `outline` | Последовательность чтения с раскрытиями, ссылками и причинами остановки |
| `context` | Действующие роли контекста и происхождение/основания через общий projector, включая sources/observed pins, comments, present/missing и относительный scope. Реальный доступный body источника включается в entities; ID/название не заменяют его value |
| `canon` | Привязки теории, «Каноны», «Общее»/legacy guidance, «Известные ошибки»; связанные Info, открываемые из этой теории. Текст находится в entities, а не копируется в каждой привязке |
| `findings` | Относящиеся к предмету Findings и Findings, реально участвующие в его context, с subject/scope/relative level; bodies в entities. Не весь список Findings owner |
| `questions` | Canonical Questions, связанные через relatedRefs с предметом или включёнными Findings; ответы, assessment и их provenance в полном body. Legacy embedded questions читать совместимо с явной пометкой, без миграции. Source refs вопроса не запускают бесконечное раскрытие источников |
| `completion` | Текущее вычисленное completion/review для предмета: условия/блокеры, прошлое подтверждение и необходимость пересмотра различимы; внешние блокеры — refs. Не глобальная карта owner |
| `recommendations` | Применимые адресные рекомендации предмета с текстом «когда/как», происхождением, версией и статусом цели; ссылка не раскрывает всю линзу и не означает применение |
| `dependencyApplications` | Только конкретные приложения зависимостей предмета: направление, основания/роли, observed/current pins, disabled/stale/review и ссылки на определения. Полный dependencyCatalog и чужие приложения не включаются |
| `subjects` | Разрешение subjectRefs включённых Actions по общему resolver, со статусом недоступности/версии; переход к предмету не включает его поддерево |
| `plan` (только явный include) | Только placements включённых Actions и необходимая информация для адресного открытия placement; не весь Plan и не косвенное включение внешних метадействий по их subjectRefs |

Стандартный пакет — все перечисленные секции, кроме `plan`. Состав entities определяется областью и материалами стандартного пакета, независимо от include: выбор секций управляет передачей, а не меняет набор entities между страницами. Если entities не запрошена, материал содержит ref и явное bodyState=notRequested; если body ожидает следующей страницы entities — bodyState=pendingPage. Эти состояния не означают отсутствие объекта. Для каждого вида материалов определить точный фильтр по указанному предмету и тесты, не копировать фильтр старого `item` по предположению. Пустое значение, отсутствие поля и незагруженная секция различимы. Внешние документы/attachments представлены refs и статусом; их bytes и сетевое содержимое автоматически не скачиваются. Связанные чужие процессы не читаются в обход текущих ограничений.

**5. Ответ, полнота и страницы**

Сохранить общий envelope компактного read: `schemaVersion`, `package`, краткий `graph`, `snapshot`, `detail`, `loaded`, `data`. Добавить `scope:{kind,rootRef,viewOnly:true}`; rootRef использует существующий codec. В `data` каждая секция имеет `items` и прежнюю форму `page:{total,limit,returned,nextCursor,hasMore}`. Строка entities имеет `ref` и `entity` с неизменённым каноническим body; остальные строки используют refs и исходные semantic projections, не создавая вторую редактируемую модель. Полные формы строк публикует schema.

`limit` — на секцию, прежние default 25/max 100. При нескольких секциях возвращается первая страница каждой; продолжение запрашивает одну секцию с её cursor. Дополнительный `reading` сообщает `requestedSections` и `scopeEnumerated`: перечисленная область не означает, что все её записи уже переданы. Сервер stateless и не утверждает, что клиент получил предыдущие страницы. CLI показывает `pagesComplete=true` только когда в его собранном результате присутствуют все записи всех запрошенных секций одного снимка; последняя страница отдельной секции сама по себе этого не доказывает. Незапрошенные секции отмечаются loaded=false, без обещания содержательной полноты. Инструкция продолжения присутствует в CLI.

Курсор переиспользует общий version-bound механизм и дополнительно привязан к detail/root/секции/правилам проекции и требуемым версиям источников. Он сохраняет первоначальную сигнатуру области и её pins: continuation с include одной секции не пересчитывает другой набор bodies и не ослабляет исходный снимок. Pins включают package/Graph SHA, Plan при запросе plan, Registry и доступные source revisions/digests при зависимых материалах. Изменившийся снимок даёт явный stale/conflict; нельзя склеить две версии. Каждый повторный запрос заново проверяет доступ: cursor не даёт grant. Существующие identitySpace/namespace/observed pins и copy bindings сохраняются.

Сервис не обрезает длинный Markdown/body по символам. Если один body превышает жёсткий транспортный бюджет, вернуть явную ошибку с ref/размером и адресным способом чтения, если он действительно поддержан; не выдавать обрезанный текст за полный. Технический byte budget, если нужен, публикуется schema. Отсутствующий, удалённый, исторический, недоступный или изменившийся объект получает точный статус общего resolver; никакой подстановки одноимённого объекта/новой версии. Причины и названия показываются в пределах прав, без утечки скрытого body.

Не включать layout/координаты, весь Registry, полный dependencyCatalog, общие receipts, snapshot inventory и History. Ссылка на доступный отдельный read допустима. Не добавлять `history --node` и не объявлять историю отфильтрованной фокусом. Чтение не создаёт owner/граф/Plan, не пишет review, selection, result, применение линзы или историю.

**6. Реализация и приёмка**

Переиспользовать `focused_view`, общие relation/membership indexes, projectors контекста/Findings/Questions/completion/recommendations/subjects и qualified resolver. Branch добавляет read-only вычисление структурного замыкания; не копировать kernel-правила в отдельный validator. Пакет формируется адресно: нельзя сначала построить весь full и лишь удалить лишние поля. Внутри одного неизменяемого read_scope повторно используется таблица сущностей; writer этот режим не включает. Между страницами Application хранит только сериализованные производные completion/dependencyApplications в существующем ProjectionCache (до 4 записей и 48 MiB), без persistent state. Перед cache lookup заново проверяются права, Graph/Plan, Registry и разрешение/версии источников; ключ включает текущий snapshot и hash actor token. Кэш не подтверждает grant или действительность cursor; обычная snapshot-bound проверка обязательна. Возвращаемые данные изолированы JSON decode/deepcopy; перезапуск просто пересчитывает их. Допустим общий расчёт, необходимый по семантике, но его стоимость измеряется; проекции/источники не перечитываются по одному разу на каждую связь.

1. **Точность focus:** тесты R/Decision/Action и поддержанных auxiliary/external roots сравнивают структурный состав с действующим projector. Корень один; родители краткие; Decision-focus не получает siblings/внуков. Зафиксировать D-SQL, R-STORE, R-SAFE, R1 из текущего учебного примера как воспроизводимые изолированные fixtures, а не зависимость CI от живого owner.
2. **Полнота branch:** длинная невыбранная ветвь, DERIVES/INTRODUCES/Actions, несколько групп, исключённые Decisions, границы WorkGraph, несколько родителей и внешняя входящая связь. Все ожидаемые IDs/edges/memberships возвращены; upstream и посторонние ветви не раскрыты. Сравнение — с независимым ожидаемым набором.
3. **Повторы/циклы:** ромб с общим потомком даёт один body, все связи и shared refs; back edge в изолированном тесте обхода даёт cycle ref. Запрещённый Graph остаётся отклонён валидатором; реальный цикл ради теста в живом owner не создаётся. Число outline строк ограничено размером области/связей.
4. **Качество данных:** по одному пакету и его страницам однозначно читаются родитель/альтернатива/контекстный источник, роль и происхождение value, полная теория и Info, Finding/Question/ответ/assessment, estimates/resultCondition, selected против confirmed/reviewRequired, конкретный блокер, рекомендация и недоступная ссылка. Не требуется читать реализацию или угадывать значение пустого списка.
5. **Страницы и доступ:** несколько facets, limit=1, повтор курсора, restart/readback без изменения снимка, чужой detail/root/facet, устаревший Graph/Plan/Registry/source, удаление/отзыв доступа между страницами. Сборка --all-pages равна неизменяемому контрольному ответу; конфликт не печатается как полная ветвь.
6. **Совместимость/отсутствие записи:** прежние read/full/item и Agent defaults; API/Agent/Gateway одинаковы; focus Graph/Structure не меняется. До/после совпадают Graph/Plan/Registry и persistent history; free Markdown не превращается в сущности.
7. **Размер и стоимость:** сравнить прежний full и новые режимы на одинаковых данных: UTF-8 bytes/строки, RPC/число страниц, отдельно backend/transport, p50/p95 для областей 50/500/5000. Контроль роста: добавление несвязанной большой ветви/чужого каталога не раздувает содержимое адресного ответа. Не задавать ложный фиксированный SLA; рост стоимости общих вычислений отразить отдельно.
8. **Выпуск:** schema/help и операторский вход объясняют режимы, состав/страницы/ограничения; обновлены текущие владельцы docs и проверки CI. Для runtime — адресные unit/API/Gateway/CLI проверки и полный Docker CI, точный READY/source SHA и readback установленного buildId по обычному регламенту. Ручная Windows/UX-приёмка отдельно; актуальный полный учебный пример и команда установки готовятся по тому же регламенту, не меняя живые рабочие owners ради теста.

**Порядок реализации:** schema/совместимость → адресный focus → branch/outline и граничные refs → материалы и pins/страницы → Agent/Gateway/--all-pages → качество данных/метрики/регрессии → релизные gates. Промежуточный срез не объявляется завершением B03A без всех критериев выше.

**Граница B03A:** это удобное чтение API/Agent, а не третий Markdown-renderer, импорт Markdown, новый режим редактирования или новый смысл существующего focus. Новый Viewer branch-screen и автоматическое извлечение сущностей из текста в это ТЗ не входят.

<a id="rdg-structured-markdown-contract"></a>
### Структурный Markdown B03B

**Статус — согласованная задача, реализация перед B04/T6.** Цель — прочитать один снимок RDG в трёх структурных видах, Графе, Структуре и Markdown. Markdown использует общую смысловую проекцию и те же owner, ID, доступ, область, связи и предметные состояния. Полный свободный текст теории хранится как связанный [исходный материал линзы](RDG-LENSES.md#теоретический-текст-и-его-представление-линзой).

#### Порядок документа

1. **Область.** Название, тип области, ревизия и полнота. Фокус открывается на заданной сущности и содержит краткий путь к родителям.
2. **Ветвь читается сверху вниз.** Последовательность заголовков и вложений показывает требование, варианты решения и дальнейшие действия. Использовать названия сущностей, рядом показать условия группы, выбор, результат и нужду в пересмотре. Связь, которую трудно понять из вложения, подписать явно.
3. **Сведения находятся у элемента.** Описание, условия результата, оценки, предметные ссылки и все применимые разделы текущих сведений. Контекст с ролью и происхождением, теория со всеми разделами и связанным Info, Findings, Questions и ответы, зависимости и влияния с причинами, рекомендации. Заголовки обозначают смысловые группы полей. Короткие значения располагаются строками под ними.
4. **Полное тело один раз.** При первом вхождении показывается карточка. Повторное вхождение сохраняет отношение и ведёт к этому же ID. Цикл имеет явную ссылку на предка. Полные связанные материалы раскрываются рядом с первым осмысленным обращением, другие обращения ведут к тому же телу.
5. **Отдельные области.** Plan, History, банк контекстов, рабочие области и определения политик имеют адресные разделы при включении в выдачу и ссылки для отдельного чтения. У границы сохраняются направление, тип и смысл связи. Для «Зависимостей» и «Влияний» фокуса сохраняются существенные сведения о применениях во всём процессе, которые доступны из текущего Inspector. Участник за границей фокуса может быть представлен ссылкой со статусом и версией.

#### Две формы выдачи

| Читатель | Поведение |
| --- | --- |
| Пользователь в Viewer | Оформленный документ. Видимый основной ход ветви, заметные состояния и причина review. Связанные материалы, подробности и технические IDs раскрываются у элемента. Переход по ссылке открывает нужный раздел и позволяет вернуться. При смене Граф/Структура/Markdown сохраняются owner, рабочая область или фокус, выбранная сущность и контекст возврата. |
| ИИ через API и Agent | Обычный Markdown с теми же заголовками, порядком ветвей и доступными фактами. Все запрошенные сведения присутствуют в тексте, с ID, типами отношений и точными ссылками. Через опубликованную schema выбираются формат и область. Поддержать чтение фокуса процесса, полной линзы и полного графа. CLI выводит читаемый Markdown без ручной склейки JSON-секций. |

Порядок общий для обеих форм. В Viewer можно добавить навигацию из тех же заголовков. Важные состояния видны до раскрытия, технические версии и подробности доступны по запросу. Сохранять полный исходный текст и Markdown-формат описаний и теории. Снимок, разрешения, доступность материалов, правила границ и переходы используют общий Application/resolver. Для адресного чтения использовать семантику областей и привязку к снимку из B03A. Отличать «пусто», «за пределами запроса», «есть продолжение» и «недоступно». При сборке полного результата все страницы должны принадлежать одному снимку.

**Граница первого среза — чтение.** Переключение вида сохраняет Graph, Plan и History. Предметные изменения используют действующие формы и writer. Импорт, редактирование исходного Markdown и файловый экспорт требуют отдельных критериев, если возникнет потребность.

<a id="rdg-markdown-implementation"></a>
#### ТЗ реализации Markdown

**M1 · Общая проекция.** Добавить в общий Application чтение упорядоченного документа из одного проверенного снимка. Переиспользовать семантику фокуса и ветви B03A, текущую проекцию состава области, порядок вхождений Структуры и общие projectors материалов, completion и зависимостей. Порядок сравнивается с развёрнутой Структурой для той же области и действующих фильтров, независимо от локального раскрытия строк. В местах, где Структура открывает материал из Inspector, Markdown показывает соответствующую секцию или точную ссылку. Если у проекций есть расхождение в существующих фильтрах или scope, согласовать один источник состава и покрыть его тестом. Дополнительные данные Inspector, например применения зависимостей за пределами фокуса, проецируются с сохранением предмета и границы. Презентационный код выбирает порядок и форму, смысл состояний и отношения вычисляют действующие owners.

Результат проекции — последовательность именованных блоков с типом, qualified identity, уровнем, полями и адресными переходами. Один обход определяет первое раскрытие и все последующие ссылки. Порядок повторяем на одном снимке. Уровни заголовков ограничены возможностями Markdown. Для более глубокой ветви сохранять отношение и путь к родителю в явной строке, а в Viewer — визуальное вложение. Генерировать устойчивый уникальный якорь из identity объекта, чтобы одинаковые названия, несколько родителей и несколько областей в одном документе разрешались однозначно. Технические ключи, наблюдения и provenance выводить в именованных группах сведений. Краткие повторные ссылки могут показывать название и состояние, полный текст объекта передаётся один раз.

**M2 · Viewer.** Добавить `presentation.mode=markdown` к существующему переключателю и валидатору `view_session`, включая возвраты и чтение старых сессий. Для прежней сессии сохраняется её текущий режим. Markdown открывается в выбранном Graph/WorkGraph/Focus. Заголовки, существенные состояния и причины review видны сразу, сведения и технические идентификаторы раскрываются на месте. Оглавление при длинном документе строится из тех же заголовков. По ссылке на скрытую секцию открыть её и сфокусировать нужный объект. На переходе к другому owner или панели применять существующий navigation trail. При смене области сбрасывать поздний ответ прежнего запроса. Если новый read показывает сменившуюся ревизию, обновить документ целиком с явной отметкой о версии. Текст исходных полей обрабатывать как данные. Viewer выводит безопасные текстовые блоки и навигационные ссылки, сырой HTML из полей экранируется. Код, Markdown описаний и примеры сохраняют содержимое в выделенном блоке.

**M3 · Публичный read и Agent.** Добавить опциональный селектор `format: "markdown"` к текущему `method: "read"` и опубликовать доступные формы, лимиты и ошибки в `schema(read)`. Без селектора сохраняется прежняя JSON-форма ответа. Публичные случаи для `rdg-decision-v1`:

| Запрос с `format: "markdown"` | Область документа |
| --- | --- |
| `detail: "full", packageId` | Весь Graph выбранного процесса, готового графа или линзы. Полная линза читается по её package ID из каталога линз. |
| `detail: "full", packageId, view: {kind: "workGraph", id}` | Та же рабочая область, которую открывает Viewer. Viewer может также передать действующую допустимую `view` для переключения из текущего фокуса. |
| `detail: "focus", packageId, nodeId` | Существующий фокус B03A, включая поддержанные вспомогательные виды. Корень, его ближайшее окружение и относящиеся сведения. |
| `detail: "branch", packageId, nodeId` | Полное структурное продолжение R или Decision по B03A. Выдача scope отличается от фокуса явно. |

Для B03A сохранять совместимые значения `include` и семантику секций. Для полного представления отдельно явно включается Plan по существующему `includePlan`. History остаётся адресуемой штатной операцией. В режиме чтения все доступные поля запрошенных сущностей и материалы остаются полными. Области за пределами запроса и записи без доступа обозначаются по действующему resolver. Неподдерживаемые профиль, detail, scope или их комбинация возвращают явную ошибку. Запросы JSON и старые клиенты продолжают использовать свои существующие схемы.

Gateway и браузерный endpoint сохраняют JSON-конверт протокола, без отдельного HTTP endpoint. Ответ Markdown содержит `schemaVersion`, `format`, `scope`, `snapshot`, `markdown` как строку обычного UTF-8 текста и `page: {hasMore, nextCursor}`. `reading.pagesComplete` означает, что ответ или собранный клиентом результат содержит весь запрошенный документ. Последняя страница, прочитанная отдельно, не означает полную выдачу. Viewer использует ту же проекцию и структурные границы блоков, чтобы раскрывать сведения. Agent добавляет `open --format markdown` с прежними селекторами области. Для полной линзы поддержать выбор по ключу через `lens --lens KEY --format markdown` на подготовленном API. Agent получает строку `markdown` и печатает её как текст, без JSON-кавычек и escape-последовательностей. Для сборки использовать `--all-pages` также с Markdown полного графа. Сборка страниц проверяет ревизии и область и печатает полный документ только после успешного завершения. Частичная выдача явно обозначена в самом тексте и метаданных. Диагностика CLI уходит отдельно от Markdown.

```jsonl
{"method":"read","format":"markdown","detail":"focus","packageId":"<id>","nodeId":"D-SQL"}
{"method":"read","format":"markdown","detail":"full","packageId":"<process-or-lens-id>"}
```

**M4 · Полнота, размер и ссылки.** Один запрос возвращает весь документ, если он укладывается в поддерживаемый бюджет транспорта. Длинный документ делится по границам полных структурных блоков. Не разрезать внутри текста сущности, таблицы или fenced code. Cursor привязывается к формату, области, составу секций, порядку и версиям Graph, Plan, Registry и источников, которые реально участвуют в выдаче. При смене снимка возвращать явный stale; клиент заново читает область. Доступ проверяется на каждой странице. Размер измерять в UTF-8 для фактического JSON-конверта ниже лимита Gateway 16 000 000 байт. Если один блок превосходит бюджет, сообщить его ref и размер и опубликовать доступный адресный маршрут либо явную ошибку. Ссылки между страницами несут адрес сущности, чтобы её можно было открыть до загрузки другой страницы. Статусы «пусто», «вне запроса», «продолжение» и «недоступно» различаются в Viewer и в тексте API.

#### Приёмка Markdown

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| M-A1 | Короткая цепочка, альтернативы с материалами, два корня с общим продолжением | На одинаковых снимках совпадают доступные сущности, typed edges, группы, предметные состояния, поля Inspector и разрешимые источники. Порядок Markdown сохраняет ход ветви, общий body один, повторные вхождения показывают их реальные связи. |
| M-A2 | Фокус, WorkGraph, полный процесс, полная линза и возврат из материала | Viewer сохраняет область и выбранный объект при смене вида. Причина review видна до раскрытия, переход открывает нужный раздел. Agent читает те же факты в Markdown через public Gateway. |
| M-A3 | Общий узел, цикл в допустимой фикстуре, граница фокуса, закрытый и пропавший источник | Статусы точны, значимые отношения сохранены, скрытый body не раскрывается. Материалы, связанные с текущим элементом, не теряются из-за узкого scope. |
| M-A4 | Много страниц, смена ревизии, отзыв права, длинный Canon и код | Сборка на одном снимке совпадает с непостраничным результатом по смыслу и порядку. Смена снимка или права видна явно. Длинный текст доступен полностью, вложенный Markdown безопасен, частичная выдача помечена. |
| M-A5 | Совместимость JSON, старые сессии, отсутствие записей | Прежние запросы и режимы сохраняют поведение. После чтения совпадают Graph, Plan, Registry и предметная History. Новые Viewer-состояния совместимы с существующим session lifecycle. |

<a id="rdg-text-search-contract"></a>
### Текстовый поиск B03C

**Статус — согласованный первый срез того же этапа.** Цель — по знакомому слову найти объект без заранее известного ID и сразу перейти к его сведениям. Совпадение — обычное вхождение строки без учёта регистра. Viewer, Gateway и Agent используют одну реализацию в Application.

<a id="rdg-search-implementation"></a>
#### ТЗ реализации поиска

**S1 · Запрос и области.** Опубликовать `schema(search)` и добавить `method: "search"` в закрытый dispatch. Поля запроса — `query`, `scope`, `packageId`, `limit`, `cursor`. При `scope: "package"` нужен конкретный package ID. Viewer и Agent подставляют открытый owner из контекста, если он задан однозначно. `scope: "catalog"` указывается явно и проверяет доступ к каждому owner до чтения его объектов. Для каталога не подставлять `packageId`. Нормализовать пробелы по краям и сравнивать через Unicode casefold. Пустой запрос отклоняется с понятной диагностикой. Опубликовать предел запроса, для первого среза до 180 символов, и `limit` по умолчанию 25, максимум 100. Запрос трактуется как буквальный текст, включая знаки пунктуации.

```jsonl
{"method":"search","query":"p95","scope":"package","packageId":"<id>"}
{"method":"search","query":"p95","scope":"catalog","limit":25}
```

**S2 · Поля и доступ.** Использовать читаемый текущий снимок и существующий набор сущностей ядра, в том числе внешние Actions. Вынести явную карту «kind → текстовое поле → раздел сведений». Базовые поля — ID, название, описание. Включить условия результата, текстовые оценки и основания Action, значения и текст Context и Info, все содержательные секции Canon, формулировку и основания Finding, вопрос, влияние, условие достаточности и доступные актуальные ответы Question. Роли Context в Decision относятся к этому Decision и ведут в его раздел контекста. Связанный Canon или Question возвращается как собственная сущность. Для недоступного owner, поля или источника не формировать совпадение, фрагмент или счётчик. Начать с ограниченного обхода доступных канонических данных. Не строить полный визуальный Graph/Layout/History ради поиска; необходимость отдельного индекса оценить по замерам.

**S3 · Результат, порядок и продолжение.** Возвращать одну строку на qualified identity, с `ref`, `kind`, `title`, контекстом owner, `matches` и адресным `target`. В `matches[]` передавать `field`, `label` и `snippet`. `target` содержит тот же точный ref и ключ раздела сведений. Общий конверт содержит `schemaVersion`, `scope`, `items` и `page: {hasMore, nextCursor}`. Тексты и пути относятся только к доступной сущности. Точный ID выше совпадения в названии, совпадение в названии выше совпадения в содержимом. Остальные совпадения упорядочивать стабильно по owner и entity ID. Показать основное совпадение сразу, остальные поля той же сущности раскрывать в одной строке. Возвращать явный пустой список при отсутствии совпадений. Cursor привязывается к нормализованному запросу, области, стабильному порядку и видимому снимку. При смене Graph или доступности, которая меняет состав, ответить stale и перечитать первую страницу. Проверка допуска выполняется заново перед каждой страницей и переходом. Изменение закрытых owners не должно выдавать их наличие через результат или метаданные.

**S4 · Viewer и Agent.** Одна форма поиска с текущим процессом/линзой по умолчанию и явным переключателем «Весь доступный каталог». Viewer показывает совпадение с фрагментом безопасным текстом и сохраняет запрос, область и позицию выдачи при возврате. При изменении запроса или области предыдущая запоздалая выдача отбрасывается. Открывать точную сущность по qualified ref и существующему resolver. Для R/Decision/Action возможен прямой Markdown-фокус. Для Canon, Context, Finding или Question открывать соответствующий блок Markdown или текущую адресную карточку/вкладку, сохраняя связь с найденным объектом. Если target исчез или стал недоступен, показать статус актуального read. Agent получает ту же JSON-выдачу поиска и использует найденный ref для следующего `read(format=markdown)`.

#### Приёмка поиска

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| S-A1 | `p95` в названии Requirement, условии результата Action и содержании Canon | Три точных сущности, корректные поля и фрагменты, каждый переход ведёт в нужные сведения. Поиск по ID, другому регистру и буквальным знакам работает предсказуемо. |
| S-A2 | Несколько полей одной сущности, одинаковый ID в разных owners, ноль совпадений и несколько страниц | Один результат на сущность. Разные qualified identities остаются разными. Порядок стабильный, без дублей и пропусков на неизменном снимке. |
| S-A3 | Правка, удаление, смена owner или отозванное право между запросами | Новый запрос видит актуальный состав. Старый cursor возвращает явную ошибку при смене видимого снимка. Закрытые данные и их фрагменты не попадают ни в выдачу, ни в доступные метаданные. |
| S-A4 | Один сценарий в Viewer, Agent и Gateway | Совпадения одинаковы при одинаковых правах, переход открывает правильный объект, возврат сохраняет поисковый контекст. Сценарий «найти слово → открыть Markdown → объяснить основание» проходит без предварительного знания ID. |

#### Совместная проверка этапа

1. Проверить общую проекцию и renderer Markdown на трёх изолированных снимках. Затем подключить Viewer и Gateway/Agent.
2. Проверить поля, права и страницы поиска на тех же данных. Связать результат поиска с Markdown и действующими карточками.
3. Пройти адресные unit, HTTP/CLI и браузерные проверки, затем сравнить JSON, Markdown и файлы на одинаковых задачах по [плану исследования](RDG-DEVELOPMENT-PLAN.md#rdg-ai-read-baseline). Отдельно зафиксировать корректность, шаги поиска, объём и время.
4. Сверить контракт и бэклог с реализацией, пройти обычный [release gate](RDG-OPERATIONS.md#разработка-и-обновление-серверного-runtime) и предъявить результаты вместе с кодом и документацией. [Чек-лист этапа](../../BACKLOG-IMPROVEMENTS.md#rdg-markdown-search-stage)

### Самостоятельные Questions

**T3 — реализовано в исходниках.** Общие Application/kernel обслуживают CRUD, `question_answer` (add/edit/remove с version guard), `question_assess`, `question_migrate`, copy/remap и batch. Viewer использует тот же preflight/apply/receipt. Поля и обязательные ограничения:

| Поле | Целевое содержание |
| --- | --- |
| `relatedRefs` | Предмет/область: Finding, D, R/Action, Context/Canon/Info, рабочая область либо процесс; структурный родитель не нужен |
| `sourceRefs` | Происхождение вопроса; отдельно от предмета и от подписок на изменение |
| `impact`, `answerCondition` | Почему ответ важен и что считается достаточным ответом |
| `blocking` | Необязательное описание blocking/non-blocking/partially blocking; для partial указан конкретный блокируемый scope, включая текстовый scope, когда элемента ещё нет |
| `answers` | Записи со стабильными IDs, текстом, видом hypothesis/observation/user_answer, источником/основаниями; actor/time фиксирует writer |
| `assessment` | Необязательные answerIds, sufficient и непустое обоснование оценки достаточности; предыдущие оценки сохраняются исторически |

Подтверждение `user_answer`: writer создаёт `userSource` с режимом `direct-user-entry` и ID доверенного user-события либо `user-context` с ID последнего user-события изменения Context и его nodeId. ИИ обязан передать актуальный qualified sourceRef и точно воспроизвести value этого Context. Неподтверждённый текст, устаревший pin и подстановка recordedBy/userSource отклоняются. Редактирование ответа заново проверяет источник; прежний источник остаётся в answerHistory.

Qualified entity refs сохраняют исходный observed pin. При copy/remap writer производит read-only `referenceBindings` через существующий entityLineage; это привязка к конкретной локальной копии, без второго редактируемого списка вопросов. Две вставки одного шаблона не связывают вопросы с элементами соседней копии. Ответы/assessment IDs remap-ятся; исходные события остаются в проверенной inheritedHistory. При удалении предмета вопрос и история сохраняются, его ссылка становится historical. Предварительная проверка показывает questionLinks. Шаблон ready/lens принимает только бумажные Questions без ответов, оценок и live источников.

Для entity используется общий qualified codec; дополнительные типы `process`/`workGraph` адресуют тот же owner, `document` хранит HTTPS-ссылку, не загружая и не подтверждая содержание. Cross-owner процессные refs по-прежнему не поддержаны. В batch `$alias` адресует ID предыдущего шага, `$entityRef` формирует его qualified ref в текущем подготовленном Graph; ответы и оценки возвращают собственные IDs.

Заголовок обязателен; отсутствующие сведения не заполнять догадками. Существенный/формально запрашиваемый вопрос должен иметь понятные impact, блокирование и достаточность ответа. Не вводить отдельную произвольную шкалу приоритета или обязательный опросник для каждого сообщения. Ответ с видом user_answer ссылается на действительно полученный пользовательский ответ; recordedBy/actor не подменяется его происхождением. Гипотеза ИИ не становится ответом пользователя или permission grant.

`relatedRefs` — единственный записываемый источник новых привязок: списки вопросов в Finding/Decision и группе «Вопросы файндингов» вычисляются из него. Один Question может использоваться несколькими источниками, без отдельных editable-копий. Использовать существующий qualified-reference codec; для scope/lens/document добавить минимальные явно типизированные варианты поверх общего resolver, без второго формата entity refs. Обычная ссылка/происхождение не создаёт зависимость автоматически.

Добавить CRUD через `core add/edit/remove` и команды `question_answer` (add/edit/remove), `question_assess`, `question_migrate`. Generic edit не должен обходить отдельную валидацию ответов/оценки и writer attribution. Question поддерживает общие dependency/review-проекции и наблюдение семантического содержания; review-флаг не является новым definition-событием. Содержательная смена вопроса/условия достаточности сохраняет прежние ответы и оценку с явной необходимостью перепроверки. Изменение ответа не назначает disposition Finding, новый R/D или выбор автоматически.

Старые embedded questions читать совместимо без записи. Новое создание/редактирование вопросов основного профиля использует canonical Question; legacy payload можно сохранить неизменённым, а его редактирование требует явного переноса с понятным сообщением schema/UI. Старый клиент не может перезаписать новые привязки своей устаревшей копией. Перенос создаёт canonical IDs; исходное содержимое остаётся в принятой версии/истории, второй редактируемый набор не ведётся. Одинаковые локальные IDs разных Findings/Decisions не сливать. Preflight показывает переносы, используется точный retry. Удаление Finding не удаляет общий Question; удаление Question предварительно показывает затронутые ссылки, не стирает чужую историю.

UI: вкладка процесса «Вопросы», группа Findings и остальные вопросы, поиск/переходы к тем же IDs из Inspector/Canon/scope/Plan. Видны вопрос, имеющиеся ответы и достаточность, отдельно review; подробности и происхождение раскрываются. В Graph/Structure узлов Question нет. Подготовка формального запроса показывает доступные данные/собственные возможные ответы ИИ и оставшиеся вопросы после checkpoint; создание записи не отправляет сообщение и не пытается получить разрешение. Новую подсистему переписки/полномочий не строить.

Copy/remap переносит Questions, answer IDs и локальные refs; live scope и пользовательские ответы не выдаются за факты reusable ready/lens. Локальные бумажные вопросы для повторного использования допустимы по общим role-ограничениям, внешние process refs не протаскиваются. Нужны проверки общего Question у F1/F2, разных источников одного ответа, insufficient/достаточного ответа, смены оснований, одинаковых legacy IDs, явного переноса, remove/copy/restart и невозможности превратить ответ в selection/disposition/permission.

### Оценки Action

**T4 — реализовано в исходниках, без формальной шкалы.** Необязательное поле `estimates` для Graph и external task Actions:

```json
{"complexity":"свободная оценка сложности исполнения","time":{"minSeconds":60,"maxSeconds":180},"basis":"основание оценки"}
```

Внутри достаточно complexity или time; basis необязателен. complexity — непустой текст, time — конечные неотрицательные minSeconds≤maxSeconds; точечная оценка имеет равные границы. Неизвестное отсутствует, не подставляется как ноль. Удаление оценки явно поддерживается edit-формой: `changes.estimates=null` удаляет поле из текущего Action. Это целевой технический выбор ТЗ: новая числовая шкала сложности не вводится. Календарные даты, фактическая длительность и общая сложность планирования имеют отдельное значение.

CRUD/read/schema, API/Agent и компактные сведения используют одно поле. Изменение estimates входит в обычное definition-наблюдение Action, сохраняет before/after и не проходит под cosmetic. Не пересчитывать календарь, selection или completion автоматически. Старые Actions без поля читаются без записи; оценки проходят copy/remap и History. Проверки: частичная/точечная оценка, неверные границы/типы, удаление, старые данные, наблюдающее применение, Graph/Structure, F5 и сохранение результата Action.

### Планировочные метадействия

**T5 — Planning Meta Action. Уточнённое ТЗ пользователя 2026-11-08; реализовано в исходниках, release gate и Windows/UX проверяются отдельно.** Предметные нормы принадлежат [смысловому контракту](RDG-ACTIVE-CONTRACT.md#планировочные-метадействия). Это обычный внешний Action для работы над самим процессом RDG, размещаемый непосредственно в Plan без R/Decision-родителя и без показа в Graph/Structure. Использовать существующие `externalActions` с `actionType:task`, для нового метадействия `lowLevel:false`; не создавать новый kind/owner или параллельную модель Action. Сохраняются обычные название, описание, условия результата, оценки сложности/времени, состояние выполнения, подтверждение результата, History, редактирование и удаление.

**Предметные ссылки.** Поддержать необязательные типизированные ссылки на реальные объекты RDG: Requirement/Decision/Action, Question/Finding, Context/Canon/Info, процесс/рабочую область, линзу/элемент её графа и другие применимые цели общего resolver. Можно указать несколько целей; отсутствие ссылок допустимо для общей работы над процессом. Ссылки определяют предмет работы, не структурную зависимость, автоматическое изменение или completion-обязательство. Переиспользовать qualified-reference codec и общий resolver; сохранять идентичность объекта, namespace и необходимую версию определения. Переход разрешает реальную цель либо показывает recorded/deleted/changed/unavailable состояние по общим правилам, без подстановки одноимённого ID. Не расширять права или возможность межпроцессных core-зависимостей одним наличием предметной ссылки.

**Минимальное расширение.** Прежняя проектная конструкция `workflow:{targetRefs:[...]}` отменена как выбранная форма T5; она не вводится как самостоятельное предметное понятие. После сверки существующих механизмов выбраны optional `Action.subjectRefs` и обычное поле `Action.resultCondition` (строка условий результата); оценки остаются в `estimates`, результат — в прежнем `result`. Операция Application/schema — `plan_action` с `entity`, `placement`, обычными package/graph/plan CAS, transactionId и note. При отсутствии Plan операция создаёт его тем же атомарным commit. Batch-шаг `plan_action` принимает `alias`, `entity`, optional `placement` и note; alias адресует Action, alias+`Placement` — placement. Расширение нормализуется в существующие core add external + plan create/place; прежнее ограничение Graph-команд перед Plan для остальных шагов сохраняется. Не дублировать систему ссылок, writer, validator, статусы или механизм исполнения. Существующие low-level операции и legacy targetIds/groupIds сохраняют свой смысл и не становятся предметными ссылками метадействия автоматически.

**Создание и размещение.** Application/schema предоставляет одну операцию создания Planning Meta Action с первым размещением в Plan, а `batch` — соответствующий шаг через те же механизмы записи. Общий `preflight` без записи проверяет обе части и показывает Action ID, placement ID и изменения Graph/Plan. `apply` сохраняет их атомарно общим coordinator; `receipt` содержит идентификаторы и ревизии. Ошибка не оставляет половину операции; exact retry после потери ответа не создаёт дубль; recovery и restart/readback используют существующие механизмы. Plan ссылается на существующий к моменту commit Action с identity. Атомарность — техническая гарантия создания, а не самостоятельная семантика метадействия.

**Редактирование и навигация.** Из Plan доступны создание, обычный Inspector Action/оценки, редактирование предметных ссылок, стандартное изменение placement, порядка/времени/ветви, переход к предмету работы и возврат к исходному метадействию с сохранением рабочего контекста. Удаление placement и удаление самого Action остаются разными операциями. Открытие линзы/её элемента не означает применения. Создание, размещение и выполнение метадействия не меняют связанные сущности без отдельного явного действия; завершение подтверждает только само действие, а не разрешение Question, изменение Finding, выбор Decision, применение линзы или completion связанных R.

**Примеры свободных задач:** «Уточнить ответ на Question Q1», «Исследовать причины Finding F2», «Применить линзу анализа решений к Decision D3», «Пересмотреть Requirement R1 с учётом нового контекста», «Исследовать дополнительные альтернативы», «Проверить согласованность структуры процесса», «Пересмотреть временной Plan». Название, описание и условия результата формулируются свободно; закрытая классификация типов не создаётся.

**Сверка перед кодом.** Проверить существующие `externalActions` и обычный Action lifecycle в [ядре](../../tools/rdg-decision-model.py), qualified references/resolver в [общей модели](../../tools/rdg-portable-model.py), расширения scope/lens refs у [Questions](../../tools/rdg-questions.py), [Application/placement/coordinator](../../tools/rdg-portable-service.py) и существующий атомарный [batch Graph+Plan](../../tools/rdg-batch.py). Использовать эту основу; добавлять только недостающее. Наличие основы не закрывает приёмку T5.

Предметные ссылки используют прежний entityRef (`packageId`, `identitySpace`, `nodeId`, mode/revision/graphRevision/SHA256) или scopeRef (`schemaVersion:1`, kind `process|workGraph|lens`, packageId/identitySpace/graphRevision/SHA256 и workGraphId для области). Namespace задаётся авторизованным store; новая запись допускает местные объекты или читаемую линзу того же профиля, а не межпроцессную core-связь. Read отдаёт `scopeReferences` и разрешённые `actionSubjects`; compact facet — `subjects`, cursor учитывает digest разрешённых целей. Старые pins/недоступность сохраняются; копия локальных entity refs использует общий referenceBindings/lineage, scope refs переводятся в копируемую область, внешние ссылки линзы сохраняются. Семантические изменения subjectRefs/resultCondition участвуют в обычном definition-review и History. [Адресная приёмка](../../tests/rdg-planning-meta-actions.test.py), [Gateway](../../tests/rdg-gateway.test.py), [Viewer/F5](../../tests/visual/rdg-planning-meta-actions.cjs) включены в CI.

**Критерии завершения T5:**

1. Прямое создание в Plan без R/Decision-родителя.
2. Обычные свойства, оценки и жизненный цикл Action.
3. Сохранение, чтение, редактирование и разрешение типизированных предметных ссылок.
4. Переход к предмету работы и возврат к исходному метадействию в Plan с сохранением контекста.
5. Атомарное создание Action и placement через API и batch.
6. Общие CAS, receipt с обеими частями, exact retry, recovery и restart/readback.
7. Отрицательные проверки: нет частичной записи, дублей или подмены удалённых/недоступных/изменившихся ссылок.
8. Нет показа в Graph/Structure, автоматических предметных изменений, selection или completion связанных объектов.
9. Старые external Actions, ID, ссылки, размещения, история и состояния совместимы; автоматическая миграция не требуется.
10. API, Viewer и соответствующие тесты подтверждают одну семантику действия; отдельная система workflow/статусов/исполнения не появляется.

### Теория принятия решения B02A

**ТЗ согласовано пользователем 2026-11-07; реализовано в исходниках. Release gate и Windows/UX проверяются отдельно.** Только `rdg-decision-v1`: сохраняются `kind:canon`, `CANON_FOR`, ID, ссылки и прежние версии/история. Единственный источник «Общего» — существующая строка `guidance`; дополнительные необязательные поля: `canons` (строка) и `knownErrors` (упорядоченный массив `{id,title,description}`). ID ошибки непустой и уникален внутри теории, title непустой, description — строка, допускается пустая. Локальная identity ошибки — пара ID теории и ID записи; копия теории получает собственный набор, локальные IDs могут сохраняться. Самостоятельных typed refs на ошибки этот этап не вводит.

`guidance` остаётся строкой, допускается пустая; хотя бы один из трёх разделов должен содержать данные (непробельный guidance/canons либо непустой список ошибок). Отсутствующие canons/knownErrors читаются как пустые без записи. Явная очистка — `canons:""`, `knownErrors:[]`, `guidance:""`, при сохранении непустого содержания теории. Null, неверные типы/неизвестные поля записи и повторяющиеся локальные IDs отклоняются. Старый guidance показывается полностью в «Общем»; description и Info не перемещаются. Переход нового объекта на legacy форму не должен молча терять новые разделы: частичный edit меняет только явно названные поля, замены содержимого устаревшим snapshot API не предоставляет.

Общие add/edit, schema, Agent/API, batch, copy/import/capture/apply и компактный/full read используют одну валидацию. Schema показывает все разделы; guidance больше не объявляется единственным обязательным непустым содержанием. Любое содержательное изменение canons/knownErrors/guidance включается в definition/Canon-наблюдения, History before/after и обычный CAS/receipt/recovery; cosmetic допускает только название. Выдержка источника анализа включает все содержательные разделы. Старые исторические pins не переписываются. Просмотр/редактирование доступны одинаково из Graph и Structure, включая теорию у связанного элемента, саму теорию и её Info/контекст/Findings-переходы.

Приёмка: старые данные без автозаписи/потерь; создание и очистка полей, добавление/изменение/удаление/порядок ошибок; негативные формы; schema/API/batch; no-write preflight и поздний atomic failure, CAS/exact retry/restart/readback; copy/import и независимость копий; History/review для каждого поля; Graph/Structure и F5. После изменения подготовить новый полный пример с новым path/journal, не создавая живой owner до совместимого runtime. Полный Docker CI и отдельная Windows/UX-приёмка сохраняются.

### Адресные рекомендации B02B

**Требования пользователя уточнены 2026-11-08; реализовано в исходниках. Docker READY, Windows и UX проверяются отдельно.** Семантика готовых графов, принципов/процедур линз, рекомендаций и сохранения применения имеет [одного владельца](RDG-ACTIVE-CONTRACT.md#готовые-графы-линзы-и-рекомендации). Расширить существующий recommendation-механизм, общий Application/coordinator и codecs, без нового Graph-kind/owner.

Привязки должны адресовать реальные R/Decision/Action (включая external task), Context/Canon/Info, Finding/Question, процесс и рабочую область, в том числе существующие элементы графов линз и готовых шаблонов. Использовать квалифицированные typed refs, сохраняя namespace и локальный scope; визуальное вхождение не является отдельной сущностью. Новая запись из элемента по умолчанию относится к нему. Более широкий охват автор выбирает явно; создание/установка фундаментальной линзы или чтение каталога не создаёт и не подключает массовые рекомендации.

У рекомендации сохраняются устойчивая identity, цель и свободные пояснения «когда использовать» и «как использовать». Ознакомиться с принципом, перечитать часть и пройти методику как процесс — примеры свободного содержания, не закрытая таксономия режимов и не команды auto-run. Текст не исполняется как предикат. Разные авторские советы об одной линзе не сливаются только из-за одинаковой цели; повторное попадание одной записи может объединять основания. Реализация сохраняет `recommendationPackage.authored:true`, `rules[].whenText/usageText`, квалифицированный `anchor` с optional `kind:entity|process|workGraph` и optional `lensRefs[].nodeId` для шага. Identity авторского совета — пара definition ID и rule ID; legacy правила сохраняют прежнюю дедупликацию. Раздел compact read — `include:["recommendations"]`; cursor учитывает Registry и digest проекции рекомендаций, включая доступность/версию цели. Поля обнаруживаются через schema. Создание из вкладки атомарно использует `recommendation_edit` с `attachTo`; снятие привязки — `recommendation_attach`, прежнее определение и pins не стираются. При вставке шаблона рекомендация для его процесса не расширяется на весь принимающий owner: сохраняется диагностика `instance-process-scope-not-transferable`; рекомендации элементов/перенесённых областей остаются локальными. При копировании всего процесса его собственная привязка переносится. Адресный UI не редактирует общий для нескольких consumers пакет; его редактирование остаётся явным маршрутом Explorer. [API-приёмка](../../tests/rdg-recommendations-authoring.test.py) и [browser/F5](../../tests/visual/rdg-recommendations-authoring.cjs) включены в CI.

UI: отдельная вкладка «Рекомендации · N» в сведениях выбранного объекта, включая пустой список и создание на месте; одинаково из Graph/Structure и из собственных карточек Questions/Findings. Карточка показывает цель, пояснения, охват/происхождение и состояние ссылки; доступны редактирование, снятие привязки и переход. Создание записи и её привязка атомарны, CAS/exact retry/receipt общие. Локальная правка не меняет чужие процессы; изменение явно общего определения предварительно показывает затронутых consumers. Компактный read должен отдавать рекомендации по запросу вместе с их текстом и IDs; полный read сохраняется совместимо.

Отдельно проверить совместимость профиля, namespace/identity и доступ к цели; пропавшая цель остаётся понятной recorded/unavailable ссылкой. Возврат восстанавливает рабочий контекст, фокус/вкладку и режим Graph/Structure. Создание рекомендации, открытие определения, реальное использование методики, сохранение полезного результата работы, необязательная запись применения с pins и вставка готового содержания — разные операции. Содержательные последствия и последующие действия определяются методикой, задачей и применимыми критериями по [общему принципу линз](RDG-ACTIVE-CONTRACT.md#готовые-графы-линзы-и-рекомендации). Recommendation API не вводит для применения линз отдельный закрытый набор допустимых сущностей/операций, не требует фиксированного набора выходов или копирования определения как доказательства применения; сами операции используют обычные writers и проверки. Наличие `lens_apply` не требует события на каждое чтение/мысленное использование; уже выполненные предметные записи и их историю сохранять по обычным правилам.

Переход старого массового `fundamental`: сначала read-only inventory подключений, затем конкретный diff отдельной явной операции. Не выдавать прежний auto/default за вручную созданный совет; не удалять линзы или исторические pins и не переписывать данные при чтении/обновлении runtime. Адресное содержание фундаментальных рекомендаций согласуется до source/live правок.

Приёмка: все адресуемые типы/области; пустая вкладка и CRUD; два разных совета одной линзы; отсутствие default-раздачи; текст в компактном/full API; корректные copy/remap и независимость копий; плохие refs/права/профиль, поздний atomic failure/CAS/retry/restart; nested-переходы/возврат/F5; ознакомление и повторное обращение без копий/обязательных событий применения; получение результатов по назначению конкретной линзы и сохранение уместной части работы по критериям, без обязательного набора новых сущностей; осмысленная вставка готового содержания проверяется как отдельный способ переиспользования, а не как общее определение результата применения. Runtime gate и Windows/UX отдельно.

### Теория, линзы и рекомендации

**T6 — полноценное содержание после B03B.** Развивать [две группы фундаментальных линз](RDG-LENSES.md#rdg-fundamental-groups) в порядке «обязательный бутстреп → методики эффективной работы». Пересобрать `model` по [целевому описанию](RDG-LENSES.md#полное-целевое-содержание-model): два родительских R, одна общая R сохранения/пропуска, 11 непосредственных способов, их содержательные Canons и Info. Общая формула сохранения адресует единственный нормативный источник. Совместимые способы добавления не взаимоисключаются, skip конфликтует с сохранением того же фрагмента. Questions/оценки/Planning Meta Action показывать как доступные только после реализации T3–T5; чтение линзы не выбирает Decisions.

Сохранить 15 существующих ключей и profile boundaries. Добавить Decision-only `dry`, `kiss`, `yagni`, `decision-analysis`, `research`, `specify`: содержание первых трёх и границы с существующими линзами — в [сверке покрытия](RDG-LENSES.md#dry-kiss-и-yagni--покрытие-и-целевое-разбиение), analysis покрывает Canon→контекст→Finding→Questions/ответы. Не создавать фиктивные legacy-варианты. Восстановить специфический смысл каждого Decision-шагa в остальных фундаментальных линзах, включая известные потери preserve/checkpoint и чрезмерный запрет D→D. Общий технический протокол — одним Info/ссылкой; одинаковая вставка этого протокола не заменяет разные методики. Research и specify добавлены к проекту второй группы 2026-11-11: получение проверенных сведений и согласованная постановка имеют самостоятельные результаты. Полные тексты и границы — в [реестре](../lenses/README.md); новые ключи не создают новый профиль, Graph kind или автоматическое применение.

Обычный полный теоретический текст сохраняется по [правилу источника и карты](RDG-LENSES.md#теоретический-текст-и-его-представление-линзой). Реализовать проверяемую source-map таблицу/JSON для каждого перенесённого смыслового фрагмента: source file/URL + версия/якорь, target lens/namespace + IDs/отношения, смысл разделения/объединения/ссылки. Формат выбрать один для всего каталога и отдать его через lens-read; это не новый Graph kind. Автоматическая проверка находит отсутствующие исходники/якоря/IDs и устаревшие версии; содержательная приёмка проверяет полноту смысла. Полный текст/примеры доступны пользователю обычным файлом либо сохранённой редакцией источника; контейнерный путь не выдаётся за открываемую Windows/Web-ссылку. Краткое изложение в линзе не удаляет оригинал, синхронизацию смыслов не объявлять автоматической.

Использовать существующие recommendation packages/rules и nested navigation: из процессов/готовых графов и из конкретных шагов самих линз. Каждый переход оформлять явно созданной адресной рекомендацией с пояснением использования по [B02B](#адресные-рекомендации-b02b). Подготовить маршруты shape→dry/kiss, explore/clarify→kiss/yagni по ситуации, review/develop→нужный принцип, взаимные рекомендации трёх при соответствующем условии; анализ Decision и Questions адресуют свои методики. Дополнить целевые рекомендации маршрутами clarify/decision-analysis/explore→research для проверяемого неизвестного, уточнённые цели и выводы→specify, specify→shape для подготовки исполняемых задач; при противоречии вернуться к clarify, при нехватке данных — к research. Это адресные переходы по ситуации без обязательной последовательности. Проверять реальные anchors/keys, исходный рабочий scope отдельно от namespace инструкции, возврат, несколько совпадений, циклы без auto-run и отсутствие расширения правила из-за пропавшей опоры. Не auto-seed весь каталог при create working.

Source definitions/catalog/routes, опубликованные owners и их исторические pins имеют разные версии. Подготовить явный импорт/обновление через Application: read-only inventory, diff/preflight, существующие supplied-management операции, CAS/receipt/readback. Сохранять packageId/identitySpace/lensKey и принятую историю существующих определений, не переписывать старые применения новой теорией. Изменение общего Registry показывает всех затронутых consumers. Live-переход выполняется отдельной явной операцией владельца после предъявления конкретного diff, а не при обновлении кода или чтении каталога.

Сохранить развязку кода и данных: source JSON линз не возвращаются в серверный ZIP как автоматически устанавливаемые определения. Теория/source-map и опубликованные графы являются явно загружаемыми данными/ссылками; новая сборка не подменяет ими существующие live owners.

### Список линз с триггерами — следующий этап

**Зафиксировано пользователем 2026-11-11; реализация отдельно после уточнения Markdown.** Цель — получить доступный список линз вместе с достаточными пояснениями выбора. Общая стратегия принадлежит [work](../lenses/bootstrap/work.md#общий-цикл-решения-задачи), назначение и триггеры каждой методики — её собственному тексту/определению, механизм обращения — [lens-system](../lenses/bootstrap/lens-system.md#найти-линзу-и-понять-рекомендацию).

1. **Инвентаризация и совместимость.** Сверить текущие schema, catalog, Agent/CLI и локальный source catalog до выбора формы расширения. Локальные purpose/appliesWhen для прежних 15 ключей уже существуют; публичный catalog даёт метаданные пакетов без этих пояснений. Переиспользовать действующий подходящий маршрут; не объявлять обязательным новый endpoint заранее. Сохранить прежние формы, identities, профильные границы и отсутствие auto-seed.
2. **Достаточная карточка в списке.** Помимо точной identity/ключа и названия вернуть краткое назначение, текст триггеров оценки и, когда уместно, адресный контекст workflow с пояснением. Указать источник, версию и доступность содержания. Список с пояснениями должен позволять выбрать кандидатов без чтения полных графов каждой линзы. Точные имена полей и формы публикуются schema на этапе реализации.
3. **Один владелец смысла.** Карточки формируются из согласованных данных соответствующей линзы и той же версии. Не создавать второй независимо поддерживаемый реестр правил и триггеров. Краткое изложение и связанный полный источник сохраняют прослеживаемость. До переноса новые Markdown-проекты не выдаются за установленные live definitions.
4. **Смысл триггеров.** Свободное описание предлагает оценить применимость. Оно может ссылаться на конкретный этап work или другой workflow. Ссылка не задаёт auto-run, принудительное перечитывание или автоматическую обязательность. Условие для программного фильтра имеет отдельный явно поддержанный смысл. Registry адресных рекомендаций и каталог доступных методик сохраняют свои назначения.
5. **Scope, права и полнота.** Использовать действующие namespace, проверку доступа и разрешение ссылок. Не раскрывать недоступные материалы и не подменять missing source одноимённой линзой. Отличать пустой список, отсутствующее описание, недоступность и следующую страницу. Если список постраничный, описать версионную привязку и сбор согласованного результата; чтение не создаёт записи, selection или подключения.
6. **Приёмка.** Проверить, что пояснения и триггеры приходят непосредственно в ответе списка, а не только после отдельного lens-read. Сопоставить полный доступный набор на всех страницах, identity/версию и разрешимость контекстных ссылок. Проверить выбор по неизвестному факту, неясной цели, рекомендованной линзе, прямому указанию и структурному шагу метода. Покрыть отсутствующие legacy-поля, закрытый источник, смену версии, прежнего клиента и отсутствие побочных записей.

Общая стратегия и триггеры дополняют друг друга; отдельный классификатор, оркестратор задач или автоматический запуск линз в этот scope не входят. После реализации API-каталога согласовать его с T6 definitions/source-map и включить оба пути выбора в B05/T7.

### Совместимость, пример и сквозная приёмка

**T7 — проверки.** Расширить обязательный CI адресными suites для Questions, estimates, Planning Meta Action atomic create/place, compact/batch и содержания линз; базовая discovery suite проверяет все новые формы/возвращённые IDs через настоящий публичный маршрут. Для каждого writer — successful preflight/no-write, apply, bad input/CAS atomic failure, exact retry, restart/readback; для новых полей — copy/remap и старый owner без автозаписи. Browser/desktop проверяют полный пользовательский сценарий, общие действия из Graph/Structure и отсутствие скрытых сущностей в дереве. Semantic source-map и разрешимость рекомендаций проверяются машинно; правильность содержательных переходов — на положительных/отрицательных случаях, не по числу заголовков.

Подготовить рецепт нового полноценного учебного процесса через публичный API по [матрице](RDG-LENSES.md#фундаментальные-линзы-как-образцы-и-полный-учебный-процесс): основания R/общие IDs, бумажные варианты/группы/выборы/отмена/результаты, Canon с внешним материалом, Context, четыре Finding, Questions/ответы, оценки, планировочных метадействийи, инвалидация/disabled, Plan forks/общая часть и History. До READY рецепт и сквозной проход выполняются на изолированной совместимой сборке; доступный пользователю процесс создаётся по нему после установки совместимого runtime. Все результаты ограничены учебным scope; пример ответа пользователя не выдаётся за его реальное сообщение. Рецепт создаёт новый owner, не превращает прежние процессы в fixtures, и проверяет фактические receipt/readback.

После подготовки фундаментальных линз выполнить полный сценарий ИИ: уточнить исходные R → оценить сохранение → создать непринимаемые сразу варианты/продолжения → найти и применить подходящие линзы/Canon → сохранить контекст с ролями → оформить Findings и Questions → получить/оценить ответы → принять обоснованный Decision → запланировать предметные и планировочных метадействийи → записать действительный учебный результат → изменить основание → проверить review/disabled → пересмотреть/отменить выбор → продолжить другой сессией по сохранённым данным. Исходные ID, вопросы, pins, принятые факты и исход неопределённого запроса должны восстанавливаться без догадок. Это проход по подготовленным методикам; он не заменяет их подготовки. Приёмка различает ознакомление с принципом, повторное уточнение и прохождение процедуры; полнота методической работы не измеряется числом вставленных копий линз или событий `lens_apply`. Объём сохраняемых результатов определяется [семантическим контрактом](RDG-ACTIVE-CONTRACT.md#готовые-графы-линзы-и-рекомендации).

Артефакты приёмки: матрица требований→реализация→проверки, исходная теория/source-map, source и опубликованные ревизии линз, ID/путь нового примера, отчёт compact/batch baseline→итог и сквозной протокол с существенными ограничениями. Обновить существующие документы/матрицу API/bootstrap; не создавать параллельные нормативные планы и не копировать определения норм между ними.

### Очерёдность и выпуск

Рекомендуемый порядок: T1 → T2 → T3/T4 → T5 → B03A → этап B03B/B03C → T6 → T7 → release. Внутри T6 сначала `model`, затем остальные определения и рекомендации. Сценарии/fixtures готовить заранее; полную содержательную работу ИИ проводить после готовности линз. Совместимость проверять на каждом шаге, не откладывая до импорта живых данных.

**T8 — выпуск.** Полный CI в Docker на точном source SHA, проверка READY/ZIP/manifest и сохранности HEAD/index/чужих данных. После runtime-изменения выдать готовую PowerShell-команду обновления с фактическими BuildId, Source/ZIP SHA256 и рабочим container ID по [регламенту](RDG-OPERATIONS.md#разработка-и-обновление-серверного-runtime). Пользователь запускает её на Windows, затем F5; установку подтверждают installer и запущенный buildId. Затем выполнить отдельно разрешённую публикацию линз и создание нового доступного пользователю учебного процесса с live receipt/readback; обновить указатель актуального примера только после фактического создания. Удобство проверяет пользователь. README version или source PASS не заменяют этих свидетельств.

## History: факты и фильтры

Новые события Graph-команд `core` и создания процесса сохраняют `historyDetail`: команда, прямые цели/созданные ID, снимки названий/отношений, изменённые поля и before/after, явный `cosmetic`, фактические activated/deactivated Requirement IDs. Это метаданные существующего события, не второй журнал. `decide_acceptance` сохраняет исполнение Action и отдельный факт изменения выбора Decision. Вычисление R activity использует общий `support_state` до/после операции, без нового selected-состояния R.

`history` возвращает `historyView` и `modes`; опциональный `view.historyMode` принимает `important / meaningful / technical / all`. Без параметра API возвращает полный поток; Viewer по умолчанию показывает `important`. Классификация — read-only [проекция](../../tools/rdg-history-view.py), семантика — [контракт](RDG-ACTIVE-CONTRACT.md#события-истории). Старые данные читаются по сохранённым принятым версиям; отсутствующий cosmetic flag не угадывается. Исторические записи/удалённые участники не подменяются текущими одноимёнными объектами. `core edit` с `cosmetic:true` допускает только title и не меняет definition-наблюдение.

Plan v3 сохраняет собственные версии и полное уникальное членство размещений в основной полосе/cases. Fork имеет прежние `id/title/afterStepId/cases`, опциональные `startAt` и `end={title, at?}`. `afterStepId:null` означает начало Plan без Action; конец отображается после выбранного case перед следующими общими размещениями. Маркеры не являются сущностями Graph. Время использует общий ISO literal: дата либо timestamp с явным offset/Z. Старые Plans без маркеров читаются без миграции; copy/remap сохраняет даты и конец. Операции проходят тот же Plan writer/CAS/preflight/receipt и требуют `plan.branch` при изменении развилок.

Развилка привязана только к основной полосе; вложение в case не допускается. `shownCases` и History modes — view spec. Переключение продолжения использует [чистую UI-проекцию](../../tools/rdg-visual-projection.js) последнего авторизованного снимка и сохраняет view-session с CAS: без нового чтения Graph/history, без перерисовки полотна и без Owner writes. Refresh получает свежие факты обычным путём. [Интеграционные проверки](../../tests/rdg-decision-integration.test.py) сверяют клиентскую проекцию с серверной, даты/конец, права, atomic failure и copy; [масштаб](../../tests/rdg-plan-view.test.cjs) проверяет линейный объём без перемножения вариантов. Семантика — [в контракте](RDG-ACTIVE-CONTRACT.md#возможные-ветви-plan).

## ТЗ реализации файндингов

**Исправляющее ТЗ реализовано в исходниках 2026-11-06; результат release gate проверяется отдельно.** Заменяет прежнее задание на resolve/proposals в `rdg-decision-v1`. Смысл принадлежит [контракту](RDG-ACTIVE-CONTRACT.md#файндинги), комментарии и Canon — [его разделу контекста](RDG-ACTIVE-CONTRACT.md#контекст-и-canon), действия — [Viewer](VIEWER-EXPLORER.md#файндинги). Здесь зафиксированы изменения кода и приёмка, а не повтор типов/шкал.

### Исходное состояние и границы

Исходная реализация поддерживала R/D/Graph Action и resolve/proposals. Новый writer создаёт Findings только у Decisions; прежние payloads и связи читаются в режиме совместимости. Общая логика находится в [rdg-analysis.py](../../tools/rdg-analysis.py), Finding — в [rdg-findings.py](../../tools/rdg-findings.py); оба работают внутри существующей Graph-транзакции. Прежний READY не проверяет новый срез. Legacy-профили и живые owners ради fixtures не меняются.

Сохраняются Finding identity, четыре типа, rationale/evidence, questions/User Assistance, reviewLimitations, disposition/history, review и относительный scope. `Next Gate` не хранится. Удаление специального workflow не удаляет обычные Decisions, историю, факты выбора/выполнения и свидетельства.

### Принадлежность и обязательность R

Новые Finding и явная смена subject допускают только Decision того же Process Graph. Проверять это в schema, preflight и writer, включая generic add/edit: скрыть кнопку недостаточно. Старые R/Action Findings читаются без записи; обычное редактирование их содержания, зависимости, review/disposition и удаление сохраняют совместимость. Перенос к Decision (`finding_transfer`) — явная команда с выбором получателя, сохранением ID/истории и обновлением subject-наблюдения; нового subject и его основания не угадывать.

Сценарий обсуждения обязательности R использует обычный Decision и `INTRODUCES` к существующему R. Родительское основание Decision выбирается явно. Предусмотреть явную составную Graph-транзакцию создания/привязки Decision и, при необходимости, удаления конкретной выбранной прямой обязательной связи; preflight показывает изменение оснований и cascade. Без явного выбора связь не удаляется. Не создавать цикл «R поддерживает Decision, который только и вводит этот R», скрытый root cause, копию R или новый selectionState у requirement. Сохранять остальные основания, подтверждённый result и evidence; новый Decision остаётся на бумаге. Несколько Decisions для одного R выражают разные основания, а не неявное взаимоисключение.

### Удаление специального workflow и совместимость

Исключить из нового schema/UI команды `finding_response`/`finding_proposal`, создание соответствующих отношений и специальных групп; отклонять новые запросы также на apply. Старый подтверждённый receipt и exact retry той же транзакции обязаны возвращать прежний результат, не создавая дубль. Общие группы обычных Decisions не отменяются.

Существующие `FINDING_RESPONSE`/`FINDING_PROPOSAL`, `findingOrigin`, `impactTargetIds`, response/proposal read-поля и специальные группы читаются как совместимые данные с прежней семантикой оснований/completion до явного преобразования. Не убирать их из support/cascade молча: это могло бы снять сохранённый выбор. В интерфейсе оставить доступ к этим реальным Decisions и recorded происхождению, убрать действия развития прежней цепочки. Явное преобразование/удаление существующих связей показывает последствия в preflight и проходит общие guards; молчаливой миграции при read/F5 нет. Новые Findings не получают response/proposal-поля как часть рабочего workflow.

### Комментарий роли и единый контекст

В Decision хранится `contextNotes`: необязательную совместимую карту `sourceId → непустой пользовательский текст`. Это один Graph-owned комментарий на пару Decision–элемент независимо от числа ручных зависимостей/находок; не поле исходного X и не view session. Ключ допустим только для действительного ручного или производного участия X в контексте. Системное происхождение в эту карту не записывать.

Новое ручное участие требует комментария; существующие ссылки без него показывать как «Роль не описана», не заполнять догадками. Для производного участия системного пояснения достаточно; личное дополнение необязательно. Удаление последнего участия очищает текущую запись комментария в той же транзакции, сохраняя before/after в истории. Удаление только ручной части при оставшемся Finding сохраняет комментарий. Текст наблюдается как содержание контекста Decision; автоматически выведенные подписи не становятся definition исходного X или Decision.

Общая проекция объединяет старые `decisionContextIds`, явные `DEPENDS_ON` с `dependencyPurpose=decisionContext` и источники Findings в kernel/read projection `decisionContexts` ответа Application. Один X — одна строка; provenance перечисляет ручное участие и каждый Finding/application/роль. Обновить все потребители: Inspector, Focus, API read, наблюдение `context`, зависимости/влияния, copy/remap. Проекция — реальное участие в аналитическом контексте, не декоративный список только в UI и не структурный родитель. Допустимые kinds должны покрывать конкретные источники поддержанных зависимостей, сохраняя их настоящий тип, включая Info/Canon и совместимые старые записи там, где их разрешает реестр.

### Источники Finding и происхождение

Использовать участников и наблюдения общего resolver политик, а не второй обходчик/evaluator. Наследовать конкретные наблюдаемые источники существующих не удалённых зависимостей Finding. Член набора, содержание которого действительно наблюдается, учитывается; ID политики/версии, служебные anchors и промежуточные вершины пути не объявляются аналитическими источниками только из-за участия в вычислении. Subject-Decision исключается из собственного контекста. Не раскрывать транзитивно все зависимости источника и не создавать вторую независимую копию bindings для X → Decision.

Для каждого включения возвращать стабильные Finding ID, application ID, роль/источник и основание включения. Read вычисляет пояснение «Относится к файндингу …» и ссылку; несколько Findings дают несколько ссылок. Изменение/удаление исходной зависимости или Finding обновляет только соответствующее происхождение, сохраняя ручное участие и другие Findings. Ни UI, ни API не позволяют удалить производную часть через обычное редактирование контекста; изменение идёт через исходный Finding/зависимость.

Disabled-применение сохраняется по общему lifecycle: доступные разрешённые участники и происхождение видны с отметкой отключения, без действующего наблюдения от этого применения. Удалённый/неразрешимый участник — recorded reference, не живая активная ссылка. После восстановления нельзя автоматически активировать применение. Ручной/другой действующий источник той же строки сохраняет своё значение. Disposition Finding сам по себе не удаляет его зависимости и происхождение.

Автоматическое `builtin:finding-subject` продолжает наблюдать содержание Decision. Создание Finding не инвалидирует его самого. Review Finding, его disposition и выведенные подписи не создают специального обратного stale Decision; наблюдения Decision остаются общими настроенными политиками. Изменение контекста проверяется ими обычным образом. Нельзя получить петлю Decision → Finding → производная подпись → definition Decision. Loss of applicability, ручная активация, pins/CAS/locks и recorded причины сохраняют прежний смысл.

### Группы контекстов процесса

**Реализовано в исходниках.** Семантика — в [банке контекстов](RDG-ACTIVE-CONTRACT.md#банк-контекстов-процесса), действия — в [Viewer](VIEWER-EXPLORER.md#банк-контекстов-процесса). `renderContextBank` использует общую readonly-проекцию `contextTree`.

Graph хранит `contextGroups: [{id, title, parentId}]`, где `parentId=null` означает корень, и необязательный `Context.contextGroupId`. Один Context состоит в одной группе или не имеет группы; группа может содержать факты и подгруппы. ID стабильны, ссылки локальны одному владельцу; группы не добавляются в `nodes/objects` как новый kind и не смешиваются с `decisionGroups`, Work Graph или структурными отношениями. Проверять непустые имена, уникальность ID, существование родителя/группы, применимость поля только к Context, отсутствие циклов/самородительства. Старый owner без этих полей читается как «Без группы» без записи/автомиграции.

Расширить общие schema/preflight/Graph writer операциями создания, переименования, перемещения и удаления группы, а также создания/переноса Context с выбором группы. При удалении группы её непосредственные подгруппы получают её родителя, факты — ту же родительскую группу либо отсутствие группы на верхнем уровне. Операция атомарна, preflight показывает переносы; Context, зависимости, история и собственные поддеревья дочерних групп не удаляются. Отдельное удаление факта остаётся существующей предметной командой. CAS/locks/actor rights и exact retry обязательны для всех операций, включая generic add/edit обходы.

Классификацию исключить из `definition` Context и структурных наблюдений: перемещение факта и переименование/перемещение группы меняют организационные метаданные и Graph history, сохраняя value/description, ID, `contextNotes` у Decisions и bindings на факт. Обычное переименование самого факта или изменение его содержания наблюдается политиками; исключение для `cosmetic:true` — в [общем контракте](RDG-ACTIVE-CONTRACT.md#события-истории). Само включение факта в группу не включает его в контекст Decision, не создаёт Finding, выбор или обязательство; наблюдение всей группы как нового источника в этом этапе не вводится.

Банк строит дерево со сворачиванием, корневыми фактами «Без группы» и доступными пустыми группами. Подгруппы и факты имеют устойчивую сортировку по имени/ID. Создание в выбранной группе подставляет её ID; перенос доступен через выбор места, без обязательного drag-and-drop. Поиск по факту или его пути показывает совпадение с предками; совпадение имени группы раскрывает её содержимое. Временно раскрытые поиском узлы не перезаписывают прежние раскрытия. Поиск/раскрытие/выделение — view-only; структура групп хранится в Graph и переживает restart/F5. Выбор Context в редакторах контекста Decision/зависимостей показывает те же пути, передавая прежний ID факта.

Process copy/remap переносит группы, parentId и contextGroupId; частичный перенос фактов подтягивает цепочки предков без посторонних фактов и пустых чужих ветвей. Производный контекст из Findings продолжает ссылаться на конкретные источники независимо от их места в банке. Группы не обходят ограничения process context для `ready/lens`. UI банка и его команды общие для Графа/Структуры/Focus/Working Graph; группировка не меняет состав этих представлений или owner фактов.

### Canon и интерфейс

Из канона Decision доступны «Добавить в контекст решения» и «Записать файндинг». Первое выбирает существующий реальный элемент процесса и запрашивает его роль; второе открывает Finding с subject текущего Decision и явным выбором типа. Сохранить необязательную provenance-ссылку к Canon/Info и точному фрагменту, если у него есть устойчивый адрес; иначе хранить ссылку на объект и записанный excerpt/revision без выдуманного fragment ID. Источник рассуждения не становится автоматически процессным фактом, подтверждением результата или зависимостью наблюдения. Предложенные формулировки пользователь проверяет перед общим preflight/apply.

На R/Action нет создания новых Findings; старые записи обозначены как совместимые и доступны для явного переноса. Контекст показывает роль, ручное/производное происхождение и переход к Finding; системный текст отделён от редактируемого дополнения. Удаление ручного участия не предлагает удалить чужие основания. Карточка Finding сохраняет CRUD, disposition, review и свои обычные зависимости, без resolve/proposals. Переходы имеют возврат; технические сведения раскрываются. Граф и Структура работают с одной проекцией/командами; ширина сведений и настройки представления сохраняются.

### Подтверждающие данные и совместимость Evidence

Новые подтверждения — обычные `context` с `value` и необязательными `scope/version/source/artifact`; группа имеет только организационный смысл. `evidenceIds` в Finding/disposition/result/lens events — совместимое имя ссылок на Context, не discriminator отдельной сущности. `artifact` и `evidenceRefs` сохраняют проверку реальных bytes; создание заметки или выбор файла не доказывает outcome.

Новый `add`/create/paper writer не создаёт `evidence`. Прежний kind остаётся читаемым, в банке — отдельной совместимой группой, без визуального блока. `context_record` явно переводит существующую запись в Context: тот же ID, claim → value, источник/версия/область/вложение и ссылки сохраняются; история остаётся прежней. Без заданной группы используется «Подтверждения». Обычные guards/preflight/receipt и применимость политик действуют, правила с прежним kind могут отключиться. Нормализованное содержание от одного перевода не меняется; неизвестные данные не дописываются. Copy/remap сохраняет подтверждения и pin вложения; reusable template исключает записи с процессными вложениями.

Finding и прежний Evidence не входят в визуальные узлы/строки Графа/Структуры, включая show-all и Focus. Ссылки ведут в вкладку Findings subject-Decision или в банк контекстов; Graph owner, старые координаты и история не удаляются.

### Команды и формат read

`context_group` принимает save/remove группы; `decision_context` — save/remove ручного участия или note для объяснения, с `nodeId/sourceId/comment`. Старый `dependency_add` с purpose decisionContext требует `contextComment`. `requirement_decision` атомарно связывает новый/существующий Decision с R; `replaceEdgeId` явно задаёт снимаемое прямое обязательство. `finding_transfer` допускает `detachLegacy=true` только как явное отсоединение прежней композиции, с общим cascade и сохранением Decisions. Точные поля выдаёт schema.

`decisionContexts[D]` содержит sourceId/present, manual, comment, edgeIds и provenance по Finding/application/rule/role с enabled/status и записанным источником. Системные подписи строятся при read, не хранятся в `contextNotes`. `analysisSources` у Finding/Decision хранит sourceId/revision/excerpt Canon/Info; это не подтверждение результата и не автоматическое наблюдение. При отключении применения новые `observedSources` сохраняют реальные наблюдавшиеся источники общего resolver; старым данным неизвестные источники не восстанавливаются догадками. Перенос между группами не входит в definition факта.

### Запись, copy и старые владельцы

Расширения выполняются в существующей Graph-транзакции: schema → readonly preflight → apply того же request/inputBinding → receipt. Источники и provenance вычисляются в авторизованном snapshot; guard/pin union включает реальные затронутые входы. Невалидный комментарий, subject, dangling ref или отказ в правах/locks не оставляет частичных изменений. Перечитывание/проекция не пишет Graph, Plan, layout или bindings. Внутри одного read-расчёта общий resolver источников переиспользуется; его временный cache не переживает расчёт или запись. Вложенные наблюдения не запускают рекурсивное наследование контекста.

Copy/insert remap переносит `contextNotes` keys, subject, источники и подтверждающие Context, replacement/question refs и Canon provenance; производное участие вычисляется заново по перенесённым ID, не копируется независимыми строками. Совместимые R/Action Findings и старые композиционные связи сохраняются с происхождением; обычный add не может использовать этот путь как обход запрета. Частичный перенос не оставляет dangling refs. Граница `ready/lens` прежняя: живые процессные Findings/контекст не просачиваются в reusable definition; `capture_ready` содержащего их фрагмента явно отклоняется. Новые разделы инструкций линз обновлять отдельно, без автоматической перезаписи supplied definitions.

### Приёмка и порядок реализации

| Gate | Обязательный сценарий |
| --- | --- |
| Subject и legacy | Создать Finding у непринятого/selected D; создание/перенос к R/Action отвергаются всеми writers. Старый owner читается без изменения bytes; перенос к выбранному D сохраняет историю |
| Обязательность R | Существующий R вводится Decision без копии/самоподдерживающего цикла; прямое обязательство меняется только явно; другое основание сохраняет актуальность. Создание не принимает D/ветвь |
| Отказ от workflow | UI/schema не предлагают resolve/proposals; новый ручной запрос отвергается. Старые Decisions/связи/receipt доступны, read/restart не снимает выбор и не меняет completion |
| Контекст и комментарий | Новый ручной источник без текста отвергается атомарно; один X имеет разные роли у двух D. Старый пустой комментарий не выдумывается; изменение роли наблюдается как context |
| Происхождение | F1/F2 зависят от X, также включённого вручную: одна строка, обе ссылки, отдельное объяснение; удаление F1 сохраняет F2/ручное, удаление последнего источника не оставляет dangling note. Отдельное снятие производной части отвергается в API и UI |
| Resolver и lifecycle | Direct, сохранённая политика и динамический набор дают реальные наблюдаемые источники; промежуточные узлы/self-D исключены. Disabled/удаление/восстановление не активируют применение и не создают ложной живой ссылки или feedback loop |
| Группы контекстов | Создание пустой группы/подгруппы и факта в ней, rename/move/delete группы и перенос факта в «Без группы» сохраняют ID, ссылки и комментарии; удаление группы сохраняет всё содержимое. Циклы, dangling refs, чужой owner и неверный kind отвергаются атомарно |
| Банк и наблюдения | Классификация не создаёт stale содержания, изменение самого факта создаёт обычную причину Finding/Decision. Поиск показывает путь, сброс возвращает раскрытия; раскрытие не пишет Graph/Plan. Старый плоский owner, restart/F5, частичный copy предков и выбор факта из обоих режимов сохраняют корректные ID |
| Canon | Из ориентиров пользователь создаёт контекст/Finding с проверяемым provenance; критерий не выдаётся за факт, ссылка — за проверенное подтверждение, отсутствие условия — автоматически за Problem |
| Целостность и UX | CAS/pins/locks/actor isolation, uncertain receipt/retry, restart/copy/remap; одинаковые ID/источники/роли и возвраты в Graph/Structure. Открытие существующей разветвлённой композиции с несколькими Findings завершается без повторного вложенного расчёта всего каталога. Выбор D может сохраняться при открытых Findings; ни review, ни completion не присваивают Finding resolved |

Порядок выполненного изменения: (1) совместимость/валидация subject и отказ от создания старого workflow; (2) единая проекция контекста, комментарии и resolver provenance; (3) группы банка контекстов, сценарий R, Canon/UI/copy; (4) регрессии и release gate. Обновить существующие [Finding](../../tests/rdg-findings.test.py), [модель](../../tests/rdg-decision-model.test.py), [политики](../../tests/rdg-dependency-policies-v2.test.py), [API](../../tests/rdg-portable-service.test.py), [проекции](../../tests/rdg-decision-structure.test.cjs) и [desktop](../../tests/visual/rdg-decision-desktop.cjs); старые проверки workflow оставить только как явно обозначенную совместимость. Новые сценарии — в [analysis suite](../../tests/rdg-analysis.test.py); существующие workflow-сценарии в Finding suite собирают только старые payloads и проверяют совместимость, не доступность старых writers.

При завершении сверить [карту функций](RDG-FUNCTIONS-AND-TESTS.md#файндинги) с фактическими тестами, выполнить полный [CI](../../tools/rdg-ci.py), проверить архив и выдать [Windows-команду](RDG-OPERATIONS.md#разработка-и-обновление-серверного-runtime) с новым BuildId/SHA256. READY, установленный buildId и пользовательская UX-приёмка — отдельные факты. Наличие реализации не означает прохождение этих gates или установку на Windows.

## Представление и клиент

[Проектор](../../tools/rdg-visual-projection.js) и [Decision UI](../../tools/rdg-decision-ui.js) строят Graph/Structure/Focus из того же snapshot. `presentation`/view session, camera, раскрытия, фильтры и focus layout не становятся Graph фактами. Политика readonly view не исключает отдельной авторизованной команды редактирования. `panels.inspectorWidth` — необязательная ширина 260–1000 px в view session (по умолчанию 340); доступное место ограничивает отображение, старые сеансы без поля допустимы.

[Поддержка обоих режимов](VIEWER-EXPLORER.md#граф-и-структура) проверяется на одном owner snapshot: общие сущности, связи, состояния и результат команд сохраняют один смысл. Если новая функция трудно переносится между режимами, нужно найти и устранить расхождение модели/проекции/renderer; отдельная предметная логика для каждого вида не вводится.

В текущем Renderer Canon/Info открываются через сведения/фокусы; Context процесса — через банк контекстов. Пересекающиеся области и группы сохраняют identity. Черновик, введённый во время фонового сохранения, не откатывается старым ответом. Полный список поведения — в [Viewer](VIEWER-EXPLORER.md).

HTTP/runtime identity и архивы проверяют [server tests](../../tests/rdg-server.test.py), [CI tests](../../tests/rdg-ci.test.py), [CD tests](../../tests/rdg-cd.test.py). Эти проверки не утверждают power-loss durability или завершённую пользовательскую UX-приёмку.
