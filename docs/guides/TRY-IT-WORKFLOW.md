# RDG Pilot — практическая проверка в новом чате

**Цель:** проверить не текстовую имитацию, а реальную последовательность PLAN → выбор пользователя → сохранённый JSON → TRACE / STATUS → IMPACT → продолжение в отдельном чате.

## Что есть

- Тестовые данные: `/workspace/repos/rd-graphs/graphs/workspaces/try-it/graph.json` (изначально revision=1, одна R-001, нет выбранных D).
- Комплект Planning Helper: `/workspace/repos/rd-graphs/kit/planning-helper-import.txt`.
- Главный промпт `rdg.pilot.main`, остальные: `plan`, `commit`, `trace`, `status`, `impact`. Все используют три `rdg.pilot.*` модуля.
- Запись: `tools/graph-apply.py`; отдельный patch JSON и обязательный `expectedRevision`.
- Viewer отображает JSON; в режиме выбора папки после изменения нажать **Обновить**.

## Подготовка

1. В Planning Helper открой **Import from ChatGPT**. В открывшееся текстовое поле **вставь весь текст** из `kit/planning-helper-import.txt` (один блок `[PLANNING_HELPER_PATCH]`); preview должен показать **6 ADD prompts + 3 ADD modules**, 0 DELETE. Затем нажми **Import local**. Если элементы уже есть, preview покажет UPDATE/UNCHANGED. Не используй Hard Reload ради импорта: импорт локальный.
2. В списке Prompts найди `RDG Pilot — старт практического теста`. При Copy/Run ссылки `[[module:rdg.pilot.*]]` должны быть раскрыты — это проверка DRY.
3. Открой **новый чат**, разреши ему использовать уже подключённый Fortis Repo. Отдельный новый Tunnel/Host не нужен.
4. Убедись, что `graphs/workspaces/try-it/graph.json` имеет `revision=1` и только `R-001`. Если уже выше 1, **не сбрасывай молча**; тестируй на текущей версии либо явно согласуй новый тестовый прогон.

## Маршрут в одном чате

| Шаг | Что вставить / написать | Что увидеть в ответе и в graph.json |
| --- | --- | --- |
| 1. START | Запусти промпт **RDG Pilot — старт практического теста** | ChatGPT через Fortis читает файл, сообщает `revision=1`, `R-001`, предлагает 1–2 варианта D и новых R. **Ничего не записано**. |
| 2. SELECT | Напиши: «Принимаю предложенный вариант [точно назови выбранный] для R-001. Запиши это как тестовое решение.» Затем запусти промпт **RDG Pilot — записать выбранное решение** (или добавь эту инструкцию к нему). | ChatGPT явно ссылается на твоё согласие, готовит patch, делает --dry-run → apply → read-back. В графе появляется D-001 с status committed, новые R, типизированные edges и один event; `revision=2`. Никаких других изменений. |
| 3. STATUS | Запусти **RDG Pilot — состояние достижения цели**: «STATUS R-001» | Дочерние R видны, но исходная цель **не названа достигнутой**: выбранный план ≠ выполненная цель. `revision` не меняется. |
| 4. TRACE | Запусти **RDG Pilot — трассировка цели/решения**: «TRACE одной из новых R» | Показана настоящая цепочка R-001 → D-001 → R-00X и зачем возникла новая R. Без вымышленных рёбер, без записи. |
| 5. PLAN deeper | Запусти **RDG Pilot — планировать подцель**: «PLAN по одной из новых R» | Предложен один небольшой следующий шаг (D и при необходимости дочерние R) как кандидат, без сохранения. |
| 6. ACCEPT deeper | Явно выбери предложение и запусти **RDG Pilot — записать выбранное решение** | После нового patch сохраняется следующий D и связи; `revision` увеличивается на 1; TRACE возвращает цепочку на 2 уровня. |
| 7. IMPACT | Запусти **RDG Pilot — последствия изменения**: «Теперь требуются повторяющиеся бронирования. Что пересмотреть?» | ChatGPT показывает потенциально затронутые R/D и предполагаемую новую работу; **не изменяет** граф и не отменяет старые решения. |
| 8. NO-OP | Попроси: «Ничего нового не принято. Проверь, что обновление не нужно.» | Нет новых узлов, событий и роста revision. |
| 9. UI | Открой граф в просмотрщике, нажми **Обновить** (папка) или повторно выбери JSON-файл | На экране показаны те же IDs и текущая revision, что реально лежат в graph.json. |

## Проверка между чатами

1. Открой **второй новый чат**, без копирования старых ответов.
2. Вставь из Helper **RDG Pilot — состояние достижения цели** и добавь: «Прочитай `graphs/workspaces/try-it/graph.json` через Fortis Repo. STATUS R-001. Ничего не изменяй.»
3. Затем **TRACE** для последней принятой подцели.
4. PASS, если чат опирается на реальные узлы и revision из файла, а не пытается восстановить историю из предыдущей переписки.

## Отрицательные сценарии

- Нельзя сохранять предложенный D без явного согласия пользователя; если не выбрал вариант — **нужен вопрос, граф не меняется**.
- Если `expectedRevision` устарела — CLI должен вернуть `REVISION_CONFLICT`; перечитать и предложить корректное применение, без silent overwrite.
- Нельзя создавать ребро к неизвестному узлу, неверный parent, цикл, повторный ID, D без события выбора: CLI должен отвергнуть patch, а файл остаться прежним.
- Нельзя записывать историю переписки вместо событий принятия решений. Повторный UPDATE без изменений не увеличивает revision.
- Нельзя считать граф «сохранённым» по тексту ответа: проверь actual read-back и визуальную ревизию.

## Признаки успеха и границы

**PASS пилота**: минимум два явных выбора реально сохраняются, появляются 2 уровня R/D с верной трассировкой, отдельный чат продолжает работу по JSON, IMPACT не меняет принятого и UI показывает записанное. Сохранение имеет revision guard и read-back.
**Не проверено этим пилотом**: автоматическое отслеживание любых других промптов/чатов, полная отмена/замена исторических решений, multi-user merge, масштабирование до сложных графов. Это отдельная разработка, а не результат одного успешного теста.

Правило теста: не трогать `graphs/examples/example/graph.json` и другие проекты; не создавать лишние отчёты, snapshots и commits. Если используешь рабочую методологию OBS, сохранить её semantic owners; тестовые файлы не имеют authority над ними.
