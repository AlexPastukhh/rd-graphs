Новые примеры на каждый этап автоматически не создаются; самостоятельная приёмка ИИ B05 не подменяется учебным рецептом.

## Оптимизации чтения в Docker (2026-11-07)

В текущих исходниках реализованы scoped-кэш производных отношений Graph (A), быстрый путь явных заметок Decision (B2), однократные digest/revision для полного Read (F-01), digest текущего Graph для History (F-02), однопроходная загрузка/валидация Snapshot и WAL операторского учебного сценария. Добавлены ограниченные **per-Application** кэши только производных ответов: визуальная `layout(project)` и **только полная** History (обычная или `detail=full`). History на каждом обращении повторно проходит авторизацию, полный Snapshot и проверку SHA256 всех артефактов inventory под общим read-lock; `compact`/`item` обходят кэш. Визуальный кэш учитывает полный вход Graph/view/layout после проверки Snapshot, не перехватывает записи layout. Оба хранят только ограниченный объём сериализованных JSON-байтов в памяти Application; при рестарте ничего не восстанавливается, целостность/CAS/receipt не ослаблены.

Регрессионные проверки — [адресный набор](../../tests/rdg-projection-cache.test.py), зарегистрированный в [CI](../../tools/rdg-ci.py). Контроль **внедрённой реализации**, один и тот же временный Graph после 60 записей, по 5 чередующихся измерений с принудительным cache bypass и разрешённым cache hit, при полном равенстве ответов: full Read 250,88→148,86 мс (−40,7%), полная History 657,46→287,21 мс (−56,3%, 359 проверяемых исторических артефактов). JSON-ключ и авторизация/верификация сохранялись даже при контрольном обходе кэша. Логи: `/workspace/repo/Workfiles/rdg-operator/Visual-Cache-Product-Benchmark.json` и `History-Cache-Product-Benchmark.json`. Эти медианы не являются Windows/production SLA. B4, глобальный/межоперационный кэш `describe_applications` и skip `boundaries()` не приняты после контрольных измерений. Актуальная поставка определяется только совпадением `ready.json.sourceSHA256` с текущими исходниками после полного CI; Windows-runtime требует отдельной установки и приёмки.

## Оптимизация вычислителя зависимостей при записи (2026-11-07)

Для `rdg-decision-v1` каждое Graph-действие по-прежнему выполняет полный предметный пересчёт: `POLICIES.reconcile`, автоматические/исторические переходы, согласование заметок, `native_dependency_impacts`, review/evidence и валидацию промежуточного Graph. **Нельзя сравнивать только начало и конец batch**: Decision, созданный одним шагом, должен получить review при изменении своего источника на следующем. Семантика L1/L2, блокировок, CAS, событий и атомарности не изменена.

Только внутри одного вызова `native_dependency_impacts(before, after)` используется `ANALYSIS.read_scope(after, fresh=True)` с производными индексами отношений/контекста. Новый `fresh=True` обходит возможный внешний кэш даже при той же идентичности Python-словаря Graph. Scope закрывается **до** постановки review и до следующей операции; после исключения он также сбрасывается. Хранимые записи отношений представлены кортежами примитивных полей, каждый вызов `POLICIES.relations` получает отдельные словари. Нет нового глобального/дискового кэша, межоперационных результатов или обхода проверки корректности. Чистота `_native_dependency_impacts_unscoped` обязательна: добавление мутации внутри вычислителя нарушит контракт и потребует отдельной проверки.

Контроль **внедрённого writer** на одном изолированном synthetic owner, три чередующихся измерения каждого варианта, строго одинаковые prepared effects: 30 Graph-шагов — 3226,75 → 1990,27 мс (−38,3%); 50 Graph-шагов — 18372,51 → 10393,27 мс (−43,4%). Измерена только подготовка batch, без `apply`/сети/LLM и Windows; p50/p95 для 500/5000 и пиковая память больших Graph ещё не проверены. Журналы: `/workspace/repo/Workfiles/rdg-operator/Writer-Scoped-Integrated-5.log` и `Writer-Scoped-Integrated-10.log`.
