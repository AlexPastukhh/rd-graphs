# Temporal Plan — минимальный контракт owner/version/as-of, P1

**Статус:** CANDIDATE, подготовлен для следующего локального пилота P2.
Это семантический контракт-кандидат, а не изменение действующей JSON schema,
не утверждённая production architecture и не реализация Plan writer.
Stage 4 остаётся NOT ACCEPTED.

Основание: FR-06/11/12/13/14/15, SRU-11/12, WR-45…53 и EA-30…36 полного
Candidate Pre-work v4.1. P0 закрывает проверенный branch-membership дефект
для текущих проекций с одной условной ветвью. P1 определяет границы owner,
версии, временного знания и будущего lifecycle; не расширяет полномочия ОС.

Таблица ниже описывает baseline на момент P1. Последующий локальный
candidate-only writer и точные snapshots Plan реализованы в
[пилоте P2](RDG-TEMPORAL-PLAN-OWNER-PILOT-P2.md). Этот пилот не закрывает
future acceptance, event attestation и полный двухвременной as-of.

## 1. Что уже существует и что предлагается

| Слой | Текущее исполнение | Роль P1 |
|---|---|---|
| Plan JSON schemaVersion=1 | `status=candidate`; steps/events/sequence/branches/timeConstraints; read-only validation | Сохраняется без миграции |
| Plan identity | identitySpace + id; Gendocen resource ID зависит от этой пары | Уточняется owner/path binding и конфликт владельцев |
| RDG refs | graphFile/identitySpace/nodeId/observedGraphRevision | Отделяются текущая ссылка и проверенная историческая версия |
| Future acceptance | Отсутствует; `status=accepted` отклоняется | Определяется смысл принятого будущего baseline, не способ обхода валидатора |
| Actual events | Отсутствуют; event только expected | Отделяются ожидание, заявление, attestation и verification |
| Version/as-of | Есть revision и metadata текущей проекции; исторических snapshots нет | Определяется двухвременной запрос и fail-closed при отсутствии snapshot |
| Writes/permissions | Plan writer отсутствует | Требования к P2; права записи здесь не выдаются |

В этой работе не добавлены новые поля в действующие Plan JSON. Названия
`PlanRef`, `PlanRevisionRef`, `knownAt`, `effectiveAt`, `recordedAt` ниже описывают
контракт-кандидат. Они не являются обещанием доступного CLI/API или принятой
сериализацией. `planId` — имя идентификатора в ссылке; в schemaVersion=1
соответствующее поле по-прежнему называется `id`.

## 2. Owner, identity и расположение

**P1-I01.** RDG остаётся единственным смысловым владельцем R/Action/Canon/Finding,
выбора Action и его T1/selectionBasis. Temporal Plan владеет временным содержанием
и своей историей. Gendocen, Viewer, Markdown и внешние readers получают проекции.

**P1-I02.** Логическая identity Plan — `(identitySpace, planId)`. В выбранном
owner-контуре она связывается ровно с одним writable source. `sourcePath` —
локатор этого source относительно явно заданного Plan root. Он не создаёт
нового Plan и не заменяет identity. Root должен быть выбран явно в пределах
действующего разрешённого доступа; production root сейчас не назначен.

**P1-I03.** Предлагаемый `PlanRef` содержит identitySpace, planId и sourcePath.
Reader проверяет совпадение ссылки, owner binding и содержимого файла. Два
независимо изменяемых файла с одной identity — конфликт owner; выбирать самый
новый файл, искать его по другим mounts или создавать копию нельзя. Read-only
snapshot с известным origin не становится вторым writable owner.

Step ID обозначает отдельное вхождение в Plan и отличается от RDG Action ID.
Два разных шага могут ссылаться на один Action, в том числе в разных cases.
Это не две копии Action. Ветвь и событие связываются с точным Plan/step/revision;
один step ID нельзя переиспользовать для другой по смыслу сущности.

**P1-I04.** `sourcePath` нормализован относительно выбранного root. Абсолютный путь,
выход через `..`, неоднозначные разделители и symlink за пределы root не дают
доступа. Docker-путь не доказывает доступность Windows-пути. Перенос sourcePath
с той же identity требует явного авторизованного переноса и сохранения origin;
физическая копия сама по себе таким переносом не считается.

Глобальная уникальность identity между независимыми installations не доказана.
До общего owner binding коллизию нельзя молча считать одной сущностью.
Конкретный registry, root, GitHub repo/branch/writer и размещение snapshots
остаются решениями соответствующего этапа, а не частью уже выполненного P1.

## 3. Версия и основание записи

**P1-I05.** `PlanRevisionRef` уточняет PlanRef точной revision и digest конкретного
snapshot. Revision различает версии одного owner. Digest связывает байты snapshot
с записью; он не подтверждает реальность события, человеческую личность или
правомерность принятия. Число revision и присланный клиентом hash без доступного
snapshot и проверенного owner недостаточны для исторической оценки.

**P1-I06.** Материальное изменение создаёт следующую версию с origin, основанием,
ссылкой на предыдущую версию и неизменяемым сохранением прежней версии. У writer
должны быть CAS/expectedRevision и серверная проверка права до durable commit.
Точная раскладка content versions, lifecycle records и state revision — Proposal
для P2. P1 не вводит скрытый второй счётчик и не меняет текущую schemaVersion=1.

Текущая `revision` увеличивается и при некоторых косметических правках. P0
сравнивает адресные смысловые поля, а не весь номер revision: это не разрешает
удалять историю cosmetic edits из будущего writer.

**P1-I07.** Происхождение версии включает writer principal, операцию, основание,
предыдущую версию, recordedAt и ссылки на использованные snapshots/evidence.
Writer principal из bearer receipt — технический actor. `by=user` или имя,
написанные клиентом, не подтверждают личность пользователя.

## 4. Candidate и принятый будущий baseline

**P1-I08.** Candidate — предложенный временной план. Принятый будущий baseline —
конкретная версия Plan, отдельно принятая разрешённой операцией с проверенным
основанием. Самостоятельно записанный статус или receipt неизвестного issuer
не переводит candidate в принятый baseline.

| Состояние или запись | Что означает | Что из этого не следует |
|---|---|---|
| candidate | Будущий вариант для анализа | Обязательство проекта или выбор Action |
| accepted future | Принятый временной baseline с известной версией/областью | Action.selected, наступление события, исполнение или результат |
| новая редакция candidate | Предложение изменить будущее | Молчаливая замена принятого baseline |
| замена/отзыв baseline | Авторизованное изменение будущего с сохранением истории | Переписывание T1 или удаление фактических событий |

**P1-I09.** Принятый baseline может оставлять условные альтернативы открытыми и
ссылаться на candidate Actions. Его принятие не вызывает `graph.select_action`.
Новая редакция не меняет прежнее основание выбора Action. Поздняя оценка Plan
может требовать review RDG, но не переписывает исторический selectionBasis.

Точные enum, acceptance/revise/withdraw operations и их grants — предложения
для P2. Существующие права создания/редактирования/ветвления не должны
автоматически давать принятие baseline. Связь принятия baseline с доверенным
пользовательским подтверждением должна быть проверена отдельно от bearer.

## 5. Время, неизвестная дата и ограничения

**P1-I10.** Date-only — календарная дата с точностью до дня. Instant — момент
с явным UTC offset. Они не приравниваются добавлением полуночи или локального
timezone компьютера. Нельзя сравнить разные precision без явного правила.

**P1-I11.** `sequence.before/after` задаёт порядок. `minDelayDays` — нижняя граница
задержки, не длительность Action и не срок выполнения. У ожидаемого события
без даты относительная зависимость остаётся относительной. Неизвестная дата
не заменяется текущей датой, нулём, пустой строкой или произвольной оценкой.

Текущее поведение impact: для date используются календарные дни; для instant
сравнение идёт в UTC, а `timedelta(days=n)` означает n×86400 elapsed seconds.
Это не локальные рабочие дни и не DST-aware календарный расчёт. Явные units,
рабочие календари, months, ресурсы и критический путь не реализованы.

**P1-I12.** В schemaVersion=1 отсутствие absolute constraint не задаёт дату.
Поле `at:null` не поддерживается. Окно для одного step можно выразить парой
`notBefore` + `deadline`, сохранив обе precision, strength и basis. Это описание
ограничений; текущая структурная валидация не доказывает выполнимость окна.

**P1-I13.** `hard/soft/hypothetical` характеризуют заявленное ограничение, а не
авторитет источника. Кандидатный hard deadline не становится committed FR.
Принятие будущего baseline также не создаёт новый нормативный FR автоматически:
если ограничение является обязательством проекта, его независимый owner,
принятие и applicability должны быть доступны отдельно. Нарушение гипотезы
или будущего срока не даёт F-P без независимой проверки текущего факта.

## 6. Событие и условная ветвь

**P1-I14.** `planned`, `possible` и `expected` описывают будущее. Case/outcome в
Plan — условие сценария, а не сообщение о том, что outcome уже произошёл.
Принятая условная ветвь будущего и фактически наступившая ветвь — разные вещи.
Read-only оценка выбранного сценария не выбирает действующую ветвь.

**P1-I15.** Запись о событии должна различать: заявление источника, attestation
уполномоченного actor и независимую проверку результата. Предлагаемый factual
record ссылается на стабильный event ID, точный Plan/step/revision, outcome,
время события с его precision, recordedAt, issuer и evidence. Эти сведения
не добавляются в действующий expected event клиентским текстом.

Event-attest требует отдельного права и доверенного пути ввода. Право не
превращает само утверждение в объективную истину; технический receipt сам по
себе не доказывает факт и не открывает F-P. Требования к реальному источнику
и механизму verification остаются отдельным gate перед фактическим применением.

**P1-I16.** Исправление/оспаривание факта добавляет новую запись, которая указывает,
что именно supersedes или оспаривает. Старое событие и позднее время знания
сохраняются. Конфликтующие outcomes не разрешаются выбором последнего файла
или произвольным приоритетом автора. До разрешения конфликта соответствующее
основание оценки остаётся неопределённым.

## 7. Два времени и исторический as-of

**P1-I17.** `recordedAt` — время появления версии/сведения в owner history.
`effectiveAt` — заявленное время применимости или события в предметном мире.
Для records истории recordedAt должен быть timezone-aware instant из доверенного
пути commit. Effective time может иметь date-only или instant precision;
сравнение допустимо только в согласованной precision. Поздняя запись с ранним
effectiveAt не становится тем, что было известно раньше.

**P1-I18.** Исторический запрос должен явно различать:

- точный snapshot по PlanRevisionRef;
- знание на `knownAt` и применимость на `effectiveAt`;
- текущую реконструкцию прошлого с более поздним knownAt.

Нельзя подменять отсутствующую историческую версию текущей проекцией. Для
as-of отбора записи должны быть доступны в owner history к knownAt и подходить
по effective context. Среди допустимых snapshots действует проверенный порядок
owner revisions, а не недоверенный клиентский timestamp. До реализации этого
порядка reader сообщает `historicalSnapshotAvailable=false`/неполное evidence.
Запрос также явно задаёт область lifecycle: candidate version или принятый
будущий baseline. Последний candidate не подменяет более ранний принятый
baseline. Сначала разрешаются lifecycle и branch context, затем версия в
соответствующей области; брать максимум revision среди всех состояний нельзя.

Пример: r1 записана 10:00, действует с 10:00. r2 записана 14:00 и сообщает
исправление, действующее с 10:30. При knownAt=11:00 r2 исключена даже для
контекста 10:45. При knownAt=15:00 её можно рассмотреть как позднюю реконструкцию
контекста 10:45. Это не меняет сведения, доступные на историческом T1=11:00.
Все времена примера — timezone-aware instants одного UTC-дня.

**P1-I19.** Plan-aware RDG assessment фиксирует точные Plan/branch/outcome,
PlanRevisionRef и использованные RDG snapshots. `observedGraphRevision` остаётся
заявленной ссылкой на наблюдение, пока snapshot этой RDG revision не разрешён.
Если исторический RDG snapshot отсутствует, полноценный T1-as-of review не
подтверждён даже при наличии старого Plan. Evidence gap возвращается явно;
автоматически создавать F-U в каноническом графе для этого не требуется.

## 8. Граница P0, P2 и последующих этапов

**P1-I20.** Новый lifecycle, sourcePath binding, статусы или event records нельзя
подключать к старой P0-проекции с декларацией прежней полноты. При реализации
расширяется coverage contract и отрицательные тесты. Старый consumer должен
явно отклонить неподдержанные данные или потребовать review, а не сообщать valid.
P0 остаётся ограничен `current-projection` и одной условной ветвью.

| Операция следующего пилота | Требуемая граница | Что не разрешает |
|---|---|---|
| Plan create/edit/branch | Plan-scoped grant, CAS, проверка owner/path | graph.select_action, factual event attestation |
| Принятие/пересмотр baseline | Отдельно определённое право и проверенный lifecycle record | Исполнение Action и факт события |
| Event-attest | Отдельный grant и проверенный источник; сохранение происхождения | Автоматический F-P или выбор Action |
| Read historical context | Разрешённые точные snapshots и явные known/effective time | Поиск в owner home, расширение mounts или current fallback |
| Recovery | Завершение/откат уже принятой технической транзакции по журналу | Новое пользовательское принятие или переписывание T1 |

Следующий P2 может исследоваться на временном synthetic root с явно заданным
локальным authorizer. Это не назначает production storage и не доказывает
trusted Helper/user bootstrap. Реальные grants, owner relocation, event source,
installed rollout и canonical remote требуют соответствующих решений.

## 9. Статусы Proposals и оставшиеся решения

| Proposal | Статус | Что конкретно подготовлено | Gate |
|---|---|---|---|
| PR-P1-01 owner/path binding | CANDIDATE | Identity отдельно от разрешённого locator; конфликт двух writers | P2 synthetic binding; production root не выбран |
| PR-P1-02 version/lifecycle | CANDIDATE | Точная revision, неизменяемая история, отдельный accepted future baseline | Сериализация, acceptance/revise rights и CAS proof в P2 |

принципы не открываются заново. Конкретные поля, transitions и persistence
формат надо проверять как реализацию этих принципов, сохраняя статусы Candidate.

## 10. Проверка и передача

`docs/handoffs/rdg-p1-plan-contract-20261019/`. Это индекс контрактных правил и
план доказательств, не JSON Schema для текущего Plan и не результаты новых
runtime tests. Полные N/FR/WR/EA остаются в v4.1; этот документ не создаёт им
