# RDG — текущий план

> **СТАТУС: ДЕЙСТВУЮЩИЙ ПЛАН РАЗРАБОТКИ.** Сверка 2026-11-06. Реализованный функционал и тесты — в [карте](RDG-FUNCTIONS-AND-TESTS.md), правила — в [контракте](RDG-ACTIVE-CONTRACT.md).

## Реализовано

Этапы политик 1–3 завершены в исходниках: общий каталог/версии/роли, зависимости и конкретные инстансы в Inspector, полноэкранные карточки инвалидации и история. Graph/Structure, контексты/Canon, Plan, copy/ready/lens, API и recovery имеют проверки, указанные в [карте функций](RDG-FUNCTIONS-AND-TESTS.md).

Наличие реализации и PASS не означает, что весь интерфейс принят пользователем или проверена любая комбинация входных данных.

## Внедрение файндингов

Семантика — в [контракте](RDG-ACTIVE-CONTRACT.md#файндинги), интерфейс — в [Viewer](VIEWER-EXPLORER.md#файндинги), кодовое задание — в [техническом ТЗ](RDG-DECISION-V1-CONTRACT.md#тз-реализации-файндингов). Реализация и ограничения имеют один технический источник.

Исправляющее ТЗ реализовано: подтверждения как Context вместо нового Evidence, Findings только в сведениях, Decision-subject, совместимость без молчаливого удаления, обсуждение обязательности R через обычный Decision, комментарии роли и производный контекст, переходы из Canon и вложенные группы банка контекстов. Старые тесты workflow проверяют чтение/сохранение совместимых данных; новый writable surface проверяет [analysis suite](../../tests/rdg-analysis.test.py), включённый в обязательный CI.

Результат полного release gate относится к точному source SHA и архиву в status/ready. Следующий gate после READY — установка Windows и пользовательская UX-проверка; если появится конкретное расхождение, воспроизвести его и исправить. Supplied definitions автоматически не переписывались; инструкции линз обновляются отдельно по текущей семантике.

## Работа через API

UI и AI используют общий Application. Проверяемые сценарии и путь schema → preflight → apply → receipt описаны в [техническом контракте](RDG-DECISION-V1-CONTRACT.md#владельцы-и-api). Доступ к живому API не разрешает превращать существующие процессы в destructive fixtures.

### Удобство API для ИИ

Порядок согласованного этапа: (1) полнота/обнаружение операций и корректность форм → (2) компактные чтения → (3) скорость записи и пакетный авторинг → (4) согласованные фундаментальные графы, рекомендации и операторская документация → (5) сквозная работа ИИ по этим линзам → (6) исправления и приёмка. Сценарий и критерии готовят заранее; полный проход выполняют после подготовки линз. Настройка прав и отдельных ограниченных ролей исключена из текущей задачи; используется штатный подготовленный доступ ИИ.

Пункт 1 реализован в исходниках: [матрица API](RDG-DECISION-V1-CONTRACT.md#матрица-операций-api-для-ии), явный выбор основного профиля в Agent/CLI, типизированные add-формы, согласованные paper capabilities и locks, прямые маршруты dependencies/history и режимы истории. [Discovery suite](../../tests/rdg-api-discovery.test.py) включён в CI; gateway проверяет формы и реальные записи. **T1 реализован в исходниках как первый срез**: schema для read/history, `summary`/`item` и отдельно `full`, адресные facets/recordId, страницы с version-bound cursor, компактный Agent по умолчанию и [проверки](../../tests/rdg-compact-read.test.py). T3 добавил facet `questions`, редактирование Viewer, явный перенос и copy/remap. Для compact History сохранён старый полный внутренний сбор исторических артефактов; измерения 50/500/5000, оптимизация внутренних затрат и release gate ещё не завершены. **T2 добавлен как первый рабочий срез**: `batch` до 100 шагов для одного Decision owner, Graph-команды и Plan create/place/unplace через общий coordinator/receipt, alias→ID и ссылки на предыдущие шаги; атомарное отклонение поздних ошибок, CAS, exact retry, preacceptance recovery и HTTP gateway проверяются [batch suite](../../tests/rdg-batch.test.py) и [gateway suite](../../tests/rdg-gateway.test.py). Ограничения: Graph-операции пока должны предшествовать Plan; отдельные `complete/review`, Registry и служебные операции исключены, а Question-возможности batch и estimates реализованы в T3/T4, Planning Meta Action реализован в исходниках T5; список публикуется schema. Метрики p50/p95/bytes/RPC для 50/500/5000 и оптимизация внутренних затрат ещё не завершены. Доступность пользовательского T1/T2 runtime определяется текущими `buildId`/READY и отдельной Windows-установкой, а не одним наличием Docker-исходников. Дальнейшие пункты исполняются по единому [кодовому ТЗ](RDG-DECISION-V1-CONTRACT.md#тз-оставшегося-внедрения): T3/T4 реализованы в исходниках, T5 — Planning Meta Action, T6–T8 — линзы, сквозная приёмка и выпуск.

**Ближайшая задача по уточнению пользователя 2026-11-08 — B03A, адресное чтение фокуса и полной ветви.** Реализовано в исходниках по [ТЗ](RDG-DECISION-V1-CONTRACT.md#read-focus-branch-b03a): detail focus/branch, родительские и граничные refs, общий resolver, полные bodies один раз, материалы, cursor и CLI --all-pages. [Адресные тесты](../../tests/rdg-scoped-read.test.py), HTTP Gateway и новый полный учебный рецепт входят в CI; установленный runtime/Windows/UX проверяются отдельно. Существующий focus не переопределяется: новый компактный пакет убирает необходимость читать full owner ради текущей области. Отдельный branch от R/Decision раскрывает всё структурное продолжение с краткими родителями, ссылками на общие узлы/замыкания циклов, материалами и явными страницами одного снимка. Приоритет — до согласования B04/T6 и реального ИИ-прохода B05/T7. Graph/Structure/будущий Markdown — отдельный вопрос представления, в B03A не реализуется.

**Измерение B03A:** воспроизводимый [benchmark](../../tests/rdg-scoped-read-benchmark.py) использует изолированные FileStore fixtures 50/500/5000 и прежнее full как baseline. Отдельно выводит первый запрос, тёплые повторы, p50/p95, UTF-8 bytes и число RPC/страниц. Для default first-page режимов — пять повторов, для полной сборки ветви — один проход с проверкой объёма/числа запросов, без оценки p50/p95 этой сборки. Это синтетический backend на общем Docker host, без HTTP/model/tool времени и без SLA; он не закрывает полный рабочий этап B07/T7. Последние результаты задачи — /workspace/repo/Workfiles/rdg-b03a-20261108/metrics-complete.json и metrics-baseline.json. Дорогой первый общий расчёт остаётся отдельным направлением B07, а неизменные страницы используют bounded cache после проверки pins/прав.

**Основание B03A:** read-only проверка текущего учебного процесса показала: Agent item для D-SQL — 1828 UTF-8 байт без focus; full с focus — 1859787 байт/59129 pretty-JSON строк, сама view начинается на строке 54123. В существующем фокусе данные есть; проблема — адресность/объём доставки, а не отсутствие ближайших участников. Это единичный замер конкретного снимка, не p50/p95 и не оценка будущего пакета. Проверяемые fixtures качества/полноты, сравнение объёма и нагрузочные измерения входят в ТЗ; живые owners для этого не менять.

**Быстрый проверяемый цикл T1/T2, 2026-11-07 (изолированный fixture, не автономная работа ИИ):** [workflow test](../../tests/rdg-t1-t2-workflow.test.py) провёл 13 шагов (10 Graph и 3 Plan) от требования до альтернатив, Context/Canon/Finding и плана; readback подтвердил отсутствие выбора Decisions, связи и receipt/restart. Один замер: полное чтение 213901 байт против компактного overview 2569 байт; отдельные 10 Graph-команд — 20 preflight/apply вызовов и 1825 мс локально, один batch с эквивалентной структурой — 2 вызова и 387 мс. Это разовые локальные измерения, **не p50/p95 и не доказательство сетевого или реального ИИ-потока**. Позднее T3/T4 реализованы и получили адресные проверки; их статус указан ниже. Следующий быстрый цикл — самостоятельный ИИ с публичным API и диагностикой лишних запросов; нагрузка 50/500/5000 и полное T1/T2 завершение остаются проверками T7. Не оптимизировать History заранее без наблюдаемой проблемы, но не объявлять T1/T2 полностью принятыми.

**Ускорение повторных вычислений writer, 2026-11-07:** каждый шаг batch сохраняет свой пересчёт зависимостей и историю; временный кэш отношений/контекста ограничен одним вызовом `native_dependency_impacts`, без общей памяти между операциями. На синтетическом пакете из 30 Graph-шагов подготовка сокращена с 3,23 до 1,99 с, из 50 шагов — с 18,37 до 10,39 с (по три чередующихся измерения на вариант, точное равенство prepared effects). [Тест на scope/эквивалентность](../../tests/rdg-writer-calculation-cache.test.py) включён в CI. Это не завершает нагрузочную приёмку 500/5000, сетевой путь, реальный ИИ и p95. Процедура релиза и отдельная Windows-проверка остаются обязательными.

До изменения графов в пункте 4 отдельно представить **полный перечень семантики** для пользовательской проверки: действующие правила, новые уточнения, пробелы переноса и ссылки на их нормативных владельцев. Включить сохранение контекста и масштаб Action, границы процесса/фундаментальные R, C1/C2/C3, стоимость планирования и раннюю сквозную проверку, возврат к исходным целям, отдельные Questions/ответы и Findings-утверждения, планировочные метадействия, checkpoint перед формальным запросом ответов и защищённым исполнением. Текущий контур ограничен ИИ–пользователь; checkpoint не требуется перед каждым обычным сообщением. Это дополнение к прежним правилам модели, выбора/результата, Canon/Findings, зависимостей, Plan/History и линз. Точные нормы принадлежат [контракту](RDG-ACTIVE-CONTRACT.md), согласование перечня предшествует обновлению definitions и сквозной приёмке ИИ.

В пункте 4 сначала согласовать [целевую базовую `model`](RDG-LENSES.md#полное-целевое-содержание-model), затем строить остальные линзы по её правилам с равной поддержкой Graph/Structure. Смысловое содержание принадлежит указанному проекту и контракту, формат преобразования — [карте источник–линза](RDG-LENSES.md#теоретический-текст-и-его-представление-линзой). Исходный JSON и live owners пока сохраняют прежние версии; перенос проверяет recommendation anchors и доступность возможностей.

[Сверка DRY/KISS/YAGNI](RDG-LENSES.md#dry-kiss-и-yagni--покрытие-и-целевое-разбиение) предлагает три самостоятельные линзы и контекстные переходы из существующих через штатные recommendation packages/rules. Частичное старое покрытие сохраняется как соответствующий шаг/ссылка, общие правила имеют одного владельца. Восстановить специфические описания Decision-шагов, утраченные при замене общим текстом; legacy-формулировки сверять с действующим контрактом.

После согласования линз создать [полный учебный процесс по матрице](RDG-LENSES.md#фундаментальные-линзы-как-образцы-и-полный-учебный-процесс), сохранив старые примеры. Фундаментальные линзы и этот процесс должны служить образцами дальнейшего переноса теории/гайдов и пройти отдельную проверку до полной сквозной приёмки ИИ.

### Рекомендации линз — проверка реальной работы

**B02B реализован в исходниках по уточнению пользователя 2026-11-08; отдельный live-переход и смысловое содержание фундаментальных рекомендаций остаются.** [Смысл готовых графов, линз и рекомендаций](RDG-ACTIVE-CONTRACT.md#готовые-графы-линзы-и-рекомендации) определяет свободный способ использования методики и объём сохраняемых результатов; [техническое ТЗ B02B](RDG-DECISION-V1-CONTRACT.md#адресные-рекомендации-b02b) владеет формами/совместимостью/приёмкой.

1. Реализованы адресные привязки, устойчивой identity рекомендации и свободными пояснениями «когда»/«как использовать». По умолчанию выбран только текущий элемент; охват задаётся явно. Каталог фундаментальных линз остаётся доступным без автоматической раздачи всем элементам.
2. Реализованы «Сведения → Рекомендации · N»: просмотр, создание на месте, редактирование и снятие привязки из Graph/Structure и карточек вспомогательных объектов. Поддержать компактный API, copy/remap и общий writer/CAS/receipt, без скрытого изменения других процессов.
3. ### Question как самостоятельная сущность

**T3 реализован в исходниках:** canonical CRUD, typed refs, ответы hypothesis/observation/user_answer с проверенным происхождением, version guards, answerHistory, assessment/history и переоценка. Copy/remap сохраняет observed pins, remap-ит IDs ответов/оценок и связывает вопрос с конкретной копией элементов. Ready/lens не принимает live ответы и источники.

Формальный checkpoint не отправляет сообщения и не выдаёт разрешений.

### Планировочные метадействия

**T5 — Planning Meta Action, уточнённое ТЗ 2026-11-08; реализовано в исходниках.** Обычный внешний Action в Plan для работы над самим процессом, без структурного R/Decision-родителя и без показа в Graph/Structure. Частичная основа есть: external task, обычный lifecycle/оценки, placement, qualified refs и атомарный batch Graph+Plan. Существующие механизмы сверены: добавлены предметные ссылки, прямое создание Action+placement одной операцией API/batch, редактирование и навигация с возвратом. Общий writer/CAS/receipt/recovery; отдельные статусы, исполнитель и система workflow не вводятся. Прежняя форма `workflow:{targetRefs:[...]}` отменена; используются optional Action.subjectRefs, обычное resultCondition и операция plan_action через прежний batch/coordinator. [API-приёмка](../../tests/rdg-planning-meta-actions.test.py) и [Viewer/F5](../../tests/visual/rdg-planning-meta-actions.cjs) включены в CI; отдельные Windows/UX и release gate сохраняются. Завершение подтверждает только само действие; предметные изменения, selection и completion целей требуют отдельных явных действий. Старые external Actions/Plan сохраняются без автоматической миграции. [Технические критерии T5](RDG-DECISION-V1-CONTRACT.md#планировочные-метадействия), [смысл](RDG-ACTIVE-CONTRACT.md#планировочные-метадействия).
