## Реализовано

Этапы политик 1–3 завершены в исходниках: общий каталог/версии/роли, зависимости и конкретные инстансы в Inspector, полноэкранные карточки инвалидации и история. Graph/Structure, контексты/Canon, Plan, copy/ready/lens, API и recovery имеют проверки, указанные в [карте функций](RDG-FUNCTIONS-AND-TESTS.md).

Наличие реализации и PASS не означает, что весь интерфейс принят пользователем или проверена любая комбинация входных данных.

Следующий gate после READY — установка Windows и пользовательская UX-проверка; если появится конкретное расхождение, воспроизвести его и исправить. ### Удобство API для ИИ

Порядок согласованного этапа: (1) полнота/обнаружение операций и корректность форм → (2) компактные чтения → (3) скорость записи и пакетный авторинг → [B03B/B03C, структурный Markdown, поиск и проверка чтения ИИ](#rdg-structured-markdown) → (4) согласованные фундаментальные линзы двух групп, рекомендации и операторская документация → (5) сквозная работа ИИ по этим линзам → (6) исправления и приёмка. Сценарий и критерии готовят заранее; полный проход выполняют после подготовки линз. Настройка прав и отдельных ограниченных ролей исключена из текущей задачи; используется штатный подготовленный доступ ИИ.

Пункт 1 реализован в исходниках: [матрица API](RDG-DECISION-V1-CONTRACT.md#матрица-операций-api-для-ии), явный выбор основного профиля в Agent/CLI, типизированные add-формы, согласованные paper capabilities и locks, прямые маршруты dependencies/history и режимы истории. [Discovery suite](../../tests/rdg-api-discovery.test.py) включён в CI; gateway проверяет формы и реальные записи. **T1 реализован в исходниках как первый срез**: schema для read/history, `summary`/`item` и отдельно `full`, адресные facets/recordId, страницы с version-bound cursor, компактный Agent по умолчанию и [проверки](../../tests/rdg-compact-read.test.py). T3 добавил facet `questions`, редактирование Viewer, явный перенос и copy/remap. Для compact History сохранён старый полный внутренний сбор исторических артефактов; измерения 50/500/5000, оптимизация внутренних затрат и release gate ещё не завершены. **T2 добавлен как первый рабочий срез**: `batch` до 100 шагов для одного Decision owner, Graph-команды и Plan create/place/unplace через общий coordinator/receipt, alias→ID и ссылки на предыдущие шаги; атомарное отклонение поздних ошибок, CAS, exact retry, preacceptance recovery и HTTP gateway проверяются [batch suite](../../tests/rdg-batch.test.py) и [gateway suite](../../tests/rdg-gateway.test.py). Ограничения: Graph-операции пока должны предшествовать Plan; отдельные `complete/review`, Registry и служебные операции исключены, а Question-возможности batch и estimates реализованы в T3/T4, Planning Meta Action реализован в исходниках T5; список публикуется schema. Метрики p50/p95/bytes/RPC для 50/500/5000 и оптимизация внутренних затрат ещё не завершены. Доступность пользовательского T1/T2 runtime определяется текущими `buildId`/READY и отдельной Windows-установкой, а не одним наличием Docker-исходников. Дальнейшие пункты исполняются по единому [кодовому ТЗ](RDG-DECISION-V1-CONTRACT.md#тз-оставшегося-внедрения): T3/T4 реализованы в исходниках, T5 — Planning Meta Action, T6–T8 — линзы, сквозная приёмка и выпуск.

**B03A — адресное чтение фокуса и полной ветви.** Реализовано в исходниках по [ТЗ](RDG-DECISION-V1-CONTRACT.md#read-focus-branch-b03a): detail focus/branch, родительские и граничные refs, общий resolver, полные bodies один раз, материалы, cursor и CLI --all-pages. [Адресные тесты](../../tests/rdg-scoped-read.test.py), HTTP Gateway и новый полный учебный рецепт входят в CI; установленный runtime/Windows/UX проверяются отдельно. Существующий focus не переопределяется: новый компактный пакет убирает необходимость читать full owner ради текущей области. Отдельный branch от R/Decision раскрывает всё структурное продолжение с краткими родителями, ссылками на общие узлы/замыкания циклов, материалами и явными страницами одного снимка. Приоритет — до согласования B04/T6 и реального ИИ-прохода B05/T7. Третий структурный вид принадлежит отдельной задаче [B03B](#rdg-structured-markdown).

**Измерение B03A:** воспроизводимый [benchmark](../../tests/rdg-scoped-read-benchmark.py) использует изолированные FileStore fixtures 50/500/5000 и прежнее full как baseline. Отдельно выводит первый запрос, тёплые повторы, p50/p95, UTF-8 bytes и число RPC/страниц. Для default first-page режимов — пять повторов, для полной сборки ветви — один проход с проверкой объёма/числа запросов, без оценки p50/p95 этой сборки. Это синтетический backend на общем Docker host, без HTTP/model/tool времени и без SLA; он не закрывает полный рабочий этап B07/T7. Последние результаты задачи — /workspace/repo/Workfiles/rdg-b03a-20261108/metrics-complete.json и metrics-baseline.json. Дорогой первый общий расчёт остаётся отдельным направлением B07, а неизменные страницы используют bounded cache после проверки pins/прав.

**Основание B03A:** read-only проверка текущего учебного процесса показала: Agent item для D-SQL — 1828 UTF-8 байт без focus; full с focus — 1859787 байт/59129 pretty-JSON строк, сама view начинается на строке 54123. В существующем фокусе данные есть; проблема — адресность/объём доставки, а не отсутствие ближайших участников. Это единичный замер конкретного снимка, не p50/p95 и не оценка будущего пакета. Проверяемые fixtures качества/полноты, сравнение объёма и нагрузочные измерения входят в ТЗ; живые owners для этого не менять.

**Быстрый проверяемый цикл T1/T2, 2026-11-07 (изолированный fixture, не автономная работа ИИ):** [workflow test](../../tests/rdg-t1-t2-workflow.test.py) провёл 13 шагов (10 Graph и 3 Plan) от требования до альтернатив, Context/Canon/Finding и плана; readback подтвердил отсутствие выбора Decisions, связи и receipt/restart. **Ускорение повторных вычислений writer, 2026-11-07:** каждый шаг batch сохраняет свой пересчёт зависимостей и историю; временный кэш отношений/контекста ограничен одним вызовом `native_dependency_impacts`, без общей памяти между операциями. ### Исследование чтения для ИИ — API, файлы и представление

**Цель** — определить, насколько удобно ИИ находить объект, понимать область ответа и проверять смысл. Сравнивать отдельно способ доставки (Gateway или файл), форму данных (канонический JSON или текстовая проекция) и выбранный объём (карточка, фокус, ветвь). Файлы с фиксированной редакцией теории и текущие факты изменяемого owner проверяются как разные задачи.

**Что приходит сейчас.** `schema(read)` перечисляет режимы и секции. `summary` возвращает заголовок процесса, pins и страницу сущностей. `item` даёт body узла и отдельно запрошенные секции. `focus` и `branch` выдают JSON с `scope`, `snapshot`, `loaded`, `data` и `reading`. В `data.entities` находятся полные bodies с qualified refs. `outline` задаёт вхождения, `parents` — кратких родителей, остальные секции задают связи, контекст, теорию, Findings, Questions, completion, рекомендации и зависимости. Для связанного материала ИИ сопоставляет ссылку с body в `entities`. У секций свои cursor и признаки полноты, а Agent `--all-pages` собирает их на одном снимке. `full` возвращает весь Graph и производные представления даже при запрошенном фокусе.

**Живой замер 2026-11-10.** Gateway, учебный owner `examples/planning-meta-actions-20261108`, Graph revision 89, 28 структурных узлов и 31 ребро. Одна выборка каждого режима, размеры в байтах UTF-8 при пересериализации одного и того же ответа в компактный JSON и формат вывода Agent. Время — один наблюдавшийся клиентский HTTP-вызов с разбором JSON, без времени модели. Строки с разным scope покрывают разный объём фактов.

| Чтение | Компактный JSON | Вывод Agent | HTTP, мс |
| --- | ---: | ---: | ---: |
| `summary`, первые 25 из 66 сущностей | 4 903 | 7 450 | 130,1 |
| `item D-SQL` | 1 470 | 1 827 | 86,7 |
| `item D-SQL` с context/canon/findings/questions/completion/recommendations | 7 866 | 11 606 | 202,5 |
| `focus D-SQL`, стандартный набор | 57 493 | 107 117 | 227,1 |
| `focus D-SQL`, родители/outline/entities/context/canon/findings/completion | 20 176 | 31 247 | 203,1 |
| `branch R-STORE`, стандартный набор | 116 411 | 220 901 | 244,3 |
| `full` с фокусом `D-SQL` и Plan | 1 125 332 | 1 863 608 | 3 323,9 |

Из стандартного `focus` секция dependencyApplications занимала 30 745 байт компактного JSON. Выбор нужных секций сократил пакет примерно на 65%. Для `branch R-STORE` с `include=[entities,edges,outline]` и `limit=5` первая страница была неполной. Сборка на одном снимке заняла 6 RPC и дала 16 bodies, 7 рёбер и 9 вхождений. Обнаружение owner через каталог в этом запуске заняло 2,1 с, отдельным вызовом.

**Файловая проба на той же редакции.** Временный локальный JSON содержал тот же выбранный `focus` объёмом 20 176 байт. Медиана чтения и разбора за 30 тёплых повторов составила 0,277 мс. Для одинакового набора из 13 фактов о D-SQL отдельная компактная JSON-памятка заняла 1 988 байт, а экспериментальная Markdown-памятка — 1 784 байта. Медиана чтения Markdown составила 0,031 мс. Файлы были заранее подготовлены из API. Замер не включает построение и поддержание файлов, работу модели, сетевой перенос файлов и реальный рендерер B03B. Памятка содержит выбранные факты и не заменяет полный снимок. Результаты относятся к одному учебному примеру и не являются оценкой p95 или качества ответов ИИ.

**Практический вывод.** Для известного ID карточка с нужными секциями даёт компактный ответ. Для структурного обхода `focus` и `branch` дают состав области и явную полноту, но требуют работы со ссылками и секциями. Файлы удобны для поиска по тексту, цитирования и повторного чтения фиксированной редакции. Для текущего состояния API несёт проверенные права, ревизию и машинно различимые связи. В этой пробе на объём сильнее повлиял выбор области и секций, чем смена синтаксиса при одинаковом наборе фактов.

**Оставшаяся приёмка этапа B03B/B03C.** На одинаковом снимке и с одинаковым доступным объёмом сравнить API JSON, структурный Markdown и файлы с сопоставимыми фактами. Задачи — найти неизвестный ID по смыслу или названию, объяснить одно решение с материалами, восстановить ветвь с общим узлом и проверить источник или смену ревизии. Для свободной теории отдельно сравнить поиск нужного раздела и проверку ссылки на линзу. Зафиксировать корректность ответа, пропущенные факты, точность ссылок, discovery, число RPC и шагов поиска, UTF-8 bytes, время доставки и время работы ИИ отдельно. Сначала провести компактный проход на учебном примере. Расширять замеры при обнаружении конкретного узкого места.

### Планировочные метадействия

**T5 — Planning Meta Action, уточнённое ТЗ 2026-11-08; реализовано в исходниках.** Обычный внешний Action в Plan для работы над самим процессом, без структурного R/Decision-родителя и без показа в Graph/Structure. Частичная основа есть: external task, обычный lifecycle/оценки, placement, qualified refs и атомарный batch Graph+Plan. Существующие механизмы сверены: добавлены предметные ссылки, прямое создание Action+placement одной операцией API/batch, редактирование и навигация с возвратом. Общий writer/CAS/receipt/recovery; отдельные статусы, исполнитель и система workflow не вводятся. Прежняя форма `workflow:{targetRefs:[...]}` отменена; используются optional Action.subjectRefs, обычное resultCondition и операция plan_action через прежний batch/coordinator. [API-приёмка](../../tests/rdg-planning-meta-actions.test.py) и [Viewer/F5](../../tests/visual/rdg-planning-meta-actions.cjs) включены в CI; отдельные Windows/UX и release gate сохраняются. Завершение подтверждает только само действие; предметные изменения, selection и completion целей требуют отдельных явных действий. Старые external Actions/Plan сохраняются без автоматической миграции. [Технические критерии T5](RDG-DECISION-V1-CONTRACT.md#планировочные-метадействия), [смысл](RDG-ACTIVE-CONTRACT.md#планировочные-метадействия).
