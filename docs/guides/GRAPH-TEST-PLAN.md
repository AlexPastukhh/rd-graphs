# План тестирования Requirements–Decisions Graph (pilot)

Дата: 2026-10-12. Объект: данные графа, построение/просмотр, содержательные рабочие сценарии и обновление графа через Fortis Repo.
Не входит в объём: установка расширений, метаданные userscript и локальные лоадеры. Не изменять настоящие графы при тестировании.

## 1. Состав системы и границы проверки

Текущее физическое хранилище: `graphs/workspaces/<slug>/graph.json` со `schemaVersion: 1`, `revision`, `nodes[]`, `edges[]`, `events[]`.
Текущая реализация: `tools/rd-graph-viewer.user.js` — просмотрщик только для чтения; загрузка файла/папки, диаграмма, поиск, инспектор, pan/zoom, ручное перечитывание.
Отдельный механизм применения дельт с атомарной записью, проверкой revision и управлением историей пока не реализован. Промпты — инструкция для ChatGPT, но не механизм автоматической записи.

Объекты R (Requirement/Goal) и D (Decision); Context, Question/QRPE, Variant и другие записи вспомогательны. Ребро `DRIVES` указывает требование/драйвер → решение, `INTRODUCES` — решение → дочерний R с обязательным parent R. Делегация сохраняет тот же ID.
Предложенное решение ≠ принятое, принятое ≠ реализованное, реализованное ≠ проверенное. История принятия отдельно от актуальной проекции.

## 2. Критерии проверки

- PASS: автоматический assert либо наблюдаемый результат в браузере совпадает с ожидаемым.
- FAIL: есть воспроизводимое расхождение (оформить finding, входные данные и фактический результат).
- BLOCKED: функция не реализована либо среда не даёт выполнить сценарий; не считать PASS.
- NOT_RUN: тест запланирован, но ещё не выполнялся.
- Не менять канонический исходный граф ради теста. Использовать временную копию/отдельный fixture.
- Критично (P0): потеря информации, принятие решения без полномочий, несогласованный граф, тихая перезапись, неверная трассировка.
- Важно (P1): неверные связи/визуализация, непонятный статус, обновление не видно, UI недоступен.
- Дополнительное (P2): удобство, масштаб, длинные подписи и сложная навигация.

## 6. Порядок и условия готовности

Этап A (сейчас): G01–G05, G12–G15, V01–V08 — автоматические проверки JSON + модель браузерного UI.
Этап B: G06–G11, S01–S11 — содержательные и модельные испытания на специально подготовленных наборах; нужен механизм сохранения смысловых операций.
Этап C: S12–S18 — интеграция Fortis Repo и реальные двухсессионные обновления, конфликт/rollback, просмотр результата.
Этап D: V09–V10 и браузерные V01–V08 — реальный браузер и ручные UX-пробы.

**Минимальная готовность v1**: P0 проходят без нерешённых дефектов, для V01–V08 есть результат реального браузерного прогона, S01–S17 воспроизводимы end-to-end; каждый BLOCKED имеет владельца/следующий шаг.
Логировать для каждого кейса ID, fixture, revision before/after, expected, actual, PASS/FAIL/BLOCKED, proof (файл/скриншот/тест-лог). Не требовать длинных отчётов для каждого успешного прогона.

## 7. Отдельные ограничения текущего пилота

Проверка `validate` просмотрщика сейчас гарантирует только базовую форму данных и существование ID, но не всю семантику: G06–G12 могут обнаружить реальные пробелы.
Текущий `events[]` есть в формате, однако средство сохранения/проверки событий отсутствует: не объявлять S09/S13 пройденными только из-за наличия массива.
Браузерный File System Access зависит от среды. Файловый режим и режим папки проверять отдельно.

## 8. Четыре воспроизводимых пользовательских маршрута

Вход для каждого маршрута — отдельная копия JSON; проверять **фактический файл**, не только ответ ChatGPT.

### M1. Первая цель и планирование (S01–S03)

1. Пользователь: «Нужно приложение бронирования. Сформируй исходную цель и варианты разбиения».
2. До принятия: R определён; D и введённые им дочерние R остаются явно **proposed**, действующий план не меняется.
3. Пользователь: «Принимаю разбиение по сценариям и функциям».
4. После сохранения: один committed D, связанные дочерние R с parent и порождающим D, ревизия увеличена один раз, зафиксировано событие принятия.
5. Пользователь: «Уточним R сценариев». Дальнейшее D/R-разбиение трассируется до исходной цели. Не требовать полного дерева заранее.

### M2. Выполнение, один общий ответ, статус (S04–S07, S10–S11)

1. Пользователь: «Проработай обработку потерянного ответа подтверждения».
2. Полученное решение может отвечать функциональной потребности и части описания ошибок одновременно — один D в корректном scope.
3. Делегация R в другой Target Module сохраняет его прежний ID и источник; не считается выполнением.
4. Если возможность проверить статус сервера неизвестна, прикрепить к D конкретный QRPE-вопрос, не объявлять достаточность подтверждённой.
5. Запрос «STATUS по исходной цели» отдельно показывает selected D, фактически выполненное, evidence и остаточные требования.

### M3. Пересмотр при изменении контекста (S08–S09, S18)

1. В исходном контексте уже есть выбранное D про описание Behavior.
2. Пользователь: «Появились внешние события, зависящие от состояния. Проверь влияние».
3. IMPACT: затронутые D/R и необходимость revalidation, но без автоматической отмены прежнего D.
4. Предложения Hybrid и State Transitions остаются кандидатами; если пользователь выбирает один, записать реальный transition/event.
5. TRACE после изменения показывает актуальный выбор и восстановимую предысторию; отсутствие изменения — без искусственного нового event.

### M4. Постоянное хранение и две сессии (S12–S17)

1. Сессия A читает revision=1. Сессия B тоже читает revision=1.
2. A согласованно записывает обновлённые nodes/edges/events как revision=2; повторное чтение подтверждает 2.
3. B пытается сохранить изменения из revision=1: обязан получить конфликт, повторно прочитать 2, а не перезаписать файл.
4. Отдельная новая сессия читает revision=2 и способна выполнить TRACE, PLAN, STATUS без восстановления из чата.
5. Во время записи имитировать сбой: старый graph.json или полностью новый, без полусохранённых связанных узлов.
6. Повторить тот же UPDATE: без изменений нет дублирующих ID, пустых событий или нового revision.
7. Перечитать файл просмотрщиком и проверить точный состав графа и новую revision.

Маршруты M1–M4 — **приёмочные сценарии**, а не заявление, что все эти функции уже реализованы. Прогон требует подсистемы записи и связанности с рабочими промптами.
