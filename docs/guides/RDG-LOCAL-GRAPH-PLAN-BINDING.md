# Локальный большой рабочий граф ↔ реальный Plan — Viewer 2.4.0 Candidate

**Решение пользователя (2026-10-20):** может быть несколько больших рабочих графов, для каждого свой план. При выборе большого графа Viewer автоматически показывает план соответствующего рабочего контекста. Это переключение представления, **не** автоматическое размещение всех Actions/R во времени, **не** объединение Graph и Plan в один владелец данных.

## Viewer 2.4.0 — никаких отдельных режимов учебного/предварительного Plan

Вверху две единственные вкладки **«Граф»** и **«План во времени»**; если пользователь выбрал read-only пример — в той же вкладке показывается `workflowExample` только для чтения, а если рабочий `workspaces/*` — его **реальный Plan owner**, при отсутствии файла ошибка. Отдельная кнопка «Учебный план» и отдельный обработчик демо удалены. «⋯» открывает JSON/обновление/source только на Graph, а параметры связей и позиций перемещены в видовые контролы **«Связи»**, **«Варианты»**, **«Вид ⚙»**. Это UX изменение, не создание/изменение Plan. Breadcrumbs и «Уровень выше» дают путь из подграфа в полный; история, размещённые и неразмещённые R/Actions не меняют provenance при переключениях. Проверено на desktop/mobile + старом Helper E2E; установка версии 2.4.0 не подтверждена.

## 2.3.9: переходы из истории и плана к Graph declaration

Каждая **запланированная** карточка R/Action, каждое историческое **выполнение Action / достижение R** имеет собственную заметную кнопку **«Открыть блок в графе ↗»**. Исторические события **смены статуса / пересмотра графа** раскрывают ссылки на соответствующие существующие R/Actions; в `action_reconsidered` — на исходный, review, replacement и compensating Action при их наличии. Переход открывает вкладку **«Граф»**, выбранную (центрированную) сущность и её канон/QRPE в owner, не клонируя узел из Plan. Если историческая R уже деактивирована или её edge архивирован, Viewer при необходимости открывает весь исходный Graph, чтобы показать **тот же node ID**. Ненайденные или неподтверждённые references не становятся новыми узлами и не имеют работающей ссылки.

**Исторический материал и текущий Graph — разные состояния.** Снимок канона/QRPE на момент записи сохраняется в History; переход раскрывает **текущее** объявление (в том числе superseded). На read-only учебном графе возвращение обратно на вкладку Plan сохраняет опубликованный educational `workflowExample` и все исторические события, а не заменяет его пустым планом. Никаких записей в пользовательские Graph/Plan этот переход не создаёт; прямой Viewer только переключает просмотр, полный writable Helper использует те же owner refs и права.

## 2.3.8: пересмотр Action и пара замена + компенсация

В событии `action_reconsidered` показаны **старый Action → выбранный новый Action** и **как поступили с последствиями старого**. Режимы: явное «дополнительных действий не потребовалось» с обоснованием на Graph evidence либо «выполнен компенсирующий Action» со ссылкой на существующий Graph Action и принятый `action_executed`. `reviewActionId` — самостоятельный Action пересмотра, **не** обязательная замена. Plan не создаёт и не выполняет компенсирующий Action; исторические записи без полей показывают неопределённость. [Полный контракт](RDG-DEEP-ACTION-AND-HISTORY.md).

## Новые визуальные правила 2.3.7 — классификация истории, варианты с канонами, Plan не создаёт Graph

- **История** классифицирует события одновременно текстом и оформлением: **РЕЗУЛЬТАТ** — подтверждённое исполнение Action или достижение R; **СОСТОЯНИЕ** — активация/деактивация/отзыв; **ВЫБОР** — решение или выбор Action (не выполнение); **ИЗМЕНЕНИЕ ГРАФА** — изменение определений/связей/контекста. Типы `requirement_activated` доступны в отображении, но их отсутствие в конкретном Graph не дополняется фальшивыми событиями. Учебная история явно помечена. `complete/currentScopeComplete` и исторические material snapshots по-прежнему определяет writer, не цвет и не дата.
- **Варианты**: у R видны реальные Graph `Option`/`Action` из её рёбер, каждый с собственным `canonBlock` («когда подходит / когда не подходит»), QRPE и статусом. У размещённого Action видны другие способы для той же R, включая кандидаты и пересмотренные (явно помеченные) исторические варианты. План может содержать только размещения реально объявленных Graph R/Actions; до Graph selection Action-кандидат не может быть размещён в реальном Plan.
- **Почему два примера**: старый `reference-mixed-active-work` содержит только `Option/Decision` плюс пять событий изменения модели; он не может законно смешивать их с `candidate-v6 Action` (валидатор отказал в изолированной проверке). Его образовательные 3 Plan размещения указывают на существующие R в **его** Graph. Новая навигационная кнопка открывает **отдельный** `reference-action-time-plan` — там действительно есть Actions `A-IDEMPOTENT` и `A-SERVER`, размещённые в учебном Plan, и другие Action-альтернативы с отдельными канонами. Это переход между примерами, не слияние владельцев и не добавление сущностей из одного Graph в Plan другого.
- Валидатор `localPlanPreview` теперь проверяет каждый учебный Plan reference по реальному node id, graphFile, identitySpace, kind и выбранному статусу размещённого Action. Поддельный или потерянный узел приводит к отказу вместо появления фиктивного блока. Для реальных записей дополнительно действуют штатные Plan/Graph writers, bearer и CAS. **Ни один Graph writer, authority/grant или реальный Plan user owner не изменён.**

## Срез 2.3.6: выполнено ≠ размещено во времени

Новая третья группа **«Без места во времени»** выводит актуальные R и выбранные Actions без `Plan` placement. Это не дополнительный Plan owner и не новая семантика завершения. Размещённые R/Actions находятся в **«План во времени»**, события изменения Graph и результаты выполнения в **«Истории»**, при этом события выбора/редактирования явно не обозначаются выполнением. Если факт completion не удостоверен доступным writer journal/resolver, интерфейс пишет о непроверенном результате вместо фиктивной успешности. И даже подтверждённый исторический Action может не подтверждать актуальную композицию R — учитывается `currentScopeComplete`. Потенциальные R, непринятые Action-кандидаты и неактуальные ветви не являются текущими обязательными задачами.

**Учебный пример со скриншота — `reference-mixed-active-work`, а НЕ `reference-feature-root`** (ошибочную прежнюю идентификацию сохраняем ниже только как исторический контекст). Этот архивный `readOnly/exampleOnly` граф имеет 5 исторических записей **изменения графа**, **0 событий выполнения**. Для демонстрации отдельного Plan задан `workflowExample`: 3 гипотетических образовательных размещения уже существующих R, остальные актуальные R видны без места во времени. Размещения имеют только демонстрационные ссылки на `examples/*` и **НЕ** являются нормативным Plan owner (`rdg-temporal-plan.py` для реально записываемых steps требует `workspaces/*` graph refs). Никаких фальшивых `action_executed`/`requirement_achieved` не создавали. Другой архивный пример `reference-action-time-plan` продолжает иллюстрировать исторические записи выполненных действий с подготовленными учебными данными.

Тесты: `tests/rdg-workflow-ui.test.cjs`, `tests/visual/rdg-always-on-plan.cjs`, `tests/visual/rdg-workflow-tabs.cjs`. Browser проверяет 5 карточек исторических **правок**, 3 размещения и раскрываемый список неразмещённых целей, а также отсутствие ошибочных заявлений о выполнении. **Это только source 2.3.6; Installed 2.3.6 не подтверждён.**

## Исправление UI 2.3.5 — учебный пример ≠ пользовательский Plan

**Историческая неточность версии 2.3.5:** На скриншоте установленного Viewer 2.3.4 с «Рабочий пример разбиения функциональности» отображалась надпись «Предварительный план». Тогда граф ошибочно назвали `reference-feature-root`. Правильный исходный файл — **`examples/reference-mixed-active-work/graph.json`**, также архивный (`readOnly`, `exampleOnly`), не живой editable `workspaces/*` owner, несмотря на историческое значение `presentation.usage='working'`. В 2.3.5 учебная лента без авторского `workflowExample` явно пишет **«Учебный пример: запланированных шагов нет»**, а не «Предварительный план»; она не приписывает примеру реальный Plan-файл. Учебные примеры, уже имеющие `workflowExample`, показывают прежние 15 исторических карточек и 4 размещения. Для реальных рабочих графов `workspaces/*` правило ниже **не изменилось**: сохранённый Plan owner обязателен и должен быть создан штатным writer с разрешением; при отсутствии файла — ошибка, без сгенерированного placeholder. Source 2.3.5 ещё не установлен/не подтверждён пользователем.

## Актуальное решение 2.3.4: один настоящий Plan, без «предварительного» режима для рабочих графов

**Требование пользователя:** реальный `plan.json` у каждого рабочего Graph существует **до первого Action/размещения**; если история и будущее пусты — отображаются две пустые секции уже **реального** плана. Никакой браузерный placeholder не должен изображать сохранённый Plan.

**Сделано в исходниках:** `tools/rdg-workflow-helper.py` при старте `FileSession` вызывает `WorkspaceEditors.initialize_missing_plans()` **до** открытия сессии. За один проход проверяет доступ к графам и `plan.create/plan.read`, затем создаёт каждый отсутствующий `plans/<slug>/plan.json` через `rdg-temporal-plan-owner.py`, вместе с обычными revision, историями owner и индексом. Второй запуск не сбрасывает планы. Если прав нет, не создаёт файл, не открывает ложную сессию и показывает отказ. Поддерживается `--initialize-plans-only` для отдельной подготовки Plan-файлов **без запуска браузерной сессии**.

**Важный legacy-случай:** опубликованный рабочий `workspaces/try-it/graph.json` с прежней Graph-моделью теперь тоже обнаруживается, и для него можно создать **реальный пустой Plan owner** с identitySpace плана `legacy-try-it` без изменения Graph. Этот Plan в read-only до отдельной разрешённой миграции Graph на candidate-v6: legacy Graph **не имеет** необходимых identity/completion ссылок для безопасной записи размещений. Отсутствие Action-модели не позволяет молча включать запись в такой Plan. Примеры (`readOnly` / `exampleOnly`) остаются учебными, не требуют пользовательских owners и не смешиваются с рабочими графами.

**Viewer source 2.3.4:** при выборе рабочего графа читает **сохранённый** `plans/<slug>/plan.json` (в формате `temporalPlanOwner`) через ту же локальную read-capability Loader, проверяет `planId`, `identitySpace`, `sourcePath` и ревизию. Если файла нет или он не соответствует графу — **явная ошибка**, а не подставленный «пустой план». Без Helper сохранённый Plan можно **просмотреть**, но полная сверка журнала Graph/Plan и подтверждение результатов действий требуют авторизованного Helper. Когда он подключён, редактор использует тот же Plan owner и штатные writers. Таким образом, для рабочих графов **один Plan**, не два режима хранения.

**Граница auto-init:** браузерный Viewer не вправе сам создавать Plan за пользователя. На компьютере владельца необходимо один раз запустить разрешённый локальный процесс. Для стандартного проектного расположения `plans/` рядом с `graphs/` используется **`--root` проекта RDG**; для другого `--root` доступ к Plan обеспечивается Helper, а не прямым чтением Viewer. Не передавать реальные токены в ChatGPT или файл конфигурации.

```sh
# Запуск из корня rd-graphs; уже установленный scoped RDG_AUTH_TOKEN в доверенном окружении.
python3 -B tools/rdg-workflow-helper.py --manual-session \
  --auto-workspaces --initialize-plans-only \
  --root . --store /authorized/private/grants.json
```

В дальнейшем при добавлении нового рабочего Graph повторная инициализация (или запуск `--auto-workspaces` session) создаст только отсутствующий Plan. **Сам Graph writer не выдаёт себе права на создание Plan и не изменён на неатомарный двойной write.** Содержимое live RDG в этой реализации не менялось: в доступном mounted источнике нет настроенной рабочей bearer-сессии, поэтому не было незаконной ручной записи пользовательского Plan.

Тесты: `tests/rdg-workspace-switch.integration.test.py` — новый граф и legacy-копия, реальный Plan writer и чтение, отказ без grant, повторная инициализация, session-before-first-action; `tests/visual/rdg-always-on-plan.cjs` — граф `try-it` с валидным *синтетическим* сохранённым owner, случай отсутствующего файла, учебный snapshot истории; `tests/rdg-workflow-ui.test.cjs` — несовпадение владельца/ревизии отвергается. Установленный у пользователя Viewer 2.3.2; **2.3.4 пока только исходник**. Полная локальная приёмка и миграция старых планов не заявлены.

## Обязательная вкладка плана у каждого графа (2.3.3)

После открытия в **«Папках»** рабочего графа (включая старый `workspaces/try-it/graph.json`) или полного графа-примера вкладка **«План во времени»** немедленно показывает две уже существующие секции интерфейса: **«История»** и **«План во времени»**. Даже если шагов ещё нет, будущая часть видна пустой. Переключение графов немедленно переключает ленту; для её просмотра папка Helper не требуется. Раздел истории в Viewer **не создан заново**, используется прежняя отрисовка.

Без Helper это **временная read-only проекция**, формируемая из доступных graph.json: показывает события, присутствующие в графах, и пустую будущую часть; история journal-only записей, сохранённые размещения и актуальность источников **не подтверждены**. В статусе явно указано «предварительная лента»; никакой Plan owner не выдаётся за созданный/сохранённый. Пример `try-it` имеет 1 R, 0 событий и 0 явных размещений; показываются явные предупреждения «журнал writer не загружен» и «сохранённые размещения не загружены», чтобы предварительное состояние не выдавалось за пустой сохранённый Plan. Рабочий учебный полный граф `reference-feature-root` отображается аналогично (только просмотр). Пример `reference-action-time-plan` **повторно использует уже существующий авторский `workflowExample`**, сохраняя 15 исторических записей и 4 учебных размещения; этот read-only snapshot **не** является настоящим Plan owner. Не создавать вымышленных событий или шагов.

**Постоянный Plan owner** при наличии авторизованного Helper: для уже зарегистрированного или автоматически обнаруженного **candidate-v6 рабочего графа** Helper на первом чтении создаёт пустой `plans/<rootSlug>/plan.json` через **существующий Plan writer** (с журналом, `revision=1` и CAS), только когда `graph.read`, `plan.create`, `plan.read` разрешены bearer. Уже существующий owner **не переписывается**; если прав не хватает, файл не создаётся. Содержание Graph не меняется. Для старого `try-it` без `identitySpace` / `actionModel=candidate-v6` постоянный Plan нельзя безопасно объявить записью текущего workflow API; его **не мигрировать молча**. Для такого формата до отдельной разрешённой миграции доступна предварительная лента, не полноценный persisted owner.

**Автоматическое обнаружение нескольких новых рабочих графов**: вместо ручного файла соответствий разрешено запускать Helper в режиме `--auto-workspaces`, который читает `graphs/index.json`, выбирает совместимые writable full roots в `workspaces/`, сопоставляет каждому план `plans/<slug>/plan.json` и создаёт отсутствующие только при первом авторизованном обращении. Когда авторизованных candidate-v6 рабочих графов в каталоге нет, Helper сообщает `NO_WRITABLE_WORKSPACES_FOR_AUTOMATIC_PLAN`, **не создаёт ложные owners**. Для ручной/редкой привязки остаётся `--contexts-file`.

Пример запуска (после выбора отдельного существующего `--root`, оформления штатных grants и новой разрешённой session-папки):

```sh
python3 -B tools/rdg-workflow-helper.py --manual-session --auto-workspaces \
  --root /existing/plan-owner --store /existing/grants.json \
  --session-dir /existing/authorized/new-session-folder
```

`--auto-workspaces` работает с текущим опубликованным набором на момент запуска Helper; новые рабочие графы, добавленные **после** запуска, требуют обновления сессии. Нет нового backend и нет обхода bearer. Viewer source 2.3.3 **не равен установленному Viewer 2.3.2**; установленную 2.3.3 на устройстве пользователя не проверяли.

## Модель

- **Большой граф** выбирается по точке входа `fullGraphs[].slug` в существующем `graphs/index.json`. Подграфы того же `identitySpace` входят в этот рабочий контекст и используют один Plan. Семантическими владельцами узлов по-прежнему остаются исходные `graph.json`, а не проекция Viewer.
- **Plan** — отдельный versioned owner `plans/<имя>/plan.json` в указанном `--root`; он хранит ссылки на R/Actions, явное время/порядок и собственные CAS, журнал и историю. Создание Action не добавляет размещение автоматически.
- **Связь** root graph → Plan задаётся владельцем явно при запуске Helper (`--contexts-file`), не угадывается по имени Plan ID или совпадению папки. Сохраняются прежние штатные Graph/Plan writers и bearer. Нового хранилища, новых grants или скрытого перехода между владельцами нет.
- Одна файловая сессия Helper содержит список допустимых root→Plan-пар. Viewer сверяет четыре поля `rootSlug`, `graphFile`, `identitySpace`, `rootRequirementId` с выбранным полным графом. При A → B → A переключается соответствующий Plan, без повторного выбора session-папки. Внутренние уровни большого графа не переключают Plan.
- При отсутствии сопоставления, отказе `plan.read` или невалидной identity старый Plan и его кнопки скрываются, отображается ошибка. План не создаётся молча. Reader Helper требует права на весь источник в той же `identitySpace`; неподтверждённый child-source не считается доступным.
- В одной конфигурации rootSlug, graphFile, planFile и identitySpace уникальны. Переключение запрещено пока исход предыдущей записи неизвестен. Admin grants как и прежде — отдельная opt-in capability, не включена автоматически.

## Пример локальной настройки (синтетические пути, без токенов)

В отдельном доверенном JSON-файле, не в `graph.json` и не в `graphs/index.json`:

```json
{
  "schemaVersion": 1,
  "contexts": [
    {
      "rootSlug": "workspace-a",
      "graphFile": "workspaces/workspace-a/graph.json",
      "planFile": "plans/workspace-a/plan.json",
      "identitySpace": "workspace-a",
      "rootRequirementId": "R0"
    },
    {
      "rootSlug": "workspace-b",
      "graphFile": "workspaces/workspace-b/graph.json",
      "planFile": "plans/workspace-b/plan.json",
      "identitySpace": "workspace-b",
      "rootRequirementId": "RB"
    }
  ]
}
```

Значения должны совпадать с **реальным** каталогом и Graph owners. Соответствующие Plan owners должны **уже существовать**, быть созданы штатным Plan writer, иметь подходящие `identitySpace` и текущие права `plan.read/plan.edit`. Конфиг не создаёт Plan, grants или новые каталоги.

Пример для оператора с уже разрешённой локальной средой:

```sh
python3 -B tools/rdg-workflow-helper.py --manual-session \
  --root /existing/plan-owner --contexts-file /trusted/local/workspaces.json \
  --store /existing/grants.json --session-dir /existing/authorized/new-session-folder
```

`RDG_AUTH_TOKEN` находится только в доверенном окружении процесса; его **не надо** копировать в Viewer или этот файл. `--contexts-file` относится к файловому transport, не к loopback UI. Старый однорабочий запуск `--graph ... --file ...` сохраняется. В Viewer подключите session-папку обычным способом один раз; затем выбирайте большой граф из каталога. У графа без настроенного плана отображается «план не подключён», а не предыдущий Plan.
