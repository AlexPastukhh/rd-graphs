# RDG: рабочий учебный Graph = обычный рабочий Graph (source 2.4.8)

## Текущее состояние после полного сброса — 2.4.8

**Решение пользователя после промежуточной демонстрации 2.4.6:** локальный граф R должен всегда показывать все связи, без второго переключателя; искусственный `C-ASSURANCE` не нужен. Для учебного графа выполнена **полная очистка старого Graph, Plan и Gendocen владельцев с их историей**, затем штатный builder создал их заново через авторизованные API. `C-ASSURANCE`, его `CONTEXT_FOR` и все события о них отсутствуют **даже в журнале текущего учебного Graph**. Graph r10 содержит только R/Action, Plan r4 содержит три реальных размещения. Читателю доступны 18 вновь созданных provenance rows, 14 основных карточек, 7 целей отслеживания Gendocen и три `review_required`.

Теперь учебный Graph перечисляется в **«Папки → Примеры»** (каталожный folder override); физическая каноническая запись остаётся под `graphs/workspaces/` из-за ограничения реального Graph API. Повторить reset можно только явной командой и подтверждением имени. [Граница удаления, команда и ограничения типов](RDG-TEACHING-EXAMPLE-RESET.md). Обычные Graph owners нельзя так сбросить. По умолчанию `candidate-v6` позволяет создавать только R и Action; Context — отдельная регистрируемая возможность, выключенная у этого примера. Установленный пользовательский Viewer 2.4.8 не подтверждён.

Следующий раздел о 2.4.6 — **история прежнего промежуточного состояния**, не текущее содержание учебного Graph.

## АРХИВ: временный пример с контекстом 2.4.6 — **не использовать как инструкцию**

Сведения до раздела «Как открыть опубликованные реальные данные» ниже описывают **удалённое состояние**. `C-ASSURANCE` и его события отсутствуют в текущем Graph. Переключателя связей локальной R больше нет; кнопки и маршруты этого блока устарели. **Применять только [текущий контракт 2.4.8](RDG-CURRENT-STATE.md)**.


**Проверено на настоящем рабочем Graph.** Изначально все его семь связей относились к `DRIVES` или `INTRODUCES` — поэтому «Основные связи» и «Все связи и контекст» действительно не имели видимой разницы. Это был пробел в примере, а не повод выдумывать новые типы отношений.

`tools/rdg-extend-teaching-context.py` добавил **через штатный авторизованный Graph writer**, отдельными CAS-транзакциями с notes/receipt/journal, один Context `C-ASSURANCE` («Условие выбора: учитывать актуальность требований и канонов») и три настоящие связи `CONTEXT_FOR`: к `A-DESIGN`, `A-CANON`, `A-VERIFY`. Исторический Graph **revision 14**, девять исходных R/Action/Context узлов, три новые связи помимо семи `DRIVES/INTRODUCES`; записаны четыре новые транзакции API r11–r14. В истории: `context_added`, затем три `context_link_added` — **производные семантические названия** из принятых состояний до/после, не новые неподтверждённые события. В сохранённом `graph.events` присутствуют настоящие `graph_changed` с текстовыми notes. Исходные четыре `action_selected/requirement_reformulated` и критерии выполнения не изменены.

**ИСТОРИЧЕСКИЙ МАРШРУТ, БОЛЬШЕ НЕ РАБОТАЕТ:** открыть «Папки → Рабочие графы → Рабочий пример», перейти в полный граф Requirements. Нажать `R0`, `R-CANON` или `R-VERIFY`, чтобы открыть локальный одноволновый граф. В выпадающем меню будут **«Основные связи»** и **«Все связи и контекст (+1)»**. В основных связях сохраняются R и Actions; во втором режиме дополнительно появляется `C-ASSURANCE` и ровно одна стрелка к соответствующему выбранному Action. Общий контекст не подтягивает в локальный граф Actions других волн: traversal ограничен одной структурной волной и одной вспомогательной связью от неё. В разных локальных графах работают соответственно `C-ASSURANCE → A-DESIGN`, `→ A-CANON`, `→ A-VERIFY`.

Публикация офлайн-чтения в тот момент была обновлена **только после успешных транзакций** и реального Gendocen refresh; Plan owner остался **r4** (поскольку новые Context/links не являются placement или выполнением). Историческая версия истории содержала **22 реальные provenance-записи**, сгруппированные Viewer в **18 основных карточек**; Gendocen по-прежнему содержит 7 dependency targets и три `review_required` по `A-CANON`, `A-CANON-ALT`, `A-VERIFY`. При редактировании Graph будущий устаревший bundle-снимок **не выдаётся за актуальный**, но не блокирует запись нового Graph — после неё требуется новая явная публикация snapshot. QA: `tests/visual/rdg-graph-scope.cjs` проверяет оба режима всех трёх R, число стрелок, изоляцию волн, отсутствие ошибок страницы; `tests/rdg-active-example.test.cjs` проверяет реальные Graph receipts, owner/Plan и опубликованные snapshots; `tests/visual/rdg-active-example.cjs` — Graph/Plan/Gendocen live/loopback.

**Историческое поведение 2.4.5 (до удаления локального переключателя):** в полном Requirements-обзоре блок «ГРАФ R» (двойная рамка) означает вход в одноволновый локальный граф этой R — он не является отдельной записью нового типа и не означает, что существует файл на каждую R. Из полного обзора нажмите `R-CANON`: откроется её настоящий локальный Graph с R и Actions. В локальном графе обычные R-блоки имеют одинарный контур, а переключатель «Основные связи / Все связи и контекст» никогда не скрывает Actions. Нажатие дочерней R внутри локального графа переходит к следующему локальному графу, полный обзор возвращается через breadcrumbs. `tests/visual/rdg-graph-scope.cjs` проверяет все эти переходы с настоящим учебным graph owner и отсутствие JS ошибок.

## Семантика событий в Plan — Viewer 2.4.4

Карточки теперь подписаны по принятой **операции**, а не только по техническому `graph_saved`: «Создан рабочий Graph», «Добавлен кандидат Action», «Создана Requirement», «Подготовлена потенциальная Requirement», «Активирована Requirement», «Выбран Action», «Переформулирована Requirement» и т. п. Writer не создавал задним числом новых событий: `changeKind` вычислен по неизменяемым `before/after` в журнале; при недоступных доказательствах остаётся универсальное название. `Action-selected` не означает завершения, а `Requirement-added` не означает достижения. Выбор декомпозиции уже ввёл `R-CANON`, `R-VERIFY` **внутри одной транзакции выбора**, поэтому R не требуется дополнительно «выбирать». В карточке выбора видны обе введённые R, их роли и переходы в Graph. В другом рабочем графе Action может активировать уже подготовленные `potential/candidate` R: reader честно показывает предыдущий статус, а не приписывает повторное создание R. История Plan по-прежнему отдельно фиксирует их размещение во времени, выполнение Action / достижение цели требуют своих критериев.

Техническая строка о сохранении Graph и `action_selected` остаются в исходном journal, но Reader/Viewer **визуально объединяет** их в одну смысловую карточку, а ревизии и `transactionId` доступны через «Технические сведения о транзакции». Первые три транзакции текущего примера = создание Graph r1 → новый кандидат `A-DESIGN` r2 → альтернативный кандидат `A-DESIGN-ALTERNATIVE` r3. **На этапе 2.4.4 это было 18 записей источника → 14 основных карточек; после добавления Context в 2.4.6 — 22 → 18.** Offline bundle повторно опубликован реальным reader, online Helper использует те же выводимые типы. Браузер и writer проходят адресные E2E.

## Что действительно произошло

Graph revision **14** (8 R/Action блоков и 1 Context), записанный по одной Graph writer транзакции на изменение. Начальная корневая Requirement — «Сделать проверяемую рабочую демонстрацию зависимостей RDG». Создан Action `A-DESIGN` (выбранная декомпозиция), альтернативный `A-DESIGN-ALTERNATIVE` остаётся кандидатом. Реальное событие `action_selected` для `A-DESIGN` привело к двум подцелям `R-CANON` и `R-VERIFY` через настоящий `INTRODUCES`/`DRIVES`. Для `R-CANON` созданы `A-CANON` (выбран) и `A-CANON-ALT` (кандидат с самостоятельным каноном); для `R-VERIFY` выбран `A-VERIFY`. Эти выборы оставили **три отдельных** подписанных события `action_selected` (не события выполнения).

Plan revision **4** был создан отдельным штатным owner writer как действительный **пустой Plan r1**. Затем три принятых CAS-транзакции разместили `R-CANON`, `A-CANON`, `R-VERIFY` на даты в ноябре 2026 г. Каждый placement ссылается на настоящий узел этого Graph. `A-VERIFY` выбран, но **не размещён**; `A-CANON-ALT` остаётся альтернативой и не является обязательным запланированным Action. Отсутствие размещения не равняется выполнению.

Gendocen зарегистрировал реальные `semantic_review` подписки на канон `A-CANON` с `checkRequirements: ["R-CANON"]`, на канон `A-VERIFY` и на структурные `DRIVES`/`INTRODUCES`. Для **семи** зависимых объектов принят исходный baseline: Gendocen сохранил **7 реальных receipts**. Затем очередная авторизованная `graph_edit.reformulate_requirement` изменила R-CANON: из «Проследить, какие способы зависят от актуальности канона» на «Проверить каноны с учётом новой редакции требований». В Graph появляется `requirement_reformulated` с **обоими снимками** и реальным writer `recordedAt`; в Gendocen после повторного пересчёта появились **три** `review_required`:

- `A-CANON`: выбранный Action, чей канон использует изменившуюся R.
- `A-CANON-ALT`: кандидат-альтернатива, зависящий от той же R через `DRIVES`; её канон **не** объявлен выбранным.
- `A-VERIFY`: выбранный Action с явной `checkRequirements` на R-CANON.

Остальные четыре зависимых объекта остаются `valid` относительно принятого engine baseline, но это **не** сертификат бизнес-корректности. Review-событие не меняет статус Action на неверный и не выполняет его автоматически.

**Чего НЕ произошло:** ни один `action_executed` и ни один `requirement_achieved` не были записаны; `R0` и дочерние Requirements всё ещё требуют фактической работы и собственных доказательств завершения. В учебном графе не рисовали вымышленные исторические блоки. История, доступная через Helper, содержит **14 настоящих Graph writer сохранений**, **3** `action_selected`, **1** `requirement_reformulated` и **4** события отдельных версий Plan owner (создание + 3 размещения) — **22** подлинные записи provenance, показанные в source 2.4.6 как **18 основных карточек** (технический `graph_saved` объединён с семантическим событием той же транзакции). Временная последовательность и фактическое время каждого события происходят от журналов writer, а не от демонстрационного JSON.

## Как открыть без обхода прав

Убедитесь, что ваш обычный локальный bearer действительно разрешает **`graph.read`** для `workspaces/requirements-dependencies-demo/graph.json`, `plan.read` для `plans/requirements-dependencies-demo/plan.json`; любые будущие изменения потребуют отдельных `graph.write`/`plan.edit` прав. **Сборщик не создаёт полномочия для пользователя и не изменяет его существующее хранилище grants.** Создание пользователем новых scopes — отдельное явное административное действие.

В Viewer **2.4.3**: открыть «Папки → Рабочие графы → Рабочий пример · зависимые Requirements и Actions», затем вкладку **«План во времени»**. Если локальное чтение доступно, Plan открывается из настоящего файла даже без Helper (только чтение; Graph event snapshots + версии Plan, без подтверждения всего writer-journal). Для живой проверки и записи Gendocen подключить обычный локальный Helper к **тем же owners**. Например, когда уже есть grant, переменные `RDG_AUTH_STORE`, `RDG_AUTH_TOKEN`, `RDG_GENDOCEN_SOURCE` и отдельный новый локальный session folder:

```sh
python3 tools/rdg-workflow-helper.py --manual-session \
  --root /ABSOLUTE/PATH/TO/rd-graphs \
  --auto-workspaces --transport files \
  --session-dir /ABSOLUTE/PATH/TO/NEW-PRIVATE-SESSION \
  --gendocen-project /ABSOLUTE/PATH/TO/rd-graphs/.rdg-gendocen-projects
```

`--auto-workspaces` привяжет Plan owner по published fullGraph и выберет для него **существующее** engine state `<gendocen-project>/requirements-dependencies-demo`. Отдельный проект Gendocen необходим, иначе вкладка «Зависимости» честно покажет «недоступны», не «0». Через вкладку **«Зависимости»** можно раскрыть реальные affected Actions, перейти в Graph и отдельно прочитать engine event/receipt history. Прямой loopback Helper использует тот же Graph/Plan/Gendocen и ту же авторизацию.

## Одно активное семейство моделей

Исторические `graphs/examples/**`, `graphs/2d/**`, старый `graphs/workspaces/try-it/graph.json` остались **неизменёнными** для возможного *офлайн* разбора/миграции. Они **не отображаются в активных папках**, не входят в JS bundle рабочего Viewer, не открываются загрузкой JSON и не могут изменяться через штатный Graph writer. Legacy Plan reader для них удалён из активного Helper. Миграция старого проекта, если понадобится, будет **отдельным** явным процессом; старые `Decision/Option` не остаются вторым режимом текущего приложения.

`tests/rdg-active-example.test.cjs` проверяет эти запреты и подлинность журналов; `tests/visual/rdg-workspace-plans.cjs` отдельно использует второе временное `candidate-v6` scope только в браузерной памяти для регрессии переключения **A→B→A** (не создаёт фальшивый второй канонический Graph).

**Проверенный локальный HTTP Helper:** в Source 2.4.2 исправлена отложенная инициализация Viewer: `ui.js` запускает штатный каталог через `host.rdgStart()` после подключения к HTTP-сессии.
