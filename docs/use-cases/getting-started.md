# RDG — начать пользоваться и вести решение

> **СТАТУС: ДЕЙСТВУЮЩИЕ ПОЛЬЗОВАТЕЛЬСКИЕ МАРШРУТЫ.** Основной профиль — `rdg-decision-v1`; точная доступность конкретного UI зависит от установленного `buildId`. Эти UC не запускают обновление Windows и не мигрируют данные.

## UC-RDG-001

**Когда:** человек хочет открыть RDG, увидеть свои процессы и начать работу; либо ему нужна отдельная песочница для знакомства с интерфейсом.

**Цель:** попасть в корректный Viewer с реальными правами на выбранный процесс, отличая живой сервер от preview.

**Предпосылки:** RDG уже установлен на компьютере владельца в режиме Local либо имеется действующий HTTPS-доступ. Для **остановленного, но уже установленного** сервера владелец может использовать штатный `Start-RDG.ps1` **из своей проверенной распакованной сборки** с теми же настройками Local/HTTPS и выбранным рабочим Docker согласно [регламенту запуска](../guides/RDG-OPERATIONS.md#запуск-на-fortis_m); скрипт не просто открывает вкладку, а запускает/собирает сервисы и проверяет окружение, поэтому выполняется владельцем осознанно. Учётные данные предоставляются владельцем, не через чат. Первичное развёртывание и **обновление сборки** — отдельные операторские процедуры, **не** этот UC.

**Как:**

1. Для Local на самом Fortis_M открыть `http://localhost:18880`. Для HTTPS использовать **фактический согласованный домен** своего RDG, не придумывать адрес. При запросе браузера указать логин `rdg`; пароль владелец берёт приватно согласно [регламенту](../guides/RDG-OPERATIONS.md#запуск-на-fortis_m), не присылает в чат.
2. Убедиться, что открыта именно RDG-страница, а не ошибка браузера/старый preview. В Explorer выбрать «Графы / Пакеты» → нужный процесс либо создать новый рабочий процесс через разрешённый интерфейс. Профиль и доступность операций определяются выбранным owner.
3. Переключиться между «Граф» и «Структура», открыть сведения выбранного Decision, «Контекст процесса», затем Plan / History. Это разные виды **одних** данных; положение блока и размещение в Plan сами по себе не являются выбором/исполнением.
4. После внешней записи через API нажать «Обновить» в Viewer; если обновлялся сам интерфейс — F5. Проверить, что выбраны нужный owner и актуальная ревизия, а не архивный read-only снимок.
5. **Отдельный учебный вариант**, не заменяющий рабочий сервер: из **существующей локальной копии проекта на компьютере пользователя** запустить `Start-Decision-Preview.cmd`. Он открывает отдельный Decision preview с собственной песочницей и данными `%LOCALAPPDATA%\RDG-DecisionPreview\data`; не переносит туда серверные процессы. [Порядок preview](../guides/RDG-OPERATIONS.md).

**STOP / UNKNOWN:** сервер не отвечает, порт занят, нет учётных данных, другой `buildId`, отсутствуют права, неизвестен реальный HTTPS-адрес или показан лишь offline snapshot — **не** очищать данные/volumes, не создавать новый namespace, не считать пустой экран успехом. Сообщить оператору конкретный сбой; [раздел диагностики](../guides/RDG-OPERATIONS.md#запуск-на-fortis_m).

**Готово:** Explorer открыл нужный owner, доступны Graph/Structure и сведения, Plan/History отражают реальное состояние; режим live/preview известен. **Граница:** browser UI/Windows ещё требует отдельной пользовательской приёмки после релиза; Linux CI не доказывает её.

**Владельцы и тесты:** [Viewer](../guides/VIEWER-EXPLORER.md), [операции](../guides/RDG-OPERATIONS.md), [браузерные проверки](../../tests/visual/README.md).

## UC-RDG-002

**Когда:** пользователь разбирает задачу с несколькими вариантами, фиксирует основания выбора, меняет исходные условия или пересматривает Decision.

**Цель:** сохранить *обоснованную* рабочую ветвь, не путая возможные варианты с принятым решением, а Plan — с выполнением.

**Предпосылки:** выполнен [UC-RDG-001](#uc-rdg-001), открыт подходящий `rdg-decision-v1` owner с разрешёнными операциями.

**Как:**

1. Зафиксировать главную Requirement и её основания. На бумаге можно создавать длинные непринятые ветви Decisions/Actions; структурно запрещён только D→D как родитель, но предметные зависимости между Decisions возможны. Не принимать все дочерние решения автоматически.
2. Сохранить Context в общем банке и вложенных группах. У выбранного Decision объяснить роль источников через комментарии и provenance; «Теорию принятия решения» (технический `canon`) использовать как нормативную/теоретическую опору: «Каноны», свободное «Общее», именованные «Известные ошибки». Старый текст доступен в «Общем»; редактирование одинаково из Graph/Structure. Теория сама не доказывает исполненный результат.
3. Записать Findings **для конкретного Decision** (например, риск или возражение); это утверждения с собственными источниками и review, а не скрытый resolve/proposal workflow. Самостоятельные Questions, ответы и оценки достаточности редактируются в панели «Вопросы» через предварительную проверку. Старые встроенные вопросы переносятся явно. Оценки сложности/времени Action сохраняются отдельно от результата исполнения.
4. Посмотреть «Зависимости» → источники/влияния, затем «Инвалидация». Если исходные условия изменились, прочитать конкретные reasons review и disabled applications, пересмотреть Decision отдельно от реактивации политики. Не объявлять stale доказанной ошибкой или автоматической отменой выбора.
5. При использовании готового графа или линзы выбирать уместный способ работы и объём сохраняемого результата по [семантическому контракту](../guides/RDG-ACTIVE-CONTRACT.md#готовые-графы-линзы-и-рекомендации); рекомендации помогают обратиться к методике без обязательного переноса её структуры при каждом использовании.
6. Только когда выбор действительно сделан, зафиксировать его явной командой. Plan допускает временные возможности/ветви; placement и даты не подтверждают completion. History и Graph readback нужны для проверки совершённого действия.

**STOP / UNKNOWN:** если нет оснований для выбора, не отмечать selection/completion; если статус review или источник неясен, сохранить неопределённость и обратиться к исходному событию/версии; при отказе writer не пытаться обойти его ручным редактированием JSON.

**Готово:** в одном owner читаются Requirement, альтернативы, контекст, Canon/Findings, зависимости и причины review; выбранное/невыбранное и план/выполнение различимы. События и ID подтверждаются readback.
