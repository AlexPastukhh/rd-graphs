# RDG — работа ИИ через API и продолжение после обрыва

> **СТАТУС: ДЕЙСТВУЮЩИЕ МАРШРУТЫ ПОДГОТОВЛЕННОГО ДОСТУПА.** Проверенный API-контур существует; качество полностью автономного ИИ-прохождения по завершённым линзам **не принято** — [backlog T7](../../BACKLOG-IMPROVEMENTS.md). Эти UC не выдают себе права, не устанавливают сервер и не изменяют live линзы без поручения владельца.

## UC-RDG-003

**Когда:** пользователь даёт ИИ практическую задачу — исследовать альтернативы, вести требования/решения, фиксировать Context/Findings/Questions и проверять результат в RDG.

**Цель:** выполнить разрешённую предметную работу через настоящий Application API, без ручной сборки JSON пользователем и без подмены существующих owners.

**Предпосылки:** ИИ работает из допущенного Fortis Repo Docker; владелец заранее подготовил работающий private gateway и несекретный `/workspace/repo/Workfiles/rdg-gateway-context.json`. Это **доступ контейнера**, а не специальный доступ каждого чата. Правила Fortis/GitHub — в контейнерных `UC-CONT-002`/`UC-CONT-003`, GitHub и RDG — разные эффекты.

**Как:**

1. Из `/workspace/repos/rd-graphs` проверить подготовленный API, затем прочитать каталог. Никаких секретов в аргументах или тексте запроса:

   ```sh
   python3 -B tools/rdg-agent.py doctor --context /workspace/repo/Workfiles/rdg-gateway-context.json
   python3 -B tools/rdg-agent.py catalog --context /workspace/repo/Workfiles/rdg-gateway-context.json
   ```

2. Выбрать **реальный** owner, прочитать `coreModel`, идентификаторы и `commandAccess`; для новой рабочей задачи запросить `schema --action create`, по умолчанию `rdg-decision-v1/working`. Существующий owner не пересоздавать. Получать нужные summary/item/facets; для существующего фокуса использовать detail=focus, для всего структурного продолжения R/Decision — detail=branch. Agent --all-pages собирает выбранные секции одного снимка; без него продолжения видны явно. Режимы сначала проверить через schema(read), установленный runtime может быть старее исходников. [Команды и границы](../guides/RDG-AGENT-BOOTSTRAP.md#адресное-чтение-фокуса-и-ветви); полный Read/History — при необходимости.
3. Для каждого действия сначала получить штатный `schema`; по матрице API сформировать request с UUID transactionId и предметным основанием. При записи использовать **`preflight → command/apply` с неизменным request и точным `expectedInputBinding`**, затем `receipt → readback`. Несколько связных шагов можно объединить через `batch` в пределах опубликованных schema capabilities (первый срез T2: до 100 шагов, Graph перед Plan).
4. Отличать Requirement/Decision/Action, общие Context, Canon и Findings; Questions документируют неопределённость и проверенные/непроверенные ответы. Не выбирать альтернативы, не записывать выполнение и не объявлять результатом только потому, что они появились на бумаге или в Plan. По [смыслу линз](../guides/RDG-ACTIVE-CONTRACT.md#готовые-графы-линзы-и-рекомендации) выбирать ознакомление, уточнение или прохождение методики, сохраняя уместные результаты по C1/C2/C3; вставка графа и запись каждого применения для этого не обязательны. Наличие source definition не означает live installation или адресную рекомендацию всем элементам.
5. После изменения источника читать конкретные причины stale/review, а не строить второй алгоритм инвалидации. При существенном запросе ответа пользователю выполнить checkpoint: проверить сведения, попытаться ответить самостоятельно, пометить гипотезы и задать только действительно необходимые вопросы. В обычном чате checkpoint не нужен перед каждой репликой.
6. Сообщить пользователю, что принято writer, что остаётся предположением и какие настоящие `packageId`, revisions/receipt и вопросы позволяют продолжить. Для Viewer обновить данные через «Обновить».

**STOP / UNKNOWN:** `doctor` FAIL, неизвестная версия/owner, отсутствующие capabilities или grant, конфликт CAS, ошибка gateway или неопределённый результат транзакции — не создавать новый токен, обходной transport, иной transactionId для *той же* попытки и не править owner-файлы напрямую. При неизвестном результате использовать [UC-RDG-004](#uc-rdg-004).

**Готово:** реальная операция прошла проверку права/смысла, receipt и независимый readback согласованы; user/AI знают, что выбрано, а что остаётся гипотезой. **Не утверждать**, что полный автономный сценарий T7 уже принят.

**Владельцы и тесты:** [вход ИИ](../guides/RDG-AGENT-BOOTSTRAP.md), [точный API и матрица](../guides/RDG-DECISION-V1-CONTRACT.md#матрица-операций-api-для-ии), [gateway и авторизация](../guides/RDG-OPERATIONS.md#private-api-для-ии), [API discovery](../../tests/rdg-api-discovery.test.py), [T1/T2 workflow](../../tests/rdg-t1-t2-workflow.test.py).

## UC-RDG-004

**Когда:** ИИ/оператор отправил запись, но соединение оборвалось, ответ потерян или следующий запрос получил CAS/input-binding конфликт.

**Цель:** выяснить, была ли принята **эта же** транзакция; не создавать двойной эффект и не терять её историю.

**Предпосылки:** сохранены точные request, transactionId, prior preflight/inputBinding и доступ к **тому же** owner/namespace; не пытаться восстановить только по воспоминаниям чата.

**Как:**

1. Не объявлять операцию ни успешной, ни проваленной только по network timeout. Прочитать `receipt` по **прежнему transactionId**, затем текущее состояние и ревизии владельца.
2. Если receipt подтверждает accepted/published — проверить именно его effects и readback; повторная запись с новым ID **не нужна**. Если принято, но исполнение не завершилось, использовать разрешённый `recover` старого принятого payload по [операционному контракту](../guides/RDG-OPERATIONS.md), не готовить новое содержимое.
3. Если операция не принята и разрешён **exact retry**, повторить **тот же request и transactionId**; при изменившемся read set получить новый preflight и новый request/transactionId только для **нового логического действия**, осознанно согласовав изменения.
4. При `PREVIEW_INPUTS_CHANGED`/CAS перечитать текущий owner, сохранить независимые параллельные изменения и решить вопрос новой попытки без скрытого overwrite.

**STOP / UNKNOWN:** неизвестные права, receipt/recovery недоступны, несовпадение namespace/owner, неподтверждённая прошлaя acceptance, утерян точный request — остановиться и сообщить конкретную неопределённость, не «восстанавливать» эффект прямой правкой JSON или новым create с похожим path.

**Готово:** известен статус старой транзакции либо зафиксирован честный blocker; повтор не создал лишний Graph/Plan эффект, последствия видны в receipt/readback/History.
