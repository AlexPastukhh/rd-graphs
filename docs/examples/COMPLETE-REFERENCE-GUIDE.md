# Связанные графы Requirements–Decisions: бронирование переговорных

Редакция учебных графов: revision 3, 2026-10-13. Вход: `graphs/examples/reference-complete-app/graph.json`.

Один файл раскрывает один основной R: ответы D, дочерние R, основания и связанные записи. Сам основной R может присутствовать в родительском графе с тем же ID. Название графа соответствует его R.

Это условный сюжет, а не принятые решения реального приложения. Все SH-графы read-only / exampleOnly / hypothetical; selectedInProject=false. Редакция примера не является реальным пересмотром D пользователя. Исходный EX-документ и 2D-заготовки сохраняются отдельно.

В семи файлах — **73 записи узлов (включая ссылки на те же R/D), 73 связи и 17 именованных типов Viewer**. Это покрытие текущей проекции и существенных случаев исходника, а не обещание реализовать любую будущую возможность. Writer принимает семь типов: DRIVES, INTRODUCES, DERIVES, CONTEXT_FOR, APPLIES_TO, OPTION_FOR, OUTCOME_OF. Остальные отношения исходного корпуса Viewer показывает как иллюстративные.

## 1. Каждый граф — по одному R

| Граф | Корневой R | Основное содержание |
|---|---|---|
| Спланировать приложение бронирования | SH-R-APP | D о составе: функциональность, сценарии, реализационные ограничения |
| Расписать функционал | SH-R-FUNC | Готовое PER_ITEM 1..N, точные две Features, реальные части описаний Scenario как основания, один общий выбор Behavior |
| Описать сценарии | SH-R-SCENARIOS | Создание и отмена; конкретный ответ отмены и получатель делегации создания |
| Определить реализационные ограничения | SH-R-REALIZATION | IDENTIFIES, DERIVES, один сквозной R и области APPLIES_TO |
| Проработать Feature Availability | SH-R-FEAT-AVAIL | Прямой локальный ответ, условный состоявшийся пересмотр, ссылка на общий Behavior и отдельный локальный State |
| Проработать Feature Reservation | SH-R-FEAT-RES | Локальный Behavior, ошибки из общего контракта, тот же D-STATUS, ответ занятого слота, другой локальный State, pending пересмотр |
| Описать сценарий создания бронирования | SH-R-SCREATE | Подробный ответ в SH-TM-SCREATE, выявленная функциональная потребность, статусный способ с явными условиями достаточности |

Шесть переходов между R-уровнями вычисляет graph-index.py: выбранное INTRODUCES → rootRequirementId того же R в общем identitySpace. Новые информационные ссылки **не** превращаются в эти parent-child переходы. Старые EX-проекции и DEMO-цепочка имеют свою роль и не сливаются с SH-сюжетом.

## 2. Как пройти существенные смысловые случаи

1. Открой **Примеры → Связи графов → Связанные графы R · 1. Приложение**, затем SH-R-FUNC.
2. Сравни готовое правило 1..N и SH-D-CHOOSE-FEATURES: только последнее вводит две конкретные R. Готовая TM-FEATURE определена одна; её условных применений две.
3. На том же уровне выбери INFORMS:
   - SH-D-DESCRIBE → SH-D-CHOOSE-FEATURES использует SH-CREATE-SLOT и SH-CREATE-CONFIRM;
   - SH-D-CANCEL → SH-D-CHOOSE-FEATURES использует SH-CANCEL-RESULT.
   Сценарии и Features остаются соседними ветками; использованный фрагмент ответа не создаёт дочернюю Feature.
4. Выбери SH-D-BEHAVIOR-SHARED. Его scope — Behavior **Availability и Reservation**. Это одно решение о форме. Оно отображается ссылками в двух Feature-графах. Локальные ответы этих Features и их State D различаются и не выбирают общую форму заново.
5. В Reservation проследи SH-R-BEHAVIOR → SH-D-BEHAVIOR-SHARED → SH-R-ERRORS. Parent локального R ошибок — общий R Behavior; это не новый Target Module.
6. Проследи SH-R-ERRORS → SH-D-STATUS и SH-R-RESULT → **тот же SH-D-STATUS**. Первый путь покрывает только потерю ответа в описании ошибок; второй отвечает функциональной потребности. SH-D-BUSY описывает другой случай — занятый слот. Полнота всех ошибок не заявлена.
7. В инспекторе SH-D-STATUS нажми **«Открыть источник»**: откроется тот же ID в Scenario Create. **«← К предыдущему графу»** возвращает в Reservation. Это информационный переход, не новый parent-child.
8. В Scenarios выбери SH-R-SCREATE: делегация указывает конкретный условный SH-TM-SCREATE, модель TM-SCENARIO-PLANNING, неизменный R-ID и внутренний ответ SH-D-DESCRIBE. Делегация не означает исполнения.
9. В Realization сравни IDENTIFIES с INTRODUCES, затем DERIVES и APPLIES_TO. Сквозной R один; внешние R являются ссылками, не созданными здесь копиями.
10. В Reservation SH-PR-STATE pending и RECONSIDERS относятся к общему D о форме. Новый контекст его не отменяет. В Availability, напротив, отдельное событие decision_revised описывает состоявшийся **условный** пересмотр.

## 3. Части ответа и граница достаточности

SH-D-STATUS имеет четыре адресные части:

| ID части | Содержание |
|---|---|
| SH-STATUS-UNKNOWN | Потеря/промежуточный ответ сохраняют неизвестность, а не становятся отказом |
| SH-STATUS-CORRELATE | Проверяется то же подтверждение; возможность корреляции требует evidence |
| SH-STATUS-FINAL | Подтверждение/отказ показываются только после установленного окончательного результата |
| SH-STATUS-NO-DUP | Повторное создание не является автоматическим способом получить ответ |

answerBindings показывает, какие части отвечают SH-R-RESULT, SH-R-FEEDBACK и части SH-R-ERRORS. Достаточность conditional / partial, evidenceStatus=unverified. QRPE SH-Q-STATUS partially-blocking только заключение о достаточности и реализацию способа; описание и обсуждение продолжаются. Закрытие требует реального контракта и проверки корреляции, окончательности и возможности установить результат после потери ответа.

Выбранный D, написанное описание и имеющееся ребро не доказывают работающий booking app.

## 4. Типы отношений и поддержка

| Тип | Пример | Поддержка writer |
|---|---|---|
| DRIVES | R → конкретный ответ D | Да |
| INTRODUCES | D → под-R с parent, который DRIVES это D | Да, только действующее committed D |
| DERIVES | Уточнение предмета R; отдельные локальные State R | Да |
| CONTEXT_FOR | Исходный контекст → общий выбор Behavior | Да |
| APPLIES_TO | Один сквозной R → две Feature R | Да |
| INFORMS | Часть описания Scenario → границы Features; потеря ответа → D-STATUS | Нет |
| IDENTIFIES | Выявление актуального реализационного R | Нет |
| REVEALS_NEED | Описание создания → функциональный R результата | Нет |
| USES_VARIANT | Общий выбор Behavior → готовый Behavior Path | Нет |
| OPTION_FOR | Готовые альтернативы для R | Нет |
| USES_PREPARED | Конкретное разбиение → заготовка 1..N | Нет |
| PER_ITEM_MODEL | Готовый способ → одна модель каждого элемента | Нет |
| GENERATES_ITEM_ROLE | Роль будущего R, не фактическая ветвь | Нет |
| INSTANCE_OF_MODEL | Модель → два условных применения | Нет |
| GOVERNED_BY_SHARED_CHOICE | Общая форма → разные локальные ответы | Нет |
| QRPE_FOR | Вопрос необходимости R / достаточности D | Нет |
| RECONSIDERS | Pending предложение → прежний действующий общий D | Нет |

## 5. Владение записью и её проекции

Повторённый узел с тем же ID и identitySpace содержит **projectionOf**:
- graphSlug — файл исходной смысловой записи;
- nodeId — тот же ID, без создания нового R/D.

Описание и основания читаются из владельца; инспектор показывает адрес источника и позволяет открыть его. Scope и нормативное requirementText проекция не меняет. Локальная подпись/пояснение не заменяет исходную формулировку. Это контракт текущего Viewer/index для проекций; writer не получил новые типы, автоматическое создание R-уровней или полный протокол делегации.

Индекс проверяет parent DRIVES, выбранность D, исключает template/candidate introductions, проверяет явные ссылки и конфликт нормативного смысла root identity. Для узла без projectionOf fallback statement — requirementText либо title. Для контекстной подписи используй явного владельца, а не иной смысл под тем же ID.

## 6. Проверки и ограничения

Генератор: tools/build-complete-reference.py; --check проверяет семь файлов. graph-index.py создаёт index/bundle. Новые проверки в tests/review-fixes-viewer.test.cjs сопоставляют **смысловые пути**, source links, части ответа и геометрию; tests/graph-index-contract.test.cjs проверяет контрпримеры индекса.

Viewer 1.1.1 разводит подписи с учётом узлов и других подписей; смещённые подписи имеют линии привязки к кривым. При reload свежий файл не заменяется старым bundle. Некорректная форма events отклоняется до изменения рабочего состояния.

Реальный Edge/Tampermonkey и bootstrap нового чата требуют отдельной приёмки. Этот пример не доказывает реальную инстанциацию SDS, runtime API, полноту evidence или внедрение всех отношений в writer. История и выборы SH условны; не копируй их в рабочий проект.
