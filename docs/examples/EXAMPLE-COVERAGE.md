## Модель — что источник реально подтверждает

- Unit планирует конкретное Requirement, **но не каждое R является отдельным Unit**. `Decision` — ответ в конкретном предмете/scope; контекст и другие D могут влиять на выбор, не становясь ложными ребрами `DRIVES`.
- `EX-D-APP` раскрывает семь **соседних** под-R, а не строгую временную последовательность. Потребности из `EX-D-SCREATE/SCANCEL/SLOOKUP` адресно влияют на `EX-D-FEATURES`.
- `EX-R-DESCRIBE-CREATE` при делегации в Scenario S-CREATE не переименовывается, не клонируется и не считается выполненным.
- `EX-R-RESULT` — функциональная потребность, отдельная от R «описать сценарий». `EX-D-STATUS` помогает в оговорённой части, но статус `неизвестно` нельзя превращать в отказ или доказанную завершённость.
- Готовый `Behavior Path` — вариант; `EX-D-BEHAVIOR` — его конкретный выбор для общего scope. `EX-PR-HYBRID/STATE` остаются pending в добавленном контексте, прежний D не отменён.
- `EX-E1/E2/E3` различают условные выбор, изменение контекста и подготовку кандидатов; это **не** реальные даты/коммиты приложения.
- Пересечения с другими Requirements, Target Module delegation, QRPE, Context и history не означают, что все вспомогательные объекты являются новыми нормативными Units.

## Один уровень — одно корневое Requirement: многоуровневая учебная проекция

**Уточнение после анализа:** любой **новый иерархический граф конкретного уровня** начинается с одного корневого Requirement. На его уровне видны возможные готовые способы и условно выбранное D; дочерние Requirements ведут на собственные уровни с **тем же ID R**. Это правило учебного нового представления; старые обзорные reference-графы пока остаются многообъектными историческими проекциями, не переписаны.

В исходном файле уже есть reusable variant против конкретного D (§4), дочерние R сценариев (§1), делегация одного неизменного R в Scenario TM (§3) и единый scope выбора на многие Feature Target Modules (§5). Существующие эталоны сохранены. Для недостающего случая добавлена **новая условная** иерархия, не текст из исходного v0.2:

1. **Уровень 1:** `reference-feature-root`. Корневое `DEMO-R-APP`: «Описать приложение». Примерное `DEMO-D-APP` вводит **нейтральное** дочернее `DEMO-R-FUNCTIONALITY`: «Расписать функционал». **Ни слова о том, что Features уже выбраны** на этом уровне. `DEMO-R-FUNCTIONALITY` повторяется как корневой R следующего файла; отдельная навигационная ссылка внутри узла не нужна.
2. **Уровень 2:** `reference-reusable-vs-concrete`. Его корневое R — **тот же** `DEMO-R-FUNCTIONALITY`. Для него возможны **два разные готовых варианта**: `DEMO-V-BY-FEATURE` (через Features, `PER_ITEM 1..N`, одна подготовленная `TM-FEATURE` Model) и `DEMO-V-OTHER` (иной подход, в примере через сценарии). Оба заготовлены, пока не приняты. Отдельный `DEMO-D-BY-FEATURE` — **выбранное только внутри условного примера** D. Оно вводит **ровно 4** конкретных дочерних R, а не диапазон `1..N`. Это одно D, не четыре одинаковых.
3. **Уровень 3:** четыре дочерних графа `reference-feature-auth/catalog/cart/payment`. У каждого корневое Requirement с ID **ровно тем же**, что было в родительском графе. На этом уровне можно видеть `TM-FEATURE` как готовую возможную модель и альтернативу; **никаких придуманных фактических Units или выбранных решений для Feature нет**.

В режиме **«Карточки»** папки «Примеры» показан только входной `reference-feature-root`; пять внутренних уровней помечены `catalogHidden=true`. В прежнем историческом срезе рассматривались **17 файлов** (цепочка DEMO, цепочка SH и четыре независимых); это не новое число файлов всей папки. Современные дочерние Unit-графы открываются по клику на R. Связь **вычисляется** по `INTRODUCES` (решение вводит R) и `rootRequirementId` (именно R — корень другого графа) внутри одного `identitySpace`. По клику на дочерний R навигация идёт в найденный отдельный граф, «← Уровень выше» возвращает по той же трассировке. Поля `nextGraphSlug`/`parentGraphSlug` из новой учебной цепочки удалены.

Кардинальность `1..N` — свойство **подготовленного варианта разбиения**, не число ветвей фактического графа. Условное D из уровня 2 имеет `concreteBranchCount=4` и четыре `INTRODUCES`. Подготовленная TM-FEATURE Model не копируется по числу Features; R сохраняют ID. При пятой Feature меняется условный фактический состав (после отдельного решения), не готовое правило. Наличие коллекции само по себе не требует создавать Target для каждой строки.

Все `DEMO-*` — **придуманные учебные ID**, не `EX-*` источника и не реальные принятые решения. Поля `rootRequirementId`/`identitySpace` используются в действующем индексе; `OPTION_FOR` поддержано writer в v7. Другие иллюстративные элементы старой цепочки (`USES_PREPARED` и сходные дополнительные связи) **не разрешены для записи** в рабочие графы. Историческая проекция не равна v7-контракту.

**Не смешивать с исходными заготовками 2D**: `graphs/2d/template-tm-2d-*/` хранит настоящие определения `TM-2D-*` и `RU-*`, без принятых решений. Для готового внутреннего разбиения отдельного Unit требуются исходные подтверждённые под-R, иначе их не придумывать.

## Текущие ограничения физического формата (важно!)

Reference-графы предназначены только для **просмотра и исследования**: `exampleOnly=true`, `readOnly=true`. Исторические проекции содержат описательные ребра `INFORMS`, `IDENTIFIES`, `REVEALS_NEED`, `QRPE_FOR`, `USES_VARIANT` и `RECONSIDERS`. Они полезны для старого материала, **но не являются разрешёнными типами рабочих связей**. Современный Viewer показывает подписи стрелок и инспектор; «Все связи» управляет вспомогательными ребрами, «Показать все варианты» — кандидатами. Прежняя классификация: `docs/examples/RELATION-SEMANTICS-AND-VIEW.md`.

В v7 `graph-apply.py` разрешает **семь** типов ребер: `DRIVES`, `INTRODUCES`, `DERIVES`, `CONTEXT_FOR`, `APPLIES_TO`, `OPTION_FOR` и `OUTCOME_OF`. `rdg-v7-model.py` дополнительно обрабатывает операции с вариантами, QRPE, композитом, Collections, выбранным D и изменением R; writer проверяет ревизию и события выбора. Это **не** означает поддержки каждого произвольного вспомогательного ребра старых диаграмм, полной делегации или исполнения Helper в браузере. Нельзя переносить произвольный тип связи в writable-граф в обход валидатора.

В исходном корпусе **нет отдельного законченного примера сквозного требования с ребрами `APPLIES_TO`** в нашем текущем физическом формате. Этот сценарий проверяется отдельно через рабочий пилот/тесты writer, а не выдаётся за источник из v0.2.

**Это ограничение реализации, а не дефект исходного документа.** Например, смешать все дополнительные драйверы с `DRIVES` было бы семантически ошибочно: часть драйверов — Context или конкретное содержание другой D.

Не считать reference-графы доказательством реализации описанного приложения. Источник сам отмечает непроверенными runtime-достаточность статуса, независимость Feature, реальную хронологию, стоимость и автоматическое извлечение из Markdown.

## Как пользоваться примерами в bootstrap

Основная точка входа для ChatGPT: `/workspace/repos/rd-graphs/docs/examples/EXAMPLE-COVERAGE.md` (индекс).
Точный источник: `/workspace/repos/rd-graphs/docs/examples/requirements-decisions-graph-examples-v0.2.source.md`.
Посмотреть в UI: кнопка «Граф R–D» → папка «Примеры» → **«Связи графов»** (схема связанных и независимых графов) или **«Карточки»** → нужный граф. Новая многоуровневая демонстрация: `Уровень 1 · Описать приложение` → клик `Расписать функционал` → готовые варианты и условный выбор четырёх ветвей → клик конкретной Feature.
Чтобы увидеть **17 исторических видов отношений**, открой архивный `reference-complete-app` и путеводитель `docs/examples/COMPLETE-REFERENCE-GUIDE.md`. Только семь типов прямо разрешены рабочим writer v7. Для конкретного вопроса об исходном файле достаточно прочитать **одну нужную секцию** и её reference-проекцию. Не загружать весь документ при каждом PLAN, не навязывать всю структуру App Definition другим проектам и не записывать иллюстративные `EX-*` в пользовательский пилот.

Граф `try-it` отдельно существует только для проверяемой записи; reference-графы не изменяются без явного запроса.
