### Текущий рабочий кандидат — разделение RDG-кода и данных, одно обновление + F5 (2026-11-03)

> **СТАТУС: CANDIDATE / подготовлен до изменений кода; не исполнен и не принят как разрешение на deploy.** Пользователь определил Need и границы ближайшего цикла: до **90 минут**, без написания нового watcher/dev-сервера/importer, с переиспользованием существующих компонентов; для этой разработки AI-код рассматривается как доверенный, можно сократить дополнительные AI-specific checks. Допустимо одно удобное ручное обновление Windows PowerShell и затем F5. Это ограниченное решение для разработки, **не** постоянное изменение политики доверенного Windows-деплоя из Fortis. Открытый вопрос о применении старого updater на основном доверенном Windows необходимо разрешить перед фактическим запуском (ниже).

> **Scope clarification:** это исторический RDG code-update candidate, а не описание текущего Fortis Sonar runtime. Упоминание `RUN_APPROVAL` ниже было предположением/требованием кандидата; действующий Fortis R7 сейчас выполняет Sonar `accept_issue`, но D3/D4 Windows Importer и owner RUN gate ещё не реализованы.

**Need / наблюдаемый сценарий:** AI изменяет **код RDG** в Fortis Repo → имеющийся CI собирает готовый runtime → владелец один раз вызывает готовую команду обновления → в существующей браузерной вкладке F5 открывает новый Viewer и backend. Отдельно AI создаёт/меняет **Graph/Plan/линзы/рекомендации** через действующий RDG API с receipt/readback; это не изменяет исходники и не требует CI/CD приложения. Эти две ветви нельзя смешивать. Пользовательские Graph/Plan/History/layout и grants переживают upgrade; никакой скрытой миграции.

**Действующие требования (основание: уточнения пользователя 2026-11-03):**

- **FR: code/data boundary.** В рабочем runtime никакие конкретные фундаментальные графы и глобальный список рекомендаций не должны требоваться для создания или чтения нового Decision-процесса. Schemas/kernel/API/Viewer — код. Содержимое фундаментальных и тематических графов, их рекомендации и версии — данные RDG с правами/CAS. Не удалять исторические файлы для Agent/fixtures без проверки их потребителей.
- **FR: one-command browser loop.** Не более одной повторяемой команды владельца на установку новой проверенной версии, затем F5 по ранее открытому адресу. Не требовать нового Dev Server, auto-reload Python или нескольких PowerShell-команд ради каждой правки.
- **FR: preservation.** Основной namespace, packageId/identitySpace, Registry, History/pins, Plan/layout, grants и data volumes не сбрасываются, не пересоздаются и не мигрируются неявно. Не удалять/не делать writable старые `supplied` owners этой задачей.
- **FR: timebox and trust.** 90 минут — верхний лимит попытки реализации; длительность полного CI/Windows неизвестна, запас не доказан. Отсекаем отдельный Sonar/security-аудит AI-кода и новую approval-инфраструктуру, но оставляем адресные проверки корректности, авторизацию API, сохранность данных, SHA/manifest и startup/readback. Ручной запуск владельцем не объявлять эквивалентом реализованного Fortis RUN_APPROVAL. Действующий Fortis §D3 по-прежнему требует owner RUN_APPROVAL для доверенного Windows; отдельное осознанное решение об ограниченном trusted-development исключении либо изолированный preview требуется **до установки**, но не мешает code/test части.

**Исходное фактическое состояние:** `tools/rdg-portable-service.py` вызывает `ensure_fundamental()` при `create(role=working, coreModel=rdg-decision-v1)`, импортирует JSON из `tools/rdg-agent-lenses` и добавляет `fundamental-all`. ZIP упаковщик `tools/rdg-server-package.py` включает эти JSON. `tools/rdg-ci.py --watch` уже работает, fingerprint следит за source в tools/tests/deploy/docs; запись данных через API в отдельный FileStore не запускает CI. `Update-RDG.ps1` уже имеет режим **без** `-Watch`: копирует ready ZIP, проверяет размер/hash/manifest, вызывает `Start-RDG.ps1` и сверяет buildId через `/healthz`. Сервер отдаёт JS с `Cache-Control: no-store`, **но** `tools/rdg-server.py` генерирует новый случайный `/session/<cap>/` после restart: F5 в старой вкладке сейчас может попасть на `SESSION_DENIED` (исправить). В `tests/rdg-portable-service.test.py` зашито `len(effectOwners)==13`; после расширения исходных линз это неустойчивое условие. При составлении плана `ready.json` соответствует старому sourceSHA; текущий watcher выдал ошибку теста portable-service. У RDG-кода и документации много уже незакоммиченных/частично staged правок — ничего не reset/clean и не переписывать целиком.

**План реализации и проверка, с ограничением 90 минут (временные окна — бюджет, не измеренные обещания):**

| Окно | SRU / действие | Исполнитель | Проверяемый выход / gate |

| **0–10 мин** | Read-only: сверить `git status`, CI ready/status/source hash, текущие вызовы `ensure_fundamental`, конфигурацию существующего updater, список живых owners только при доступном API. Зафиксировать исходные тестовые IDs. | AI; пользователь только если требуется доступ к Windows | Не менять live registry/volumes/grants; не выдавать старую сборку за новую. После проверки runtime callers — убрать lens JSON из **серверного** пакета, оставив исходные определения для Agent/fixtures до отдельного перехода. Volatile view state может сброситься, persistent Graph/Plan не должен. |
| **45–65 мин** | **Адресная регрессия:** заменить `effectOwners=13` проверкой типизированного read/effect set; проверить создание без seed, старые supplied read-only, управляемую lens и рекомендации, сохранение Plan/History/layout на отдельных fixtures, server route, CI unit. **Историческая развилка кандидата перед Windows (не текущий Fortis status):** прежний текст предполагал наличие Fortis `RUN_APPROVAL`; это предположение не является свидетельством реализованного D3/D4 RUN gate. Текущий Fortis R7 approval для Sonar не подключён к старому `Update-RDG.ps1` и не разрешает автоматически устанавливать RDG code. D3/D4 Windows Importer + exact SHA admission + owner RUN остаются будущими задачами. Для этого RDG кандидата Windows upgrade не разрешён данным документом; автоматический `-Watch` не запускать. Не получать host Docker socket, token или Windows shell через Repo.

**Не входит в этот часовой цикл:** замена модели ролей/версий `supplied`; миграция 11 старых + 4 новых линз; полная смена API/UX Registry; отдельный CI/CD для содержимого линз; постоянный dev-сервер, Python hot reload, HMR; новый Fortis Importer; общий рефакторинг dirty worktree; пользовательские тематические примеры. Следующий цикл — инвентаризация установленных линз и управляемый переход на API с сохранением historical pins. Source JSON остаются архивным/редакционным материалом только после проверки потребителей; считать устранением зависимости от runtime можно лишь фактическую проверку серверного ZIP.

**Контроль объёма и stop rules:** к 45-й минуте не начинать новые функции, если F5 gate не закрыт; к 65-й минуте не начинать масштабную миграцию или рефакторинг; к 80-й минуте установить только точный READY или остановиться. Изменение docs в этом репозитории также меняет fingerprint текущего CI watcher: запись **этого плана** может вызвать очередную попытку CI, что не является готовым релизом и не санкционирует install. Старое supplied не пересоздавать, live graph metadata не менять для демонстрации, никакой `git reset/clean`.

**Статус / Next Gate:** текущий план — **кандидат рабочего исполнения** с принятыми пользовательскими Need/ограничениями, но предложенной технической композицией; до начала правок кода — согласовать его объём. Перед разрешённым Windows upgrade отдельно установить целевую среду и способ авторизации запуска. Ничего из этапов 0–90 не считается выполненным от появления этой записи.
