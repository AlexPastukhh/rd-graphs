# Specify — собрать согласованную проверяемую постановку

> **СТАТУС: АКТУАЛЬНЫЙ ПРОЕКТ СЕМАНТИКИ ДЛЯ СОГЛАСОВАНИЯ.** Вторая группа, методики эффективной работы. Редакция 2026-11-11.

Specify помогает собрать результаты обсуждения и исследования в достаточное описание предстоящей работы. Результат — согласованный по содержанию scope, по которому исполнитель понимает назначение, ожидаемое поведение, существенные ограничения и способ проверки. Сам текст спецификации не создаёт разрешения или факта пользовательского согласования.

## Требуемый результат и основания

**R-LENS-SPECIFY:** «Постановка соответствует действующей задаче, внутренне согласована и достаточна для исполнения и проверки в своём scope».

Область: одна задача, ограниченный эксперимент, этап либо продукт. Родительские основания: [R-USEFUL-RESULT](../requirements.md#r-useful-result), [R-JUSTIFIED-EFFORT](../requirements.md#r-justified-effort), [R-CONTINUITY](../requirements.md#r-continuity). Отношение при переносе определяется по [правилу оснований](../requirements.md#как-выразить-родительские-основания-в-графе).

Исполнитель получает нужный смысл без угадывания важных условий и повторного восстановления обсуждения. Объём текста и сам факт создания спецификации не доказывают достаточность или согласие пользователя.

Проверка: [достаточность результата](#проверить-согласованность).

## Когда оценить применение

- Цели, ответы и решения уже есть, но остаются разрозненными или противоречивыми.
- Исполнитель вынужден угадывать существенное поведение, границу этапа или приёмку.
- Нужно подготовить задачу, этап либо эксперимент с достаточными входами, выходами и условиями.

Это часть [подготовки постановки в work](../bootstrap/work.md#подготовить-постановку-и-ближайшую-работу). Достаточное существующее ТЗ используется адресно; объём определяется текущей работой.

## Определить область и источники постановки

Установить, описывается ли одна задача, этап или продукт. Прочитать действующие R, решения и основания, Context, Findings, Questions и текущий разговор. Для неясной цели использовать [clarify](clarify.md), для недостающих проверяемых сведений — [research](research.md).

Отделить уже установленное от предлагаемого. Рекомендация ИИ, принятый способ, проверенный факт и предположение имеют разное происхождение. Непринятые варианты остаются на бумаге по [decision-logic](../bootstrap/decision-logic.md).

Не требуется заново оформлять полную спецификацию для очевидной небольшой правки. Объём определяется ценой недопонимания и следующей работой. Достаточная существующая постановка может требовать только адресного уточнения.

## Собрать достаточное содержание

Использовать нужные части следующей карты; обязательная анкета из всех разделов не вводится.

| Что объяснить | Для чего это нужно |
| --- | --- |
| Назначение, получатель пользы и исходная цель | Проверить связь работы с реальной потребностью |
| Сценарии и наблюдаемое поведение | Понять результат глазами пользователя или потребителя |
| Требования и существенные ограничения | Определить достаточность и допустимые способы |
| Термины и правила предметной области | Сохранить одинаковое понимание смысла |
| Принятые решения, основания и затронутые альтернативы | Не заставлять исполнителя угадывать важный выбор |
| Входы, выходы, интерфейсы и зависимости | Обозначить условия исполнимости и совместимость |
| Граница этапа и явно отложенное | Предотвратить неподтверждённое расширение scope |
| Проверка результата, неизвестные и предположения | Понять, что можно принять и что ещё требует решения |

У количественного критерия указать условия измерения. Качественный критерий должен позволять содержательно оценить достаточность. Существенные ошибочные и пограничные случаи входят по смыслу задачи.

Нефункциональные требования включать, когда они действительно применимы: например, ожидаемая нагрузка, сохранность данных, доступность интерфейса или совместимость. Не добавлять вымышленные масштабы и ограничения ради полноты шаблона.

## Проверить согласованность

Пройти сценарии от исходной цели до результата. Найти противоречия, неопределённые термины, скрытые предположения и важные решения, которые описание оставляет исполнителю случайно.

Для каждого существенного обязательства установить способ проверки и ответственного за следующий шаг, когда он нужен. Обратная проверка также полезна: каждая существенная работа и проверка должны иметь понятное основание.

Открытый вопрос может блокировать всю работу, её часть или не мешать ближайшему шагу. Оставить это явно. Предложить разрешение значимой развилки через clarify/explore; независимая разрешённая работа может продолжаться.

Изменение постановки сверять с принятыми решениями, ограничениями, уже выполненной работой и затронутыми потребителями. Существенный пересмотр проходит [checkpoint](../bootstrap/checkpoint.md). Согласие требуется в действительных границах полномочий, без повторного запроса уже данного разрешения.

## Сохранить один источник смысла

Спецификация может быть связным Markdown-текстом, содержанием цельного Action или выбранным представлением существующих данных. Новые Graph kind, owner и обязательный документ для каждого шага не вводятся.

У каждого изменяемого правила остаётся свой владелец. Рабочие требования, решения и источники адресуются по реальным IDs. Самостоятельный полный исходник и связанные представления сохраняют версии и прослеживаемое соответствие по [lens-system](../bootstrap/lens-system.md).

Не создавать независимо редактируемые копии одного требования в брифе, ADR, спецификации и задачах. Краткое изложение, пример и снимок конкретной версии допустимы с понятной связью с источником. При изменении обновляются затронутые изложения по [dry](dry.md).

Структурный Markdown показывает данные текущего scope по общим правилам; выбор этого формата сам по себе не проверяет полноту постановки и не создаёт согласование.

## Подготовить переход к исполнению

Когда описание достаточно, выбрать ближайший проверяемый результат и передать декомпозицию в [shape](shape.md). У задачи должны оставаться доступными её цель, нужные сведения, зависимости и критерии результата.

При существенной неопределённости можно подготовить постановку ограниченного эксперимента, получить сведения и пересмотреть продолжение. Не нужно заранее закрывать все вопросы всего продукта.

Фактическое исполнение, запись выбора и подтверждение результата проходят [work](../bootstrap/work.md). Полезный сохраняемый объём оценивается через [preserve](preserve.md).

## Пример и проверка

Для поиска по каталогу достаточно описать запросы, состав выдачи, область поиска, актуальность данных и проверку результата. Выбор конкретного индекса остаётся вариантом, пока не имеет нужных оснований. Экспорт, совместная работа и сложная аналитика могут быть явно оставлены за границей этапа.

Проверить, что постановка соответствует исходной задаче, а следующий исполнитель может воспроизвести сценарий, объяснить приёмку и назвать оставшуюся неопределённость. Внутренняя непротиворечивость описания другой задачи не подтверждает этот результат. Разобрать противоречащие ограничения, предложенный вместо принятого способ, достаточное существующее ТЗ и разрешённую работу при частично блокирующем Question.
