## Краткий результат

Пользовательские функции в D1–D9 в основном перечислены. Но одного этого списка недостаточно для безопасного переноса в существующее приложение. Обнаружены пять существенных рисков перехода и одна возможность улучшить порядок проверки. Подтверждённых нарушений работающего нового Decision-приложения не заявляется: такого backend ещё нет.

Три главных риска: новый профиль может не пройти существующие входы Helper/Viewer; раскладки и IDs визуальных повторов несовместимы без дополнительной политики; первый шаг Plan без даты и привязка начала ветви требуют явного контракта. Два других риска относятся к переносу пересмотров/guards и к сохранению новых registry/reference данных через общий storage. Все пять требуют HIGH внимания и проверки **до соответствующего этапа**, а не немедленной переделки всего приложения. Срок и бюджет не заданы; Intervention Priority на этот срез — NEXT.

## Находки и предложения

### F-R-1

**Новый профиль нужно провести через все входы приложения.** Тип Risk; target: D1/D2/D7/D8 → profile dispatch и основной Viewer. Level CURRENT; User Review Priority HIGH; Intervention NEXT; disposition unresolved.

План называет общий kernel/Application и «существующие точки включения» Viewer, но не выделяет все material потребители версии и обязательную проверку их совместимости. В `tools/rdg-workflow-ui.js:369` проверка требует именно `coreModel === 'rdg-core-v1'`, `actionModel === 'candidate-v6'` и прежний schemaVersion. В том же source есть branch по старому coreModel при mount. `tools/rdg-workflow-helper.py:67,85`, `tools/rdg-agent.py:112,241` и `tools/rdg-catalog.js:16` содержат отдельные проверки/развилки. Нельзя считать каждую из них автоматически ошибочной: часть должна остаться для legacy. Но их назначение надо явно определить при добавлении нового профиля.

**Механизм риска:** новый Graph проходит новый kernel, затем read/import/catalog или основной Viewer направляет его в прежнюю проверку/renderer. Результат — отказ открыть Graph, неверная трактовка Action или несовместимые инструкции линзы. Это возможный сбой переноса, не заявленная текущая регрессия.

Сборка также отдельный путь: `tools/build-rdg-layout.py:7` встраивает восемь shared blocks в `tools/rd-graph-viewer.user.js`; правка одного portable UI не обновляет все source validators или итоговый bundle.

**PR-1 — pending, HIGH autonomy, impact CURRENT.** Дополнить inventory и матрицу profile dispatch: core/model/service; `rdg-portable.py`; workflow/Helper/Agent; workflow UI, catalog и основной userscript; lens-session; build. Для каждой точки определить: новый профиль поддержан / legacy-only с явным отказом / требуется adapter. Сохранять прежний профиль отдельной веткой, не менять глобальную константу так, чтобы сломать старые owners. Gate: один новый временный процесс проходит schema/preflight/apply/receipt, основной Viewer и подходящую фундаментальную линзу; прежний synthetic R/A-процесс остаётся читаемым/редактируемым своим поддержанным путём; generated blocks побайтно совпадают с sources.

Цена: дополнительный ранний интеграционный проход и адресные adapters; выигрыш — обнаружение отказа до полной переделки UI/линз. Точный effort неизвестен. Next Gate: техническая карта входов и первый проход до завершения D2; пользовательский выбор сейчас не блокирует.

### F-R-2

**Общая раскладка процесса и стабильность визуальных вхождений требуют отдельного контракта.** Тип Risk; target: D5/D6 → layout keys, occurrence identity и copy. Level CURRENT; User Review Priority HIGH; Intervention NEXT; disposition unresolved.

`tools/rdg-portable-model.py:presentation` формирует разные graphKey для full, WG и focus. Исполненная проба на одном synthetic Graph дала:

```text
full:      ["review-space","review-graph"]
workGraph: ["review-space","full-WG1"]
focus:     ["review-space","review-graph","R0"]
```

Прототип использует `prototypeLayoutKey()` на уровне процесса, без WG/focus. Простое подключение старых ключей к новому UI поэтому не обеспечивает принятую общую раскладку. Старые keys нельзя молча объединять при разных координатах.

Есть второй проверенный стык. Prototype `RDGPrototypeBranches.occurrenceId(path)` хеширует путь с entity IDs. В `tools/rdg-layout-core.js:remap` меняются `entityId`, `parentId`, `viaEdgeId`, но сохраняется ключ occurrence. После ремапа R0/R1/D и e0/e1 контрольная проба показала:

```text
исходный ID:              occ-branch-f74c72e8a4acd4c0
сохранён codec-ом:         occ-branch-f74c72e8a4acd4c0
вычислен новой ветвью:     occ-branch-54066b52baaa81a0
сохранённая позиция:       (-123, 456)
полученная позиция:        (300, 450)
```

Все semantic refs в сохранённой записи переназначены корректно, но renderer не находит запись под новым вычисленным ID. Проба исполняла совместно существующий codec и чистую policy из prototype на совпавших SHA-256; это интеграционный контрпример, не дефект уже существующей production Decision-copy операции.

Общий `rdg-visual-projection.js` также не содержит всей новой policy: `project` принимает canonical Decision, но `addBranch` для Decision в адресной пробе возвращает `VISUAL_ROOT_UNKNOWN`. Политика автоматических локальных входов находится в prototype, а не в этой общей функции.

**PR-2 — pending, HIGH autonomy, impact CURRENT.** До D6 зафиксировать key policy для нового процесса, связь screen state с layout owner и устойчивую identity вхождения при remap. Варианты, которые стоит проверить технически: сохраняемый occurrence ID, не вычисляемый заново из сменившихся entity IDs; либо согласованное переназначение пути, ID вхождения и всех его ссылок codec-ом и projector-ом. Не выбирать вариант только по удобству одной стороны. Вынести нужную R/D/Action policy из HTML в общий код и связать с реальными edge IDs. Существующие legacy layouts сохранять своим reader-ом; импорт/слияние конфликтующих координат — только при отдельной явной migration policy, не автоматом.

Gate: drag в full виден в WG/focus/другом экране; два изображения одной entity сохраняют независимые позиции; copy/insert remap сохраняет координаты корня и продолжения после reload/restart; раскрытие после zoom/pan не меняет экранную матрицу. PR-2 рекомендован вместе с PR-5 из-за общего remap/reference контракта. Next Gate: pure remap/projection checks до подключения D6 к Viewer. Выбор конкретной identity policy ещё открыт, но техническое исследование не требует пользователя.

### F-R-3

**В Plan нужно проверить пустое начало и сохраняемую развилку, а не только наличие шагов без даты.** Тип Risk; target: D3 → canonical Plan contract. Level CURRENT; User Review Priority HIGH; Intervention NEXT; disposition unresolved.

D3 правильно требует порядок без обязательных дат и показ начала ветви, но не фиксирует две важные границы. В `tools/rdg-portable-model.py:place` первый placement без `at` и `afterStepId` завершился `PORTABLE_PLACEMENT_POSITION_REQUIRED`. Контроль с датой создал один шаг; второй шаг без даты, но после первого — sequence `s1 → s2`. Исходный Plan остался неизменным. Значит, тест «шаг без даты» на уже заполненном Plan не проверяет обязательный сценарий одного первого шага без даты.

Portable branch сейчас имеет только `id/title/cases`; добавление `afterStepId` к отдельно валидной ветви отвергнуто как `PORTABLE_PLAN_BRANCH`. В legacy `tools/rdg-temporal-plan.py:135` другой формат: branch с `eventStepId` и cases/outcomes. Оба reader-а называют свой Plan schemaVersion 2, но payload shapes различаются. Prototype fork `afterOrder` — UI fixture, не подтверждённая canonical связь. Это нельзя переносить как будто уже существующий общий формат.

**Механизм риска:** UI отрисовывает развилку и первый порядок, а API либо отвергает их, либо после reload теряет место начала/трактует первый шаг unresolved. Смена показываемой ветви не должна решать этот пробел записью selected в Graph или отдельным Plan owner для каждой альтернативы.

**PR-3 — pending, HIGH autonomy, impact CURRENT.** Перед D3 определить canonical форму первого order-only placement, якоря развилки, case membership и namespace-aware ссылок на относящиеся сущности; обозначить profile-aware adapter для legacy/portable форматов. Не предписывать конкретное новое поле API на основании названий пробы. Gate: пустой Plan → один шаг без даты → следующий шаг по порядку; последующее добавление/снятие времени; две альтернативы до selected; общий preparation step и отдельные placements одной entity; пустая/удалённая ветвь; изменение источника, фильтра дней и restart. Фильтры дней проверять на границах включительно, отдельно для date-only и timezone-aware времени.

Next Gate: schema и reducer/projection fixtures до дороги Viewer. Пользовательский результат не меняется; дата завершения проекта не задана.

### F-R-4

**Добавление типов недостаточно: нужны явные последствия изменения связей и состояний.** Тип Risk; target: D1/D2 → completion, freshness, guards и lifecycle. Level CURRENT; User Review Priority HIGH; Intervention NEXT; disposition unresolved.

В `tools/rdg-core-model.py` допустимые пары, `DEPENDENCY_TYPES`, `LOCK_OPERATIONS`, completion types и команды заданы отдельно. Комментарий у DEPENDENCY_TYPES требует положительного выбора freshness policy для новой связи. Проба подтверждает отсутствие `DECISION_MEMBER` и `REQUIRES_ACTION` в текущем наборе — ожидаемое состояние прежнего профиля. `guard_method`, unlink, withdraw и remove учитывают именно прежний Action-способ и его R-источники. D1 перечисляет новые entities/completion, D2 — общий permission path, но не задаёт регрессионную матрицу этих последствий.

**Механизм риска:** новый тип принимается validator-ом, но изменение обязательного Action/членства D не вызывает нужный пересмотр; либо прежний guard применяется к реальному действию как к способу. Отмена, unlink и физическое удаление могут получить разные effects на общий R, Plan и сохранённые факты, не проверенные сценарием одного unselect. Действующий L1/L2/guard путь — существующая логика приложения, не новый гипотетический security-проект.

**PR-4 — pending, HIGH autonomy, impact CURRENT.** До D1–D2 определить по новым типам/связям effects на актуальность, completion/review, допустимость команды и затронутые объекты. Прежний R/A-профиль сохранить с его проверками. Новый свободный Canon не заставлять проходить старую структурированную assessment-схему; отдельно установить действие явно объявленных зависимостей. В acceptance включить select/unselect/complete/reopen, definition edit, membership change, unlink/remove; несколько действующих оснований общей R; сохранение исторических фактов и корректную очистку current refs. Прогнать относящиеся synthetic core/native-dependency/locks/workflow/portable-service regressions в соответствующих профилях. Не расширять права/eligibility операций автоматически.

Next Gate: матрица effects и отрицательные fixtures до объявления нового ядра поддержанным. Схема эффектов требует технического уточнения, а не нового пользовательского сценария.

### F-R-5

**Новые данные и ссылки должны участвовать во всём persistence и transaction path.** Тип Risk; target: D1/D4/D5/D6 → source of truth, reference closure и remap. Level CURRENT; User Review Priority HIGH; Intervention NEXT; disposition unresolved.

`tools/rdg-portable-store.py:validate_head` допускает current components `graph/plan/layouts`; stage/publication также перебирает фиксированный набор. `tools/rdg-portable-model.py:definitions` перечисляет entity/edge/workGraph/exclusion, а `graph_references` знает конкретные slots прежних групп и lensRecommendations. Новые внешние Actions, правила/опоры/подключения пакетов не становятся частью сохранения и closure от наличия массива в UI. D4/D5 правильно требуют общий registry и remap, но не выделяют owner/schema и весь lifecycle gate.

**Механизм риска:** изменение пакета видно в открытом Explorer, но не попадает в durable owner; либо source package меняется после preflight и вставка использует смешанные версии. Удаление опоры, копирование или перенос могут оставить чужой ref, активировать слишком широкую область правила или потерять local binding. Atomicity Graph/Plan/layout не покрывает новый объект автоматически, если он не включён в coordinator.

**PR-5 — pending, HIGH autonomy, impact CURRENT.** До D4 зафиксировать authoritative owner и schema для внешних Actions, определений/версий пакетов и подключений. Выбрать способ хранения через существующий Application/IO/coordinator; отдельный writer не вводить. Участие новых refs зарегистрировать в definitions, typed reference traversal, capture/remap, incoming closure, source pin/CAS, delete/unlink/copy/move и recovery. Подключение по ID должно ссылаться на одно определение; локальный template instance остаётся независимым согласно принятому scope.
