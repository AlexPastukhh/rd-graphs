# Глубокие предварительные ветви, разбиение и история результатов

Статус: **Candidate, локальная реализация в Repo**. Определения принадлежат
[руководству граф-модели](RDG-V7-WORKING-GRAPHS.md). Этот документ описывает API.
Stage 4 остаётся **NOT ACCEPTED**. Установленный Windows Viewer не проверен.

## Подготовка без принятия

В opt-in `actionModel: candidate-v6` можно строить продолжения под непринятыми
Actions и под их непринятыми потомками. Каноны и QRPE остаются на своих владельцах;
глубина предварительной ветви не требует принятия предыдущих Actions.

У Action есть необязательное поле `actionType`:

| Значение | Смысл |
|---|---|
| `general` или отсутствие поля | Обычный Action. Может выполнять работу и выделять связанную группу подцелей. |
| `decomposition` | Action выделения одной подцели или связанного набора подцелей. Выбор другого набора представлен другим Action. |

У обоих типов допустимы дочерние R двух ролей:

| `childRole` | Чьё выполнение требует достижения R |
|---|---|
| `subgoal` | Родительская R: это часть её разбиения. |
| `method_correctness` | Сам Action: это Requirement его корректного выполнения. |

Все `subgoal` одного Action составляют связанный набор. Несколько альтернативных
наборов задаются несколькими Actions; несколько выбранных Actions входят в текущую
обязательную композицию совместно. Тип Action не заменяет роли его дочерних R.

К существующему package writer добавлена операция:

```json
{
  "op": "graph_edit",
  "action": "prepare_action_requirement",
  "actionId": "A1",
  "childRole": "subgoal",
  "edgeId": "A1-R1-potential",
  "node": {"id": "R1", "kind": "requirement", "title": "Подцель"},
  "event": {
    "id": "EV-PREPARE-R1", "type": "graph_changed",
    "operation": "prepare_action_requirement",
    "by": "assistant", "note": "Проработать предварительную подцель"
  }
}
```

Вместо `node` можно передать `requirementId` существующей локальной R. Нужен grant
`graph.graph_edit.prepare_action_requirement` либо существующий `graph.write`
с подходящим scope. Новый узел получает `status: potential`; связь — `OUTCOME_OF`
с явными `parent` и `childRole`. Это не `INTRODUCES` и не принятие.

Под этой R обычный `add_action` создаёт следующие варианты. Каноны редактируются
через `graph_edit/edit_node`, QRPE — существующими операциями. Ненужную
предварительную связь можно архивировать через `graph_edit/archive_edge`.
Старый узел и история сохраняются. Нет автоматической миграции legacy O/D.

`select_action` переводит подготовленные связи выбранного Action в `INTRODUCES`
с сохранением ID. Потенциальные локальные R становятся активными. Каноны, QRPE
и дальнейшие непринятые Actions сохраняются; потомки не выбираются автоматически.
Другой предварительный вариант может ссылаться на ту же R, не становясь принятым.
Для принятого `decomposition` требуется минимум одна активная R с ролью `subgoal`.
Это условие проверяется после всех операций нового пакета: удалить последнюю
подцель без замены нельзя. Атомарная замена набора разрешена. Предварительный
Action может оставаться без подцелей во время проработки.

Viewer в исходнике показывает глубокую предварительную ветвь через «Все ветви»;
каноны, QRPE, тип Action и роли R доступны в существующем подробном просмотре.
Явное `expansionOf/projectionOf` позволяет продолжать предварительную R в другом
файле с одним владельцем. Совпадения ID недостаточно.

## Результат и расчёт

Новые операции package writer:

- `record_action_execution`: `targetId` Action, событие `action_executed`;
- `record_requirement_achievement`: `targetId` R, событие `requirement_achieved`.

Событие содержит уникальный `id`, тот же `targetId`, `by` и непустой `note`
с описанием результата. Нужны соответственно `graph.record_action_execution`
и `graph.record_requirement_achievement`, либо `graph.write`. Writer назначает
технического автора, время записи и снимок состава/определения результата.
Клиент не подставляет `basis`, `basisSHA256`, `completionMode` или `recordedAt`.
Это запись результата в графе, а не независимая проверка реального мира или F-P.

Action — экземпляр действия. После выполнения он остаётся в истории;
writer отклоняет вторую запись выполнения того же Action ID. Производный расчёт
также не создаёт второго выполнения этого экземпляра. Чтение старых событий
сохраняется без миграции. Смена варианта по той же цели представлена отзывом
старого Action и выполнением другого Action с отдельным ID.

`complete` у Action показывает сохранённый факт выполнения, включая отозванный
Action. `currentScopeComplete` дополнительно показывает, подтверждает ли этот
результат текущий состав и определение. Родительская R использует именно эту
проверку состава: правка не стирает сделанное, но и не даёт ложного достижения
изменённой цели. Цели рассчитываются по своей актуальной выбранной композиции.

Листовой Action не требует искусственной R результата. Сам факт выбора, пустой
список дочерних R и редактирование графа не означают выполнение. Action выделения
подцелей может быть выполнен, пока созданные подцели ещё не достигнуты.

Составной Action рассчитывается по своим `method_correctness`. Родительская R —
по выбранным Actions и их `subgoal`. Когда все обязательные зависимости выполнены,
writer добавляет отдельные производные события выполнения/достижения на итоговом
состоянии пакета. Промежуточное отсутствие заменяемой зависимости не создаёт
достижения. Явно записанный результат сохраняет состав на момент своей операции;
последующая правка в том же пакете не переносит его на новое определение.
Невыбранная альтернатива не блокирует результат. Обязательную невыполненную или неизвестную
зависимость нельзя обойти прямой записью успеха. Запись вне актуального выбранного
пути отклоняется. Каноны/QRPE не стирают уже сделанную работу.

Снимок результата Action с выходными подцелями содержит `basis.outputs`: связи
и определения R выполненного набора. Достижение этих R не является условием
выполнения самого Action. При поздней правке исходный снимок остаётся в истории;
выполненный Action не возвращается в будущее. Для другого выполняемого варианта
используется другой Action, а не повторный результат для прежнего ID.

Старые события и snapshots читаются без перезаписи. Прежний снимок без
`basis.outputs` не подтверждает текущий набор автоматически; для старого пустого
`decomposition` текущий состав остаётся неподтверждённым. Сам сохранённый факт
выполнения Action не стирается. Новая запись должна исправить
набор в том же пакете либо пересмотреть выбор Action. Миграция не выполняется.

Межфайловой расчёт теперь реализован для опубликованной candidate-v6 композиции
в одном Graph root. `projectionOf` разрешается до единственного владельца, а
`expansionOf` связывает продолжение конкретной R. Расчёт и запись результатов
используют общий resolver; отсутствие владельца/права не превращается в успех.
Точный scope и ограничения описаны ниже.
Однофайловой сквозной путь будущего/истории реализован через `rdg-workflow.py`:
используются те же R/Actions графа с сохранением ID и ссылок. Выполненное
исключается из предстоящего при чтении, без записи новой версии Plan.
Размещение остаётся явным. Модель повторных физических исполнений не вводится.

## Межфайловая обязательная композиция — 2026-10-19

Статус: **Candidate, локальный API/controller proof**; установленный Windows/G2
не проверен. Общий `rdg-completion-context.py` используется package writer и
activity/workflow readers. Временное объединение источников нужно для расчёта;
оно не сохраняется как второй owner и не копирует проект.

| Связь/поле | Смысл |
|---|---|
| `projectionOf: {graphSlug,nodeId}` | Точный владелец той же сущности. Совпадают identitySpace, ID, kind и нормативный scope. Локальное название может отличаться. |
| `expansionOf` и такая же projectionOf корневой R | Явное продолжение конкретной R в другом файле. Название папки, одинаковый title или root ID отдельно этого не доказывают. |
| `ownerRef` результата | Настоящие graphFile/identitySpace/nodeId; размещение может ссылаться на проекцию, но факт результата принадлежит owner. |
| `selectionBasis.driverOwnerSnapshot` | При новом выборе под projected R дополнительно закрепляются ownerRef и её настоящее определение. Старый driverSnapshot с локальным display title сохраняется. |

Общий расчёт сохраняет прежний смысл: subgoal блокирует родительскую R до своего
достижения; method_correctness блокирует выполнение соответствующего Action.
Выбранная локальная работа под непринятым предком не делает всю ветвь актуальной.
Повторные отображения Action/его причинных связей не создают новые обязательные
исполнения. Выбор и явная запись выполнения Action должны идти в его собственный
файл; запись достижения R через projection отклоняется.

### Запись и права

Существующий package writer рассчитывает **финальную** композицию пакета, затем
добавляет недостающие производные события в настоящих владельцев. Например:
запись выполнения C в continuation-файле → достижение R1 в родительском owner →
выполнение составного D при method_correctness → достижение R0. При subgoal
выполнение D по созданию R1 не ждёт достижения R1; достижения ждёт R0.
Изначальная история экземпляра Action не переписывается и не выполняется вновь.

Запрос не получает новых полномочий. Нужны права исходной операции, `graph.read`
на все загружаемые источники и права каждой новой производной записи у owner:
`graph.record_action_execution` / `graph.record_requirement_achievement` либо
`graph.write`, в соответствующем scope. Отсутствие необходимого права отклоняет
весь новый пакет до публикации; нет частичного «C записан, parent молча пропущен».
Grants не выдаются и не расширяются автоматически. В прежних policy callsites
для projected R проверяется политика её настоящего владельца; alias не обходит
protected/stable. Новые самостоятельные policy правила этим не вводятся.

Для первого межфайлового среза читаются **все опубликованные workspace-файлы
затронутого identitySpace**, включая предварительные ветви. Поэтому узкий токен
без одного из этих read scopes даст отказ всему межфайловому расчёту. Это граница
текущей реализации; адресный dependency-only read не заявлен. Prepared/read-only
источники, legacy-модели и чужой identitySpace не импортируются как актуальные
candidate-v6 владельцы. Нужен проверенный опубликованный catalog; новый жизненный
цикл принятия Plan или автоматический as-of baseline не вводится.

### Согласованность, история и ошибки

Reader держит общий shared writer lock на весь набор источников; workflow также
держит Plan read lock. Writer под прежним exclusive lock фиксирует source hashes
и catalog hash (`completionReadSet`) и проверяет их перед durable acceptance,
вместе с повторной проверкой read/write grants. Смена входа между расчётом и
acceptance даёт отказ, а не результат на смешанных revisions.

Публикация нескольких файлов остаётся **recoverable**, не одним atomic rename.
Один prepared journal содержит все изменённые owners. До завершения/recovery
читатель не выдаёт частичный успех. Уже долговечно принятый пакет восстанавливается
и после revoke; новая запись/replay отозванным bearer отклоняется. Повтор запроса
проверяет также прежние зависимости, не создавая ещё одно исполнение.

`compositionOrder` назначает writer для новых событий одного межфайлового пакета.
Лента применяет его только при подтверждённом completionReadSet журнала: сначала
исходные факты в порядке операций, затем производные результаты в порядке
зависимостей. Факты остаются в своих файлах. В basis только реально пересекающие
границу связи получают `compositionGraphFile` / `targetOwnerGraphFile`; локальные
снимки без таких связей не переписываются. Старые receipts/events не мигрируют.

Missing/ambiguous owner, несовместимые kind/scope, неверная expansion binding,
циклическая projection или обязательная зависимость, неподдержанная модель,
недостаток read/write прав и изменившийся источник не дают успешного результата.
Для старого/imported состояния, где расчёт уже готов, но события результата ещё
нет, reader показывает `historyPending` / unresolved вместо фиктивной истории и
автоматического исчезновения из будущего. Обычная авторизованная material-запись
пересчитывает компонент и сохраняет готовые производные результаты. Это не
отдельный Plan closing lifecycle.

Согласованность гарантируется для штатного writer/catalog/lock protocol одного
Graph root. Прямая запись в JSON/индекс вне этого протокола не становится
контролируемой ОС-песочницей. Проверяются используемые source pins и известные
catalog refs; полнота произвольно подменённого raw catalog не доказывается.
Полная Gendocen проверка канонов нового контекста из completion proof не следует.

## Отзыв Action

В том же Graph package writer доступна операция `withdraw_action` для уже выполненного
Action с отдельным
`graph.withdraw_action` либо `graph.write` в scope владельца:

```json
{
  "op": "withdraw_action", "actionId": "A1", "dispositions": [],
  "event": {
    "id": "EV-WITHDRAW-A1", "type": "action_withdrawn", "actionId": "A1",
    "driverRequirementId": "R0", "by": "assistant", "note": "Выбран другой вариант"
  }
}
```

Пример без дочерних R. При наличии INTRODUCES нужен полный `dispositions`:
`retain_supported` с точными `supportingActionIds` выбранных независимых Actions
либо `deactivate` с причиной и проверенным локальным scope. Используются те же
проверки зависимостей и общего владения, что в существующем reconsider writer.
Нельзя деактивировать общую R или R с зависимостями; внешние references проверяет
catalog до записи. Политики stable/protected, verified receipt и recovery сохранены.
Запись отзыва выполненного экземпляра сохраняет факт смены варианта и не
выдаётся за пройденную оценку канонов. Она не отменяет внешние эффекты действия.
Прежний богатый `reconsider_action`, включая пересмотр ещё не выполненного
выбранного Action, остаётся отдельной операцией с прежними проверками.

Отзыв переводит Action в `superseded`, сохраняет исходный snapshot, рёбра и судьбу
каждой дочерней R. Историческое выполнение не меняется. Выбор нового A2 отдельный;
сам выбор не создаёт факт его выполнения.

## Размещение R и Actions через Plan owner

Schema v1 дополнена видом шага `requirement` с `requirementRef` того же вида,
что `actionRef`. Старые snapshots и принятые retries читаются как прежде.
При новой записи обе сущности требуют времени либо порядка.

Вместо полной замены `plan` можно отправить удобные операции внутри прежнего edit:

```json
{
  "transactionId": "place-goal-1", "op": "edit", "file": "plans/example/plan.json",
  "expectedRevision": 1,
  "operations": [{
    "op": "place",
    "step": {"id": "S-R0", "kind": "requirement", "title": "Цель", "state": "planned",
      "requirementRef": {"graphFile": "workspaces/example/graph.json", "identitySpace": "example", "nodeId": "R0"}},
    "timeConstraints": [{"type": "notBefore", "at": "2026-10-20", "strength": "soft", "basis": "Ручное размещение"}]
  }]
}
```

`place` создаёт либо меняет размещение того же step/ref. `timeConstraints` и
`sequence`, если переданы, заменяют относящиеся к этому шагу записи. Можно дать
только порядок. `unplace` с `stepId` удаляет размещение, его сроки и incident links;
сами сущности графа остаются. Все операции проверяются совместно на итоговом Plan.
Если соседний шаг после снятия порядка остался без размещения, запрос отклоняется;
можно исправить оба размещения одним пакетом. Ветви редактируются прежним полным
Plan API с его branch grant. Права plan.edit/branch, CAS, журнал, повтор и recovery
не менялись. Эти операции не выбирают и не выполняют Actions и не пишут в граф.

```sh
python3 -B tools/rdg-temporal-plan-owner.py apply --root /path/to/plan-owner \
  --store /path/to/grants.json --request /path/to/request.json
```

Graph refs структурно проверяются owner; чтение workflow разрешает их по реальным
владельцам и kind. Результат для неверного owner или недоступного источника не
выдаётся за выполненную работу.

## Единые будущее и история

```sh
python3 -B tools/rdg-workflow.py --root /path/to/plan-owner \
  --file plans/example/plan.json --graph-root /path/to/graphs \
  --graph workspaces/example/graph.json --store /path/to/grants.json --format html
```

Варианты формата: JSON, Markdown и самостоятельный HTML-снимок. В JSON — `future`,
`history`, `unresolved`, provenance Plan и ревизии graph owners. Дополнительный
`--graph` даёт историю выполненного без размещения; автоматического обхода всех
графов нет. Нужны plan.read и graph.read каждого явно читаемого владельца.
Чтение держит Plan и Graph read locks, отклоняет pending journals и сохраняет
источники. Исторический Plan-as-of с текущими результатами за полный as-of не выдаётся.

В будущем остаются размещённые невыполненные сущности, включая предварительные.
Выполненный Action и отозванный вариант не показываются как предстоящие. История
показывает выполнение A1, отзыв A1 и выполнение A2 в порядке событий, в том числе
внутри одного пакета. Неполная или неразрешённая R не получает успеха. Формат HTML
предназначен для чтения. Ручной редактор Viewer/Helper 2.2.1 описан ниже; его установленный Windows/G2 путь пока не проверен.

Gendocen projection теперь учитывает actionType. Requirement steps пока явно
получают `REQUIREMENT_STEPS_NOT_COVERED`, а не ложное полное покрытие; произвольный
новый Canon context этим пакетом не реализован.

## Общая читаемая история

```sh
python3 -B tools/rdg-activity.py --graph-root /path/to/graphs \
  --graph workspaces/example/graph.json --format markdown
```

`--graph` можно повторить для нескольких разрешённых владельцев. По умолчанию
возвращается JSON с `activities` и `currentCompletion`; `--outcomes-only` показывает
только результаты. При включённом bearer store нужны `graph.read` и scope каждого
указанного файла. Автоматического расширения прав нет.

Лента объединяет сохранения графов, выполнения Actions, включая `decomposition`,
и достижения R. Сохранение правки остаётся отдельным видом записи. Время успешного
сохранения берётся из completed journal, старое неизвестное время остаётся `null`.
Технический bearer principal сохраняется и для правок без отдельного graph event.
Повтор транзакции не добавляет второй успех; prepared/отклонённые операции не выдаются
за завершённые сохранения. Reader держит общий read lock writer. Pending journal
запрошенного графа вызывает RECOVERY_REQUIRED, включая сбой после записи graph.json,
но до завершения журнала. Чтение не меняет источники и не создаёт Temporal Plan.
В schema-v2 journal добавлен необязательный authorityPrincipal; старые schema-v1/v2
читаются, exact-history reader принимает это поле с проверкой типа.

Общий HTML-снимок будущего/истории и ручной раздел Viewer/Helper уже доступны.
Контроллер GUI-ленты и ручной записи проверен с настоящими writers при имитации DOM;
установленный Windows/G2 путь ещё не проверен. Скрытие и понижение приоритета
событий пока не реализованы. Просмотр истории результатов конкретного узла
сохранён. Публичный API не меняет границы аутентификации Helper.

## Локальная ручная сессия Viewer/Helper 2.1.0

Статус: **Candidate, локальная интеграция**. Viewer 2.2.1 использует один настроенный
файл ручной записи и существующий Plan; зависимости и производные результаты
разрешаются через остальных авторизованных владельцев композиции.
Контроллер Viewer проходит оба транспорта через настоящие writers в синтетическом
acceptance-прогоне. DOM в этом прогоне имитируется; это не установленный браузерный
или Windows/G2 proof. Исходник Viewer обновлён до 2.2.1; установленный Tampermonkey
не обновлялся. Local Loader не получает новых grants или @require: общий UI-модуль
встраивается штатным `build-rdg-layout.py` из `rdg-workflow-ui.js`.

Ручной раздел «План и история» позволяет:

- создать candidate Action с обычным типом или decomposition и каноном;
- изменить название, простой канон, добавить открытую запись QRPE;
- подготовить дочернюю R с ролью subgoal или method_correctness, в том числе
  под непринятым Action; затем строить следующую волну без принятия предков;
- явно разместить R/Action по дате или после другого размещения, изменить место
  и снять размещение;
- отдельно выбрать Action, записать его выполнение или достижение R, отозвать
  выполненный Action с точной судьбой введённых R;
- прочитать общее будущее и историю из тех же владельцев. Выполнение не требует
  предварительного размещения; нового lifecycle закрытия шага нет.

Поддержка простого канона ограничена id/text случаев. Сложные case metadata,
ссылки проверки и расширенные материалы не обрезаются: их GUI-правка отклоняется
с `HELPER_COMPLEX_CANON_USE_FULL_API`. Чтение таких материалов остаётся во Viewer,
а изменение — через полный API. Пустой выбранный decomposition, неизвестные роли,
неполная композиция и повторное выполнение экземпляра по-прежнему отклоняются writer.

### Безопасная правка размещения — Viewer 2.2.1

Изменение даты начала сохраняет deadline, strength и basis существующих правил,
а также исходящие связи других шагов. Изменение предшественника сохраняет
minDelayDays; он показан в интерфейсе. При переключении сохранённого размещения
его дата и порядок загружаются заново. Пустая дата снимает только notBefore,
пустой предшественник — входящую связь. Полное удаление размещения выполняется
отдельной кнопкой «Снять размещение».

Простой GUI поддерживает одну дату notBefore в формате YYYY-MM-DD и одного
предшественника. Несколько таких правил, несколько предшественников либо точное/
относительное время не обрезаются: редактирование через этот GUI блокируется,
а Helper отклоняет такой запрос с HELPER_COMPLEX_PLACEMENT_USE_FULL_API.
Deadline, в том числе заданный полным API, сохраняется и виден в описании правил.
Полный Plan API сохраняет прежний явный replace-контракт sequence/timeConstraints.

### Файловое подключение без нового сервера

Оператор запускает Helper в Repo, указывая существующих владельцев, grant-store
и **новую папку сессии внутри уже разрешённого RW-монтирования**. Токен берётся
из существующего `RDG_AUTH_TOKEN`; выдача/расширение grant, mounts, ACL и Windows
полномочий не выполняются автоматически.

```sh
python3 -B tools/rdg-workflow-helper.py --manual-session \
  --root /path/to/plan-owner --file plans/example/plan.json \
  --graph workspaces/example/graph.json --store /path/to/grants.json \
  --session-dir /path/on/existing-mount/new-session-directory
```

1. В обновлённом Viewer нажмите «План и история».
2. Выберите **эту же папку сессии** через системный picker и разрешите запись
   в неё. Windows-путь и доступность для учётной записи G2 проверяются отдельно;
   соответствие Docker/Windows не выводится из старого пути Loader.
3. Проверьте выбранные цель/Action и версию; выполните нужную операцию.
4. После работы остановите свой процесс Helper. Общая инфраструктура не перезапускается.

Нужен браузер с File System Access API в текущем контексте Viewer. Если picker
недоступен, подключение не имитируется. В папке лежат только descriptor сессии,
временные запросы и ответы. Это транспортные снимки, не новый owner. Браузер удаляет
свои завершённые exchange-файлы; чужие файлы не трогает. Bearer/HMAC ключи в эту
папку и браузер не передаются. Доступ к активной папке даёт локальную capability
запросов в пределах настроенного grant; папку выбирает оператор/пользователь.
При остановке descriptor помечается inactive. После перезапуска подключают новую
папку сессии; интерфейс можно перечитать/открыть заново.

Дополнительный **opt-in** `--transport loopback` открывает временную сессию на
127.0.0.1 со случайным портом и секретным URL. Это необязательный адаптер для
среды, где браузер уже видит этот loopback. Docker-loopback не объявляется
Windows-доступом; порты, туннели и общие сервисы не создаются/не публикуются.
Проверяются точный Host, Origin, session capability, content type и размер запроса;
нет CORS или маршрута произвольного чтения файлов/исполнения команд.

### Права, ручное авторство, отказ и восстановление

В межфайловом пакете каждое новое производное выполнение/достижение требует
соответствующего result permission либо graph.write у владельца. Обычная правка
этого же файла в исходном запросе не заменяет право на производный результат.

Права совпадают с API: plan.read и graph.read для источников, plan.edit для
размещения, отдельные Graph permissions или graph.write для Graph операций.
Существующие branch grants, CAS, catalog, snapshots, журналы и recovery применяются
штатными владельцами. Helper не создаёт граф или Plan и не меняет grant-store.
Файл прямой ручной записи фиксируется при запуске Helper. Он читает разрешённую
композицию владельцев; производные результаты writer сохраняет в их настоящих
файлах с отдельной проверкой прав. В объявленном continuation-root можно создать
новый принадлежащий этому файлу Action, хотя сама R принадлежит другому владельцу.
Plan без старых event/gate steps и branches; предварительные **ветви графа**
поддержаны. Произвольного GUI-переключения write owner, Plan branch editor и
удалённой записи пока нет.

Обычный bearer по-прежнему не может присвоить `by:user`. Явно запущенная локальная
manual-сессия создаёт временный process-local HMAC key; существующий verifier
проверяет точный пакет, TTL и principal того же bearer grant. Для этого запуска
writer получает opt-in `RDG_LOCAL_MANUAL_SESSION=1`; без него присланный HMAC при
bearer остаётся запрещённым. Receipt помечается `local-manual-session`.
Это **локальное ручное авторство, не проверенная личность человека**, не remote
identity и не разрешение protected-owner операций. Этот Helper отклоняет Graph
запись, если в загруженной композиции есть protected R; она не разблокируется локальным MAC.
Операции изменения политики и административные операции через GUI не предоставлены.

Writer-отказ не меняет локальный результат на «выполнено». При потере ответа
интерфейс удерживает **тот же запрос** и не начинает новую операцию; retry не
создаёт новое действие. Уже сохранённый запрос подтверждается повторно без новой
записи, после проверки актуальных прав. Если writer успел принять журнал, но не
закончить запись, чтение успеха блокируется до существующего recovery. Нет
автоматического повторения после timeout. Ошибка отрисовки после подтверждённого
сохранения показывается отдельно от исхода записи. После перезапуска Helper его
in-memory cache утрачен: сначала перечитайте фактическое состояние/журнал, не
пересоздавайте прежнее действие с новым ID вслепую.
