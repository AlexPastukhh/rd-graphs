## 3. Пользовательский смысл, который нельзя потерять

### Каноны и теория

Каноны могут ссылаться на информацию/теорию, помогающую выбирать решение. Желательно интерпретировать её применительно к конкретным цели R и варианту: связать абстрактную теорию с графом.

При этом допустим честный блок «пока только ссылка». Готовые графы бывают разной степени подготовки; при повторном использовании материал можно доработать по ситуации. Нельзя запрещать такой материал, требовать полной интерпретации в каждом случае либо изображать его полностью разработанным.

**Объяснение самого поля** также может ссылаться на теорию, раскрывающую концепт и смысл ожидаемого ответа. Ссылка необязательна у каждого поля.

### Готовые поля и общий контекст

Готовые поля — переиспользуемые понятные определения, как готовые графы. Их использование должно быть явно в данных, чтобы ИИ и приложение легко получали список полей графа/набора; одного упоминания в тексте канона недостаточно.

Нужно различать:
1. Определение поля.
2. Его использование/роль/условия в конкретном месте.
3. Ответ/значение в проекте.

**Несколько графов одного проекта используют общий контекст всего проекта.** Подходящий ответ мог быть получен при первом подключении готового графа, раньше в другом графе или ранее в обсуждении. Сначала находить известное, а не повторять вопрос. Общность не отменяет время, scope и происхождение.

Свободные записи разрешены. Если сведения подходят готовому полю, можно сопоставить/связать их, сохранив смысл и источник. Пользователь не обязан знать технические IDs или сразу выбирать правильное название. Неоднозначный match не должен молча подменять факт.

### Веточность и момент вопроса

«Веточное поле» — **характеристика использования в полном списке потенциальных полей**, не отдельный контекст/хранилище/ответ ветки.

- То, что действительно нужно сейчас, выясняется как можно раньше с учётом уже известных ответов.
- Поле только для дальнейшего прохождения условной ветки становится предметом вопроса после выбора этой ветки.
- Полный список может показывать потенциальные поля заранее, с условиями; это не означает ранний опрос обо всём.
- Одно поле может иметь несколько consumers/условий; число упоминаний не определяет актуальность.
- Поле для **оценки варианта до выбора** может быть нужно сейчас, даже если встречается у одного варианта.
- Изменение выбора меняет актуальность usages, а не стирает ранее полученный ответ.
- Открытие графа и показ альтернатив на экране не являются выбором решения.

Различие оценки до выбора и исполнения после выбора — логическое уточнение реализации; его нужно критически проверить на реальных сценариях, а не механически присвоить всем полям.

### UI и DRY

Предложенная форма принята к исполнению командой выполнить план: блок полей около главной R, сверху немного слева; агрегат на графе графов; режим инспекции полей вместо перехода при клике; выключение возвращает навигацию; общий блок открывается в любом режиме. Информационные блоки не R/D и не участники graph-set. Пиксельная геометрия не FR.

DRY относится к смыслу, данным, документации и общим алгоритмам. Один authoritative owner определения, источника и общего ответа; consumers используют refs и собственные условия. Производные bundle/index/cache и исторические snapshots допустимы, если не становятся вторыми редактируемыми owners. Не сливать разные концепты из-за совпавшего имени; не строить универсальный framework без нужды.

- один уровень под-R, группы/возврат/поиск и общий layout для пользователя/ИИ;

- кнопки прежнего R→D→R/«Все связи» переименованы в **«Основная цепочка»** и **«Связи и контекст»**, с пояснениями.

## 8. Начальные оси независимого review

Сначала составь собственные оси, затем исполняй проверку. Этот список — ориентир, не исчерпывающий baseline:

1. **Полнота смысла и provenance:** что было прямым уточнением, что tentative UI, что технический выбор; не изменена ли задача ради реализации.
2. **DRY и owner:** все consumers, актуальные definitions/sources, запись значений, history/pins; действительно ли нет скрытых вторых owners или вручную расходящихся алгоритмов.
3. **Пользовательский путь:** подключение готового графа/набора → общий список → ранее известное → только нужные вопросы → выбор/пересмотр → reuse; usefulness, затраты пользователя.
4. **Условия и ветки:** поле оценки до выбора; execution после выбора; несколько условий; несколько путей к одному графу; неизвестный путь; скрытые альтернативы; single-graph из набора.
5. **Полнота данных/ссылок:** link-only, пустые declarations, missing owner/member, sources для самого поля и канона; безопасность URL; отсутствие ложного complete.
6. **Свободный контекст и актуальность:** ранний ответ, ambiguity, provenance, конфликт, дата/timezone/scope, template/example/другой project, отсутствие identitySpace.
7. **Реальная запись:** schema/guards, revision/replay, восстановление при сбое, cross-file package, Context owner, annotations, сохранность T1 при обновлении source/answer; read-back и derived rebuild.
8. **UI/регрессии:** служебные blocks/режим клика/возврат/поиск, видимость/доступность ссылок, layout IDs, колесо/подписи/группы, drag/autosave/native recovery.
9. **Доставка/доказательства:** одинаковый shared embed, генераторы, import/13 IDs, два delivery files, что реально установлено. Зелёные тесты не равны полной семантике или Windows E2E.
10. **Качество исполнения ассистента:** достаточность исходных данных, реальные операции/ссылки, scope/полномочия, неоправданная сложность, полнота выводов.

Для material осей нужен фактический тест/чтение/evidence или конкретное ограничение. WR/EA плана — начальные ссылки, не весь review. Подтверждённый defect = Problem, механизм будущего сбоя = Risk, реальная развилка = Decision Uncertainty, улучшение допустимого пути = Opportunity. Evidence Gap отдельно. Для material находок: воспроизведение, источник ожидания, CURRENT/UPSTREAM относительно scope, disposition, срочность/внимание и связанный Proposal/следующее действие. Не присваивать Problem лишь по новому удобному маршруту, не подтверждённому пользователем.

После основного review сделай один короткий контроль исполнения самой команды; не создавай бесконечное meta-review.
