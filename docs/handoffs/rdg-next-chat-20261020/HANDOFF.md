## 2. Поздние уточнения пользователя о модели — обязательная основа продолжения

### 2.1. Что является моделью планирования

Граф RDG уже моделирует цели, способы их достижения, Requirements и предварительные продолжения.
Можно подробно построить несколько ветвей вперёд, не принимая предыдущие Actions.
Новая отдельная сущность называется «план во времени»: она задаёт явные время и/или порядок существующих R и Actions.

Временной план не является планом функциональности создаваемого приложения.
Приложение, описание функций или другой артефакт может быть результатом достижения цели RDG; содержание артефакта не превращается автоматически в расписание работы самой RDG-модели.

Создание Action не размещает его в плане. Создание R также не размещает её.
Пустая будущая часть допустима. Планировать можно ещё не выбранные Actions и потенциальные R.
Размещение не является выбором, выполнением или доказательством достижимости.

В плане нет самостоятельного создания новых предметных «пунктов».
Ручное создание и изменение сущностей находится во вкладке графа; план только ссылается на уже существующие записи и меняет их размещение.

### 2.2. Action — один экземпляр действия

Один Action ID — один экземпляр действия. Выполненный Action остаётся выполненным историческим экземпляром.
Правка графа, канона, QRPE или определения после выполнения не создаёт второе исполнение того же ID.

Для той же цели можно:
A1 выполнен → выбор A1 отозван → выбран другой Action A2 → выполнен A2.
Старое выполнение, отзыв и новое выполнение сохраняются отдельными фактами.
Сам выбор A2 ещё не означает его выполнения.

Повторные физические исполнения одного Action были предположением ассистента и исключены из текущего scope.
Не вводить recurrence engine, обязательные occurrence для каждого исполнения или отдельную модель повторений без нового требования.
Исторические эксперименты с несколькими Plan-вхождениями одного Action не означают несколько исполнений Action.

Отдельный lifecycle закрытия шага расписания сейчас не нужен.
Будущее исключает выполненное по данным/расчёту графа; историю хранит тот же semantic owner.
Отзыв выполненного Action не стирает факт его выполнения и не доказывает отмену результата во внешнем мире.

### 2.3. Разные факты и два вида дочерних R

Не смешивать:

- существование предварительного варианта;
- принятие/выбор Action;
- введение подцели;
- выполнение Action;
- достижение R;
- размещение во времени;
- сохранение правки графа;
- подтверждение внешнего факта.

Связи и роли:

| Смысл | Представление |
| --- | --- |
| Выделение подцели или связанного набора подцелей | Родительская R → Action → дочерние R с childRole=subgoal. |
| Корректность выполнения конкретного способа | От этого Action идут необходимые ему R с childRole=method_correctness. Challenge относится к способу. |
| Выбор, каким способом выполнить Action | Через R «решить, как выполнить Action» и её варианты Actions. |
| Введение необязательной R для Action | Семантически отдельный Action; физическое представление этой дополнительной связи пока не определено. |
| Уточнение существующей R | DERIVES. Это не принятое разбиение и не замена INTRODUCES. |

Action типа decomposition выделяет подцель или связанный набор. Обычный general тоже может вводить подцели и иметь свои Requirements корректности.
Не создавать фиктивный отдельный Action для каждого обязательного Requirement корректности.
Не строить произвольное дерево Action → Action вместо этих R.
Не навязывать листовому Action дополнительную цель результата, если его собственное определение достаточно.

Непринятые продолжения: prepare_action_requirement / OUTCOME_OF.
Нельзя просто разрешить актуальное INTRODUCES у candidate, меняя смысл связей.
При выборе повышаются подготовленные связи и те же ID только выбранного Action; непринятые потомки не выбираются автоматически.

### 2.4. Как понимать завершённость

R достигается по обязательным выбранным Actions и подцелям своей выбранной композиции.
Невыбранные альтернативы и необязательные ветви не должны блокировать её.
Пустой список зависимостей не означает автоматического успеха: листу нужен записанный результат по его определению.

Выполнение Action определяется его собственным определением и Requirements корректности.
Выполнить Action разбиения — ввести нужные подцели и выполнить требования корректности разбиения.
Достичь созданных подцелей — отдельная работа. Родительская R может оставаться недостигнутой после выполненного decomposition.

У выполненного Action различаются неизменный исторический complete и currentScopeComplete для подтверждения текущей композиции.
Поздняя смена обязательного состава не должна делать старый результат доказательством нового состава родительской R.
Недоступный/неразрешённый обязательный owner — неполнота знания или отказ, не автоматический успех.

Нужно сохранять исходные basis, basisSHA256, определение и набор выходных R на момент результата.
Явные результаты сохраняют свой scope операции; автоматические производные результаты вычисляются по финальному составу транзакционного пакета, без ложных промежуточных успехов.

### 2.5. История и поздние сведения

Выполнение возможно без предварительного размещения: результат сразу попадает в историю.
Фиктивный будущий шаг задним числом не создаётся.

История сохраняет те же сущности, ID и owner refs; правка графа не равна выполнению всех изменённых Actions.
Неизвестное старое время/автор не выдумываются.

T1 — исходное основание выбора. Позднее знание о существовавшем во время T1 обстоятельстве отличается от действительно нового изменения после T1.
Не переписывать исторический T1 текущими ответами, канонами или source revision.
В текущих legacy-примерах T1 остаётся на подготовленном source revision 3; современные pins уже на revision 6.

С Viewer 2.3.0 новые action_executed и requirement_achieved содержат отдельный viewSnapshot материала с SHA.
Канон/QRPE как аннотации не включены в нормативный completion basis и не сбрасывают выполненную работу.
История берёт именно сохранённый материал; для отзыва — priorActionSnapshot.
У старого результата без снимка канона/QRPE UI явно сообщает об отсутствии. Текущий узел не подставляется как якобы исторический.

### 2.6. Что поздние уточнения отменили как обязательный маршрут

- Автоматическое добавление всех созданных Actions в будущий план.
- Отдельное закрытие шагов расписания как второй owner выполнения.
- Повторное исполнение того же Action ID после его правки.
- Обязательную дополнительную цель результата для любого листового Action.
- Автоматический baseline по knownAt/effectiveAt как предварительное условие ручного пути.
- Обязательный lifecycle принятия Plan перед текущим явным размещением.
- Обязательные три стадии claim/attestation/review для каждого результата текущего workflow.
- Возврат ко всем старым P2 PARTIAL перед проверкой готового пользовательского пути.
- Новый сервер, production root, scheduler или миграцию legacy как само собой назначенную следующую задачу.

Код этих прежних исследований может сохраняться. Не удалять его и не объявлять бессмысленным; не навязывать его текущей работе без сопоставления с действующими требованиями.

## 6. Семантика writers, owners и прав, которую нельзя потерять

- RDG — semantic owner Requirements/Actions/Canon/QRPE/Findings/выбора и результатов.
- Plan — отдельный owner времени/порядка/ссылок и прежних поддержанных условных данных; не копия Actions.
- Activity/workflow — read-only представления существующих owners, не отдельная база выполнения.
- Один semantic owner на identity; projectionOf/expansionOf и continuation не создают второго владельца той же R.
- Межфайловой расчёт ограничен опубликованной авторизованной candidate-v6 композицией внутри одного Graph root.
- Один rdg-completion-context.py обслуживает writer и readers, разрешает владельцев и roles.
- При выборе в continuation driverOwnerSnapshot закрепляет настоящую R; локальный driverSnapshot сохраняется.
- События результатов записываются в настоящих owners; вычисленный, но ещё не сохранённый результат не выдаётся за историю.
- Locks, exact read set, catalog/source pins и permissions обязательны; missing owner — отказ/неполнота.
- Пакеты остаются CAS/revision checked, восстановимыми, с idempotent retry.
- Retry одной транзакции — повтор подтверждения записи, не новое физическое выполнение Action.
- Потерянный ответ сохраняет точный pending request и блокирует новое действие, пока исход не определён.
- Право создавать candidate не даёт права select; право Plan edit не даёт graph.select_action.
- Отзыв имеет отдельное право; protected R и shared-child dispositions не обходятся.
- Клиент не задаёт basis, basisSHA256, completionMode, recordedAt, triggerEventId, viewSnapshot или его SHA произвольно — эти поля формирует writer.
- Прямая правка исторических событий/selectionBasis не используется как способ ремонта.
- Manual by:user означает origin явно запущенной локальной сессии с process-local MAC и тем же bearer principal, не verified human identity.
- Обычный bearer не получает by:user одним полем payload.
- Grants, revoke-before-commit, Origin/Host/session guards и token redaction не ослаблялись.
- Helper не содержит admin UI и не выдаёт новые grants автоматически.
- Не трогать реальные графы/Plan/ACL/mounts/туннели ради демонстрации без соответствующего пользовательского scope.

### 6.1. Точные ограничения ручного Helper

- Прямой файл записи графа фиксируется при запуске Helper. Передача graphFile не перенаправляет graph write на другой файл.
- Размещение может ссылаться на другие уже прочитанные авторизованные sources через capability plan.place.from-read-sources; это не право изменить их графы.
- Helper обслуживает candidate-v6 workspace. Учебный read-only Action-пример открывается встроенным режимом просмотра, а не выдаётся за writable Helper workspace.
- Текущий простой Helper принимает Plan без branches и без старых event/gate steps; предварительные ветви внутри самого графа допустимы.
- Двух текстовых полей канона недостаточно для сложного canon metadata. Если такой metadata присутствует, GUI отказывает до записи с HELPER_COMPLEX_CANON_USE_FULL_API; использовать полный API, не стирать sourceRefs/contextUses/interpretation/check metadata ради удобства.
- Protected R через этот ручной Helper не меняются. Нет admin/grant UI.
- Межфайловой resolver читает опубликованные workspace owners затронутого identitySpace, а не только минимальную ветвь.
  Нужен graph.read на загруженные owners; для каждого нового производного результата также его result permission либо graph.write у настоящего owner.
  Недостаток прав означает отказ без частичного пакета, а не повод расширить grants автоматически.
- Общий lock/catalog protocol является границей поддержанной записи; raw OS/file write в обход него не является distributed/OS-sandbox гарантией.

### 6.2. Безопасная правка размещения PR-01 уже сделана

Нельзя потерять при изменении UI:

- прежний Graph ref и наблюдённую revision;
- deadline, strength, basis;
- minDelayDays;
- исходящие sequence-связи других шагов.

Отсутствующее поле сохраняет прежнее условие. Явная пустая дата снимает только notBefore.
Явный пустой afterStepId снимает только входящее предшествование.
Unplace отдельно снимает размещение с incident constraints/sequence.

Простой GUI не должен упрощать несколько notBefore, несколько предшественников или precise datetime.
Он отказывает до записи с HELPER_COMPLEX_PLACEMENT_USE_FULL_API / HELPER_DATE_ONLY_USE_FULL_API и направляет к полному API.
Полный API сохраняет существующий replace-контракт явно переданных sequence/timeConstraints.
