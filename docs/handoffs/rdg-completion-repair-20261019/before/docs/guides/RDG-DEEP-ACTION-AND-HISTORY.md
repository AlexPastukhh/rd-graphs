# Глубокие предварительные ветви, разбиение и история результатов

Статус: **Candidate, локальная реализация в Repo**. Определения принадлежат
[руководству граф-модели](RDG-V7-WORKING-GRAPHS.md). Этот документ описывает API.
Stage 4 остаётся **NOT ACCEPTED**. Установленный Windows Viewer не проверен.

## Подготовка без принятия

В opt-in `actionModel: candidate-v6` можно строить продолжения под непринятыми
Actions и под их непринятыми потомками. Каноны и QRPE остаются на своих владельцах;
глубина предварительной ветви не требует принятия предыдущих Actions.

У Action есть необязательное поле `actionType`:

| Значение | Смысл |
|---|---|
| `general` или отсутствие поля | Обычный Action. Может выполнять работу и выделять связанную группу подцелей. |
| `decomposition` | Action выделения одной подцели или связанного набора подцелей. Выбор другого набора представлен другим Action. |

У обоих типов допустимы дочерние R двух ролей:

| `childRole` | Чьё выполнение требует достижения R |
|---|---|
| `subgoal` | Родительская R: это часть её разбиения. |
| `method_correctness` | Сам Action: это Requirement его корректного выполнения. |

Все `subgoal` одного Action составляют связанный набор. Несколько альтернативных
наборов задаются несколькими Actions; несколько выбранных Actions входят в текущую
обязательную композицию совместно. Тип Action не заменяет роли его дочерних R.

К существующему package writer добавлена операция:

```json
{
  "op": "graph_edit",
  "action": "prepare_action_requirement",
  "actionId": "A1",
  "childRole": "subgoal",
  "edgeId": "A1-R1-potential",
  "node": {"id": "R1", "kind": "requirement", "title": "Подцель"},
  "event": {
    "id": "EV-PREPARE-R1", "type": "graph_changed",
    "operation": "prepare_action_requirement",
    "by": "assistant", "note": "Проработать предварительную подцель"
  }
}
```

Вместо `node` можно передать `requirementId` существующей локальной R. Нужен grant
`graph.graph_edit.prepare_action_requirement` либо существующий `graph.write`
с подходящим scope. Новый узел получает `status: potential`; связь — `OUTCOME_OF`
с явными `parent` и `childRole`. Это не `INTRODUCES` и не принятие.

Под этой R обычный `add_action` создаёт следующие варианты. Каноны редактируются
через `graph_edit/edit_node`, QRPE — существующими операциями. Ненужную
предварительную связь можно архивировать через `graph_edit/archive_edge`.
Старый узел и история сохраняются. Нет автоматической миграции legacy O/D.

`select_action` переводит подготовленные связи выбранного Action в `INTRODUCES`
с сохранением ID. Потенциальные локальные R становятся активными. Каноны, QRPE
и дальнейшие непринятые Actions сохраняются; потомки не выбираются автоматически.
Другой предварительный вариант может ссылаться на ту же R, не становясь принятым.
Для принятого `decomposition` требуется минимум одна R с ролью `subgoal`.

Viewer в исходнике показывает глубокую предварительную ветвь через «Все ветви»;
каноны, QRPE, тип Action и роли R доступны в существующем подробном просмотре.
Явное `expansionOf/projectionOf` позволяет продолжать предварительную R в другом
файле с одним владельцем. Совпадения ID недостаточно.

## Результат и расчёт

Новые операции package writer:

- `record_action_execution`: `targetId` Action, событие `action_executed`;
- `record_requirement_achievement`: `targetId` R, событие `requirement_achieved`.

Событие содержит уникальный `id`, тот же `targetId`, `by` и непустой `note`
с описанием результата. Нужны соответственно `graph.record_action_execution`
и `graph.record_requirement_achievement`, либо `graph.write`. Writer назначает
технического автора, время записи и снимок состава/определения результата.
Клиент не подставляет `basis`, `basisSHA256`, `completionMode` или `recordedAt`.
Это запись результата в графе, а не независимая проверка реального мира или F-P.

Листовой Action не требует искусственной R результата. Сам факт выбора, пустой
список дочерних R и редактирование графа не означают выполнение. Action выделения
подцелей может быть выполнен, пока созданные подцели ещё не достигнуты.

Составной Action рассчитывается по своим `method_correctness`. Родительская R —
по выбранным Actions и их `subgoal`. Когда все обязательные зависимости выполнены,
writer добавляет отдельные производные события выполнения/достижения. Невыбранная
альтернатива не блокирует результат. Обязательную невыполненную или неизвестную
зависимость нельзя обойти прямой записью успеха. Запись вне актуального выбранного
пути отклоняется. После изменения определения прежняя история сохраняется;
новое определение составного узла требует явной переоценки результата при
выполненных зависимостях. Каноны/QRPE не стирают уже сделанную работу.

Расчёт сейчас ограничен одним файлом-владельцем. Внешняя `projectionOf` не считается
достигнутой без разрешения владельца. Межфайловое завершение, повторные исполнения
в разных вхождениях плана и автоматическое исключение из будущего ещё открыты.

## Общая читаемая история

```sh
python3 -B tools/rdg-activity.py --graph-root /path/to/graphs \
  --graph workspaces/example/graph.json --format markdown
```

`--graph` можно повторить для нескольких разрешённых владельцев. По умолчанию
возвращается JSON с `activities` и `currentCompletion`; `--outcomes-only` показывает
только результаты. При включённом bearer store нужны `graph.read` и scope каждого
указанного файла. Автоматического расширения прав нет.

Лента объединяет сохранения графов, выполнения Actions, включая `decomposition`,
и достижения R. Сохранение правки остаётся отдельным видом записи. Время успешного
сохранения берётся из completed journal, старое неизвестное время остаётся `null`.
Технический bearer principal сохраняется и для правок без отдельного graph event.
Повтор транзакции не добавляет второй успех; prepared/отклонённые операции не выдаются
за завершённые сохранения. Reader держит общий read lock writer. Pending journal
запрошенного графа вызывает RECOVERY_REQUIRED, включая сбой после записи graph.json,
но до завершения журнала. Чтение не меняет источники и не создаёт Temporal Plan.
В schema-v2 journal добавлен необязательный authorityPrincipal; старые schema-v1/v2
читаются, exact-history reader принимает это поле с проверкой типа.

Общая GUI-лента, пользовательские фильтры/понижение приоритета и новый ручной editor
ещё не реализованы. В существующем Viewer добавлен просмотр истории результатов
конкретного узла. Публичный API не меняет границы аутентификации Helper.
