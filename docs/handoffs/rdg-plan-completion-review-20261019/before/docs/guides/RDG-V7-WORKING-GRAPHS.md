## Уточнение модели: граф, план во времени и выполнение — 2026-10-19

Ниже зафиксирована требуемая пользователем семантика. Она имеет приоритет
над прежними Candidate-догадками о Plan. Реализация соответствует ей частично;
наличие определения в руководстве не означает готовую операцию API.

### Граф и план во времени

Граф целей/Requirements и Actions уже позволяет планировать на бумаге:
строить несколько предварительных вариантов и их продолжения, не принимая
предыдущие Actions. Причинные связи и разбиение не задают порядок выполнения.

**План во времени** добавляет явное время и/или порядок выполнения выбранных
для размещения целей и Actions. Размещать можно предварительные, ещё не принятые
сущности. Само создание Action не добавляет его в будущую часть плана во времени.
Будущая часть может быть пустой. В текущем Plan writer новая запись Action-шага
требует timeConstraints или участия в sequence; одна ссылка без размещения
не сохраняется как новый будущий шаг. Только порядок допустим без даты.
Старые schema-v1 snapshots остаются структурно читаемыми; старый принятый
transactionId можно повторить без новой записи. Это проверка новых записей,
а не переопределение прошлой истории. Размещение R ещё не реализовано.
Назначение времени не является принятием Action. Это исправляет прежнее
предположение ассистента об автоматическом добавлении всех созданных Actions.

Можно создать Action и выполнить его без предварительного размещения.
Выполнение попадает в историю выполнения плана во времени с исходным Action;
фиктивный будущий шаг задним числом не создаётся. Предварительное размещение
нужно, когда важно заранее задать «сейчас/потом», дату или иной порядок.
История сохранённых изменений графа также должна быть доступна; запись правки
и факт выполнения работы различаются по смыслу. Существующие writer journals
и события теперь читаются через `rdg-activity.py`: сохранения графа, выполнения
Actions и достижения R. Это общая CLI-лента JSON/Markdown; отдельная GUI-лента
ещё не реализована.
Фильтры/приоритет истории второстепенны.

Предмет RDG — цели, способы их достижения, Requirements и работа с этой моделью.
План приложения, расписанная функциональность или другой создаваемый артефакт
могут быть результатом достижения цели в RDG. Содержание такого артефакта
не превращается автоматически в план действий самой граф-модели во времени.

### Откуда возникают подцели и Requirements

| Смысл | Требуемая связь и место challenge |
|---|---|
| Выделить подцель-разбиение R | Родительская R → Action выделения подцели или связанного набора подцелей → подцели R. Это тип decomposition. Другой вариант набора задаётся другим Action; каждый можно оспаривать отдельно. |
| Корректно выполнить способ A | У R есть вариант Action A; от A исходят необходимые ему R с ролью method_correctness. Challenge относится к этому способу A, а не к выдуманным отдельным Actions создания каждой обязательной R. |
| Введение необязательной R для A | Введение такой R само представляется отдельным Action и может быть оспорено. Физическое представление связи с исходным A ещё нужно определить; новый тип ребра этим текстом не вводится. |
| Выбрать, каким набором подцелей реализовать A | От A выделяется R «решить, как выполнить A»; варианты Actions и их подцели находятся в R-графе этой R. Произвольное симметричное дерево вариантов Action → Action не вводится. |

Обычный Action (general) тоже может выделять связанный набор подцелей родительской
R и одновременно иметь собственные Requirements корректности. Тип decomposition
определяет назначение Action, а не отменяет его собственные Requirements.
Роли subgoal и method_correctness сохраняют разный смысл. DERIVES как уточнение
R не является доказательством принятого разбиения или замены Action создания
подцели. Корневая R и самостоятельное уточнение R не выдаются за подцель-разбиение.
Потенциальное продолжение непринятого Action должно быть представимо без
молчаливого принятия этой ветви и без превращения потенциальной R в актуальную.
В текущем writer это реализовано через prepare_action_requirement и OUTCOME_OF
для candidate Action. Под непринятым продолжением можно строить следующие
Actions, каноны и QRPE. Выбор переводит только его подготовленные связи в
INTRODUCES, с сохранением идентичности и без выбора непринятых потомков.
Контракт API и ограничения: [глубокие Actions и история](RDG-DEEP-ACTION-AND-HISTORY.md).

### Достижение и выполнение

Достичь R — выполнить обязательные подцели выбранного разбиения и выбранные
Actions выполнения этой R. Не выбранные альтернативы и не включённые в выбранную
композицию необязательные ветви не входят в обязательное «всё выполнено».
Расчёт относится к конкретной выбранной композиции и активным связям.
Недоступная или неразрешённая обязательная зависимость означает неполноту
знания, а не автоматический успех.

Action создания подцели завершается созданием/введением подцели в модели.
Созданная подцель при этом может оставаться недостигнутой: её достижение
требуется родительской R, а не для признания выполненной работы по её созданию.

Выполнить составной Action — достичь обязательных целей/Requirements,
необходимых для его корректного выполнения. Подцели, создаваемые Action разбиения
для родительской R, и собственные требования корректности этого Action имеют
разные роли; их нельзя автоматически смешать в один список.

Action может не иметь подцелей: если его собственное определение достаточно
ясно и разбиение не оправдано действующими тремя критериями создания сущностей,
дополнительные блоки не требуются. Обязательную «цель результата» ради расчёта
завершённости не создавать. Три критерия этим разделом не переопределяются.
Листовой Action оценивается по собственному определению; пустой список подцелей
не делает его выполненным автоматически. Это же ограничение действует для
цели без дальнейшего разбиения. В текущем API результат записывают отдельные
record_action_execution / record_requirement_achievement. Составная завершённость
рассчитывается внутри файла-владельца с сохранением событий результатов.
Неизвестная роль или внешний неразрешённый владелец не даёт успеха.
После изменения определения прежняя история не переносит успех автоматически
на новый смысл: при выполненных зависимостях нужна явная переоценка результата.

Принятие, выполнение Action и достижение R имеют разный смысл. Автоматическое
закрытие предстоящего в плане во времени опирается на факт/расчёт выполнения
в графе. История, ссылки и исходные основания сохраняются. Само размещение,
создание или выбор Action не подтверждают выполнение. Успешное выполнение
без предварительного размещения имеет ту же историю, что выполнение
предварительно размещённого Action.

## Полный граф Requirements, локальный R-граф и два вида ветвления (Viewer 2.0)

**Основной пользовательский маршрут:** папка → полный граф от конкретной корневой Requirement → клик по любой R открывает **её отдельный R-граф одной волны**. Папка — организация; её расположение и список физических `graph.json` не задают границу полной структуры. Полный граф содержит все **доказанно причинно связанные Requirements от корневой R**, включая доступные продолжения из других файлов/папок. Совпадение `identitySpace`, ID или названий **само по себе не доказывает родительскую связь**; `DERIVES`, `APPLIES_TO` и «та же Requirement» не являются выбранным разбиением. Дополнительные представления связанной R доступны отдельно, без искусственных причинных R-стрелок. Отсутствующий внешний источник обозначается неполнотой, не вымышленным концом.

**Отдельный R-граф** показывает корневую R, её непосредственные варианты/решения и только одну следующую волну R; глубже можно пройти, открыв дочернюю R. Это правило **отображения**, не ограничение глубины исходного JSON, не требование создавать файл для каждой R. Прямое Decision без новых дочерних R законно.

**Полный граф** по умолчанию имеет детализацию **«Только Requirements»**; кнопка **«Показать всё»** временно раскрывает доступные на всех уровнях D и Options, включая способы, ещё не порождающие новую R. Для рабочего проекта есть независимый **охват «Принятое» / «Все ветви»**: первый показывает действующий путь; второй — ещё и непринятые варианты и все уже проработанные потенциальные R следующих волн. Значит, оба переключателя дают четыре сочетания. Подготовленный read-only граф по умолчанию показывает доступные потенциальные Requirements, **не** объявляя никакое решение принятым в проекте. Ни один переключатель не меняет граф, writer, Decision или QRPE. В подробном виде инспектор показывает **истинный тип и исходный ID** Requirement/Option/Decision, каноны, QRPE, основание выбора и источник; служебный `__cause__` — только визуальный alias. Связь `DERIVES` остаётся доступной в обоих видах как уточнение R, **не** как новая выбранная дочерняя R. Решение со статусом `selected-in-example-only` может выглядеть принятым только при всех учебных ограничениях, в том числе у исходного владельца записи; никогда не становится `main` только из-за проекции.

### Планирование будущего на бумаге

Пользователь **сам** формулирует `origin:situational` Option A и Option B (готовый reusable материал не обязателен), через `OPTION_FOR` и `OUTCOME_OF` записывает возможные будущие R со статусом `candidate/potential`, затем на каждой из них может построить несколько следующих волн. Можно заранее сравнить, как будет выглядеть план при A или B, без `decision_selected`. Даже если в глубине гипотетической ветви подробно представлен локально предпочитаемый способ, он не делает эту ветвь принятой в основном проекте. В «Все ветви» видна вся **записанная** глубина; «Принятое» скрывает всё, чей причинный путь проходит через непринятый вариант. Когда D действительно принято, writer `candidateRequirementId` позволяет сохранить тот же ID и QRPE выбранной ранее спланированной R; соперничающие R не повышаются автоматически, следующие ещё не выбранные уровни остаются потенциальными. Prepared origin и committed status — независимые признаки.

### Экспериментальное ветвление (семантика; Git-runner отсутствует)

Это **не** план на бумаге. После **отдельной санкции** действительно пробуют A и B в изолированных состояниях, часто отдельных Git-ветках, собирают сравнимые evidence и принимают основное решение после проверки. В A может быть **реально принято D-A локально A**, а в B — **реально принято D-B локально B**. Оба не становятся одновременно принятыми в `main`. Git commit/merge **не равен** RDG `decision_selected` и не санкционирует автоматическое слияние/повышение в основном проекте. Проигравшая ветка может сохранять evidence и историю, но не является main. Эта версия **не** реализует создание Git-веток, исполнение экспериментов, сравнение и merge; описан только смысл отношений и полномочий. Канон может советовать обе проверки, но не запускать их.

**Совместимость старых одиночных графов:** если у прежнего `graph.json` нет `identitySpace` или `rootRequirementId`, его нельзя без основания включать в сквозную причинную модель. Он остаётся доступным в папке как локальный граф (например `try-it`) до отдельного подтверждённого upgrade источника.

**Физическое хранение и каталог:** `graph.json` остаётся владельцем соответствующих записей. `graphs/catalog.json` несёт метаданные входов/папок, `graphs/index.json` и JS bundle — производные. Старые `graph-set.json` заменены вычисляемыми **полными графами по rootRequirementId**, после сохранения исходников в независимой проверенной резервной копии. Состав/глубина полного графа не редактируются отдельным списком участников; новые R обнаруживаются из строгих source relations. Точное состояние применимости и ограничение доступных файлов показываются честно. Исторические ссылки на graph-set в более старых обзорах — описание прежнего Viewer, не действующая обязанность создавать набор.


## 1. Что такое один логический проект

RDG хранит одну развивающуюся модель работы от исходного Requirement. Физически работа может находиться в нескольких `graph.json`: каждый раскрывает планирование конкретной R. **Где R возникла** и **где рассматриваются её собственные способы достижения** — разные вопросы. Дочерняя R принадлежит родительскому R-графу как результат принятого D; отдельный граф той же R содержит её дальнейшие варианты и действия. Общий `identitySpace` и точные идентификаторы/проекции задают границы проекта, не сходство названий.

**Не каждое R — Unit.** Unit — отдельный масштаб планирования, который имеет смысл только при действительно самостоятельной работе. Не каждая R требует собственного файла. И **не каждое D требует разбиения**: иногда прямого обоснованного решения достаточно. Соседние R от одного D не задают автоматически порядок выполнения.

## 2. Варианты и канонические ситуации

Готовые способы — **подготовленные кандидаты, которые экономят мыслительную работу, но не исчерпывают все возможные решения**. Даже при двух готовых способах можно вывести третий, ситуативный, и рассматривать все одинаково. Готовое/ситуативное/адаптированное — происхождение, не степень принятия. Принятый ситуативный способ **не становится автоматически готовым шаблоном**: будущая подготовка к переиспользованию — отдельное действие.

**На каждой ветви возможного способа ровно один логический блок канонических ситуаций**. Внутри могут быть несколько рекомендуемых и несколько противопоказанных ситуаций; каждый случай может быть сложным. Каноны не являются фактическими R, D или Context проекта.

> Канон не является фактом нашего проекта: он говорит, что проверить.

Например, для варианта «Разбивать функциональность по Features» положительный канон предлагает проверить, действительно ли нужно независимо прорабатывать функциональные части. Отрицательный канон предлагает изучить Requirements, связанные с согласованностью сквозных процессов. Первый может отсылать к конкретной R; второй — к **содержательной категории** требований. Поиск опирается на исходные R-графы, цепочки принятых D, коллекции и независимые Context. **Каноны направляют поиск, но не исчерпывают его.** Если граф категории недоступен, отсутствие найденного минуса не означает, что минуса нет.

Сильное противопоказание нельзя автоматически «усреднять» числом положительных совпадений. Если способ сознательно принят с риском, он остаётся в QRPE с обоснованием такого выбора.

### Источники, интерпретация и разная степень проработанности

Канон может ссылаться на теорию, документацию, исследование, другой граф или иной материал, который помогает оценить вариант решения. Предпочтителен не пересказ общей теории сам по себе, а смысловая прослойка между источником и конкретными R/option: что из источника здесь важно, при каких условиях это относится к цели и варианту, какие признаки контекста проверить и как результат влияет на выбор.

Допустим и честный материал «пока только ссылка», без подготовленной интерпретации. Готовые графы могут иметь разную степень проработанности; ссылку можно изучить и интерпретировать при конкретном переиспользовании. Ссылка сама по себе не доказывает применимость теории, соответствие канону или выбор D. Не нужно представлять такой материал как уже проработанное обоснование.

Отдельный блок ссылки допустим как средство представления/доступа к материалу; он сам по себе не создаёт R, D, вариант или второй независимый канон той же ветви. Один логический блок канонов может содержать несколько случаев, пояснения и ссылки.

Текущая реализация: canonBlock поддерживает sourceRefs, preparation=interpreted/link-only, interpretation и fieldsComplete; случаи поддерживают checkRequirements/checkCollections/checkCategories и contextUses. Правила источников и единый формат объявленных полей находятся в §15. Отдельный графовый узел ссылки не создаётся; ссылка отображается Viewer в инспекторе, не становится самостоятельным каноном или ответом проекта.

Объяснение готового поля также может иметь ссылки на теорию; общий формат источников/refs и правила DRY определены в §15 этого руководства.

## 3. Композитное Requirement — до принятия D

Сопоставляя каноны с текущей ситуацией, мы уточняем исходную R: **что именно требуется в данном проекте при известных условиях**. Результат — композитное Requirement; это полноценный смысловой драйвер выбранного D.

Например:

- Исходная R: «Разбить функциональность приложения».
- В ходе проверки обнаружены: потребность вести параллельную работу над функциональными областями; существенные сквозные зависимости; ограничения на дублирование.
- Композитное R: «Разбить функциональность так, чтобы части можно было прорабатывать параллельно, сохраняя согласованность сквозных процессов и избегая недопустимого дублирования».

**Один композит может служить нескольким вариантам.** Один и тот же признак бывает плюсом для Features и минусом для сценариев (или наоборот). Не надо создавать по отдельному исходному R на каждый option; специализированные композиты допустимы, если действительно нужны.

## 4. QRPE работает вместе с композитом — до и после выбора

> Композит показывает полноту обнаруженных нами существенных условий. QRPE конкретного варианта проверяет, насколько этот способ отвечает таким условиям и какие проблемы остаются.

Ещё до принятия варианта A в его QRPE может появиться: «Не нарушится ли согласованность сквозных процессов?». У варианта B на основании **того же композита** будет другой вопрос: «Не приведёт ли подход к дублированию общих функций?».

Если пользователь выбирает A, хотя первый вопрос открыт, **открытый QRPE продолжает сопровождать принятое D**. Существенные ранее разрешённые вопросы сохраняются в истории кандидата. Отсутствие QRPE не доказывает отсутствие проблем; наличие открытого QRPE само по себе не запрещает осознанное принятие.

**Сам ход разговора в RDG не записывается**. Можно обсудить много предположений и вопросов, но граф хранит материальные Requirements, варианты, Decisions, композиты, существенные QRPE, статусы и настоящие изменения, а не всю стенограмму.

## 5. История T1, T2, T3

Снимок композита на **T1** фиксирует, *что было реально известно и учтено при выборе*, а не всю объективную реальность того момента.

- **T1:** приняли Features, учитывали требование параллельной проработки; открытый риск сквозной согласованности остался в QRPE.
- **T2:** обнаружили дополнительное требование, **уже существовавшее во время T1**, но тогда пропущенное. Актуальный композит и QRPE дополнились, исторический T1 не переписан.
- **T3:** другое принятое D создало **новое** требование к совместной проверке. Это изменение самого контекста, а не забытый при T1 факт.

Обнаружение нового основания для challenge **не отменяет принятое D автоматически**: нужны повторная проверка и отдельное санкционированное решение.

## 6. От одного D могут возникнуть два вида R

Следующий пример описывает прежнюю базовую реализацию v7. Она уже различает
роли R, но не покрывает полностью уточнённое выше правило отдельных
Actions создания подцелей с собственным challenge. Пример не доказывает
реализованный расчёт выполнения и не заменяет новое уточнение модели.

Например:

    R: Разбить функциональность
      D: По Features [выбрано]
        R1: Проработать Availability               [подцель]
        R2: Проработать Reservations              [подцель]
        R3: Обеспечить согласованность Features   [правильное применение способа]

Все R введены **одним выбранным D**, но роли разные. Каждая может быть исследована через собственный QRPE. Принятие D не означает, что метод уже реализован, а тем более — что исходная R достигнута.

## 7. Коллекция — прозрачное сворачивание

> Если убрать блок коллекции и развернуть все элементы на прежнее место, должны остаться те же R, D, связи, происхождение и актуальность.

Вместо 30 ответвлений под тремя кандидатными способами можно показать три раскрываемых коллекции по 10 потенциальных R. Но коллекция **не становится новым владельцем**, не создаёт вымышленное D и не переводит гипотетические R в актуальные. Семантически её содержимое относится к тому R-графу, где находится место коллекции; физический файл может отличаться.

Так же можно группировать независимо актуальные технические Requirements и сроки под исходной работой **без выдуманного D-разбиения**. При небольшой развилке из 1–2 R коллекция не обязательна.

## 8. Два учебных графа и настоящий рабочий проект

**Текущий каталог Viewer 2.0:** только две активные карточки в папке `Примеры`: полный готовый и полный рабочий граф. Оба теперь содержат полноценный Context (общее поле доступности/WAI, срок, условные детали сценарного способа; в рабочем записан учебный текущий ответ и незамапленная свободная запись), link-only и interpreted каноны нижних вариантов. Маленькие ранние `context-*` примеры перемещены в архив. Переход по R открывает её одну волну; уточнение R (`DERIVES`) не равно введению новой дочерней R. См. `docs/examples/GRAPH-OF-GRAPHS-V7.md`.


- `graphs/examples/reference-prepared-planning-tree/graph.json` — **read-only** многоуровневые готовые способы. Для каждой показанной потенциальной подцели есть два способа с канонами; ни одно D не принято в реальном проекте.
- `graphs/examples/reference-mixed-active-work/graph.json` — **read-only условная история**: Features/Scenarios/ситуативный способ, общий композит, кандидатный QRPE, выбранное D *только внутри примера*, два вида введённых R, T1/T2/T3 и 3×10 потенциальных ветвей в коллекциях. Это не запись пользовательского согласия.
- `graphs/workspaces/<slug>/graph.json` — **настоящий writable workspace**, который создаётся для конкретного действительного требования; здесь изменения должны происходить только через штатный writer с авторитетной санкцией, а не копированием решений из примеров.

### Начать новый настоящий проект

Используй только реальную согласованную цель пользователя:

```bash
python3 tools/rdg-new-workspace.py --slug my-app --title "План приложения" \\
  --root-id R-APP --root-title "Создать приложение" --identity-space my-app --dry-run
# После проверки и подтверждения действительной цели — то же без --dry-run.
```

Создатель не перезаписывает существующие workspaces и создаёт одну R с **нулём принятых решений**, `qrpe: []` и `collections: []`.

### Записать варианты, каноны и композит

`tools/graph-apply.py` и `tools/graph-package.py` работают через `expectedRevision` и атомарный **для одного файла** publish плюс существующий recoverable multi-file package journal. На каждый набор материальных изменений — новый patch. Пример сокращённой структуры операции:

```json
{
  "schemaVersion": 1, "expectedRevision": 1,
  "operations": [
    {"op":"add_option","requirementId":"R-APP","option":{
      "id":"OPT-FEATURES","kind":"option","title":"Планировать по Features",
      "origin":"prepared","status":"candidate",
      "canonBlock":{"recommended":[{"id":"p1","text":"Нужна независимая работа над частями"}],
                    "contraindicated":[{"id":"m1","text":"Сильные сквозные зависимости"}]}
    }},
    {"op":"add_composite","requirement":{
      "id":"R-COMP","kind":"requirement","title":"Спланировать приложение с учётом ограничений",
      "compositeOf":"R-APP","status":"candidate",
      "history":[{"id":"T1","recordedAt":"2026-10-15",
                  "statement":"Спланировать приложение с учётом ограничений",
                  "facts":[{"ref":"R-APP","state":"checked-present"}]}]
    }},
    {"op":"append_qrpe","targetId":"OPT-FEATURES","issue":{
      "id":"Q1","text":"Как обеспечить сквозную согласованность?","status":"open"
    }}
  ]
}
```

Вызов: `python3 tools/graph-apply.py --graph graphs/workspaces/my-app/graph.json --patch /path/to/patch.json --dry-run`. После dry-run применить без `--dry-run` только разрешённые пользователем изменения и прочитать файл обратно.

**Выбор D** — отдельная операция `select_option` с `optionId`, `driverId`, новым D и **действительно санкционированным пользователем** событием `decision_selected` (`by: "user"`, `note`, `decisionId`). При выборе сохраняются исходный композит и блок канонов, а открытый QRPE переносится в принятое D. В операции `children[]` каждый реальный child имеет `role: "subgoal"` или `role: "method_correctness"`; потенциальные R остальных ветвей не создаются. Не записывай `by: "user"`, если пользователь не принимал решения.

Поздние изменения композита: `append_composite_revision` с `requirementId` и revision (`id`, `recordedAt`, `effectiveAt`, `statement`, `facts`). QRPE: `append_qrpe`. Переход статуса **того же** вопроса: `transition_qrpe` с `targetId`, `issueId`, `transition: {id,status,recordedAt,note}`. История остаётся в `statusHistory`; нельзя закрывать Q1 новым несвязанным Q2. Прямая перезапись `history`/`qrpe`/`canonBlock` через `update_node` запрещена.

При выборе `origin=prepared` обязательно указать `preparedSource` с `graphSlug`, `sourceOptionId`, `version`, `canonHash`. В writer проверяются реальный read-only шаблон, совпадение версии и SHA-256 канонического JSON блока канонов. Произвольные строки и отсутствующий источник отклоняются. Изменённый способ должен иметь отдельную версию или `origin=adapted`.

При выборе второго D для того же R одного различия названий `scope` недостаточно: необходимы `disjointFromScopes` и поясняющий `scopeDisjointReason`, иначе отказ `SCOPE_OVERLAP_UNKNOWN`. Это требование явного обоснования, а не автоматически доказанное отсутствие пересечений.

**Полномочия:** `event.by="user"` само по себе не удостоверяет пользователя. Writer получает утверждение из JSON, поэтому доверенный вызывающий контур обязан независимо проверить действительное согласие до записи. Подготовленный вариант, внешний Context и тестовые данные не дают права принимать D.

**Коллекция:** `add_collection` с `collection: {id,title,anchor,memberRefs}`. Это сохранённая группировка без смены owner/member ID и без событий принятия. Viewer разворачивает блок на месте.

## 9. Viewer и общий контекст

В Viewer «Показать все варианты» **независимо от** «Все связи»: если у данной R нет выбранного D, все её варианты видны по умолчанию; если выбран, в основном виде показывается принятый путь. При этом у дочерней R без выбора её варианты остаются видимы, даже если выбрано D её родителя. Для больших наборов раскрывай коллекции по запросу. Общая ситуация проекта доступна в инспекторе и определяется по реально проиндексированным R/D/C одного `identitySpace`. Если граф или внешняя категория не проиндексированы, полнота контекста неизвестна.

Viewer предназначен для чтения. Реальная запись происходит через writer/Helper; клики по SVG не заменяют commit.

## 10. Что пока не следует обещать как уже реализованное

План v7 шире текущего начального внедрения. **Пока не реализованы как полноценный подтверждённый workflow**: полная семантическая переоценка после изменения происхождения/deactivation R (локальные и межфайловые сигналы проверки уже доступны); автоматическая переоценка композита при изменении соседних файлов; автоматическое доказательство непересечения scope (неизвестное пересечение теперь отклоняется); отслеживание всех последующих версий prepared-библиотеки (при самом выборе исходный source и canonHash проверяются, T1 сохраняется отдельным снимком); полноценный поиск доступных/недоступных категорий внешнего контекста; проверка browser-installed Helper в настоящем окружении и реальный пользовательский E2E. Они остаются в v7 Verification Plan, а не объявляются завершёнными. Старые исходники, 2D и реальные принятые D не должны изменяться для демонстрации.

## 11. Санкционированный пересмотр R (частично реализован)

Writer поддерживает `deactivate_requirement` с `requirementId` и действительным `event {id,type:"requirement_deactivated",requirementId,by:"user",note}` и `reparent_requirement` с `requirementId`, `newDecisionId`, `newParentId`, `childRole` и событием `requirement_reparented`. При пересмотре исходные связи помечаются как архивные и сохраняются в истории события; зависимые записи с обнаруженными ссылками на эту R получают `needsReview` и `impactSources`. Это **сигнал проверки, не автоматическая отмена D**. Весь проектный пересчёт последствий между разными graph.json и восстановление внешних факторов пока отдельно не подтверждены. QRPE может предложить пересмотр, но сам факт вопроса его не санкционирует.

## 12. Проверить условия канонов в общем проектном контексте

Доступна отдельная **read-only** команда для поиска по точным ID Requirements и коллекций внутри одного `identitySpace`:

```bash
python3 tools/rdg-context.py --identity-space my-app --graph-slug my-app --option-id OPT-FEATURES
```

В одном `canonBlock` у любого случая можно указать `checkRequirements: ["R-TECH"]`, `checkCollections: ["COL-TECH"]` или `checkCategories: ["согласованность"]`. Команда использует проектный инвентарь R/D/C и коллекций из graphs/index.json и отдельно квалифицирует применимость найденных записей по дате/scope, не объявляя недатированные или чужие факты текущими. Она **не доказывает** фактического соответствия канону и не выбирает решение. При отсутствии точного ID/коллекции результат — `unknown`, а не «нет противопоказания». `checkCategories` пока остаётся направлением человеческого/планового поиска: свободную семантическую категорию автоматически по смыслу команда не ищет. Внешние обстоятельства вне индекса и некоторые удалённые источники также не считаются проверенными. После изменения файлов следует обновлять индекс штатным writer/package, а для ручного восстановления использовать `python3 tools/graph-index.py`.

## 13. Превратить уже подготовленную под-R в актуальную без дублирования

Если перед выбором вы расписали потенциальную R внутри варианта, не создавайте вторую R с другим ID только потому, что способ теперь выбран. В операции `select_option.children[]` можно указать **`candidateRequirementId`** вместо нового `requirement`, например:

```json
{"candidateRequirementId":"R-FEATURE-A","role":"subgoal"}
```

Writer проверяет, что это `status=candidate/potential` R и что активная связь `OUTCOME_OF` ведёт к ней **из выбранного** варианта, причём другая ветвь не разделяет ту же кандидатную R. Затем он сохраняет **тот же ID, ранее сформированный QRPE и другую предварительную работу**, архивирует прежнее `OUTCOME_OF` и создаёт настоящую `INTRODUCES` от выбранного D. Снимок исходной кандидатной R сохраняется в событии `promotedCandidateChildren`. Результаты других невыбранных ветвей остаются кандидатными. Если потенциальная R должна использоваться несколькими альтернативами, требуется отдельное осмысленное разрешение её идентичности/связей; writer откажется от неоднозначного автоматического повышения.

## 14. Принятие и повторная оценка D после усиления writer

Уточнённая семантика принятия: успешная штатная запись committed D и соответствующего material event сама является актом принятия. Ed25519-signing gate и approval-request/approval-receipt отменены. Writer по-прежнему проверяет revision, R/driver, source pin, T1/QRPE, безопасный путь и восстанавливаемый journal. by=user — атрибуция события, не криптографическое доказательство. Готовые тексты/Context/гипотезы не разрешают автоматически выбирать D. Старый процесс описан как отменённый в RDG-TRUSTED-APPROVAL.md.

Актуальная общая ситуация и проектный индекс `projectContexts.reviewAlerts` теперь дополнительно сигнализируют о T2/T3 ревизии composite R относительно сохранённого T1 basis выбранного D, о явных зависимостях варианта в другом R-графе и ссылках на R в коллекциях того же owner-графа. Это **кандидаты на переоценку**, не автоматическое подтверждение минуса канона и не отмена принятого D. Неизвестные внешние/семантические зависимости остаются непроверенными.


## Актуальная проверка ситуации после изменения модели

projectContexts.records — доступный проектный инвентарь R/D/C, а не доказательство применимости каждого факта к любому D. Для проверки варианта запусти:
    python3 tools/rdg-context.py --identity-space PROJECT --graph-slug OWNER --option-id OPTION --as-of 2026-10-15 --target-scope mobile
relevantCandidates — данные с проверенным effective-time и совпадающим scope/project-wide; candidatesNeedingAssessment — недатированные, со scope без доказанной применимости; excludedCandidates — будущие, истёкшие или с ошибочным временем. Совпадение с R/C в реестре не доказывает соответствие канону; внешние источники и свободные semantic categories требуют дальнейшего поиска.

checkCollections со строкой — локальная Collection графа, содержащего option. Межфайловый поиск требует точного объекта {"graphSlug":"another-owner","collectionId":"TECH"}. Коллекции разных графов с одинаковым ID не смешиваются.

Для второго D одного R именованный scope не доказывает непересечения с другими. Пути mobile и mobile/app теперь отклоняются как вложенные даже при заявленном disjointFromScopes. Прочие пары со свободным объяснением disjointness получают scopeCompatibility=declared-unverified. Полная модель смысловой совместимости scopes ещё требует отдельного решения.

**Автор записи:** для действительного события writer принимает by=user или by=assistant в зависимости от того, кто осмысленно записал D. Запись committed действует и при by=assistant; это не означает отдельного пользовательского согласия, если его не было. Поле template/example-only в живой записи отклоняется.


## 15. Готовые поля контекстного стейта и общий контекст проекта

Первый пакет реализован в Viewer 1.8.0 по CPW-RDGCTX-20261016-01/v2 (2026-10-16). **Позднее уточнение пользователя в тот же день заменило модель датированной истории ответов на один текущий заполненный/пустой Context value.** Формат ниже — действующий контракт, а старые CPW/handoff остаются историческими срезами. Общий контекст и момент вопроса следуют из указаний пользователя; форма интерфейса — из принятого к исполнению пакета. Здесь единый смысловой и технический owner; экранный план ссылается на него.

### Определение, использование и значение поля

Готовое поле контекстного стейта — переиспользуемое определение с устойчивым идентификатором, понятным названием и смыслом ожидаемого ответа. Такие поля готовятся для переиспользования так же, как готовые графы. Например, поле «Срок готовности» определяет, какие сведения нужны, но не содержит заранее срок нового проекта.

Нужно различать определение поля, запрос/использование этого поля каноном или графом и значение поля в конкретном рабочем проекте. Канон явно указывает нужные ему поля в данных и объясняет их роль в выборе. Упоминания только в свободном тексте недостаточно для надёжного получения списка приложением или ИИ. Поля, необходимые графу напрямую, также должны учитываться, даже если запрос не находится внутри канона.

Несколько графов одного проекта используют общий контекст всего проекта. Известный ответ переиспользуется всеми графами, которым он подходит; отдельная копия ответа на каждый граф не нужна. Ответ мог быть получен при первом актуальном запросе готового поля или раньше, в другом графе/обсуждении. При новом использовании поля сначала нужно найти уже известное значение, а не повторять вопрос автоматически. Если значение противоречиво, устарело или не подходит текущей ситуации, уточняется именно это.

Поля не ограничивают контекст жёсткой формой. Допустимы свободные записи и ситуативные сведения. Если уже известная информация соответствует готовому полю, её можно сопоставить с ним и перенести/связать по смыслу, сохранив содержание и происхождение. Не нужно спрашивать то же заново из-за другого названия или требовать от пользователя точный технический идентификатор. Неясное сопоставление требует уточнения, а не молчаливой подмены.

Готовый переиспользуемый граф содержит определения/запросы, а рабочие ответы относятся к проекту. Подключение одного шаблона к другому проекту не переносит в него факты предыдущего проекта. Общий контекст не означает, что любой факт автоматически подходит любому решению: сохраняются смысл, scope и источник значения. Даты записи не используются для текущих значений полей; временная история принятых D и QRPE остаётся отдельной.

### Когда запрашивать поле: сейчас или после выбора ветки

В списке всех потенциально используемых полей нужно показывать не только их наличие, но и момент/условие актуальности:

- Уже актуальное поле нужно заполнить как можно раньше. При обнаружении запроса сначала переиспользуется известный ответ; если его нет, задаётся вопрос. Ответ также может быть получен не сразу, а по мере уточнения реальной работы.
- Условное поле может понадобиться только для прохождения конкретной ветки после определённого выбора. До этого выбора оно видно в полном списке с условием, но вопросы по нему откладываются. После выбора ветки поле становится актуальным; сначала снова проверяется, не известен ли ответ. Для невыбранной ветки заполнение не требуется само по себе.

«Веточное поле» — характеристика применимости поля в общем списке потенциальных полей готового графа/набора. Это не отдельный тип значения, не собственный контекст ветки и не основание создавать копию поля/ответа. Одно поле может использоваться несколькими графами, ветками и канонами; его значение остаётся в общем проектном контексте.

При определении актуальности нужно различать использование для оценки вариантов до выбора и использование только при дальнейшем прохождении выбранной ветки. Число упоминаний поля не определяет момент вопроса: поле одного канона может быть нужно уже для выбора, а другое — только для последующей работы в выбранной ветке. Условие должно объяснять это различие.

Если ответ на условное поле уже есть, он остаётся доступным, но его наличие не делает невыбранную ветку текущей. Изменение выбора пересматривает актуальность запросов, а не стирает ранее полученные сведения.

### Список для приложения и ИИ

При подключении/начале использования готового графа или графа графов должен быть доступен список объявленных полей: что требуется сейчас, что может потребоваться позже, при каком выборе, где и зачем поле используется, какой ответ уже известен и что ещё нужно выяснить. Поле агрегируется без дублирования определений, но с сохранением всех мест использования и условий.

Агрегация графа графов охватывает весь состав, включая потенциальные ветки, и различает полный список и актуальную сейчас часть. Скрытие альтернатив на схеме не должно уничтожать сведения об условных полях. Известный ответ используется повторно в любом из графов проекта.

Для ИИ нужен явный доступ к этому списку из данных, а не только чтение визуальных блоков или извлечение названий из prose. Материал «пока только ссылка» может ещё не иметь полного списка полей: отсутствие объявлений не означает, что внешняя теория не потребует контекста. Неполнота должна быть видна; выявленные при переиспользовании поля дополняют описание.

### Представление в Viewer

Обычный граф показывает отдельный информационный блок контекстного стейта рядом с главной R, по исходному замыслу сверху и немного слева. Граф графов имеет собственный информационный блок со всеми используемыми полями набора и разделением по актуальности/условиям веток. Эти блоки не являются дополнительными Requirements или участниками graph-set.

В графе графов переключатель просмотра контекста меняет действие нажатия на блок графа: вместо входа открывается список полей этого графа. После выключения переключателя нажатие снова открывает граф. Общий блок контекста открывает агрегированный список при любом состоянии переключателя. Список показывает общие проектные ответы, а не отдельные значения для каждого отображаемого графа.

### Граница с действующей реализацией

projectContexts.records сейчас — производный инвентарь R/D/C и коллекций внутри identitySpace, не отдельный авторитетный владелец фактов и не готовый каталог именованных полей. Прежний запрос rdg-context.py ищет кандидатов по поддерживаемым ссылкам и оценивает дату/scope. Новый режим --fields собирает готовые поля отдельно; подробный контракт ниже.

Ответы остаются в существующих Context owners; определения и источники имеют qualified refs. Реализованный ниже контракт добавляет optional поля к schemaVersion=1 без массовой миграции. Новая функциональность не является задним числом требованием к версии 1.7.0.

### Реализованный контракт 1.8.0: источники, поля и DRY

Общий вычислительный контракт находится в tools/rdg-state.js. CLI Node и встроенный Viewer используют один исходник; Python validator/index/writer вызывает его через tools/rdg-state.py. Для этого пути нужен Node.js. Индекс и bundle — производные копии, не владельцы фактов.

У записи есть один авторитетный owner:

| Сущность | Владелец | Потребитель |
|---|---|---|
| Источник | knowledgeSources[] графа: id, title, url | sourceRefs[]: graphSlug + sourceId |
| Определение поля | contextFields[] графа: id, title, explanation, необязательные sourceRefs | fieldRef: graphSlug + fieldId |
| Использование | contextUses[] графа, узла либо случая recommended/contraindicated (не корня canonBlock) | purpose и необязательное when.allSelected[] |
| Текущее значение поля проекта | один owning узел kind=context с contextFieldRef | contextValue с value/source/scope, либо отсутствие contextValue (поле пустое); consumers читают по ref в identitySpace |

Объяснение поля может ссылаться на теорию, раскрывающую концепт. Ссылка необязательна у каждого поля. В explanation остаётся понятное объяснение ожидаемого ответа; специальная интерпретация для цели/варианта относится к purpose/канону. Один и тот же источник переиспользуется по ref, а не копируется в каждое место. Поддерживаются http/https ссылки без встроенных credentials; материал не исполняется и автоматически не загружается.

Контракт определения и использования, пример формы:
~~~json
{
  "knowledgeSources": [
    {"id": "concept", "title": "Объяснение концепта", "url": "https://example.org/concept"}
  ],
  "contextFields": [
    {"id": "delivery", "title": "Срок готовности",
     "explanation": "Когда нужен результат и насколько обязателен срок.",
     "sourceRefs": [{"graphSlug": "project-root", "sourceId": "concept"}]}
  ],
  "contextUses": [
    {"fieldRef": {"graphSlug": "project-root", "fieldId": "delivery"},
     "purpose": "Оценить способы до выбора"}
  ],
  "contextFieldsComplete": true
}
~~~
URL example.org здесь обозначает форму, а не проверенный теоретический источник. В архивных мини-примерах Context и в двух действующих полноразмерных примерах приведён настоящий источник W3C WAI; архивные `context-prepared/context-working` не служат текущими отдельными root-карточками.

Условное использование имеет when: {"allSelected":[{"graphSlug":"project-root","optionId":"O-A"}]}. Все перечисленные варианты должны быть выбраны; несколько usages одного поля сохраняют свои причины. Если хотя бы одно использование актуально сейчас, поле актуально сейчас. Отсутствие when означает текущую потребность внутри текущего пути — например для оценки ещё не выбранного варианта. Условие про дальнейшую работу задаётся явно. При инспекции невыбранной ветви сохраняется альтернативность её причинного пути; открытие полного или локального графа не активирует вопросы и не принимает D.

canonBlock может иметь sourceRefs, preparation=interpreted с interpretation для конкретной R/option либо preparation=link-only. Для link-only нужны источники; fieldsComplete=true запрещено. contextFieldsComplete описывает полноту объявленных использований графа; fieldsComplete=false/link-only в каноне сохраняет предупреждение неполноты даже при полном графовом списке. Отсутствие декларации полноты не равно доказанной полноте. Интерпретация и материал источника не являются санкцией выбрать D.

Общий Context — текущий стейт проекта, а не журнал получения ответов. У одного owning узла kind=context с contextFieldRef может быть одно contextValue: {value,source,scope}; отсутствие contextValue означает, что поле ещё не заполнено. Текущее значение заменяют или очищают, не создавая историю ответов и не требуя recordedAt/effectiveAt/validUntil/asOf. scope=project означает общее значение проекта; иной scope требует проверки совпадения с запрашиваемой областью (это не история времени). Ответ сохраняет свой смысл и источник. Отдельная история и T1 snapshot принятого Decision не переписываются при обновлении Context: именно T1 фиксирует тогдашние основания решения. Legacy contextAnswers[] в текущем contract отклоняются; существующие записи перед применением новых операций нужно явно перенести в один текущий contextValue, сохранив актуальную подтверждённую информацию, без молчаливого выбора между несколькими прежними значениями.

Штатные операции graph-apply.py / package:
- set_context_contract: contract с contextFields/contextUses/knowledgeSources/contextFieldsComplete; меняет метаданные графа.
- set_context_uses: targetId, uses, note; необязательный caseId для случая канона. Сохраняет прежнюю аннотацию.
- set_canon_material: targetId, material (sourceRefs/preparation/interpretation/fieldsComplete), note. Prepared-вариант с изменённым материалом становится adapted; прежнее основание принятого D не переписывается.
- set_context_value: contextId, fieldRef, value={value,source,scope} для заполнения или обновления одного текущего значения; value=null очищает поле. Создаёт owning Context при отсутствии узла; для смыслового связывания прежней свободной записи необходим mappingNote (исходный текст сохраняется). Даты ответа и история contextAnswers[] здесь не используются.

Пример операции ответа:
~~~json
{"op":"set_context_value","contextId":"C-DELIVERY",
 "fieldRef":{"graphSlug":"project-root","fieldId":"delivery"},
 "value":{"value":"К концу ноября; жёсткость срока ещё уточнить",
          "source":"Ответ пользователя ранее в обсуждении","scope":"project"}}
~~~
Операция входит в обычный revision-guarded patch; стандартные dry-run, transactionId/replay, recovery, read-back и workspace path guards сохраняются. Прямая перезапись привязки/истории через update_node запрещена. Один active owner ответа на qualified поле в identitySpace; другой Context с тем же полем отклоняется. Существующие D/T1 неизменны. Для нового D штатный package writer добавляет selectionBasis.contextSnapshot с разрешёнными объяснениями/ответами этого графа; его наличие не означает, что все вопросы решены.

Полный список для ИИ:
~~~bash
python3 tools/rdg-context.py --fields --graph-slug GRAPH --identity-space PROJECT
python3 tools/rdg-context.py --fields --set-id SET --target-scope project
~~~
Прежний запрос с --option-id и датированной оценкой R/D/C сохраняется **отдельно**; --as-of к --fields не относится. Список полей содержит fields[].usages, state=now/later/unknown, одно answer (или null), answerStatus, nextAction, question, incomplete и свободные Context-кандидаты. Заполненное актуальное поле переиспользуется; пустое актуальное поле требует получить ответ. Свободный контекст допускается: ИИ проверяет смысловое соответствие лишь когда это полезно, не обязан перечитывать каждый свободный Context для каждого пустого поля. При однозначном соответствии существующее значение явно связывают с полем, неоднозначность уточняют у пользователя. Само наличие свободных записей не делает вопрос по пустому полю неактуальным.

В Viewer кнопка «Поля контекста» и пунктирная информационная карточка открывают список; объяснения и источники доступны в нём. На карте наборов «Просмотр контекста: вкл.» меняет клик по графу на инспекцию полей, «выкл.» возвращает вход в граф. Общий блок работает в обоих режимах. Карточка вычисляется рядом с главной R, сверху и немного слева; следует за её положением и не получает отдельного layout key или R/D ID. Её расположение не редактируется независимо. Запись ответов выполняется через writer/ИИ; Viewer сохраняет свою read-only предметную роль.

DRY относится к общим правилам, определениям, источникам, ответам и их документации. Derived index/stateGraphs/bundle/cache и immutable исторические snapshots допустимы: они пересобираются из owners либо сохраняют конкретный прошлый срез. Нельзя редактировать их как вторую текущую базу. Сходные названия с разным смыслом не сливаются ради DRY; разные consumers сохраняют свои условия/интерпретации.

**Исторические мини-примеры (архив):** бывшие `context-prepared-{root,current,alternative}` и `context-working-{root,current,alternative}` теперь хранятся под `graphs/examples/archive/`. Они демонстрировали определения, источники, ранний ответ, условную ветку и link-only материал, но **не являются** действующими полными примерами Viewer 2.0. Вместо них открывайте `reference-prepared-planning-tree` (готовый) и `reference-mixed-active-work` (рабочий): Context, каноны, QRPE и дальние уровни находятся внутри этих двух полноразмерных root-R сюжетов. Все эти данные read-only, не факты пользовательского workspace.
