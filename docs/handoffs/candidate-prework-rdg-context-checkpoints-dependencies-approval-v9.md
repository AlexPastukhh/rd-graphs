### Мини-глоссарий — обязательный смысл для нового чата

- **R / Requirement:** требуемое положение дел с собственным смыслом и состояниями `active/potential`; R **не** получает фиктивный статус `selected` по аналогии с Action. **A / Action:** возможный способ, `candidate` или `selected`; несколько совместимых выбранных A могут работать на одну R. Выбор, исполнение A и подтверждение результата R — разные события.
- **Собственный граф R:** focus R с непосредственными исходящими под-R (`DERIVES`) и реализующими/предлагаемыми Actions (`DRIVES`) и явным **происхождением** R (породившая A через `INTRODUCES`, родительская R и атрибуты происхождения, если они существуют в предметной модели). Видимые входящие overlays сами по себе не становятся бесконечной зависимостью по L2. «Тело» — собственное определение объекта; оно не включает внутренний граф дочернего объекта.
- **Собственный граф Action:** определение A; выходные R через `INTRODUCES`; связанные Canon через `CANON_FOR`; её **реальная ситуация** — реализуемые R через `DRIVES` и реальные Context через `CONTEXT_FOR`. `RELATES_R` с ролью affected/constraining может существовать в полной ситуации RDG, но добавлять его в **L2 по умолчанию только из-за визуальной видимости нельзя**: пользователь назвал реализуемые R. Если требуется иной scope, оформлять отдельно, а не угадывать.
- **Собственный граф Canon:** отдельная фокусная проекция одного Canon и его Action; в каждом из пяти own Canon graphs видны семь повторных occurrences **тех же семи domain criterion identities**, предметно связанные с этим Canon. Один общий Canon-wide комментарий оценивает только его Action; это руководство ИИ, **не машинный veto**. Criterion C3 — вложенный предметный блок, не буквальная часть Canon только потому, что показан в его графе.
- **QRPE:** значимые предметные вопросы, проблемы, риски, возможности и основания с сохранённым контекстом, **не автоматически принятые обязательства**. **Ready/paper Graph** показывает варианты, но не доказывает выбор и исполнение; **working Graph** ведёт фактическую работу; **Temporal Plan** — размещение во времени, но не факт результата. **WorkGraph** — область единого Graph, не новый owner.
- **Stale:** только сигнал необходимости пересмотра по действительной зависимости. Он **не** равен `falsify` (реальный результат опровергнут), `withdraw`/`unselect` A, уничтожению исторического подтверждения, автоматической переделке и не означает, что родительская R сама стала stale при утрате результата дочерней R. Отдельное `review_parents`/проверка текущей полноты может существовать **без parent stale**.
- **Полномочия:** базовый Graph bearer/grant предоставляет доступ к writer; объектный warning лишь возвращает сообщение/условия; hard lock защищает **конкретную операцию конкретной R/A** и требует дополнительное допустимое разрешение. Подтверждение человеком в Viewer даёт право выполнить **только одобренное действие с полномочиями человека**, но не передаёт ИИ его ключ.

## 1. Нужды и критерии успеха

| Need | Наблюдаемая польза |

| **N-01 — Продолжение** | В новом чате ИИ восстанавливает исходную цель, работающие R/A, историю, QRPE, отложенные альтернативы и что делать дальше |

Защищённая R/A.edit в S24 — первый пример, не доказанный исчерпывающий список; точный набор поддерживаемых операций требует API/authority inventory | USER (latest confirmation of approval; scoped technical feasibility pending) |


**Отдельное различие:** новые FR-39–42 фиксируют поведение, **но не** обязывают к конкретной storage-схеме pending requests или конкретному экранному framework. Если реализация найдёт существенно разный пользовательский путь, это отдельный Proposal/decision. FR-42 — предохранение однократности/точности согласия; exact механизм транзакции решается после source inventory.

### Семь общих критериев и пять маршрутов

| Criterion | Единственный domain смысл, повторно используемый в пяти Canon |
| --- | --- |
| **CP-C1** | Компетентность и реальные полномочия текущего ИИ и доступных ответственных участников |
| **CP-C2** | User Benefit и затраты времени, денег, поддержки, багов и усложнения |
| **CP-C3** | Значимость стратегической развилки и альтернативных комбинаций решений |
| **CP-C4** | Обратимость, цена переделки, риск дорогих downstream последствий; не stability field |
| **CP-C5** | Зависимости и объём настоящих stale/review последствий |
| **CP-C6** | Действующие ограничения, locks и правила ответственности/консультаций |
| **CP-C7** | Достаточность Context/knowledge/Evidence и доступные источники недостающего |

| Checkpoint Action | Кто окончательно решает | Что Canon помогает оценить |
| --- | --- | --- |
| **CP-A1 — Self** | инициатор | можно ли исследовать и решить самостоятельно |
| **CP-A2 — Higher AI final** | ответственный другой ИИ | нужен ли перенос финального решения к компетентному и полномочному AI |
| **CP-A3 — Human final** | человек | нужна ли ценностная/полномочная финальная позиция человека |
| **CP-A4 — Advisory** | инициатор в своих правах | нужны ли сведения и/или мнение другого ИИ; сведения от человека возможны, но человеческое решение не заменяется |
| **CP-A5 — Deliberation** | при расхождении третья более полномочная сторона, которую вызывает инициатор | нужен ли обмен позициями и эскалация при отсутствии согласия |

**Own graph каждого Canon:** семь блоков CP-C1..7 именно в этом графе + **предметные связи семи критериев к этому Canon** + собственный Canon с комментарием + `CANON_FOR` к **его** CP-A. Визуально пять раз по семь, предметных criteria всего семь, session answers остаются только в рабочем контексте ИИ. Конкретный разрешённый тип ребра criteria→Canon — узкий schema-design gate: **не** делать незаконные внешние ссылки в legacy Canon conditions, не создавать 35 Context/criteria nodes и не вводить scoring formulas. **Пример произвольного комментария (не исполняемая формула):** «Самостоятельный пересмотр может быть разумен, если контекст достаточен и ошибка легко обратима. Если компетенции мало, цена ошибки велика и последствия распространяются далеко, лучше запросить финальное решение более полномочного участника. Важны сочетания факторов, а не числовая сумма». Комментарий конкретного Canon о собственной оцениваемой A, не общая инструкция всем пяти.

## 3. Desired Real-Life Scenarios — 30 (candidate / user-derived)

**Сценарная нормативность:** пользовательские прямые правила в FR действуют сами по себе. Следующие пути — реконструкция для планирования. **Fundamental Benefit**, **Concept** и **Detailed Path** образуют части **одного** Scenario; ни один путь не становится accepted Detailed Scenario только от публикации этой предработы. Для нескольких особо значимых путей детализация расширена, остальные имеют компактную концепцию, наблюдаемый итог и исключение/ветку.

### S01 — новый чат восстанавливает Benefit и решения
**Benefit:** пользователь и следующий ИИ не пересказывают проект заново. **Concept:** новый ChatGPT/AI открывает тот же RDG и находит R/Benefit, current/alternative A, QRPE, истории и план, затем выбирает обоснованный следующий шаг. **Path:** A1 выбрана; A2 остаётся невыбранной с аргументами; старый чат закрыт → новый AI читает Graph/Plan/Canon/QRPE/history → кратко восстанавливает status/provenance → не объявляет paper A реализованной → продолжает релевантную работу. **Outcome:** видны исходная польза, текущие и потенциальные решения, не только последний план. **Negative:** нет ложных завершений или потери отвергнутых альтернатив.

### S02 — пересмотр upstream без самоцелей
**Benefit:** пользователь получает более простой путь к исходной цели. **Concept:** при появлении иной глобальной комбинации ИИ сравнивает Benefit/затраты. **Path:** сначала анализирует зависимость от исходной R и фактический QRPE → находит другой путь → предлагает изменение и последующее ревью зависимых; не удаляет accepted решения без прав. **Outcome:** сравнимое обоснование альтернативы.

### S03 — QRPE до и после выбора
**Benefit:** основания не исчезают после принятия одной A. **Path:** A1 selected, A2 candidate; сохраняются существенные QRPE обеих → новый Context делает A2 перспективной → review сравнивает их и не снимает A1 автоматически. **Outcome:** наблюдаемая история выбора и повторного анализа.

### S04 — совместимые Actions
**Benefit:** не теряется удачная комбинация нескольких решений. **Path:** R удовлетворяется совместимыми A1/A3; A2 тоже допустима → оценка не навязывает XOR → конфликтные ограничения, если существуют, заданы отдельно. **Outcome:** допустимые multiple selected A.

### S05 — обязательный соразмерный checkpoint
**Benefit:** ИИ не меняет дорогое принятое решение импульсивно. **Concept:** trigger от собственных планов пересмотра → self-review → выбор одного или нескольких **последовательных** способов из пяти CP-A по Canon. Маршруты не XOR, могут следовать друг за другом (например, CP-A4→CP-A1, CP-A5→CP-A2/CP-A3). **Path:** принятая A1 имеет downstream зависимости; AI сам захотел её существенно изменить → до действия активирует checkpoint → изучает Benefit, R/A, применимые existing lenses/QRPE, CP-C1..7 → читает пять own Canon-wide comments → при достаточных основаниях самостоятельно продолжает, иначе research/advice/final decision/escalation → сохраняет лишь ценные результаты по preserve. **Outcome:** действие связано с аргументированным выбором; нет автоматического grant и лишних сохранённых ответов.

### S06 — косметическое изменение и прямая команда пользователя
**Benefit:** рутина не вызывает неоправданное ревью. **Path A:** AI сам планирует minor rename → допускается минимальная проверка и обычная L1-инвалидация при буквальном изменении, если не применён **явный** cosmetic exception. **Path B:** пользователь прямо поручил переименование → **нет pre-action checkpoint**; обычный bearer/замок/история/CAS остаются. **Outcome:** быстрое исполнение при реальных правах. **Negative:** текстовая просьба не обходит hard lock; не вводить дополнительный semantic cosmetic detector из-за OPEN risk.

### S07 — собственные графы пяти Canon
**Benefit:** каждый вариант можно проверить в собственном понятном контексте без копий критериев. **Path:** человек/ИИ открывает Canon-A1 → видит семь CP-C1..7 с реальными criterion→Canon Graph relations; открывает Canon-A2 → видит те же семь domain IDs и связи к **другому** Canon, но свои occurrences/layout; меняет определение CP-C3 разрешённым способом → оно обновляется во всех пяти. **Само обновление CP-C3 не делает L2-dependent на Action stale через Canon.** **Outcome:** 35 occurrence IDs, 7 real criterion IDs, 5 отдельных Canon и Actions. **Negative:** нельзя получить 35 самостоятельных критериев и чужой комментарий.

### S08 — комментарий конкретного Canon без программного veto
**Benefit:** ИИ оценивает произвольные комбинации условий. **Path:** Canon-A1 comment описывает неблагоприятную комбинацию компетенции и стоимости → ИИ считает A1 нежелательной → Canon-A4 comment с теми же criterion identities делает advisory разумной. **Outcome:** разное содержательное влияние на каждую Action. **Negative:** программный selection veto от текста Canon не возникает; реальные exclusion/permissions не отменяются.

### S09 — финальное решение и законное исполнение
**Benefit:** у решения есть ответственный владелец, а запись не обходит права. **Concept:** CP-A2/A3 выбирает final decider; затем отдельно выбирается lawful executor. **Path:** инициатор готовит handoff с R/A/QRPE/рисками → higher AI с реальными полномочиями или человек выносит решение → если инициатор имеет правомерный key, он исполняет; иначе исполняет key holder либо право передаётся/выдаётся уполномоченно; альтернативно AI запрашивает **точную** human approval в Viewer по S24. **Outcome:** Graph/history отражает решение и настоящего исполнителя. **Negative:** неподписанное сообщение «одобрено» не даёт права writer.

### S10 — консультация за данными или мнением
**Benefit:** получить отсутствующую экспертизу, не теряя инициативу. **Path:** self-review выявил недостающее → A4 спрашивает у peer AI facts, opinion либо оба; от человека только информацию, если тот не принимает своего решения → инициатор самостоятельно оценивает и решает в пределах прав. **Outcome:** компетентность дополнена без ложной передачи final authority.

### S11 — если человек уже принял решение
**Benefit:** человеческая воля не подменяется ИИ. **Path:** человек выражает конкретное решение; ИИ может уточнить контекст или аргументированно обсудить более выгодную альтернативу, но не записывает своё решение как окончательное человеческое. **Outcome:** decision provenance сохраняется, исполнитель авторизован.

### S12 — A5 спор и эскалация инициатором
**Benefit:** не получить произвольный компромисс при реальном расхождении компетентных мнений. **Path:** два AI обсуждают варианты, не сходятся → **тот, чей checkpoint**, формулирует точки расхождения и обращается к более ответственному третьему участнику, часто человеку. **Outcome:** причина эскалации и финальная роль понятны; peer не получает автоматически право распоряжаться initiator. **Если peer AI отсутствует, запрещена имитация консультации**: инициатор использует реальные доступные способы, указывает факт отсутствия peer, адресует handoff как fact/opinion/final/approval и соразмеряет объём контекста.

### S13 — доступ без замка: обычный bearer, свободная правка
**Benefit:** не согласовывать мелкие изменения и сохранять аудит. **Path:** agent имеет действующий scoped Graph bearer (`graph.write` или нужное разрешение), R2 не locked → меняет definition R2 → revision/history записаны → не требуется отдельный per-R key. **Negative:** отозванный bearer либо отсутствие Graph scope не превращаются в разрешённые вызовы из-за отсутствия lock.

### S14 — warning/hard и управление замками
**Benefit:** предупреждать об ответственном изменении, а действительно защищённое — блокировать. **Concept:** user/authorized AI по ситуации настраивает конкретный lock. **Path:** R1 warning возвращает настроенное API-сообщение; AI оценивает его условия, warning сам не запрещает запись. A1 hard для text edit требует K1 (либо другой явно разрешённый ключ, если назначен); A1.withdraw может иметь отдельный набор ключей. AI без подходящего ключа получает deny и может вызвать S24 вместо тайного обхода. **Outcome:** принцип warn-versus-deny соблюдён. **Negative:** прямой текст пользователя без доверенного Viewer подтверждения не исполняет hard write.

### S15 — дочерняя R не наследует замок и не делает parent stale
**Benefit:** локальная работа остаётся свободной. **Path:** R1 locked, R2 direct child R1 unlocked → AI с обычным Graph правом редактирует R2 → она не получает автоматически lock и не делает R1 stale просто как ребёнок. **Negative:** отдельное буквальное изменение самой защищённой R1 либо изменение **защищённой операции/связи R1** нельзя выдать за свободную R2-правку. При этом обычное изменение R2 не блокируется как inherited hard lock.

### S16 — L1/L2 и направленность R1→R2
**Benefit:** адресная свежесть вместо каскадного ложного устаревания. **Concept:** dependent X подписан на R1 L1, Y — на R1 L2; R2 — непосредственная подцель R1, R3 — подцель R2. **Path:** изменили definition R1 → X/Y require review; изменили definition R2 → Y L2 reacts, X and R1 do not react solely on this edge; изменили R3 → Y L2(R1) **не** reacts by one-level rule. **Outcome:** корректные причинные связи, не глобальный cascade. **Negative:** реальные независимые links по своим rules всё ещё действуют.

### S17 — косметический exception и открытый риск
**Benefit:** маленькая текстовая правка не вынуждает ненужное downstream review, когда осознанно помечена. **Path:** L1 стандартно реагирует даже на rename; API явно предлагает отдельную необычную отметку cosmetic, пользователь/AI применяет её только осознанно → история сохраняется. **Open risk:** AI может ложно обозначить содержательное изменение косметическим, избежав stale. **Не создавать автоматически проверки, blockers или approval** для устранения этого риска без нового решения.

### S18 — один Viewer/API, portable identity, ⧉
**Benefit:** любое представление показывает ту же работу. **Path:** AI API и один Viewer читают один R/A/Canon; в WorkGraph и двух Canon own views occurrences не плодят domain nodes; физический move/copy сохраняет identity, отдельный domain copy remaps; Graph/Plan/layout/history/references консистентны. **Negative:** два writable владельца одной identity не возникают молча.

### S19 — утрата результата подцели не есть stale родителя
**Benefit:** история не переписывается механической инвалидацией. **Path:** R1/R2 имели записанное подтверждение выполнения; позже фактический результат R2 утрачен → R1 **не становится stale** только из-за этого; запись об историческом подтверждении R1 не удаляется. **Допустимо:** отдельная проверка текущего состояния результата, которая **не равна** L1/L2 stale.

### S20 — native dependency API без ручного Gendocen
**Benefit:** AI может настраивать предметную зависимость обычной командой RDG. **Path:** AI с нужными правами создаёт L1 или L2 source→dependent через API → получает запись/причины future stale → после правки видит версионный impact; Gendocen manual manifest/receipt setup не требуется для исходной dependency. **Negative:** не хранить вторую truth об уровне зависимости в Gendocen.

### S21 — grants в Viewer, portable пакет с hard lock
**Benefit:** пользователь делегирует ровно нужные права, не теряя lock при переносе. **Path:** Viewer создаёт named grant, назначает на конкретную A/operation, отзывает; после переноса пакета без доступной authority hard lock не превращается в unlocked. **Negative:** AI без admin не self-grants; bearer secrets не попадают в Graph/handoff.

### S22 — Action L2: выходные R, Canon и реальная ситуация
**Benefit:** зависимые объекты получают проверку по настоящим непосредственным изменениям Action. **Path:** P L2 depends on A; изменяется definition A, definition непосредственного выходного R (`INTRODUCES`), собственный comment/definition непосредственно связанного Canon, **реальный Context (`CONTEXT_FOR`) или определение реализуемой R (`DRIVES`)** → P требует review. Добавление/снятие этих прямых связей проверяется по прежнему и новому составу. **No-hit только по L2(A):** изменение внутреннего графа выходной R, изменение определения критерия C3 внутри Canon, изменение unrelated R по `RELATES_R` только из-за присутствия в focus. **Outcome:** immediate not recursive, explicit hit/no-hit; независимые отдельные зависимости соблюдаются.

### S23 — Canon no-veto и независимые писательские запреты
**Benefit:** ИИ может оценивать сложную ситуацию без ложного machine veto. **Path:** Canon comment резко отрицательно оценивает A → выбор A не заблокирован **самим Canon**; отдельно реальная incompatibility или hard lock всё ещё может запретить конкретную запись. **Outcome:** смысловая оценка отделена от технического допуска.

### S24 — ИИ запрашивает подтверждение точного требующего ключа действия в Viewer (DETAILED, user-set)

**Fundamental Benefit of Scenario:** пользователь может разрешить **ровно одно конкретное изменение** в RDG, которое ИИ не вправе выполнить самостоятельно, не сообщая ИИ свой ключ и не выдавая ему постоянного права. Пользователь видит результат и сохраняет контроль; ИИ не оказывается бессильно заблокированным из-за отсутствия object key.

**Scenario Concept:** ИИ с обычным правом Graph API подготавливает точную операцию → создаёт request-to-approve → Viewer показывает её пользователю → пользователь подтверждает/отклоняет → RDG по доверенному человеческому подтверждению исполняет **именно исходную операцию** с полномочиями пользователя и пишет историю; отказ или изменившиеся входные данные не приводят к тайной записи.

**Detailed Desired Real-Life Scenario (candidate уточнение уже требуемого поведения):**

1. **Preconditions (иллюстрация, не ограничение всей функции):** R/A существует, на ней hard lock для операции; ИИ имеет штатный Graph bearer и обычный API access, но не имеет необходимого object key. В общем случае **это конкретная операция RDG, требующая ключа**, которую сам пользователь вправе выполнить; eligibility и полный список операций определяются владельцем API без произвольного расширения прав. Пользователь может открыть свой единственный Viewer; подтверждение приходит через настоящий trusted human path, а не текст `by:user`.
2. **AI proposal:** ИИ составляет точное изменение: object ID, operation, затронутые значения/поля, ожидаемая revision/состояние, смысловое объяснение, прогнозируемые последствия. **На этом шаге Graph не меняется.** API возвращает идентификатор ожидающего запроса и его понятный статус.
3. **Viewer presentation:** пользователь открывает список ожидающих запросов или уведомление. Видит инициатора, точный объект/операцию, было/станет, rationale и границы действия. Он может **подтвердить** либо **отклонить**; не обязан копировать ключ, выдавать permanent grant или идти в другой UI.
4. **Reject:** если пользователь отклоняет, request помечается отклонённым; **защищённая операция не выполнена**, инициатор может увидеть исход и при необходимости подготовить новое предложение. History/audit запроса не выдаёт rejected proposal за выполненную правку.
5. **Approve:** trusted Viewer path передаёт подтверждение человека RDG. Общий writer проверяет именно согласованное действие, существенные effects/inputs и права исполнителя на затронутые owners до принятия, соблюдает Graph/Plan invariants/CAS и исполняет его с пользовательскими полномочиями без выдачи human bearer ИИ. Если операция затрагивает несколько owners, их существенные эффекты входят в точность согласия; отдельный approval planner не создаётся.
6. **Changed state:** если изменились объект/запрос, значимые expected state/revisions или согласованные существенные эффекты — например, появился новый Plan owner P2 при прежних target Graph и JSON запроса, — writer не применяет старое согласие к иному результату и требует отдельного актуального подтверждения. Актуальность прав/lock проверяется до durable принятия. Это техническое уточнение FR-36/42, не новый checkpoint на каждую команду пользователя; конкретная policy read set/effects ещё требует proof.
7. **Repeat/retry:** повторный запрос/двойное нажатие с одним идентификатором той же операции не вызывает второе исполнение; при неопределённом исходе writer предоставляет версионное подтверждение результата, не повторно пишет.
8. **History and return:** фиксируются ИИ-инициатор, факт и субъект пользовательского подтверждения (насколько реально удостоверяет Viewer), фактический actor/approved operation и её before/after/revisions. ИИ получает результат и продолжает работу; любые consequential L1/L2 freshness изменения обрабатываются обычной RDG логикой.

**Expected observable outcome:** одно точное защищённое изменение после настоящего согласия человека; S24 иллюстрирует R/A.edit, **но не исчерпывает пользовательское правило подтверждать конкретное действие, требующее ключа**; у ИИ нет пользовательского bearer или общих новых прав; отказ, чужая/устаревшая операция, повтор и попытка поддельного `by:user` не изменяют защищённый R/A. **Кандидатная техническая детализация**, подлежащая source- и UX-проверке: pending requests storage, ID/replay/CAS, способ установления человеческой сессии и notification. Не вводить новую доменную сущность без сравнения с имеющимися transactions/receipts; пользователь принял поведение, а не конкретную таблицу/JSON endpoint.

### S25 — L2 Requirement: изменения тел исходящих R/A
**Benefit:** подписчик проверяет реальное непосредственное изменение собственного графа R. **Path:** Y L2→R1; изменяется определение R2 (`DERIVES R1→R2`) либо определение непосредственно исходящей A1 (`DRIVES R1→A1`), или добавляется/удаляется такая прямая связь → Y stale с адресной причиной. Изменяется внутренний граф R2/A1 без собственного definition edit → **нет** stale по этой L2 подписке. **Отдельно:** сама R1 от редактирования дочерней R2 только по `DERIVES` stale не становится. **Expected evidence:** before/after у Y, R1 и links, сопоставление causal path.

### S26 — L2 Requirement: изменение происхождения
**Benefit:** Y узнаёт, если изменилась связь или объяснение, откуда появилась R1. **Path:** R1 имеет фактическое provenance через исходную/породившую Action с `INTRODUCES` и/или parent R/роль происхождения; пересмотрено происхождение, связанный реальный origin или сведения `origin` → подписчик Y на L2(R1) становится stale. Изменение постороннего визуального overlay, не изменяющего provenance R1, **не** должно создавать ложный hit. **Expected evidence:** causal reason с указанием изменённой связи/metadata, без рекурсивной инвалидации R1 от её ребёнка.

### S27 — L2 Action: реальная ситуация и отдельный Context
**Benefit:** Y реагирует на изменение того, что Action реально реализует и какие факты на неё влияют. **Path:** Y L2→A1; `DRIVES R0→A1` — реализуемая R0, `CONTEXT_FOR K1→A1` — реальный Context. Правка определения R0, определения K1, добавление/снятие их непосредственных связей → Y stale. **No-hit:** текст любого произвольного видимого R по `RELATES_R`, если он отдельно не охвачен заданной зависимостью; внутренние графы R0/K1 не разворачиваются рекурсивно. Не приписывать R0 новое `stale` из-за изменения Action без реальной dependency.

### S28 — Общий критерий Canon не расширяет Action L2
**Benefit:** сохраняется предсказуемая одноступенчатая чувствительность. **Path:** Action A1 связана с Canon-1; Canon-1 использует C3; Y L2→A1. Редактируется буквальное содержание **Canon-1** → Y stale. Редактируется **C3** (его definition обновлено во всех пяти Canon own views) → Y **не** stale через Canon-1. Если Y имеет **отдельную** прямую dependency на C3, она проверяется независимо. **Evidence:** сохранённая причинная цепочка без ложного второго шага.

### S29 — Компонуемые checkpoint-маршруты и доступность исполнителей
**Benefit:** ИИ не теряет результат консультаций и не создаёт фиктивных людей/агентов. **Path:** self-review → CP-A4 получает факт и мнение доступного peer → инициатор выбирает CP-A1 или CP-A2; либо CP-A5 ведёт обсуждение и инициатор вызывает реального higher AI/human при споре. Если peer нет, выбирает доступные альтернативы и честно отражает отсутствие независимого мнения. **Expected:** последовательность этапов traceable, но без one-of-five XOR и ложных final decisions.

### S30 — Различные ключи для операций и human approval
**Benefit:** пользователь защищает дорогие операции без блокировки всех прочих. **Path:** R1.edit допускает K1 или K2; A1.withdraw допускает K2; один K2 покрывает обе разрешённые пары, но сам по себе не разрешает изменение A1.policy. ИИ с обычным Graph bearer, но без допустимого object key, запрашивает в Viewer approval **на точную key-required операцию**; человек вправе разрешить её без передачи bearer. **Negative:** подтверждение одной операции не распространяется на соседние R/A и другие виды правок.

## 8. Решения, находки и Candidate Composition после review v8

### Решённые пользователем смысловые вопросы — не переоткрывать

- **D-01:** default unlocked всё ещё проверяет **обычный Graph bearer/grant**, но не требует дополнительного per-object key. Прямое решение пользователя, прежняя review F-U-01 **superseded/resolved by input**. Не считать анонимный Graph writer равнозначной реализацией.
- **D-02:** AI API подаёт **конкретный** запрос, пользователь подтверждает/отклоняет его **в одном Viewer**, approved operation исполняется с человеческими правами без передачи пользовательского ключа. Не шестая checkpoint Action.
- **D-03:** пять own Canon с семью shared IDs, свободным Canon-wide comment и **без программного veto**; no automatic persisted CP answers.
- **D-04:** L2 Action = literal A + определения непосредственных output R, собственные linked Canon, реальные Context **и реализуемые R (`DRIVES`)**; L2 Requirement = literal R + definitions непосредственно исходящих R/A + changes origin (связи и сведения происхождения); ни одна L2 не рекурсивна. Parent R не становится stale автоматически из-за child definition/result loss.
- **D-06:** изменение внутреннего общего criterion C3 Canon **не** вызывает stale через L2 подписчика на связанную Action. Direct edit Canon — да; отдельная dependency на C3 — независимо.
- **D-07:** пять CP-A маршрутов допускают последовательность, criteria реально связаны с каждым Canon Graph-relations, права объектных locks относятся к паре объект+операция; no fake peer, no inherited lock bypass.
- **D-05:** без отдельной stability, locks opt-in, warning only informs, hard denies; no lock inheritance; explicit cosmetic exception и **OPEN risk без незапрошенного исправления**.

### Что доказал review v8 и чего он не доказал

Final Review v1 проверял **v8** и указанный в отчёте срез исходников с незакоммиченными изменениями, а не работающую реализацию v9. Три pure probes показали: generic revision R2 выросла 2→3 без definition edit при добавлении внутренней DERIVES; один request/target может дать effects для P1 либо P1+P2; семь info IDs через 35 INFO_FOR видны в пяти focused-view JSON. Эти наблюдения обосновывают ранние gates и повторное использование кода, но не выбирают criterion kind, не проверяют trusted approval, layouts/render или Windows. При изменившемся source-срезе существенные предпосылки сверяются заново.

### Границы принятия и совместимость композиции

1. **Редакция документа:** текущее поручение разрешает v9 и её reading copies. Оно не принимает молча будущие API/authority/schema решения.
2. **Feasibility:** Gate 0/Pilot 1 исследуют PR-V7-04/05 и PR-R8-01/03. Ранний pure proof допускается до полного исполнения PR-V7-02/03.
3. **Technical decision:** после evidence выбирается точная совместимая реализация. Полный human-approved execution требует совместно PR-V7-02/03 и соблюдения PR-R8-02; их нельзя объявить независимо принятыми частями уже работающего S24.
4. **Execution/verification:** stages выполняются только по соответствующему поручению и правам; accepted choice, code change, transaction acceptance и verified outcome остаются разными фактами.

Порядок исполнения не равен атомарному принятию всех pending PR. Поэтапные решения имеют отдельные явные границы: не коммитить условные downstream способы до их необходимого proof.

**Существенная альтернатива раннему proof:** отложить проверку trust до Stage 4. Она не меняет обязательный outcome, но оставляет более высокий риск downstream переделки, поэтому в v9 не выбрана как preferred route. Точные часы/стоимость неизвестны. Для effects binding допустимы сравнимые технические варианты с разным числом повторных подтверждений; один request hash не считается эквивалентной гарантией.

**Исключённые пользовательскими решениями варианты:** mandatory object key на каждую R/A, anonymous writer, новая stability шкала, 35 copied criteria, Canon machine veto, L3+ recursion, автоматическая выдача ИИ ключа после решения человека, шестой checkpoint route и consent text как human principal. Эти варианты не возвращаются в Candidate Composition.

### Три поверхности затрат и версия

**Deadline, budget, agreed V1 date, effort, team size и календарная feasibility не подтверждены.** Не придумывать сроки, critical path/slack или численную экономию.

- **Operation:** обычные unlocked edits и соразмерный review не получают новый обязательный процесс. Exact approval использует человеческое внимание по необходимости; более консервативная read-set policy может увеличить повторные подтверждения.
- **Realization:** ранние trust/impact/schema probes добавляют ограниченную проверку до широкой реализации и могут предотвратить переделку. Quantitative delta unknown; pilot не уменьшает полный обещанный scope.
- **Lifecycle:** общий planner/impact/codec и нормализация ссылок уменьшают число мест согласования. Исторические bytes и recovery payload не объявляются дублями текущей truth. Не добавлять framework, фоновый сервис, L3+ или второй registry ради гипотетического будущего.
