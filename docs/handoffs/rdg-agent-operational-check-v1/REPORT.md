# Практический прогон RDG: рабочий чат и передача контекста

> **СТАТУС: HANDOFF / СНИМОК ПРОВЕРКИ, НЕ НОРМАТИВНЫЙ КОНТРАКТ.** Действующий вход оператора — [bootstrap](../../guides/RDG-AGENT-BOOTSTRAP.md). Подсистема модулей остаётся в разработке.

## Проверенный сценарий

Прогон выполнен во временном workspace с настоящими Graph/Plan writers и изолированными grants. Каждая команда клиента запускалась отдельным процессом, моделируя продолжение новым чатом без памяти предыдущего процесса.

1. Создан candidate-v6 owner через авторизованный initializer; отдельно подготовлен Plan owner.
2. Дана фактическая задача: сформировать JSON summary CSV с тремя строками и суммой 60.
3. Объявлен decomposition Action, подготовлена и введена дочерняя Requirement.
4. Добавлены способ через CSV parser и альтернативный ручной способ.
5. До выбора parser проверены колонки и целочисленные значения реального input.csv; сохранён inspection evidence.
6. Выбран Action, открыт QRPE о полноте строк, отдельно записано размещение в Plan.
7. Новый процесс восстановил состояние: Action выбран/размещён, вопрос открыт, выполнения ещё нет.
8. Создан и запущен summarize.py, прочитан result.json и проверены фактические rows=3 / total=60.
9. QRPE разрешён по evidence; записано исполнение с проверенным file hash. Criteria Requirement проверены отдельно от выбора/Plan.
10. Новый процесс прочитал завершение, сохранённую историю и старый receipt после последующих Graph правок. Альтернатива осталась candidate.

События AI имеют by=assistant и bearer receipt. Роль пользователя не имитируется. Проверка не является независимой оценкой UX другим человеком или полноценным автономным испытанием другой модели.

## Находки и действия

| Находка | Результат |
| --- | --- |
| Старый initializer создавал JSON без active actionModel и обходил текущий writer | Переведён на candidate-v6, обязательный существующий bearer и canonical package writer |
| Начальный вход требовал знания внутренних файлов/схем | Добавлены tools/rdg-agent.py и отдельный bootstrap оператора |
| Не было удобной привязки линзы к текущему рабочему контексту | Добавлены work/review/handoff как обычные R/A-определения; client binds actual focus и Graph/Plan hashes |
| Неопределённость после записи могла провоцировать повтор новым ID | Есть receipt; принятый commit после сбоя ответа или последующего чтения receipt распознаётся. Уже существующий ID не исполняется повторно автоматически |
| Для отдельных Repo вызовов нельзя полагаться на общий export | Есть приватный context с authStore/tokenFile references; ключ не находится в аргументах |
| Runtime не содержит подготовленного auth/context для рабочего запуска | doctor сообщает ready=false. Доступ и пару owners требуется подготовить владельцу/разрешённой среде |
| Старый DRY/maintenance adapter ограничен пилотом | Ограничение описано в действующей инструкции линз, не выдано за универсальный анализатор |

## Что остаётся

- Нормализованная долгоживущая canon assessment с evidence и проверкой свежести для следующего чата.
- Реальные предметные runners/checks по линзам; рабочие линзы сейчас направляют AI, а не выполняют анализ сами.
- Более простой разрешённый provisioning первой пары Graph/Plan/access: текущий операторский маршрут рассчитан на уже подготовленную пару.
- Проверка удобства пользователем в собственном окружении. Viewer installation и Stage 4 acceptance не подтверждались.
