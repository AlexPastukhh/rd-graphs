# RDG — инструкции разработчику

> **СТАТУС: ДЕЙСТВУЮЩИЕ ИНСТРУКЦИИ РАЗРАБОТКИ.** Этот файл задаёт порядок работы с репозиторием. Владельцы предметных правил и плана указаны в [карте текущего состояния](docs/guides/RDG-CURRENT-STATE.md).

## Вход в работу

1. Рабочие файлы и результаты Fortis Repo сохраняй в `/workspace/repo/Workfiles` внутри Docker volume. Прежнюю Windows Workfiles не используй; оригиналы сохраняются. Проверь фактический путь проекта, mount, права и `git status`. Корень этого проекта — `rd-graphs`; `graphs/` является его подкаталогом. Сохрани чужие изменения.
2. Прочитай [README](README.md) и [текущее состояние](docs/guides/RDG-CURRENT-STATE.md); для повторяемой практической задачи выбери подходящий [RDG use case](docs/use-cases/README.md), для развития функции — [backlog](BACKLOG-IMPROVEMENTS.md), затем применимые контракт, регламент и раздел [плана](docs/guides/RDG-DEVELOPMENT-PLAN.md). Явно указанная пользователем задача определяет scope.
3. Сверь обещанные возможности с кодом и реальными проверками. Действующий план описывает будущую работу; `candidate`, принятые решения, реализация и проверка результата имеют разный смысл. Старый PASS относится только к проверенному срезу.

## Поиск и источники

Начинай с текущих `tools/`, подходящих `tests/` и действующей документации. Список действующих документов выдаёт существующий реестр `docs/DOCS-POLICY.json` через команду:

```sh
python3 -B tools/rdg-docs-audit.py --list-active
```

`.ignore` исключает архивные каталоги из обычного поиска `rg`; файлы остаются в Git и доступны по явному пути. Поиск в конкретном архиве: `rg --no-ignore 'текст' docs/handoffs/НУЖНЫЙ-КАТАЛОГ`. Полный перечень версионируемых файлов: `git ls-files`.

Переходи по существенным вызовам, ссылкам, fixtures и источникам происхождения, даже если они скрыты обычным поиском. Некоторые тесты импортируют файлы из `docs/handoffs/`, а текущий план ссылается на дизайн в этом каталоге. Исключение из поиска не доказывает отсутствие зависимости.

Исторические `CURRENT`, `CONTRACT`, `PLAN`, handoff и `before*` не становятся действующими инструкциями из-за имени. Статус проверяй по реестру и применимому источнику. Существенное нерешённое замечание переноси в соответствующий рабочий документ; не оставляй его единственной записью в удаляемом отчёте.

## Передача другому чату по запросу

Команда владельца «передай другому чату» (или аналогичная) работает **в любой момент**, в том числе посреди незавершённого этапа. Не требовать завершить задачу, устраивать уборку, восстанавливать всю историю решений или создавать очередной архивный handoff. Действующие планы, контракты и код — источник истины; текст передачи — короткий указатель на них.

При передаче: (1) сверить `git status --short`, HEAD/ветку и непубликуемые файлы, не трогая staged/dirty worktree; (2) открыть только применимые действующие документы и последний результат задачи; (3) выполнить быстрый `python3 -B tools/rdg-docs-audit.py`, если доступен, и только нужные адресные тесты, если они ещё актуальны; (4) проверить, что **новые решения этой работы** записаны в своём нормативном документе. Если нет — точечно обновить его; не чинить все посторонние документы «на всякий случай». Непроверенное/устаревшее указывать явно.

**Выход по умолчанию — компактный текст прямо в чат для копирования**, без нового файла: проект/путь и главный план; текущая задача/принятые решения; сделано и не сделано; фактические Git/тесты/аудит (с датой и ограничениями); открытые риски/запреты; один ближайший шаг новому чату. Достаточно примерно 10–20 строк. Если пользователь отдельно просит постоянный файл, использовать назначенное место, не плодить параллельный нормативный план. Не подменять PASS запуском старых тестов и не объявлять доступность непроверенной инфраструктуры.

## Изменения и завершение

Меняй относящиеся к задаче файлы, проверяй diff и подходящие тесты. Правила Graph/Plan writers, прав, журнала и reset принадлежат [операционному регламенту](docs/guides/RDG-OPERATIONS.md); Git не отменяет их.

После крупного изменения модели/UI создай новый полный актуальный пример по [регламенту](docs/guides/RDG-OPERATIONS.md#актуальный-пример-после-изменения-моделиui), сохраняя старые данные. После этапа обнови применимые действующие документы и выполни [порядок завершения и очистки](docs/guides/RDG-OPERATIONS.md#завершение-этапа-и-очистка). При изменении runtime после полного CI выдай пользователю готовую Windows-команду по [регламенту обновления](docs/guides/RDG-OPERATIONS.md#разработка-и-обновление-серверного-runtime); установку выполняет пользователь. Устаревшие материалы можно убрать из рабочего дерева после проверки зависимостей и сохранения точной версии в Git. Новые папки `before`, backup-копии, handoff и параллельные планы не нужны для обычной разработки с Git.

Не удаляй данные только по возрасту или статусу «архив». Живые owners, история Graph/Plan, Gendocen state, journal/recovery payload и необходимое evidence требуют своих предметных правил. Не применяй `reset --hard`, `git clean`, force-push или массовую перезапись для уборки. Commit включает только проверенные файлы текущей задачи; публикация выполняется в разрешённых границах задачи.
