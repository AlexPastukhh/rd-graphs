## 0. Решение, цель, границы

### Нормативная модель — ОДИН доверенный контейнер (решение владельца 2026-10-31)

**Единственная текущая цель:** один owner-controlled контейнер Fortis Secure Gateway на Windows Fortis_M. В нём живут **machine ingress, trusted operation grants/policy, WebAuthn owner UI + ASK Pending/History, защищённое хранилище service tokens, единый `Core.execute()`/typed adapters, preflight, durable receipt, readback и UNCERTAIN recovery**. Два контейнера G2/G4 сейчас — **старые раздельные тестовые установки**, а не постоянные части целевой системы. **Обязательный второй token-bearing Executor-контейнер или Approvals→Executor IPC ОТМЕНЁН.** Изолировать в будущем можно только после нового решения владельца по реальному риску, а не для соответствия старой лаборатории.

**Маршрутизация:** через Fortis направляется любое действие от Repo/ИИ, если для него **нужен сервисный секрет ИЛИ потенциально требуется owner ASK**. Это два независимых признака; политика вычисляется сервером **для конкретной операции/actor/target/params/current state**, а не определяется самим фактом наличия токена. Операции, которым не нужен ни секрет, ни ASK, также могут использовать Fortis, но не обязаны только по этому признаку. Для защищённых операций прямой обход Fortis/авторитетного service writer не должен позволять обойти политику.

| Секрет нужен | ASK для конкретного действия | Один и тот же Fortis |
| --- | --- | --- |
| Да | Нет | trusted `ALLOW` → server-picked token → typed adapter/GET/receipt; пример: Sonar READ |
| Нет | Да | immutable `PENDING` → owner WebAuthn Approve → **тот же `Core.execute()`** без секрета; будущий RDG ASK-block |
| Да | Да | immutable `PENDING` → отдельный fresh WebAuthn Approve для точного requestId/fingerprint → **тот же `Core.execute()`**, server-picked token → один typed `accept_issue` POST + independent readback/receipt; никаких writes до Approve и никаких bulk/arbitrary writes |
| Нет | Нет | trusted `ALLOW` → **тот же `Core.execute()`** без токена/prompt; synthetic FREE |

**Когда используется токен:** для секретной операции Fortis может использовать внутренний credential **до ASK только для допустимого read-only preview/current-state GET**, который нужен для frozen request и проверки области; сам **изменяющий эффект** остаётся заблокирован до точного owner Approve. Токен не нужно отдавать AI ни в одном случае.

`DENY` / owner Reject не dispatch. ИИ не отправляет mutation повторно после Approve. Fortis получает typed intent и отдельно аутентифицирует machine caller; не принимает AI-поля `approved`, owner, policy, token, произвольные URL/HTTP method/headers/shell. **Секрет выбирает сервер по trusted adapter/config**, не Repo. Owner UI требует независимую WebAuthn/session/origin/CSRF авторизацию и никогда не предоставляет свои routes машинному клиенту. Браузерные и machine routes могут быть разными WSGI-приложениями **в одном Docker-контейнере**. Repo не может управлять Docker daemon, политиками, owner state или volume. Обязательны host/mount/source isolation, ACL/TLS, allowlisted service origins/params, secret rotation/revocation, защита логов/backup и проверка всех обходных API.

**Честная граница безопасности:** один контейнер проще, но компрометация его HTTP-кода, memory, Windows/Docker admin или утечка широкого Sonar token способны **обойти Fortis ASK**. Раздельные маршруты авторизации сами по себе не изолируют процессы внутри контейнера. Владелец разрешил source change для одного typed `accept_issue` с обязательным отдельным ASK + strong WebAuthn на каждую Issue; это не blanket permission и не разрешение на rollout. Доверенная установка, token custody и owner-controlled deployment gates остаются обязательными.

**GitHub и RDG — важная граница общей модели:** если AI из Fortis Repo выполняет авторизованное GitHub действие (создание PR, comment, обновление branch, управление проверками) или RDG действие с credential/потенциальным ASK, его **сервисную авторизацию и разрешения** должен обеспечивать Fortis по scoped typed operation. **Не оставлять полноценный owner/admin GitHub connector или прямые Repo grants как параллельный обход**. D1 требует минимального GitHub typed adapter либо отдельно **явно одобренного владельцем исключения**, не невидимого обособленного secret-bearing connector. При этом GitHub-hosted Actions/SonarScanner работают **в собственной независимой CI trust boundary** с ограниченными job credentials/secrets и не превращаются в Fortis-контейнер: это не прямые AI→сервис запросы из Repo. Существующие RDG proxy/legacy paths — историческая миграция; авторитетный RDG write guard от обхода будет принятый G3. Не заявлять полное принудительное посредничество до закрытия этих прямых путей.

**Критический функциональный gap и ближайшая цель P1/P2 (2026-11-02):** source/offline логика одного R7 Core и typed Repo client проверена, но **реального пути один AI actor → Fortis Repo → Windows R7 → SonarCloud пока нет**. `fortis_approvals/repo_sonar_tools.py` содержит шесть фиксированных typed client operations: четыре READ, `sonar.propose_accept_issue` и `approvals.request_status`; source/offline E2E подтверждает READ, `PENDING → REJECTED`, actor-bound status, scoped denies и Sonar POST=0. **Уточнение P1: отдельная регистрация шести MCP tools не требуется.** Один ИИ через существующий Fortis Repo может выполнять фиксированный `repo_sonar_tools.py` или направлять HTTPS-запросы в доверенный R7; сам Fortis Gateway выбирает `ALLOW/ASK/DENY` по аутентифицированному actor + известному destination/service + точной операции и scope. Gateway служит **ограниченным reverse/application proxy**, не открытым HTTP-прокси: `service`, `target`, `operation` не дают ИИ выбирать произвольный upstream URL, метод, токен или политику. В текущем R7 allowlist маршрутов: `POST /v1/reads` (четыре Sonar READ — `ALLOW`), `POST /v1/actions` (Sonar `accept_issue` proposal — `ASK`, сохраняет `PENDING`, а не исполняет запись), `GET /v1/requests/{id}` (scoped status). Неизвестные destinations/operations и прямой Sonar POST отклоняются. Сетевой firewall ограничивает достижимость Gateway; разрешение операций обеспечивает **сам Gateway**, независимо от Repo shell/MCP. Не менять живой MCP bridge. Ближайший функциональный тест теперь не два AI actor и не вся матрица, а один авторизованный actor: запустить/получить Sonar analysis для выбранного GitHub repo, получить через Fortis подробные реальные Issues/Quality Gate, предложить точную Issue operation и отклонить её в owner UI. **Live acceptance после P2 release gates должен покрыть обе ветки на одной disposable Issue:** Reject → `REJECTED` и 0 POST; отдельно Approve с fresh strong WebAuthn → один `accept` POST → independent GET `ACCEPTED` + durable receipt. Каждый запрос подтверждается отдельно; blanket/bulk approval не предусмотрены. Отдельный owner GO на rollout/test execution остаётся обязательным.

**Минимальные prerequisites P1:** новый versioned R7 source/image package, соответствующий текущему checkout (v2 исторический из-за последующих изменений `core.py`/`owner_portal.py`); owner-reviewed Windows deployment того же целевого single-Fortis runtime; TLS1.3 с проверяемой server identity, один scoped machine client identity/grant с owner-controlled one-off provisioning/disable, private read-only client mounts, отдельный Sonar READ token только в Fortis private store, сохранение четырёх ранее owner-prepared изолированных R7 volumes (не пересоздавать) и Repo1/Repo2 Guard Preview перед воздействующими изменениями. Не переиспользовать A3/G2/G4/R5 state/token/grants; не менять текущие контейнеры без owner GO. Полная base-image digest/provenance/SBOM/CVE admission остаётся в финальной фазе, но это **не отменяет минимальные TLS/auth/secret-isolation проверки до live**. Не изменять `tunnel`/MCP bridge без отдельной задачи. R7 P2 source candidate permits only the exact typed `accept_issue` after a separate fresh WebAuthn approval per Issue; live POST remains unavailable until the P2 package/image passes release gates and the owner separately authorizes rollout/test execution.

Ранние записи и split-worker labs — исторические свидетельства, не действующие требования.

**Обязательно сохранить точные уточнения пользователя:**

1. Gateway **может иметь полноценные сервисные полномочия**; ограничивается не сам факт наличия сильного токена, а доступный AI **каталог типизированных операций** и политика. Это сознательный риск компрометации Gateway; политика не превращает сильный credential в слабый.
2. AI вправе свободно выполнять ALLOW, для ASK **действие блокируется до независимого подтверждения владельца**, DENY запрещается; подтверждение не является полем JSON от AI. Политика зависит от service + operation + actor + target + существенных params, **не только от HTTP method/endpoint**.
3. **Модуль разрешений и его UI независимы от RDG**. RDG-пилот exact approval/WebAuthn — источник технологий, не обязательный backend; предметные проверки Decision, Requirement, Evidence, Plan, CAS остаются RDG.
4. Разрешения могут покрывать RDG, Sonar, будущие внешние действия; UI Approvals доступен отдельно (порт/домен/вкладка) и умеет направлять пользователя к **нужной уже открытой вкладке RDG и конкретной сущности** с возвратом к ожидающему запросу.
5. Fortis Repo/AI не управляет доверенным Docker daemon, секретами, policy, Windows clone и Runner; в противном случае безопасность Gateway и допуска исполнения **не доказана**.
6. Успех Sonar, GitHub Actions или антивируса **не даёт права автоматически запускать код**. Не автоматизировать owner merge по зелёному Gate. Fetch, проверка допуска, импорт и исполнение различны. **IMPORT_APPROVAL — дополнительная настраиваемая политика**, не обязательное ручное подтверждение каждого pull: успешный exact-SHA admission может автоматически разрешать импорт. **RUN_APPROVAL обязателен** для build/install/run с выполнением недоверенного кода на Windows. Политика import задаётся владельцем.
7. **Старый RDG CI/CD** (tools/rdg-ci.py → ready.json/ZIP → Windows Update-RDG.ps1 -Watch) напрямую устанавливает AI ZIP и **не удовлетворяет новому trust boundary**. Прежде чем вновь запускать недоверенные AI правки, предложить владельцу временно **приостановить только Windows auto-deploy**, сохранив running RDG server и при желании Repo CI build watcher. Ничего не выключать самостоятельно; после успешного нового importer исключить legacy обход.
8. Нынешний RDG private gateway — **RDG-only**. Его не превращать незаметно в универсальный сервис с Sonar write credentials. Доверенную политику, сервисные адаптеры и UI вынести отдельно, даже если можно переиспользовать образцы кода и сети.
9. Предыдущий контур fortis-security-reports (Windows reporting/Cloud collector, Stage 7 draft, PR #32/#33) **не удалять до успешного нового smoke**. Sonar CLI на Windows ранее был авторизован, но это не авторизует новый Gateway автоматически.
10. Не путать **GitHub Issue** и **Sonar Issue**. Sonar Issue допускает конкретные статусы/переходы, отдельно существуют Security Hotspots; ни одна операция не должна выглядеть как generic «закрыть любой Issue».
11. **RDG V1 — исключение из ранней общей политики:** block protection только `FREE/ASK`, **никакого DENY как статуса блока** и **никакого ASK по умолчанию для всех writes**. Существующие bearer grants, предметные `policy` и operation `locks` RDG остаются самостоятельными проверками; технический отказ для неизвестной/неавторизованной операции в Gateway не является режимом защиты RDG. **Важное отличие:** один Fortis-контейнер ≠ общая авторизация machine и владельца. Раздельные routes/identity/grants/ACL нужны в одном runtime; токены доступны **только доверенной реализации Fortis**, не Repo или JS owner браузера. Не публиковать owner/admin через machine API, не вводить raw upstream proxy, не давать Repo Docker socket/secret mount. Скомпрометированный Fortis с широким токеном способен обойти ASK; перед реальным WRITE необходим owner-controlled security audit, а не обязательный дополнительный Docker-контейнер. RDG предметные CAS/journal и штатный writer остаются в RDG; G3 обязан закрывать прямые обходы.

## 3. Этап G1 — независимый Action Gateway и Approvals Core

**G1 минимум:** Gateway API, небольшой Policy Engine, immutable Pending Requests + Audit, проверка решения владельца, один исполнитель через типизированный адаптер. **Пользовательский интерфейс — отдельный этап G2**; в G1 достаточно synthetic adapter/verifier и адресных тестов. Необязательно разные контейнеры, но независимая доверенная граница управления нужна перед deployment. Не вводить новый backend/writer в RDG.

**Структурированный request:**
- service, operation, actor/client identity, object target (полная идентичность, namespace), parameters, reason, related context (PR/SHA, ссылки), idempotency key.
- version/expected state или RDG inputBinding; approved actions и их before/after preview привязываются к точным bytes/hash, actor, target, operation и policy version.
- Gateway самостоятельно получает текущее состояние сервиса; текст AI не считается доказательством текущего состояния.
- request ID идентифицирует логическую операцию; изменение параметров требует **нового** ID/нового разрешения.

**Политики:** ALLOW (исполнить сразу); ASK (удержать **первоначальный** запрос в доверенном pending store, показать владельцу и **после подтверждения автоматически пропустить тот же неизменённый запрос до сервиса**); DENY (нет исполнения). AI получает requestId/status/result и **не повторяет mutating call после approve**. Для неизвестного endpoint/operation DENY; конфигурацию нельзя править через AI API. Правила V1 учитывают аутентифицированного инициатора, service, operation, target и существенные params; реальные HTTP method/route фиксирует адаптер, не ИИ.

**V1 — только типизированный каталог операций:** `service + operation + target + параметры` со строгой проверкой и фиксированным service adapter (сначала synthetic, затем Sonar и RDG). Адаптер сам знает конкретный метод/маршрут сервиса; **не строить универсальный HTTP route/proxy registry** и не принимать от AI URL, headers, shell, произвольный method или endpoint. Для конкретной операции FREE/ALLOW и ASK после подтверждения сходятся **в одном и том же executor/adapter** с одинаковыми предметными проверками.

**V1 состояния — только необходимые переходы:** `PENDING → REJECTED` либо `PENDING → APPROVED → EXECUTED`; если данные изменились — `STALE`, если исполнение не установлено однозначно — `UNCERTAIN` до reconciliation. Таймаут/истечение заявки и ошибки фиксировать явно, но не вводить сложный workflow engine и отдельную роль-модель. Решение — только через независимо аутентифицированную owner session (WebAuthn или равноценно проверяемый механизм; origin/CSRF и привязка к точному запросу обязательны). `by:user`/`approved:true` от AI не являются proof. Показать неизменный preview и причину до подтверждения.

**Исполнение:** перед отправкой повторить service-side precondition + permissions. Для ASK trusted executor сам берёт исходный frozen payload, исполняет его и выдаёт result; AI не отправляет действие заново. Длительный запрос может вернуть PENDING/202 и затем завершиться в доверенном Gateway, с read-only status/receipt по requestId. Однократность и durable acceptance; при потере ответа query/status/receipt и service-specific reconciliation прежде, чем возможен retry. Не делать слепой повтор Sonar POST. После исполнения — readback и журнал. Перезапуск сохраняет pending и решения.

**Секреты и сильный токен:** пользователь допускает сервисные credentials с полными правами в доверенном контейнере. Gateway ограничивает возможные команды, но компрометация Gateway потенциально отдаёт всё. Рекомендуется отделять read/write credentials, где возможно, **не как обязательный запрет на привилегированный credential**, а как defense-in-depth. Доверенный оператор может отзывать/ротировать ключи вне AI API.

**Gate G1 — синтетический контур PASS (срез 2026-10-31), production НЕТ:** реализован самостоятельный Python-пакет `fortis_approvals/` в рабочем дереве `rd-graphs` (код не импортирует RDG). `core.py` — typed policy, actor-bound immutable pending, SQLite audit/state, точный preview, подтверждение через injected verifier, один dispatcher для ALLOW/ASK, CAS и read-only receipt recovery при UNCERTAIN; `gateway.py` — узкий WSGI submit/status **без owner/admin routes**; `synthetic.py` — отдельный фиктивный сервис с атомарными receipts. 27/27 synthetic unit/in-process WSGI tests PASS: ALLOW/ASK/DENY, подмена, replay/ID conflict, scoped status, stale, expiry, restart, revoke, policy changes, owner spoof, race, lost response, uncertain без повторной записи, ingress deny. Запуск: `python3 -B -m unittest discover -s fortis_approvals/tests -v`. **Нет** live HTTP listener, независимой owner browser authentication, реального WebAuthn verifier, живых service credentials, production runtime/deployment или RDG/Sonar adapters. Тестовый HMAC verifier живёт **только в tests**, не является реальной авторизацией. Для нового чата считать G1 synthetic проверенным, но **не говорить, что защищённый сервис установлен**; следующий этап — G2.

## 4. Этап G2 — минимальный отдельный Approval UI (RDG navigation завершается в G3)

**Согласованный сценарий использования G2 (уточнение владельца 2026-10-31):** Fortis Approvals — **постоянно работающий независимый сервис**, а не разовая тестовая утилита. Он принимает и надёжно сохраняет ASK-заявки независимо от того, открыта ли вкладка; после перезапуска компьютера/контейнера восстанавливается под контролем владельца. Отдельная вкладка браузера — удобный интерфейс «Ожидают»/«История»; очередь **обновляется автоматически** без ручного Refresh. При новой заявке интерфейс показывает счётчик/индикатор и, после разрешения пользователя, посылает **браузерное системное уведомление** (пока браузер поддерживает работу этой вкладки, в том числе на фоне). Доставка уведомлений при **полностью закрытом браузере** потребует отдельного push/desktop канала и не является обязательным условием первой V1. Не требовать открытой вкладки для работы самого сервиса.

Отдельный UI на собственном локальном origin/порту или защищённом домене с независимой owner authentication:

Отдельные экраны «Политики»/«Подключения» отложить; доверенную конфигурацию policy/credentials меняет **только владелец вне AI API**. Не строить role editor и массовое подтверждение в V1.
- **Подтверждение владельца без лишних действий:** вход в UI должен быть независимо защищён от AI (например, passkey/WebAuthn на входе с ограниченной owner session, Origin/CSRF, контролем доверенного runtime). Для обычной ASK-заявки в пределах действующей защищённой сессии достаточно явного Approve/Reject на точном frozen preview; **не навязывать Windows Hello/PIN на каждую заявку**. Не разрешать AI выдавать себе owner session.
- Карточка V1 показывает инициатора, сервис/операцию и объект, точное изменение (до/после или эквивалентный preview), объяснение, Approve/Reject и результат. PR/SHA, риск и срок действия — **только если относятся к запросу**; не делать обязательные поля и отдельные экраны для них.

Нет вкладки → проверенная deep link/открыть новую.
- Разные browser origins не делят BroadcastChannel. Использовать owner-authenticated registration/one-time navigation request по доверенному локальному bridge; контролировать destination и принадлежность browser session. Не допускать навигационных payload как команды write. Переход не одобряет запрос.

**Переиспользовать из существующего RDG approval pilot, но не объявлять готовым:** 'tools/rdg-approval-executor.py', 'tools/rdg-approval-surface.py', 'tools/rdg-webauthn.py', 'tools/rdg-credential-store.py', 'tests/rdg-approval*.test.py', 'tests/visual/rdg-approval-viewer.cjs' и 'rdg-persistent-approval.cjs'. Проверять нужные части pilot по месту при реализации; **не создавать отдельную таблицу, дублирующий дизайн-документ или копию executor**.

**Миграция RDG approval pilot:** после принятия внешнего Approvals прежние RDG approval_request/read и ApprovalSurface должны стать тонким совместимым клиентом/маршрутом к внешнему модулю либо быть явно выведены из эксплуатации. Не оставлять второй независимый approval authority, доступный AI в обход общей policy. Доменные подтверждения действий внутри RDG не выносятся: они отличаются от разрешения AI на исполнение операции.

**Контракт RDG V1 — одна операция, одна реализация исполнения:** AI сохраняет штатный `graph.write` для разрешённых операций. Обычный API-вызов после проверки затрагиваемых блоков выбирает: **FREE → сразу штатный RDG executor; ASK → сохранить тот же исходный запрос и ожидать решение владельца → после Approve тот же штатный RDG executor.** Обе ветви используют один Application/prepare/commit, одни domain guards, grants, CAS, receipt и journal; **не реализовывать второй путь записи, новый RDG coordinator или отдельные роли PROPOSE/EXECUTE**. ИИ не повторяет mutating request после approval. Владелец через доказанную browser session действует напрямую, `by:user` из payload не является подтверждением полномочий. Для прозрачного аудита сохранять исходного инициатора, проверенного владельца и контекст доверенного запуска, без системы ролей.

**RDG adapter — только проверка и остановка, не второй writer:** штатная подготовка операции определяет прямые semantic effects и inputBinding; FREE идёт в штатный commit, ASK сохраняет immutable pending; после owner Approve тот же исходный запрос заново проходит штатный preflight/CAS и **тот же commit**. Если изменились связанные данные — STALE и новый запрос, без молчаливого изменения payload. Одна атомарная операция с несколькими ASK-блоками остаётся одной заявкой. Не добавлять grant AI, не превращать owner approval в смену actor. Для targetless create/copy и multi-owner effects проверять scope воздействия; для move/folder/migration, минующих обычную подготовку, отдельно проверить реальные effects. **Чистый перенос/переименование каталога без изменения защищённых блоков не становится ASK**; только операции с возможным смысловым изменением ASK-блока, которое пока нельзя надёжно классифицировать, должны fail-closed для AI.

**Политика блоков RDG V1 — минимальный scope, принятый владельцем:**
- `FREE` по умолчанию для новых и старых блоков без явной защиты. Обычные RDG AI writes выполняются по прежнему контракту прав и предметных проверок; не вводить ASK по умолчанию для create/rename/Plan и не делать DENY третьим состоянием защиты блока.
- `ASK` — один признак **для всего блока**, без настройки отдельных видов операций. Прямые правки определения/состояния, удаление, создание/удаление связей и изменение membership Working Graph требуют approval, если затрагивают ASK-блок.
- Изменение стороннего блока с автоматическим `review_required` у ASK-блока само по себе не создаёт заявку; изменение только layout/view, а также размещение блока в Plan — FREE. Действующие доменные guards и grants не ослабляются.
- `FREE → ASK` может установить AI или владелец без дополнительного approval; `ASK → FREE` от AI требует owner approval. Владелец через **сервером проверенную browser owner session** меняет ASK-блок и снимает защиту напрямую. Нельзя доверять полю `by:user` или свободно переданному actorId.
- **Одна pending заявка на одну атомарную исходную API-транзакцию**, независимо от числа защищённых блоков внутри неё; решение целиком approve/reject, без частичного исполнения. UI bulk approve нескольких независимых pending-заявок в V1 не нужен.
- В V1 только владелец подтверждает запросы AI; AI→AI approval, роли/иерархии, разные уровни ASK, operation-specific ASK, редактор политик и групповые UI approvals **отложены**. Протокол сохраняет проверенные initiator/approver/executor identifiers, чтобы отдельный модуль политик мог развиваться позднее.
- **Не смешивать существующие RDG `policy` ('ordinary/stable/protected') и `locks` ('warning/hard') с новым ASK.** Это отдельные действующие предметные ограничения. Их не удалять и не переписывать без инвентаризации живых owners/совместимости. Для нового ASK использовать один минимальный атрибут (точное имя/schema выбрать после анализа), без дублирующего writer и ролей.
- Проверять фактические затронутые предметные сущности на общем RDG write-path, а не только переданный `nodeId`; старый Gateway/Agent/Helper direct apply не может обойти ASK. Сохранить CAS/inputBinding/journal/recovery, повторную проверку и STALE. Технический отказ для неавторизованной/неизвестной операции остаётся отдельным от block protection.

**Изменения UI RDG:** адресуемые package/entity/focus targets; Navigation Bridge handler для owner browser; подсветка объекта и безопасный возврат; optional pending badge/link на собственный Approval UI. RDG UI не хранит owner approval token; предметные domain confirmations не становятся универсальным внешним authorization.

**Критически: закрыть обход при G3 (не текущая поломка):** действующий private RDG Gateway корректно проксирует штатные AI writes; ASK пока ещё не реализован. Нельзя внедрить будущий ASK **только** в Fortis Approvals и оставить обычный direct apply в обход него. Авторитетный RDG write-path должен отличать сервером проверенную owner session от AI grant и удерживать/отклонять неподтверждённую запись, затрагивающую ASK. RDG сам определяет затронутые сущности по prepared semantic effects; независимый Fortis Approvals хранит immutable pending request и подтверждение, затем через доверенного executor выполняет ту же транзакцию с повторным preflight/CAS. `by:user` в payload не считается доказательством роли. Для FREE прежний путь без лишней заявки сохраняется. Операции move/folder/migration, идущие вне обычной подготовки, проверить на реальные смысловые воздействия: **не блокировать автоматически чисто файловые операции**, но не разрешать AI неклассифицированные изменения защищённых блоков. Не нужен второй RDG writer, второй CAS/journal или перенос доменной логики в Fortis. Старый RDG-only proxy не должен автоматически получить Sonar scope.

**Gate G3:** изолированные synthetic owners; AI с обычным scoped graph.write успешно выполняет FREE-редактирование без pending, устанавливает FREE→ASK сразу; после этого обычный edit/link/remove ASK-блока автоматически удерживается (без записи), владелец открывает R3 в существующей вкладке и утверждает, доверенный executor записывает **ровно одну неизменённую транзакцию** с CAS/receipt/readback. AI ASK→FREE создаёт pending, owner ASK→FREE и owner edit ASK выполняются прямо через доказанную browser identity. Проверить direct Gateway/Agent/Helper bypass, unrelated review/layout/Plan, multi-entity transaction, stale/reject/replay/actor spoofing. Не менять живые owners/grants.

## 9. Этап D3 — доверенный Windows Importer

Принятые предыдущие версии и hashes хранятся для восстановления.

**Раздельные действия и политики:** IMPORT_ADMISSION всегда проверяет exact final SHA, source/review/checks/AV; owner IMPORT_APPROVAL **опционален** по политике (ALLOW после всех проверок или ASK для конкретного риска). **RUN_APPROVAL обязателен** для исполнения build/install/start этой версии на доверенной Windows. Эти запросы могут жить в общем Approvals Core, но исполняет их только доверенный Windows Importer/Runner, не произвольная Gateway-команда/Windows shell от AI. Не смешивать fetch, допуск в доверенную копию и запуск.

**Gate D3:** без verified final SHA и обязательных checks/AV нельзя импортировать; без отдельного owner RUN_APPROVAL нельзя исполнять код. Если IMPORT=ASK, требуется дополнительный owner IMPORT_APPROVAL; если IMPORT=ALLOW, успешных проверок достаточно для безопасного импорта без ручного подтверждения. Проверяется fallback и возврат к ранее принятой версии.

## 10. Этап D4 — миграция RDG CI/CD и self-development Fortis

**Порядок:** D4 — часть более позднего D1–D4 secure-delivery этапа. По решению 2026-11-02 функциональная разработка/приёмка G3 RDG следует после P1, до полного D1–D4. Это не разрешает доставлять или запускать недоверенный RDG code через legacy ZIP updater: production import/run остаются заблокированы до D1–D4 и отдельного owner RUN approval.


Текущий механизм RDG (доказанная Repo сборка и zip + Windows updater -Watch) **обходит новый GitHub admission**. Спроектировать контролируемый cutover:
1. Сохранить последний known-good RDG, отдельные Graph/Plan/layout owner volumes, secrets/namespace и rollback инструкции.
2. Включить защищённый PR/CI/Sonar для RDG и при необходимости расширить scanner coverage до критичных runtime файлов; не выводить gate из узкого анализа.
3. Установить Windows Importer, подтвердить exact SHA + AV + owner approval, отделить deployment от execution и произвести smoke.

**Gate D4:** один end-to-end защищённый RDG update и один safe Fortis self-development PR без доступа AI к host/secret/production updater.

## 12. Приоритеты: P1/P2 Single AI SonarCloud Pilot и последующая очередь (срез 2026-11-03)

**Ближайшая цель — один работающий ИИ, не мультиагентная система.** P1 READ/report + typed ASK остаётся основой сценария. Владелец отдельно разрешил R7 P2 source change для одной typed operation `sonarcloud.accept_issue`: после отдельного ASK каждая конкретная Issue может быть Approve только через свежий strong WebAuthn proof, связанный с requestId и fingerprint. Это разрешение на source candidate, а не blanket approval и не production rollout. Второй ИИ, несколько grants и мультиагентная координация не являются prerequisites этого пилота.

**Очередь после P1:** следующий отдельный функциональный этап — **RDG FREE/ASK + Navigation Bridge**; после него — второй и последующие AI actors, actor-specific grants и полный lifecycle их выдачи/отзыва/ротации; затем полный защищённый GitHub PR/Actions/Sonar → exact SHA → Windows Import/RUN pipeline и оставшиеся production admission gates. Целевая топология остаётся прежней: **ОДИН доверенный Fortis-контейнер** с секретами, owner UI и typed execution; один общий `Core.execute()` для ALLOW и подтверждённого ASK. Второй Executor-контейнер, второй Approval engine, новый Gateway или IPC для ASK не нужны. Для live P1 обязательны минимальные TLS1.3/server identity, один scoped machine identity, приватный Sonar READ token внутри Fortis и изолированные volumes. Полная base-image provenance/SBOM/CVE и расширенный lifecycle admission можно завершить позднее, но минимальную аутентификацию клиента и изоляцию секретов откладывать нельзя.

**A2/A3: решение владельца об отложенных задачах (2026-11-01):** **(1) проверенная ручная процедура замены TLS-сертификата без потери state/WebAuthn; (2) возможность выдать и отозвать машинный доступ с проверкой старый DENIED / новый scoped PASS.** Статус обоих — **DEFERRED / NOT IMPLEMENTED**, не текущая работа. **Следующая работа — Sonar READ source/offline без реального токена.** Перед доверенным Windows запуском с настоящим Sonar token оба отложенных пункта вернуть в приёмку вместе с independent source/certificate admission и secret audit; их нельзя считать PASS только по status-скрипту. **Исторический чек-лист до решения об отсрочке:** (1) owner-controlled independent source/image admission и доверенная привязка TLS identity в Repo; (2) видимый срок действующего TLS cert и понятная безопасная ручная процедура его замены **до 2026-11-07T23:29:17 UTC** без повторного bootstrap; (3) решение об одной machine client identity (оставить scoped bearer grant или заменить другим механизмом), возможность её отозвать и безопасно показать статус **без секрета**; (4) базовые review границ Sonar secrets/host ACL/logs и владелец ACCEPT/NO-GO. Не разрабатывать отдельное наблюдение за ASK/WebAuthn/backup/image без нужды. Sonar READ допустимо готовить offline без реального токена; до PASS не вводить его в A3. Удаление файла grant из Repo **не** является отзывом серверного credential.

### A2/A3 — минимальная эксплуатационная приёмка без лишней логики (уточнение владельца, 2026-11-01)

**Решение по области ответственности:** срок ASK, очередь Pending/History, WebAuthn-сессии и одноразовые invitations остаются **внутри Approvals**; не создавать для них внешний монитор, отдельную процедуру администрирования или вторую базу сроков. Docker healthcheck уже есть, для него достаточно обычной диагностики при неисправности. Дополнительную специализированную наблюдаемость требуется спроектировать **только для server TLS-сертификата и выбранной идентификации machine caller**, чтобы владелец видел, почему соединение перестанет работать и что надо заменить. Не превращать это в отдельную платформу мониторинга.

**Зачем нужен machine grant:** TLS + проверка имени сертификата аутентифицируют **сервер** для Repo, но сами по себе не удостоверяют **вызывающего клиента** для Fortis. Даже `ALLOW` нельзя отдавать любому достижимому сетевому процессу. Сейчас `RepoIngress` ожидает `Authorization: Bearer ...`; `Authenticator` сопоставляет конкретный grant с доверенным actor, после чего Fortis вычисляет ALLOW/ASK/DENY. Это **отдельно** от Sonar service token (Fortis→Sonar) и owner WebAuthn (человек→ASK). **Не обязательно сохранять именно bearer grant**: допустима независимая проверяемая machine identity, например mTLS client cert/доверенная локальная аутентификация, если конкретная сеть и деплой действительно обеспечивают идентичность. В любом варианте необходимо запретить неавторизованного клиента и иметь способ отозвать доступ. Простое ограничение порта на Windows loopback и server-side TLS без client auth **не доказывают** личность клиента.
