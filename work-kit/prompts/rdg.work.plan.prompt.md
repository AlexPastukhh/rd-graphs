Найди R, которую сейчас хочет проработать пользователь. Прочитай её текущие драйверы, scope, уже выбранные D, релевантные дочерние R и существенные ограничения из graph.json. Если ID не назван, возьми однозначную активную цель; при неясности задай один предметный вопрос.

Предложи конкретное **кандидатное** решение D о способе достижения R и такое разбиение на R_child, которое действительно помогает получить результат; допустим и D без разбиения. Связи в предлагаемом плане: R → D (DRIVES), D → R_child (INTRODUCES, parent=R). Если выбор материально неоднозначен, дай альтернативу с краткой разницей и рисками. Не навязывай порядок выполнения между дочерними R.

Заверши кратким объяснением, что именно нужно принять для фиксации, не повышай revision и не записывай выбранные D/дочерние R от имени пользователя. Если уже принято ранее, не создавай его заново: работай с существующим ID или предложи осмысленное уточнение.

Сопоставь задачу с целым TM или узким Unit; выбери planningScale по смыслу. При использовании готового целого назови preparedModule owner/id/version, target R и предполагаемые bindings; при собственном способе объясни достаточность. Покажи отдельные Unit-графы только для полезных самостоятельных R. Прямой Unit-D не требует дальнейшего разбиения.

**v7:** До предложения принятого D используй каноны каждого prepared/situational варианта как направления проверки конкретных R/D/C и их категорий, собери один общий либо несколько необходимых composite R и содержательный QRPE по каждому варианту. Если часть контекста недоступна, скажи «не проверено» вместо «минусов нет». Если пользователь просит только план, не создавай user decision_selected. Результаты и примеры — docs/guides/RDG-V7-WORKING-GRAPHS.md.
