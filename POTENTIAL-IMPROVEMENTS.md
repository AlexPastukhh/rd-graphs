# RDG — потенциальные улучшения (candidate)

Это не нормативный контракт, не новый Graph/Plan owner, не журнал обязательств и не разрешение на реализацию. Исходный срез: 2026-10-22, независимый Final Review R-RDG-INDCONS-20261022-b7a4/v1 и его повторная оценка. Более поздние результаты анализа имеют собственные дату, scope и основания ниже. ## F-O-01 / PR-06 — обзор прямых DEPENDS_ON в фокусах

**Что может улучшить:** при работе с конкретной R/A иногда нужна короткая текстовая навигация по прямым `DEPENDS_ON`, поскольку собственный фокус показывает лишь связи выбранной проекции. **Кандидат:** компактный read-only список прямых зависимостей с переходами по ID. **Почему не сейчас:** отдельная вкладка зависимостей может уже закрывать нужный путь; без обратной связи нет основания увеличивать сложность UI. **Revisit trigger:** подтверждённый сценарий, когда текущий просмотр мешает восстановить причину stale. **Статус PR-06:** pending/deferred; не реализовывать автоматически.

## F-O-02 / PR-07 — дополнительная полнота ручного core UI

**Что может улучшить:** ручной ввод `unresolvedAcknowledged` при допустимом unknown canon и отдельное `resolve_finding` с evidence. **Почему не сейчас:** Agent/CLI уже обеспечивают операции; полная форма каждого API-флага не обязана входить в базовый пользовательский маршрут. **Revisit trigger:** пользовательский запрос на законченный ручной workflow и проверка действительного отсутствие поля в текущей версии. **Статус PR-07:** pending/deferred; не реализовывать автоматически.

## F-O-03 / PR-08 — более точная семантическая регрессия и DRY

**Что может улучшить:** негативный контрактный тест на конкретный новый риск смыслового расхождения между core, writer, Viewer и документацией. **Текущий достаточный путь:** при каждой material правке добавлять адресное доказательство, использовать действующий контракт и точную generated UI parity. **Не делать:** универсальный второй validator, новую taxonomy или новые нормативные копии только ради количества. **Revisit trigger:** подтверждённое новое расхождение, не покрытое адресными тестами. **Статус PR-08:** pending/conditional, без отдельной обязательной работы.

## Анализ удобства API и авторинга линз — 2026-11-12

**Статус: кандидаты по запросу анализа, не принятый план реализации.** Анализ начат 2026-11-12; завершающая проверка выполнена 2026-11-13. Каталог не изменился, Registry остался на revision 52; live write-запросов не было. Основание — фактическая публикация исправлений B04, чтение текущих schema/возможностей, безопасные preflight-пробы и изолированный конкурентный сценарий. Живые данные в этом анализе не менялись. Сопоставление выполнялось с T1/T2/B04/B05, а не с требованием создать новую платформу авторинга.

Обнаруженные ошибки самоописания API и конкурентного обновления клиента отдельно зафиксированы в [backlog](BACKLOG-IMPROVEMENTS.md#api-authoring-review-20261112). Они не подменяются возможностями улучшения ниже. Восстановление Registry-публикации уже исправлено в клиенте; унификация server receipt остаётся предлагаемым улучшением.

### Снизить стоимость клиента имеющимися средствами

**Метаданные источника.** В первом обновлении 19 линз было 207 paper-операций. В 144 менялось только description; у 137 из них отличие сводилось к SHA256 полного Markdown. Семантика соответствующего узла не менялась, но текущий формат требует обновить его описание. Кандидат: хранить точную редакцию источника один раз в существующих source Info/source-map, а в узлах оставлять устойчивые ссылки на разделы. Исторический Graph snapshot сохраняет использованную карту и происхождение. Смена формата сама имеет одноразовую цену; экономию проверять на следующей сопоставимой правке, без обещанного процента ускорения. Это изменение генератора, не новая операция API и не отказ от provenance.

**Реализовано и проверено в исходниках 2026-11-13 в рамках нового поручения на обоснованные улучшения.** Точная редакция остаётся в полном source Info и source-map; описания узлов адресуют устойчивый раздел и карту. В изолированном сравнении одинаковой правки даты введения для всех 19 линз зависимость descriptions от SHA полного текста реконструирована в памяти: 449 paper-команд против 66 после изменения. Это число команд, не замер RPC/времени и не обещание ускорения; одноразовая смена формата также требует публикации. Адресный тест проверяет сохранность остальных разделов, полного текста и нового SHA. Evidence: `/workspace/repo/Workfiles/rdg-independent-audit-20261113/provenance-isolated-comparison.json`. Paper batch, remove, новый receipt envelope и optional preview остаются кандидатами.

**Адресное чтение.** Текущий read уже предоставляет summaries, item, focus/branch, facets и version-bound страницы. В трёх чередующихся повторах на одной живой preserve полный read занимал 928 991 байт и медиану 4,9352 с; summary — 4 680 байт / 0,0969 с; source_snapshot того же Graph — 103 056 байт / 0,2637 с. В full 780 224 байта приходилось на dependencyCatalog, сам Graph — 50 825 байт. Равенство Graph проверено. Это один конкретный снимок через private gateway, не SLA и не p95.

Кандидат: обычную навигацию строить на item/focus, а для сравнения полного определения использовать summary + существующий source_snapshot по его pin, когда хватает этих данных. Сохранять reviewed package/graph revisions для CAS; старый pin не выдавать за актуальную базу записи. Full нужен для соответствующего полного аудита и доступных только там сведений, например immutable-definition metadata и полного dependencyCatalog. Сначала улучшить клиент и измерить остаток; отдельный новый read endpoint этим анализом не обоснован.

### Закончить управляемое удаление в определениях

Текущий авторинг lens/ready поддерживает add/edit/link/unlink, группы, основания и WorkGraph. Для отдельного элемента lens нет удаления: live preflight delete дал WORKING_TARGET_REQUIRED, а schema paper_edit/remove — CORE_COMMAND; источник подтверждает ограничения ролей. Отсоединить одну связь можно, но это оставляет сам элемент в текущем owner и поиске. Перемещение целого старого примера в архив не решает эту задачу.

Кандидат: расширить один существующий маршрут управляемого удаления на изменяемые определения, используя общий reducer/coordinator. Preview должен показывать удаляемые IDs, основания, memberships и затронутые текущие ссылки/рекомендации. Удаление участия через unlink и удаление общего узла различаются. Сохранить identities остальных сущностей, старые snapshots и происхождение; зависимые рабочие экземпляры не удалять автоматически. Если нужно сначала изменить текущую ссылку, показать gate вместо молчаливой уборки. Требуются проверки общих узлов и существующих references; это не простая отмена role guard и не повод менять профиль владельца ради обхода.

### Добавить пакетный paper-авторинг

Batch до 100 шагов уже существует для working/copy. Для lens/ready его нет. В первом исправлении было не более 43 paper-шагов на одну линзу: 207 Graph-мутаций могли бы укладываться в 19 owner-пакетов, если бы поддерживался paper-авторинг. Это сравнение числа публикаций, а не прогноз времени. Отдельные изменения Registry сюда не включены.

Кандидат: расширить существующий batch разрешёнными операциями авторства с семантикой paper_edit, теми же CAS/preflight/receipt и сохранением истории. Сохранить точные авторские IDs и aliases, правила групп и общих оснований. Определение не получает selection/completion или фиктивные события исполнения. Проверять промежуточные семантические ограничения и атомарный отказ. Главная польза — одна согласованная версия исправляемой линзы вместо публичной последовательности частичных изменений, а также меньше сетевых циклов. Отдельный второй writer или безусловная замена Graph целиком не нужны. Поддержку удаления и batch можно принимать отдельно; кейс полноценного пересмотра определения проверять совместно.

### Сделать receipt одинаково понятным для разных owners

У Registry-only записи apply возвращает published=true и participants с rdgRegistryReceipt. Существующий receipt(packageId=null, transactionId) возвращает accepted/completed-certificate, publicationCertificatePresent и requestSHA256, но без опубликованного participant receipt и обычного published. Клиент, предположивший package-only форму, ошибочно остановился после реально принятой записи; его восстановление уже исправлено и покрыто тестом без повторного эффекта.

Кандидат: расширить существующий receipt общим envelope с однозначными accepted/исторической завершённостью публикации и разрешёнными participant receipts/owner refs для Graph/Plan/Registry. Сохранить отличие currentStateVerified от факта прошлой публикации, exact request SHA и действующие проверки доступа. Readback текущего содержания остаётся необходимым. Новый журнал транзакций, workflow/job status и новая машина состояний для этого не требуются.

### Опционально показать будущий фокус на preflight

Preflight уже проверяет ограничения, возвращает changed/added/removed IDs, basis/dependency/review impacts и inputBinding. Но он не даёт прочитать будущий Action/Decision тем же фокусом или Markdown, которым после публикации пользуется ИИ. Для ошибок соответствия и недостающей теории это вынуждает опираться на локальные проекторы либо проверять уже записанный результат.

Кандидат: опционально возвращать выбранный focus/branch будущего Graph/Plan существующими проекторами поверх подготовленных изменений. Ответ явно относится к непринятому preview; будущие ссылки и непроверенные части обозначены, он не становится реальным source pin. Не включать полный preview во все ответы, не сохранять второй draft owner и не создавать отдельный lifecycle. Это помогает проверить смысл открываемого пути до записи, но не заменяет независимую оценку и readback после apply. Реализацию оценить после исправления клиента и основных операций авторинга.

### Что уже есть и не требует новой команды

- Создание role=lens с полным подготовленным Graph; редактирование узлов, CANON_FOR/Info-связей и групп. Исправленные ошибки соответствий не доказывали отсутствия этих операций.
- Copy/insert_copy/capture_ready/apply_ready с source pins и remap. Insert_copy из конкретного Decision живой линзы в рабочий процесс прошёл preflight; apply не выполнялся. Изучение линзы не требует вставки.
- Адресные рекомендации с whenText/usageText, точными anchors и ссылками на шаги; вопросы, контекст, Plan/History, select/withdraw и review доступны в своих профилях.
- Получение receipt и exact retry уже есть; нужна ясность форм разных owners, а не новое разрешение повторять запись с новым transactionId.

### Рекомендуемая последовательность рассмотрения

1. Исправить подтверждённое самоописание операций для роли owner и сохранение reviewed revision в публикаторе. Довести известную поставку B02A: live schema пока показывает прежний knownErrors; новое семантическое решение здесь не требуется.
2. Снизить лишние изменения provenance и использовать достаточные существующие чтения; сравнить число RPC/байты/время на одной задаче.
3. Принять scope управляемого удаления и пакетного авторинга определений. Это наиболее содержательные дополнительные возможности API для создания и пересмотра линз.
4. Унифицировать receipt. Опциональный preview-фокус и дальнейшие чтения уточнять по реальному B05 и оставшимся затратам.

Произвольные межпроцессные структурные связи, автоматическое преобразование любого Markdown в правильный Graph, второй реестр линз и полная multi-owner транзакция всех 19 линз этими наблюдениями не обоснованы. Полный автономный B05 этим анализом не выполнен. Evidence: `/workspace/repo/Workfiles/rdg-api-ergonomics-20261112/`; журналы исходной работы — у результата B04.
